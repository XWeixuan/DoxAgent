# Dashboard AUTH_UNAVAILABLE 修复（2026-11-19）

## 现象和证据

- 北京时间 06:14:33–06:15:22，生产 API 的日志样本中有 9 次 `AUTH_UNAVAILABLE`，
  覆盖 `/auth/me`、Ticker 列表、read-context 和 Runtime 指标等路由，每次约 10.1 秒。
  请求在认证边界失败，没有进入业务 SQL 查询。
- 故障时 API 容器仍 healthy、重启次数为 0。部署提交为 `1b0494dae`。
- 容器内直接请求配置的 Supabase `/auth/v1/health`、`/auth/v1/user`、`/rest/v1/`
  均复现 `httpx.ReadTimeout`，人为设置的 5 秒探测预算耗尽。
- 随后主机和容器探测恢复；Supabase 两个 DNS 解析地址均完成证书校验并返回预期响应。
  用户浏览器原页面明确显示 `AUTH_UNAVAILABLE`，点击重试后 Overview 恢复。

据此定位为认证上游 HTTPS 响应的间歇性读取超时，不是数据库慢查询、权限被取消，
也没有发现前端构建不匹配导致本次错误的证据。
现有证据不能进一步区分 Supabase 内部、边缘网关和中间网络的具体责任层；
不能把后来恢复的连通性当成整个上游故障已被永久修复。

## 应用侧机制与修改

原实现的 Supabase 请求超时为 10 秒，没有重试。30 秒认证缓存到期后，
同一登录会话并发发起的每个页面请求都分别访问身份与权限接口，短暂故障会扩散为整页报错。

本次只修改 `api_v2/auth.py`：

1. 对身份及权限的幂等 GET，在网络超时、连接错误、远端协议错误或 502/503/504 时重试一次。
   每次网络操作超时 3 秒，整个认证最多 8 秒；持续故障仍返回可重试的 503。
2. 同一个令牌的并发认证共享一个在途任务；某个页面取消请求不会取消其他页面等待的校验。
   任务完成后立即移除，不增加后台轮询或持久化状态。
3. 记录身份/权限阶段、尝试次数和安全的错误类别，不记录令牌、apikey、用户 ID 或响应正文。
4. 保留 Supabase 签名身份验证、可信 `DEVELOPER` profile 要求及最多 30 秒成功缓存。
   拒绝结果不缓存，401/403 不重试，不使用过期权限兜底；网络过程结束后再次检查令牌是否已过期。
