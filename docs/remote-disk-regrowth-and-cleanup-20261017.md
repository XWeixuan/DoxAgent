## 3. 49 小时内为什么会吃掉 50.53 GiB

### 3.1 MAIN 发布让大依赖层按提交重新生成

从清理前镜像记录重建 10/15 保留的 18 个镜像集合：去重解压层约 **13.53 GiB**。本次清理前全部镜像去重解压层约 **32.00 GiB**，新增独有解压层 **18.47 GiB**。这还不含新镜像压缩内容与未被镜像引用的构建中间快照；因此发布成本远大于源码差异。

真实 Dockerfile 在 apt/uv/Playwright 安装之前声明每次变化的 commit/source SHA，并写入早期 ENV/LABEL。真实 image history 证明这些不同值进入依赖 RUN 环境。每版约 839 MB 的 uv 层和约 1,022 MB 的 Playwright 层重复生成；当前 MAIN 后端集合有 10 个不同 Playwright DiffID，约 **9.52 GiB**。这不是假设“缓存未命中”，是文件、命令历史与层 ID 的交叉证据。

按 [Docker 官方 ARG 缓存语义](https://docs.docker.com/reference/dockerfile/#impact-on-build-caching)，应把发布身份 ARG 声明及对应 ENV/LABEL 后移到稳定依赖安装之后，不能只移动 LABEL/ENV。提交追溯字段继续保留。发布验收后定向退出已替换、无引用的上一版，而不是把每次单服务修复都永久留下整套依赖。

### 3.2 构建中间快照保留阈值高，命名镜像没有自动收尾

清理前 BuildKit 元数据合计 **19.17 GiB**，非共享可回收部分 **6.01 GiB**；清掉旧镜像又解锁 **3.02 GiB**。这些逻辑量与上面的镜像层存在重叠，不能拿来凑一个假的精确增量账。

现场 builder 有 GC，但普通规则保留时长为 1,440 小时（60 天），Reserved Space 为 **16.76 GiB**，Max Used 为 132.2 GiB，Min Free 为 33.53 GiB。对已经有约 99 GiB 数据卷的系统盘，这些默认阈值并不等于能维持发布余量；而且 BuildKit GC 不会替发布器删除仍有名字的旧应用版本。最近构建脚本完成 build/tag 后也没有标准旧版本收尾。

最小修复是先消除参数导致的依赖重建，再把现有 builder 缓存保留量收敛到正常构建需要的约 4–6 GiB 量级，并在发布成功后定向退役自己的旧资源。不需要新平台、全局 system prune 或高频人工清理。

### 3.3 每个任务反复物化整套研究输入，终态后没有退役

生产工作区有约 **5.16 GiB 的 context 目录**。对其普通文件逐个 SHA-256 核对，实际读取 258,224 个不同 inode；文件分配约 4.99 GiB，其中 **241,707 个文件可由已有相同内容文件替代，重复分配约 4.58 GiB**。目录本身的块和文件内容口径不同，不能把二者当矛盾。

典型重复物是同一套 D2 文档、研究 Shell JSON、原始 document2 和 policy/source 上下文，被复制到不同 `w3-case-*/context/research/<hash>/...`。不同任务或版本身份不意味着内容真的不同。本次即使保留每种内容至少一份，仍有 4.58 GiB 重复字节。

Worker 数据库当前有 succeeded 5,994、failed 539、cancelled 11，采样时没有 queued/running job。但“job 已完成”不自动等于整个可恢复线程结束；清理应面向终态工作区的重复输入与无效尝试，保留必要输出/收据和当前恢复责任。改用已有冻结版本重新物化或共享只读输入即可，不需要新的通用资源治理框架。**不能直接 unlink 输入后留下失效读取路径，也不应该因此放弃回收所有重复字节。**

以 10/15 03:20 清理验收时间为边界，Worker 实际又记录了 **999 个成功 Job、6 个失败 Job**；成功组涉及 477 个不同 run。存在真实而持续的任务新增，不是几份静态研究资料自己变大。逐任务全量复制输入、终态后长期保留，正是把正常任务量放大成额外磁盘消耗的机制。

### 3.4 Event Library 分支和 Read 历史继续累积

Runtime 的 492 个 runtime_artifacts 根中，约 **4.45 GiB 是 events 分支数据**。维护流程从冻结基线为每个 run 创建完整 Event Library 分支；失败/未发布尝试、旧成功分支与当前权威版本需要不同生命周期。它们是一个明确可整理的资源池，不应全部永久在线。保留当前发布/冻结执行所需版本，其余未发布无引用分支可删；旧已发布分支可按保留期压缩转冷或从有效版本链恢复。

Read 主库自 10/14 约 24.97 增至约 **27.99 GiB**，research 约 0.94 增至 **1.48 GiB**。Bus/Runtime 主库大小基本不变。Read GC 仍在实际回收健康 Bus poll 历史，Runtime 保护仍存在，因此此前的修复没有解决所有业务历史长期留存。后续应把保护限定到缺口真正依赖的对象/坐标，清理无关联过期版本；不应让局部缺口导致所有新 Case 历史永久累积。

### 3.5 浏览器缓存重新增长，但这次不是 PMA 指标暴涨

10/15 清掉过约 10.52 GiB PMA 指标和 7.27 GiB 网页缓存。本次同一指标白名单仅 **1 个 PMA、约 4 MiB**，因此明确排除它是此次大头。网页 HTTP/代码/GPU 缓存白名单目前约 **3.02 GiB**，可以再次回收；登录态和网页业务存储不在这一白名单里。

历史没有保存 10/15 每个目录的完整物理分配快照，不能现在伪造精确到每 GiB 的 50.53 GiB 分摊。已确定的是：约 49 小时发生了真实 50.53 GiB 净增长；大量新增镜像依赖层/快照、反复复制任务输入、业务历史和网页缓存共同增长。没有证据支持“又多了几十 GiB 日志”或“Bus 主库又恢复到 20 GiB”。
