# Yahoo Finance 发布至首次采集延时排查（2026-11-03）

## 1. 结论

**GraphQL 的严重延时确实存在；爬虫也在真实运行。两件事并不矛盾：目前浏览器主要读取 Yahoo ticker 页的服务端新闻列表，并不直接监测原始媒体，也不持续消费前端加载的全部新闻。浏览器正常访问，不代表 Yahoo 当前返回的列表已经包含刚发布的文章。**

本周一以来的生产记录中，以 GraphQL 最先发现、具有精确声明发布时间的 36 篇实时文章，平均发布至发现 **10分23秒**，16 篇超过10分钟，最长27分58秒。浏览器最先发现的19篇同口径文章，平均9分46秒，同样没有消除十几分钟的延时。

现场还捕捉到两篇自然发生的 TIKR 文章：声明发布约15分钟后，成功返回的 GraphQL、RSS、HTML 列表仍没有它们；生产到发布约20分钟后才首次取得，随后约1.4秒即完成 FULL 正文并可供下游消费。这把这两例的主要延时定位在**当前列表返回候选之前**，并非正文补全或接纳排队。

另有独立故障：11月3日北京时间07:40—07:57，GraphQL、RSS 同步出现约17分钟的请求失败，浏览器仍正常。这会进一步增加尾部延时，需要处理，但不能解释故障窗口之外普遍存在的10—20分钟延时。

**下一步正确方向是提高候选的提前可见性及覆盖，修复共享 HTTP 路径的故障恢复；仅提高轮询频率、恢复精确时间补查，或简单更换 GraphQL 查询名称，都没有证据足以解决主因。**

## 2. 窗口、口径与证据边界

- 历史冻结窗口：北京时间 **2026-11-02 00:00—2026-11-03 22:25**，即 UTC `2026-11-01T16:00:00Z—2026-11-03T14:25:00Z`。
- 包含周一美股完整常规交易时段：北京时间11月2日22:30—11月3日05:00。该交易时段内首次发现的可比样本32篇，平均延时8分32秒；主统计没有只选盘外样本。
- 补充现场对照：北京时间11月3日22:40—22:53；与历史冻结统计分开，不混入历史分母。
- 读取生产 acquisition、Bus、Site Access 持久记录，并通过既有出口、既有 `yahoo-main` 身份进行有界公开资源探测。未修改生产业务代码、订阅、身份、代理或调度配置，未重启服务，未注入测试新闻。
- 审查基线：本轮开始时本地及远端版本 `1b2391db`；Yahoo 相关功能来自10月31日改动。其他服务维护不等同于 Yahoo 修复。

### 统计如何避免误判

1. 177条 ticker 消息合并为163篇文章，优先按 Yahoo native UUID 合并，避免跨 ticker 重复计数。
2. 其中22篇是 `CLOSED_SWEEP`，141篇是 `REALTIME`。旧闻扫描不算实时延时；有4篇最早 origin 是 GraphQL 的旧文，也被排除。
3. 141篇实时文章中，135篇具有 `EXACT` 时间且发布至首次发现处于0—30分钟，作为可比队列；其余6篇为相对时间口径，单列、不假装精确时间。30分钟为现有实时接纳窗口，因此统计有截断，**不是全量 Yahoo 文章的无偏延时分布，也不能测出完全漏抓的文章**。
4. “首次渠道”按保留的最早 `live_origins.first_seen_at/unit`，不用当前 Raw 的 `query_mode`。后者可能在后续正文复查时改变。它说明最先留下证据的渠道，不表示其他渠道永远没看到。
5. origin 对同 URL 合并，并不保存每轮所有渠道的全部卡片。不能用缺少第二条 origin 推断该渠道未抓到。
6. 首次接纳及可消费时间使用 delivery 的持久时间字段；不使用可能被后续复查改写的 `decision_ready_at` 或 `media_enrichment.attempted_at` 计算初次耗时。
7. “发布时间”是文章/接口声明值。抽查 JSON-LD 能核对其一致性，但不能证明原站在这一秒已对公众可见；列表未返回也不等同于 Yahoo 全站任何位置均未出现。

## 3. GraphQL 是否严重延时

答案是明确的“是”。下表只算最先由相应渠道发现的独立文章，避免把同一篇在三条渠道重复计数。

| 首次渠道 | 实时独立文章（含相对时间） | 可比 EXACT 篇数 | 平均 | 中位数 | P95 | 最大 | 超过10分钟 |
| --- | ---: | ---: | --- | --- | --- | --- | ---: |
| GraphQL | 36 | 36 | 10分23秒 | 9分23秒 | 23分38秒 | 27分58秒 | 16/36 |
| RSS | 82 | 80 | 10分54秒 | 9分48秒 | 22分02秒 | 24分44秒 | 38/80 |
| 浏览器 | 23 | 19 | 9分46秒 | 9分54秒 | 23分37秒 | 27分27秒 | 8/19 |

P95采用排序后 `floor((n-1)*0.95)` 的观测值。样本量有限，不应把渠道均值的小差异解释为稳定的优劣排名；能确认的是三条渠道都存在严重延时，GraphQL 并非已经解决时效问题。

135篇可比文章在**已经取得候选之后**：

| 阶段 | 平均 | P95 | 最大 |
| --- | ---: | ---: | ---: |
| 首次观察 → Bus delivery 创建 | 0.308秒 | 0.543秒 | 1.079秒 |
| 首次观察 → 可供下游消费 | 3.475秒 | 9.456秒 | 24.605秒 |

这些数据不能代表所有失败任务，但足以说明已接纳的这批十几分钟延时消息，主要时间差并不在发现之后的消息处理。

## 5. 爬虫确实运行，但当前覆盖方式有边界

### 5.1 不是“开关开了但实际上没请求”

历史窗口内，`SUPPLEMENT_HEAD` 有35,758轮 CAPTURED、27轮 FAILED。Site Access 层可找到35,794次 CRAWLER 访问事件：35,782次 SUCCESS、12次 BUDGET_DEFERRED。两类计数分别是采集周期和物理访问事件，发生边界及记录粒度不同，不强行逐条等同。

Site 记录包含实际请求开始、响应头/响应体时间、状态码及身份 `yahoo-main`，不是只有资源许可。CRAWLER 网络耗时平均869毫秒、P95 1,320毫秒；排队平均3.86毫秒、P95 7毫秒。浏览器采集周期平均1.051秒。

原9个 ticker 的成功轮询间隔 P95 约30.4—31.0秒，最大成功间隔约60—93秒；IONQ 为60秒配置，P95约60.4秒，最大约121秒。没有看到浏览器整体停摆十几分钟的证据。

更直接的业务证据：23篇实时独立文章最先由浏览器发现，其中19篇具有精确时间。Applied Materials、Trefis 的相对标签被立即用于输出，取得候选后约2.9秒、3.3秒即可消费。当前各 ticker 的精确时间待补 checkpoint 为0，冻结窗口没有 `TAIL:YAHOO_TIME` 采集周期，**此前逐篇时间补查阻塞不是本轮主因**。

### 5.2 “浏览器能运行，所以一定能及时发现”这个前提不成立

35,794次 CRAWLER 访问中35,751次复用 anchor（99.88%）。典型流程是已有 Chrome 页内同源 fetch ticker `latest-news` HTML，再解析服务端卡片；现场三 ticker 均得到12张 HTML 卡片。它不是每30秒真实重新导航、滚动并执行整套前端新闻加载。

现在监听器支持原生 `financeTickerList` 响应，但通常需要页面发生实际加载才有该响应；反复 HTML fetch 不会自动触发这条前端查询。故当前“浏览器渠道”仍受服务端 HTML 列表的更新、排序、长度限制影响，和 HTTP GraphQL 在候选数据上也不构成独立的原始媒体监测。

这意味着两类可能性都要保留：

- 文章尚未被 Yahoo 当前 ticker 列表返回，浏览器再健康也拿不到。
- 文章已在其他接口、更多页或未解析卡片中存在，但前12张/解析路径未覆盖。当前历史日志不保存每轮完整卡片及丢弃原因，不能事后排除所有此类漏召回。

本轮已经定位“单纯恢复爬虫开关”没有意义，但尚不能宣称历史每一条延时都已证明是 Yahoo 全站入库晚。

## 7. 另一种 GraphQL 查询是否更及时

生产当前使用 `GetQSPLeafNewsStream / lightyearList`。本轮从已保存的 Yahoo 第一方前端资源提取原生 `FinancePolarisTickerListNews / financeTickerList` 的 AST 和参数，真实请求对比，而非只看接口名字。

对 INTC、MU、CEG 分别测试旧/原生查询及 `ticker-all/ticker-news` 两种 alias，共12次请求，均成功，各取前50条。结果：

- 原生与旧查询存在不同旧文章、排名差异，CEG 差异较多，因此不能认为完全等价。
- 此次三 ticker 的最新声明发布时间一致，没有找到原生查询独有且更早的新文章。
- 上述两篇 TIKR 文章在22:47旧/原生查询均已出现，原生查询没有展示提前15分钟取得的证据。

因此，原生查询值得用于**补充覆盖、减少 HTML 前12张限制及浏览器出口容灾**，但此次实测不支持把简单替换查询宣称为已解决10—20分钟延时。有限对照也不能证明未来所有时刻两种查询都一样。

## 8. 独立故障：GraphQL 与 RSS 同时失联约17分钟

全窗口 GraphQL 35,393轮 CAPTURED、400轮 FAILED，平均周期执行0.756秒；RSS 35,224轮 CAPTURED、571轮 FAILED，平均0.630秒。失败主要为超时，不能由较低平均耗时掩盖。

对 INTC 北京时间11月3日07:38—07:59逐请求抽查：

- GraphQL：33次 FAILED、9次 CAPTURED；RSS同为33/9。
- 浏览器：42次 CAPTURED、0次 FAILED。
- GraphQL 最后成功响应07:40:23，失败调度覆盖07:40:52—07:56:52，07:57:23恢复；RSS约07:40:37—07:56:37失败。
- 多数失败物理请求已到 `TRANSPORT_SEND`，有 `request_started_at`，没有响应或 HTTP 状态；少量在发送前失败。
- 全 ticker 的 GraphQL 最大成功间隔约1,020—1,080秒，和该同步窗口吻合。

GraphQL 与 RSS 共用 Yahoo 专用 HTTP 运行路径及配置代理，而浏览器身份路径独立。现有证据把故障指向**共享 HTTP 出口/传输及其恢复路径**，不是浏览器身份失效。没有足够证据把它进一步定性为 Yahoo 限流、TLS、DNS或某一代理节点故障；本窗口异常未呈现 HTTP 429/`YahooRateLimited`。

代码中的传输超时、外层任务期限和单路径资源占用可能在失联时放大连续失败；但不能把可能的放大器当成已证明的网络原发故障。这部分需要更细的连接/首字节/取消完成记录。

## 9. 接下来应做什么

按解决实际首次发现延时的价值排序，而非按改代码难度排序：

1. **优先补齐独立候选入口。** 对 TIKR、Trefis、GuruFocus 等高延时转载，以及 Reuters、The Fly、新闻稿，先盘点现有直采源是否已更早取得相同文章，再决定补充原站 RSS/HTTP/合法公开接口。统一原文链接、UUID及正文复用，保留 ARTICLE_ONCE。Yahoo 保留为广覆盖与兜底。若原站已早公开而 Yahoo 当前列表尚未返回，直采才可能跨过这段延时；同一 Yahoo 列表再加一条抓取线程不能跨过它。
2. **改善浏览器候选覆盖。** 在既有身份内消费前端原生 JSON 列表，避免长期只依赖12张 SSR 卡片；先有界对比50条覆盖与新消息首次可见性，再决定小幅分页。保留当前 HTML fallback 和相对时间立即输出，不新建身份、不常驻更多页面，不恢复逐篇精确时间阻塞。收益首先是召回和 HTTP 路径失联时容灾；是否能提前发现必须按文章验证。
3. **修复共享 HTTP 故障恢复。** 在既有期限内区分发送排队、连接、响应头、响应体、取消和重建；核对 GraphQL/RSS 同步失联时共用资源是否被长期占用。根据证据做连接/任务清理和有界恢复，避免仅延长超时或增加并发掩盖故障。保持浏览器调度独立。
4. **补最小观测缺口。** 在现有 cycle/候选台账上有界记录各渠道 native UUID 的预过滤首次出现、列表条数/最新时间、丢弃原因及输出时间，不长期落每轮完整 HTML，也不另建服务。区分“上游列表不含”“卡片没解析”“时间/去重过滤”“已经输出”，才能对所有后续坏例做因果归类。
5. **验收围绕真实新闻。** 分 publisher、ticker、盘中/盘外统计声明发布→渠道首次可见→采集→Bus→可消费，另报相对时间、更新和 sweep。对照冻结样本及自然新消息，不以 CAPTURED 次数、请求秒级耗时或“GraphQL能返回200”代替时效验收；同时统计候选覆盖，避免优化速度时漏抓。

不建议优先投入：单纯把30秒改为更高频、无证据追加随机 cache 参数、增加 Chrome 身份、重新阻塞等待精确时间、单凭渠道当前 `query_mode` 归因。现有正常30秒间隔与十几分钟延时不是同一数量级。
