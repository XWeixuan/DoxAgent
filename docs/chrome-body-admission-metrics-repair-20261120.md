# Chrome BODY 准入、生命周期与24小时指标修复

> **页面超时修复记录：不撤回本轮功能或24小时口径。** 曾误将用户“参考原取数恢复页面”理解为整段回退；01d583fa6的发布已在构建阶段取消，API/Web容器未替换。现恢复本轮全部功能（仍删除“未完成任务”指标），保留取数优化，页面走平台原有的只读异步查询协议，避免完整24小时统计被5秒同步预算截断。

## 范围和业务边界

依据 `dev_plan/workflow_v2/message_sources_chrome_latency_root_cause_audit_20261120.md` 落实五项优化。只调整执行、排队和统计，不改变消息时效准入、Ticker订阅、相关性、去重、交易时段及发布质量规则。按照用户后续更正，**删除新增的“未完成任务/最老等待”指标**，接口、界面、专用候选查询及专用索引均不保留。

## 实现

1. **稳定 BODY 等待资格**
   - `live_articles.ready_since` 是本轮正文工作的持久等待起点；领取、短暂准入延期和 `due_at` 更新不重置。内容实质更新和能力恢复的新一轮工作按现有流程建立新起点。
   - BODY 调度选择先按等待年龄，而非按重新领取后的 `due_at` 或最新文章时间插队。生产与测试、首次工作与后台工作仍按原有隔离规则执行。
   - Site Access 使用已有 `JointBudget`，BODY 携稳定文章/输入版本键申请。暂不可用立即返回 `body_admission_pending` 和预计释放/节奏算出的 `retry_not_before`；不等待3秒再退出，不固定退避5秒。Hub释放执行槽，未进行正文请求不消耗抓取次数和执行预算。
   - Site Access仅保留3秒可续期软资格。脱离申请期间仍参与公平排序；失效身份和新输入版本清理旧资格。重启后由唯一持久BODY任务恢复资格，不建另一条持久队列。
   - BODY优先，已等待的Crawler在连续3次BODY授予后获得有界机会；老化阈值小于现有准入期限。无BODY需求时Crawler可用全部原有容量；不增加浏览器并发，不保留空闲固定名额。
   - 真实执行中的请求不可抢占；不可用身份不贡献容量。容量不足仍可能延期，不能用配置身份数宣称满足吞吐。
   - 配额延期不进入60秒访问结果缓存，资源释放后可重新取得许可；真实访问回执仍保留原有幂等缓存。

2. **Reuters需求治理**
   - 仅使用每个Ticker配置的第一个L1概念，按原语言规则构建唯一QUERY；OR模式同样只用第一个概念。
   - 不再产生Reuters TAIL。Collector通过既有配置刷新/计划对账停用旧单元，不删除历史回执，不改QUERY原轮询周期。其他by-search源不变。

3. **失败和重试**
   - 页面解析或Site Access明确给出 `login_required/reauth_required/subscription_required/entitlement_missing` 时结束本次获取链，不再尝试另一条获取路径；Hub原有不可重试分类继续生效。
   - 单纯网络超时、401或临时传输失败不自动推断权限失效。
   - 只有一个可执行浏览器路径时，在现有文章总预算内执行一次，消除8秒失败、退避、再8秒的重复阶段开销。显式来源阶段预算仍优先，不增加总文章预算。保留真实正文质量检查和可恢复错误的有限重试。

4. **BODY页面生命周期**
   - Barron's、InvestorsHub、Newsfile使用现有FetchAnchors池复用至多一个独立BODY页面；不借用Crawler页面，不复用Challenge/登录维护页面。
   - 每次新文章仍导航到其URL；站点/策略版本、身份版本、出口变化时关闭旧页面。成功且无权限/Challenge标记的文章页才可入池。
   - 空闲页冻结减少脚本/广告CPU，60秒后回收；维护、关闭和失效路径沿用原有所有权清理。正式Chrome/Profile不重建。
   - 删除Barron's专门正文捕获前重复的整页序列化。增加少量阶段耗时标量用于原有回执，不新增持续截图或采样进程。
   - 生产发现Newsfile的 `public_identity` 外层会在每篇完成后立即关闭已保留的页面，抵消了复用。仅对Newsfile已成功保留的BODY页取消这次立即关闭，沿用原有空闲扫描、60秒空闲上限；不增加定时器或常驻浏览器。

5. **统计口径**
   - 滚动24小时全量有效样本；不再last20/min5/动态历史扩窗。
   - 实时首发E2E按首次Bus发布时间入窗；首次BODY耗时按首次正文结果时间入窗；正文完整率按首次发现的有效文章群体及其当前可用正文质量计算，未完成的近期文章不会被移出分母，首次失败后已获得FULL的文章不会仍被计作正文失败。
   - 内容更新、能力恢复、旧数据无法准确归类的恢复发布独立分组，不混入实时首发均值。新发布记录不可变 `first_publish_kind`，旧数据不伪造准确历史类别。
   - 全局源按源+文章去重，用最早发现/最早发布，不跨Ticker重复计权；Ticker页面仍保留其自己的交付观察。
   - 轮询成功率和刷新间隔共用24小时已闭合逻辑轮次，包含缺失/失败机会；替代路径OR、互补入口AND。当前错误状态不抹掉窗口中真实成功，也不抹掉失败。
   - 无近期数据显式显示；历史发布/正文记录另列并标明时间，不参与近期均值与排序。

## 新增指标取数与资源审查

| 内容 | 取数方式 | 成本控制 |
| --- | --- | --- |
| 首次BODY耗时 | 既有标量 `initial_result_at/first_observed_at` | 与原有文章指标同一批查询；先按独立源生成完成候选，避免每Ticker重复扫描相同BODY集合 |
| 轮询成功率 | 与刷新间隔共用逻辑轮次结果 | 不新增每源轮询请求，不另查一次周期表；共享分发源只选一个实际共享入口的绑定计算 |
| 更新/恢复分类 | 同一文章事实的枚举值分组 | Python线性聚合；不增加每文章SQL、模型调用或浏览器请求 |
| 历史展示 | 独立的最近历史有效候选 | 按复合时间索引查单条，不为凑样本反复扩窗；不回读正文 |
| “未完成任务” | 已删除 | 不扫描全历史WAIT_BODY/PENDING/L2_DUE，不创建相应索引，不为该指标投影任务年龄与延期计数 |

补查运行状态页的分页调用：`include_metrics=False` 以前仍为该Ticker全部来源计算正文与轮次指标。现先确定本页/汇总实际需要的来源集合，再调用批量取数；分页只查本页，筛选汇总只查所选来源。没有新增自动刷新：全源目录仍为进入时/手动刷新，Ticker仪表板沿用每分钟刷新。

生产成本验收发现并追加修复：

- 最初完整目录取数超过75秒，不能交付为“开销可接受”。生产SQLite的执行计划将全历史 `native:live_deliveries` 放在JOIN外层，并在时间边界之前访问索引；通过明确候选/边界/精确身份查找的JOIN顺序修复。
- `CASE + GROUP BY` 使覆盖表达式失效，排序器仍回表读取整段周期JSON。一条真实SEC轮次查询为43.16MB逻辑读取、2.89MB临时写入；只读索引标量后为1.20MB逻辑读取、无临时写入。
- 24小时约73万轮机会不必逐条传回Python再分组。沿用原OR/AND规则在SQLite内聚合小字段；同频常规路径用完整证明数量和首末完成时间精确计算平均间隔，重复due保留最早证明。混合周期继续使用原通用归并；没有小时均值近似或丢样本。
- 全局目录在读取正文/消息指标前选择每篇文章的首个交付代表，仅返回约4,700篇文章事实，避免展开约37,000份Ticker副本；Ticker自身接口仍保留独立交付口径。
- 生产数据只读、临时加载候选代码的完整函数验收：85个源，4.663秒、4.624 CPU秒；文章阶段1.202秒、轮次阶段2.948秒，保持原5秒预算。进程峰值约152MiB，包含API/日历模块的基础开销；样本不能代表高负载P95。逻辑读取约935MiB；物理读取约108KiB；临时写入计数约30.4MiB，其中绝大部分在取消/清理中撤销，不能将逻辑读取当成设备读取，也不能宣称零I/O。未增加持久化度量历史或后台刷新进程。

新增三条局部ReadStore标量索引支持发布时间、共享文章和首次正文完成时间。周期表将原 `cycles_unit_time` 原位升级为覆盖索引，排除高频SCHEDULE行，不叠加另一条周期索引，避免24小时查询逐行回表解析大型 `data_json`。索引会有空间和写入成本，不能声称免费；其实际大小、迁移耗时与查询时间在生产验收中记录。普通GET和服务启动不补历史、不执行DDL。

发布迁移只补24小时候选所需的已有交付标量、同文章旧Ticker成员及各绑定最近历史发布；不复制正文、admission文档或全量历史。500条一批，带幂等标记，由正式migration角色在相关所有者停止后执行。

全量24小时统计必然比旧last20读取更多事实；控制目标是成本随当天文章数增长，而非随累积历史或Ticker重复倍增。冻结的真实规模数据为4,316文章、35,706交付、233源/Ticker组合；删除多余读取并合并源级完成候选后，查询从本轮早期约2.687秒降至1.469秒，临时回放数据库约89.2MiB。该数字是本机冻结回放，不代表生产冷缓存SLA；生产查询与索引成本按下面验收记录另记。

## 限制

- 认证/订阅权限失效会更快且更准确地结束；此改动不能创建订阅权限，也不能保证外部Challenge不再发生。
- 软资格不是浏览器许可，不抢占已开始访问；如果真实健康容量长期不足，公平仲裁只能消除额外等待，不能凭空增加容量。
- 旧恢复数据缺少不可变分类时保留 `legacy_recovery`，不将推测填回历史事实。

## 完整接口读取修复

原页面通过普通同步读执行器取数。旧last20的查询量较小；切换完整24小时后，即使SQL已优化，生产约4.6–5.1秒的取数加序列化仍可能超过5秒，真实页面请求因此超时，之前的函数验收不充分。

复用已有 `DeferredQueries`、隔离的只读执行器及前端202结果协议：目录GET直接提交一次计算，不先运行5秒再整次重做；全局同步读预算不变，其他接口不变。目录为live head，没有view_id，跳过仅适用于固定视图的pin。手动刷新使用独立refresh值，避免复用上一轮已完成快照；同一次传输重试仍复用原任务。前端沿用现有结果轮询，不重复扫描数据库，不增加浏览器请求或持久化队列。

异步读取不等于计算免费：保留24小时全量成本，由既有后台只读执行器的单worker/有限队列隔离，首次启用可能启动其已有的按需worker。需要验收完整HTTP 202→200及最终数据，不能再以取数函数单次低于5秒作为页面已恢复的依据。
