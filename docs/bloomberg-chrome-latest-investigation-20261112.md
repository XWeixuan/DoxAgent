## 2. 对上一轮403证据的修正

重新检查了上一轮四份浏览器HTML及测试脚本：

- 旧Playwright/普通Chrome、美国/日本四份HTML均为“Are you a robot?”页面，包含`px-captcha`，属于网站风控挑战证据，而不是付费正文订阅墙的证据。

- 本轮未登录普通Chrome能够打开Latest，是对“Latest必须账号/订阅才能访问”的直接反证；它不证明匿名Chrome可以长期稳定运行。

## 3. 页面自身如何更新：已经观察到完整链路

当前页面实际加载`pages/latest-cb5f7a1939faed55.js`以及官方`artemis-client/1.1/artemis.min.js`。后者本轮下载SHA-256为`c13df63c7da10a2d13276ccd5e9844a2c89b2fd9ab51316d07037f9e0c001a59`。

实际浏览器网络与DOM证据表明：

1. 页面初始化读取完整stories列表，并读取`STORIES_SESSION / LATEST_STORIES`快照。
2. 随后建立`/artemis/oscillator/stream`，响应类型为`text/event-stream`。它使用fetch流式读取，不应仅监听原生EventSource事件。
3. 新事件提供文章ID、slug、publishedAt；页面按ID获取扩展元数据，取得headline/url后自动插入并排序，无需持续刷新整页。
4. CDP通过`Network.streamResourceContent`及后续`Network.dataReceived`能够读到页面这条连接收到的SSE字节。**观测器没有另外发起一条Artemis新闻流**。
5. 本轮确实观察到三篇增量候选走完“SSE ID→扩展元数据→DOM显示”。其中一篇是在主观察开始之后发布，其余两篇是旧发布时间的晚出现记录。

官方客户端静态代码还确认：默认polling interval为5000ms，初次SSE前会取一次快照；支持可见性变化、约31秒watchdog、短期授权刷新、SSE重连和特定错误下转HTTP polling。它也存在连接重试耗尽后stop的分支，收到消息会重置计数。**这是代码能力说明，不代表本次每次断线都真的回退了polling。** 本次未观察到403之后重新开始正常快照轮询。

解释与限制：

## 5. 持续运行失效：可见列表掩盖实时连接停止

第一窗口捕获34次SSE 200响应和32次`net::ERR_HTTP2_PROTOCOL_ERROR`。可配对响应头至失败平均16.963秒、最大30.717秒。页面会自行重连，并曾继续取得新事件。

随后浏览器Performance Resource Timing留下另一段关键证据：

- 07:24:06.949，页面stories请求403；几乎同时stream也403。
- 07:24:07.259、07:24:07.495、07:24:07.728，stream继续403，形成约一秒内四次拒绝响应。
- 期间sentry仍显示200，部分耗时仅数毫秒，可能来自缓存。**sentry 200不能证明后续stream获准访问，也不证明订阅权限有效。**
- 第二窗口CDP已启用网络观测，但没有新的stories、stream或snapshot响应；页面DOM仍保留旧列表且没有挑战控件。最后留存的网络记录也停在上述403。

因此“页面标题正确、DOM有25条、当前没有挑战元素”都不能作为持续发现正常的健康判断。未来真正接入时需要以有效新闻网络事件/列表响应及连接恢复证据判断采集状态，不能把旧DOM当成功轮询。

## 7. 已实现的精益部分、资源与生产边界

新增`scripts/ops/observe_bloomberg_latest_cdp.py`：附着现有登记维护会话，不创建Chrome、不新开新闻流、不登录、不导航、不刷新、不修改UA/Cookie/指纹。记录页面原生列表响应、SSE生命周期、可选流内容和每2秒DOM新增项，按官方ID与精确发布时间留证。结束只detach，保留浏览器供人工操作。

- 默认不开启实验性SSE字节tap；需要明确`--tap-stream`才调用CDP streaming。纯网络/DOM对照用于排查观测工具本身是否影响流，**这一无tap持续对照尚未完成**。
- 只解析允许的官方新闻路径；不读取sentry授权响应或登录响应体，不记录请求头/Cookie。SSE只接受`STORIES_SESSION/LATEST_STORIES`，支持跨字节、UTF-8及CRLF分片，排除ping、其他topic与认证数据。
- 回归40项通过；最后CLI开关调整后5项解析回归再次通过，Ruff E9/F通过。单元测试证明诊断代码正确性，不证明Bloomberg新闻时效。
- 仅作为有界诊断工具，未另造一套发布/处理系统；未切换生产Collector实现、未重建服务镜像。HTTP/Chrome观测进程均在有界窗口结束，只有人工交接Chrome保留。
- 一个Latest标签时Chrome树15个进程，RSS合计约1596.8MiB；Latest加登录标签时20个进程、RSS合计约2436.5MiB。**RSS包含共享页重复，不是实际独占内存；PSS因读取权限不可得。** 不能将常驻Chrome称作低资源，更不能仅为14–30秒小样本领先就无条件替换HTTP。
- 生产`bloomberg_massive`版本仍为3，test模式。正式raw、standard、Ticker binding及decision-model数量均0；主观察前后其他源定义、绑定、统一词修订与默认Profile哈希一致。正文未开发为订阅Chrome抓取，旧HTTP的SHORT_FULL/PARTIAL也不当作本轮正文质量验收。

## 8. 推荐实现与继续执行顺序

**当前不推荐直接把默认生产采集改为常驻Chrome唯一通道。** Chrome读取和页面自动更新可行，但长期访问已经失败，分钟级时效缺口仍在。HTTP只作真实对照和既有覆盖保留，不以“必须保持HTTP”为前提否定浏览器。

下一步按依赖关系执行：

1. 先完成同一持久化Chrome、同一出口的人工免费账号登录与Latest访问对照；没有证据前不要求购买订阅。
2. 人工交接结束后，在同一会话做一次正常重载，先运行无stream tap的网络/DOM对照，核实协议错误和403是否仍出现。页面自身403时停止自动重试并明确阻塞；不换IP、不重置Profile、不反复刷新验证页。记录真实挑战响应/console原因，补齐单变量证据。
3. 在有实际新发布文章的窗口同时比较：页面SSE、页面扩展元数据/DOM、现有HTTP快照、全列表、测试article首次接纳。保留发布时间EXACT和每路原始首次时间；冷启动、晚出现旧稿、断线窗口分别列出。小样本只能确定方向，不能承诺稳定P95；仍是分钟级就保持TARGET_UNMET。
4. **只有访问恢复、实际时效优势和覆盖补漏均证实后**，将已验证CDP读取放进现有Chrome Worker：一个共享Latest页、一个授权Identity/固定出口；SSE只负责及时ID，标题元数据就绪即沿原capture/on_page去重接纳；已有native-ID alias及测试发布隔离全部复用。DOM核对补漏；断线后做有界完整列表恢复。不要新增采集守护服务或另一套队列。
5. 同身份BODY按需开后台文章页，处理后关闭；验证实际页面可见性，避免正文访问让Latest实时客户端进入hidden暂停。没有订阅时保持正文权限与质量标识真实，不把预览或摘要标FULL。身份/站点预算只对该新源定界，不调整其他身份。

本轮最终结论是：**正常Chrome不是不可行，Artemis原生流可读且确会自动更新；但匿名持久化Chrome仍未证明稳定、及时，403根因未完成单变量定论，账号人工对照与新稿时效验收待续。**
