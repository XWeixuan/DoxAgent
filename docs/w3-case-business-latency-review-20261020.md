# W3 长耗时 Case 的业务发生机制审查

日期：2026-10-20。研究范围：上轮五小时采集的全部 21 个 Case，加北京时间 10 月 19 日、20 日截至本次取数时已产生交易意图的全部 Case，去重后 **25 个 Case**。本轮仅读取生产记录，没有开启探针、重放、派发模型、调用券商或修改业务逻辑。

## 1. 核心结论

**真正放大耗时的不是“关联了 Policy”这个标签，而是 Agent 从“条件未满足”继续走到“虽然没有 HIT，是否仍有值得交易的早期变化”。**这条分支需要同时解释 Policy 边界、建立独立 Prior/Delta、追溯有效披露、判断当前机会，并处理跨消息的历史关系。只有发现实质拒绝理由的 Case 可以提前结束；拟交易 Case 则要完成整个正面论证与机会核验。

数据要求修正“Policy Case 普遍很慢”的直觉：两天有成功 SDK 时长的 RELATED Case 中，**不交易的 67 个，SDK 中位数 64.58 秒；OPEN 的 417 个为 64.48 秒，几乎相同**。RELATED 中形成意图的 6 个，中位数变成 **327.74 秒，约前者 5.1 倍**。六个 Case 全部以 RELATED 进入，最终 1 个纠正为 Policy Trade、5 个选择 Expert Trade。不能把最终 Policy Trade 误当成最初 HIT 路径，也不能把这个差距归因于不同模型：这六个实际均为 `gpt-6-luna / max`。

长分支中又混合了三类成本：

- **必要业务研究**：分辨测试与真实迁移、谈判与已签约、行业短缺与 Intel 的暴露、罢工授权与实际执行安排。这些是避免错误交易的关键，不能一概删除。
- **可以直接降低的获取/交付成本**：原文缺失导致多轮找转载与首发；对象名、kind、Shell 猜错；长 cursor 人工转写损坏；行情分页及事件时间修正；跨 Case Thread 历史累积。
- **证据已回到模型后，仍有很长的综合判断与交付区间**：六条意图 SDK 共 2014.95 秒，外层工具执行区间并集共 200.85 秒，仅约 10%；仅最后一次工具返回至最后一条 usage 通知就有 502.23 秒，约占 24.9%。因此只把 MCP 从 0.5 秒再降到 0.1 秒，解决不了主要问题。剩余区间包含模型生成、服务、传输及其他未分解时间，不能称为“纯推理”。

还有两类独立长尾需要保留：NBIS 的 600 秒 SDK 超时恢复，以及 INTC 在 SDK 只有 8.68 秒时仍出现 158.88 秒 W3 总耗时。它们不能拿来证明业务研究本身复杂。

## 2. 样本、口径及可复核性

### 2.1 三个互补样本层

| 层次 | 范围 | 用途 |
|---|---|---|
| 逐 Case 深读 | 原采集 21 个 + 两天全部 6 个意图，重叠 2 个，合计 25 个 | 结合消息、W1/W2、冻结 task/Policy、工具参数、实际返回、公开交付还原业务目的 |
| 同窗口对照 | 原五小时窗口全部 99 个探针 turn：98 个成功、1 个 SDK 超时；对应 98 个 Case | 使用同 release 的 79 个 OPEN 与 19 个 RELATED，避免只用筛出的慢样本证明慢 |
| 两天总体校验 | 北京时间 10/19 00:00 至 10/20 19:43:08 的 546 个有 W3 阶段 Case | 检查 Policy 分布；491 个有最终 SDK 时长，另有 52 个 FAILED、3 个 PENDING_W3，未用零秒填缺失 |

两天意图另从持久化 `runtime_values / trade_intents` 全量核对，按 `released_at` 筛选，截止北京时间 **10/20 19:46:30**，共 6 条，均为 `EXECUTION_ACCEPTED`。这确认的是产生并受理意图，不是成交。额外核查了范围前创建、范围内完成的 Case，未发现遗漏意图。

25 个深读 Case 有 27 个交易阶段 job：25 个最终成功、1 个 `CODEX_TURN_TIMEOUT`、1 个尚未建立 turn 就发生的 `CODEX_START_TIMEOUT`。连同对照样本共导出 104 个 job，其中 103 个找到 native turn 起点；缺少轨迹的正是启动失败 job。失败及重试分别保留，没有用最后成功覆盖第一次失败。

**“Agent 的视角”在本文中指：它收到了什么、当前业务疑点是什么、实际采取的动作能解决什么、返回后改变了哪些可支持的选择。**没有读取隐藏思考文本。明确的输入、动作、返回与结果是观测；对目的的解释是据此作出的业务还原，不能当成逐字心理记录。没有在调用前公开说明目的时，不会仅凭读过某份资产就断言其主观动机。

原始证据和复算脚本在 [`eval/w3_business_mechanism_20261020`](../eval/w3_business_mechanism_20261020/README.md)。`native.json` 保留实际调用和返回；`metrics.json` / `turn_metrics.csv` 是复算结果。下文的 Case 尾号可以在目录的 `case_index.json` 对应完整 ID、标题和独立证据摘录。

### 2.2 时间含义

- **Case 秒**：Case 创建到交易决定提交，包含 W1/W2 等上游阶段。
- **W3 秒**：`route_to_w3` Effect 创建到交易决定提交。
- **SDK 秒**：该交易 job 的 `sdk_duration_ms`，重试单列。
- **工具秒**：native 外层调用区间并集；并行嵌套调用不重复求和。
- **返回后间隔**：工具返回到对应下一条 usage 通知的观测间隔，不是服务端精确响应延迟；最后一段也可能包含交付尾部及未观测开销。

正文只分析 `trade_decision`。后续运营不混入交易 turn，也不以最终整个运营任务的完成时间替代交易提交。

### 4.2 INTC 综合稿：从“逐项排除旧消息”扩展到“发现另一个真实触发”

**当前问题。**W2 只将卖方估值更新关联到 Policy；文章还混有 GPU/Xeon、Terafab、Applied 合作和此前工厂爆炸。Agent 需要区分：这些是否只是旧材料拼接，还是某一条改变当前 Intel 预期。不能用标题的“AI deals”替所有分支建立交易意义。

**实际行动及其业务目的。**先找 D2 中 CPU、非 CPU、Foundry、封装业务的基线，随后逐项核对分析师目标价、Terafab、Applied 合作的原始日期与内容。大部分被确定为此前公开且未改变长期模型。之后转向 PIN 中的 Kiryat Gat 背景，搜索到当日 NF3 泄漏处置，进而寻找未被当前 W2 内联的另一条 Policy，确认 C4 的早期风险边界及可执行状态，最终 SHORT。这不是单纯“重复研究已给 Policy”，而是从综合稿主动发现另一条可能的交易命题。

**多花在哪里。**9 个 Web 批次、6 个 catalog/search、5 个 read；在第一次行情调用前已用约 254.59 秒。查另一条 Policy 时先用了理由中的缩短 ID，随后经历 read→search→catalog→search→完整 ID read→usage，形成明显的对象定位成本。最后行情返回后还有 109.43 秒的交付区间。

**可降低的部分。**多催化拆解本身有价值；但旧消息日期/已证实事实可复用，搜索应直接返回完整对象身份与对应冻结状态，减少因为不能定位另一条 Policy 而反复探索。不应为提速禁止发现非 W2 候选，否则会删掉本 Case 最终交易的实际来源。

### 4.3 首条 Modal：研究轮数不多，却被重上下文、游标修复与收束拖长

**当前问题。**消息正文足以说明 Modal 计划采用 Vera、早期测试更好，但 Policy 要的是已由 Xeon 承担的生产负载迁移。Agent 必须避免把计划写成迁移，同时判断具名客户验证是否已足以形成 Expert 早期竞争信号。

**实际行动。**只有一次 Web 批次补原发和测试信息，随后主要读取市场视图，最终以“增量 CPU 竞争验证”做空，不冒充 Policy HIT。方向论证不是由 K 线产生的。

**明确发现的无效往返。**第一次行情给出未完成页与合法 `next_cursor`。后续三次请求中的 cursor 均不等于任何先前返回的 cursor，解码后签名可见抄写差错；三次实际返回 `invalid or mismatched research cursor`。最后一批改用代码解析 `r1.content[0].text`，直接把 `p1.next_cursor` 交给第二次调用才成功。

**更正上轮快速验收：三次约 307 字节的短返回是 cursor 错误，不是 PREPARING。**最终行情内容确实另有 supplement PREPARING，二者必须区分。原始文件保留不改，本报告以完整返回为准。

SDK 278.06 秒中工具区间并集仅 8.70 秒；首轮已有 120,828 token、无缓存，首个 response 就用了约 41.79 秒；最后工具返回后间隔 125.69 秒。这说明该 Case 不是“搜太多”一种问题。最直接的修复方向是取消长 cursor 人工转写，保留 Code Mode 中的原值，并控制跨 Case Thread 历史带来的输入负担。

### 4.4 第二条 Modal：正文不足，任务变成补原文、客户证据与有效公开时点

**当前问题。**Investing 输入的 body 虽非空，实际只有约 88 个字符，主要是标题。Agent 不知道“wins CPU business”究竟是正式生产迁移还是测试/计划，不能直接拿标题完成 Policy 或 Expert 论证。

**实际行动。**反复尝试 Investing 原文及移动/AMP 变体；查 Modal 官网、LinkedIn 收货公告、Sandbox 测试、可比 x86 是否明确是 Intel；还核对测试/公告公开时点。14 个 Web 批次中，很多是在补同一个缺失的原发语境，不能机械算成 14 次不同经济研究。

**为什么增长。**正文不可得使“事实状态”“Intel 真实暴露”“最早有效披露”三个问题纠缠：每找到一个新片段，既可能补强早期机会，也可能证明只是旧测试再传播。Agent 直到约 262.78 秒才查询行情，随后还有 102.08 秒的末段间隔，最终维持未 HIT、但有 Expert SHORT。

**历史关系。**此 Case 输入冻结于第一条 Modal 意图提交前，因此只看到更早的 NF3 意图；第一条 Modal 是 14:29Z 受理，而本条 Case 14:25Z 已创建。两条五分钟内相继提交，不能直接认定 Agent 忽略了已注入的 Modal 意图。这里暴露的是**并发冻结上下文看不到另一个正在研究的同催化 Case**：可以共享带时间与来源的已证实研究进度，或让提交前轻量刷新同催化已完成意图；不能靠让第二个 Agent 自己猜另一个任务在做什么。

### 4.5 MU 第二笔 $45B：需要把“巨大数字”变成“可比较的新增部署概率”

**当前问题。**已有一笔 $45B 左右协议；新消息又称第二笔。Agent 要防止把同一协议重复计算，也要判断还在谈判的第二设施是否已对 MU 有足够意义。服务金额不等于硬件采购，更不等于 MU 收入。

**实际行动。**先恢复 AI 数据中心需求、HBM、服务器内存基线；初始用 `kind:d2/id:unit0/shell:shell-0003` 及 D1 文件名式 ID 读取失败，继而 catalog 修正。Web 比较旧 SEC 文件与本条 Reuters/Bloomberg 转述；行情先按 HuggingNews 时间取，找到 Reuters 19:36Z 后重新对齐 event_time，并续读分页。最终将增量表达为新增硬件部署的概率上升，不伪造签约 HIT。

**耗时机制。**16 个 response；4 个 Web 批次、4 个行情批次，其余多为研究访问与基线恢复。一次补读 D2 state/gaps 后到下一 response 的间隔 58.39 秒，是该 turn 最大间隔；行情前后还继续取证，不能把第一次行情之后的全部 146.60 秒称为“查行情耗时”。可降的是错误对象定位、同一已读 Unit 重取以及先用转载时间、后修正为有效披露时间引发的第二轮取图。

### 4.6 INTC 欣兴：真正昂贵的是建立跨公司传导，而非判断有没有短缺

**当前问题。**20% 材料缺口、30 个月设备交期并不自动意味着 Intel 减产。Agent 必须分清预测与已发生缺料、行业与 Intel、材料扩产约束与具名产品批次延误。

**实际行动。**先尝试研究目录与搜索，未能直接定位目标；随后从 TrendForce 追到中文经济日报，核对 TPCA 发言的原始量化口径，再找欣兴与 Intel EMIB-T 的供应链关系及此前良率目标。最后选择“Intel 先进封装扩产风险提高”的 Expert SHORT，明确未满足具名批次受阻的 Policy 条件。

**耗时机制。**8 个 Web 批次、2 个行情分页批次，14 个 response。供应链关系检索后有 45.00 秒间隔，最后读较早供应链资料后有 72.10 秒间隔。它补的是“这个行业风险为什么属于 Intel”的核心前提，不能仅按读了旧资料判为重复研究。可复用的是有来源、有版本的供应商—产品—暴露关系，而非让每次消息再从 Web 建立整条链。

### 4.7 MU 罢工：区分授权、集会和真实执行安排，再重对齐早期披露

**当前问题。**输入没有正文。Policy 关心是否涉及量产轮班或瓶颈维护；旧资料只有罢工授权。Agent 要判断新消息到底是正式排期、集会，还是足以更新生产风险的实际行动。

**实际行动。**补 Reuters 转载，随后读本地中文报道：找到较早 Newtalk、LTN 的工会/员工人数和 CNA 的一日声援式罢工安排；把“授权无排期”与“确定日期”分开。由于原发早于 Reuters，又将行情锚点由 02:06Z 改到前一日 15:34Z，补取两个时点相关行情。最终选择早期风险 Expert SHORT，同时明确没有量产岗位覆盖证据，不能宣称已触发 Policy 或已减产。

**耗时机制。**SDK 510.46 秒；4 个 Web 批次、6 个行情批次、2 个 Shell 合同读取批次。读本地报道后有 **134.44 秒**间隔；行情续页之后又有 74.00 秒、最后有 63.04 秒。还发生一次 cursor 签名抄写错误，修正后成功。实际任务包含本地语义消歧、旧授权基线和两个披露时间的比较，不能只叫“看了 K 线”。

这一条确实重新 `cat AGENTS.md/skill.md`，但读取合同的直接工具耗时仅约 6.49 秒；在六条意图中也仅此一条如此。值得消除，但不是足以解释全部长尾的共同主因。

## 6. 长分支增加了哪些子任务：统计与发生机制

### 6.1 六条意图的工作量结构

| 实际动作 | 工具批次数 | 业务目的 | 可降低的成本 |
|---|---:|---|---|
| Web | 40 | 核实当前事实、找原发/有效时间、区分旧基线、证明目标公司暴露 | 空正文/标题新闻变成多站试探；原文失败后重复关键词和 URL 变体；同催化并行研究不能共享已取得证据 |
| 行情 | 19 | 对齐有效披露、读完成 bar、只做完成态否决 | 分页、cursor 抄错、事件锚点修正、重新读整视图；19 是外层批次，其中一批内部调了两次 MCP |
| catalog/search | 10 | 不知道真实对象名或主动寻找另一条 Policy | `kind:d2`、Shell 编号与业务名、缩短 Policy ID；有些请求只得到空结果，却额外占一轮 |

共 **86 个工具批次、92 个 response**。Web+行情占批次 68.6%；但批次数不等于耗时占比，尤其不能拿“工具返回之后的所有间隔”全部归到那个工具的业务类别。

### 6.2 五个互相放大的机制

**机制一：否定一个 Condition 只关闭 Policy 路径，不关闭经济机会。**

Modal 没证明 Xeon 生产迁移、欣兴没证明 Intel 批次受阻、MU 没证明关键生产岗位罢工、Nscale 还没签约。若当前证据仍可能改变重要预期，Agent 被要求继续判断 Expert。它因此多做一套正面可交易性论证，而直接 NO_TRADE 的转载 Case 不需要。合理的优化不是规定“NO HIT 就停止”，而是明确尚缺的决定性前提，避免把“可能重要”扩展成无限研究外围背景。

**机制二：拟交易触发来源/时间/当前机会的完整核验，且时间确定常发生得太晚。**

六条均查行情；Nscale 和 MU 罢工都先用较晚媒体时间，后找到更早原发再补一次。第二条 Modal 在找原文、首次收货与测试公开时间间反复切换。来源时序既决定新旧，也决定 K 线区间；晚修正一个时间，前面读取的行情和解释就需要复核。应先整理“当前最可信的有效增量时间及未知精度”，再只读与该问题适配的行情；发现真正会改变判断的新时间再更新，而非追求全球绝对首发。

**机制三：研究工具的业务定位摩擦制造额外模型轮次，游标损坏是已证实的浪费。**

本轮 99 个探针 turn 发现 11 个 cursor 错误：3 个行情错误集中在首条 Modal，8 个发生于普通 Case 的研究/目录续页；额外 MU 罢工又有 1 个行情 cursor 错误。两条意图的 4 次错误都能对照先前返回证实 cursor 原值被改写。不是数据库内容真的变了，也不是 PREPARING。每次错误工具本身不到几秒，却要新开 response 解释、重试，再让更大的上下文继续一轮。

还有一个确定的交付放大：第二条 Modal 为找工具而用包含 `search` 的宽正则枚举 `ALL_TOOLS`，这一步输出 **41,798 字节**；多数定向发现只输出约 2,052 字节。目的只是找到 W3 研究/搜索入口，却把更多工具说明带入了后续每一轮。研究与行情的多次调用还直接回显整个 MCP 对象或 JSON.stringify 包装，而非只交付一次正文及收据；应将这类格式开销与真正的业务材料分开优化。

**机制四：获取材料增多与“收束前再做综合比较”叠加，不能只用轮数衡量复杂度。**

六条意图最后输入中位数 **128,130 token**；同窗口 OPEN 为 39,703。五条从约 28k–39k 起步，逐步到 85k–134k；另一条 Modal 一开始已 121k。最终一条 response 的输出 token 数分别为 13,972、14,875、13,069、3,765、7,766、7,550，远多于用户看到的简短 JSON；这里含 SDK 记录的 reasoning token 数量，但没有读取其内容。

其最后返回后间隔中位数 **87.09 秒**，OPEN 为 16.23 秒。即使缓存已经很高，长间隔仍存在：首条 Modal 最后一轮 147,782 输入中缓存 145,152，仍有 125.69 秒间隔。因此“修好缓存就够”也不符合证据。

这更像是“前面逐条收集与局部判断，末尾再把 Policy/Expert、反证、历史及行情做一次大规模综合”的行为结果。但服务端耗时尚未拆开，**不能据此证明它在末轮逐条重想了所有问题**。最值得验证的是：每个决定性问题在被回答后能否稳定复用，最后只处理未决矛盾和输出，而不是重开一轮全面权衡。

**机制五：线程复用减省重复取证，也把旧研究留在后续输入中。**

首条 Modal 的 Thread 与更早 INTC Policy Trade 相同，开始前已有 8 个 turn；同一 Thread 后续多个 Case 首轮输入达到 176k、188k，并有一次 compaction。它们多数仍能在 10–30 秒拒绝，说明大上下文不是充分的长耗时原因；但一旦新机会还要新增多轮，历史负担会与新材料叠加。

第二条 Modal 的 Thread 是新上下文，首轮仅 29k，却因取证多轮仍到 126k。两种路径分别说明：**不能只换新 Thread，也不能只减少研究次数；需要同时处理旧内容继承和本轮材料增长。**复用确实让后续 Reuters 转载可以零工具拒绝，应保留已证实事实与历史意图，而非机械丢弃所有历史。

## 7. 从这些机制得到的优先方向

本轮不是实施方案，也不将建议收益伪装成已测提速。依据强弱排序如下。

| 优先级 | 方向 | 对齐的业务问题与边界 |
|---|---|---|
| P0 | 消除 cursor 人工复制；续读使用原始返回值，考虑短续读句柄/宿主侧保留请求 | 四次行情错误、八次普通研究错误已有实际证据。保留完整信息访问与续读，不靠截断或禁止读取提速 |
| P0 | 把不可用正文与原发材料缺失提前处理；共享同催化已获得的来源证据 | 第二条 Modal、MU 罢工是明确样本。保存来源 URL、内容版本、可用时间和适用 Case cutoff；不把后来的新事实倒灌早期 Case |
| P0 | 让已读材料支撑的关键结论持续有效，缩小提交前重新综合的范围 | 末段约占六条 SDK 总时间四分之一，是最高收益验证区。要用新样本验证末轮 token/间隔是否下降及判断质量是否保持，不能预设整段都能删掉 |
| P1 | 以真实业务对象直接定位研究；搜索返回完整 ID/kind/Shell 与冻结状态 | 防止空 catalog、错 Unit、缩短 Policy ID 反复修复；仍允许发现 W2 未关联的 Policy，保留 INTC C4 这种自主发现 |
| P1 | 行情围绕一个有效催化锚点，一次交付所需区间及覆盖限制 | 降低为时间修正、续页和数据状态反复切换；原发确实变化时仍允许补取。PREPARING 不应诱发无关研究或机械等待 |
| P1 | 同催化并行 Case 共享已证实研究进度，提交前核对新受理意图 | 两条 Modal 冻结时点产生真实信息隔离。做业务事实/状态复用，不能用标题相似就强行去重不同催化 |
| P1 | 对复用 Thread 的历史作业务级整理，保留可用结论和来源、减少无关旧输出 | 针对 121k 起步、188k 首轮输入；不能承诺仅凭 token 减少就消灭长尾，也不能破坏快速转载拒绝所依赖的历史 |
| 独立 P0 | 修复启动失败恢复和 SDK 流停顿 | `2deefb` 的 START_THREAD 失败/重试及 `6e52ca` 的 600s RUN_TURN 超时，与经济研判深度分别验收 |

最后的业务判断是：**值得交易的早期信号确实比拒绝普通转载需要更多工作；当前多出来的工作中，一部分是必要的反事实、传导和机会核验，另一部分是取证失败、对象定位、续读修复和重复综合所制造的成本。**继续优化应对准这些具体机制，而不是把 Policy 研究整体压浅，或把所有长间隔笼统叫作“模型想太久”。

## 8. 本报告仍不能回答什么

provider 端首 token 延迟、队列、生成和网络的精确分项仍没有完整记录；返回后间隔不能拆成纯模型推理。六条意图样本少、五小时中两条又属于相同 Modal 催化，不当作六次独立随机实验。HIT 只有一个无意图样本，未覆盖 HIT 交易的常见流程。

任务目的可以通过输入、调用问题、取得的事实及最终理由还原，但无法为每次 D1/D2 读取证明唯一的心理动机。本文只将能对上当前未决问题的读取解释为该问题的取证，不把“读过 C3/C5”直接改写成“为了重复证明市场主线”。已证明的 cursor 损坏和超时错误则可以直接认定为技术问题。

本轮未改 Prompt/Skill、编排、交易逻辑或生产配置。报告用于下一轮选择并验证优化点，不宣称已经达到 100 秒 p95 或非 SDK <5 秒目标。
