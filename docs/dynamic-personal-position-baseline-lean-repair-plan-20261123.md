### 本轮实施冻结补充（优先于下文原有规划性描述）

1. **持久失败闩锁**：使用既有runtime_values，按EXIT job ID记录失败版本、首次失败原因和时间。EXIT进入FAILED时与状态变化同事务写入；启动时仅为当前历史FAILED补齐闩锁，不恢复任务。lot重建、人工调整、迟到成交即使把任务改成DONE/READY，也不能清除该闩锁或重新取得新增订单资格。最终mark_submitting再次按job ID检查。只允许受控核验请求消费精确失败版本；审计保留，不用清除历史记录掩盖失败。
2. **正常路径与闩锁隔离**：闩锁只禁止该EXIT任务新增订单，不用历史FAILED或闩锁阻断同合约正常个人基线更新；真实未结策略单、成交缺口仍需处理。普通归属/快照等待不累计真实执行失败；确定的权限/路由/资金拒绝或持续的非暂时性执行异常明确FAILED。连接故障、正常未成交撤单重试保持非终态；不能用永久等待代替真实拒绝。
3. **恢复及旧单核对**：FAILED旧attempt仍可同步、落账及取消，但不走可能新增订单的完整任务步骤。受控恢复独立核实历史成交和用户人工操作，P=A-S自洽不是未代平证据。管理请求绑定组ID、实际账户、失败版本及lot余量；消费授权、更新任务、回执同事务，重复请求不重复换代或发单。
4. **统一组操作**：提前退出/恢复入口均以execution/group ID为唯一操作对象。组内任一FAILED/失败闩锁使普通提前退出请求拒绝；受控恢复核实全组后按实际剩余腿处理，不把组ID与单腿lot ID混用。订单由正常Executor执行，沿用真实成交/费用/收益账本及主后对冲顺序。
5. **历史COHR验收**：只读核对trade:case_6db274e8e6ce40bb96a4aabc55c11b8d的COHR SHORT6 / SOXL LONG7及11月13日两项人工调整；与后来个人COHR LONG6分开。已正确清零及DONE的记录不重复调整、不批量恢复。发现残余未知单或错误任务才做经核对的最小修复。
6. **资源与发布**：新增闩锁查询仅主键查找；无新增常规券商请求、EXIT WhatIf、固定等待、全历史扫描或独立服务。维护/管理沿现有回合有界处理；仅发布受影响组件并只读核验。现有未授权的源码改动不得混入发布。

## 1. 设计原则与架构边界

正常交易追求低延迟、低阻塞；严格核验集中在**终态 FAILED EXIT 的恢复**。不为不可观察的低概率事件建立全局审核系统。保留虚拟lot、订单状态机、券商同步和资金模型。

| 路径 | 行为 | 核验强度 |
| --- | --- | --- |
| 正常ENTRY / EXIT | 复用既有同步、策略账本与明确异常检查 | 不逐笔证明个人交易，不加常规请求或固定等待 |
| 普通归属等待 | 非终态RECONCILE_REQUIRED等，缺口消失后继续原任务 | 仅处理已知异常，不进入FAILED EXIT人工审核 |
| 策略提前退出 | 用户授权后按execution/group ID请求MANUAL_EARLY_EXIT，由正常Executor退出 | 确认对象、账户、lot余量及既有委托；幂等 |
| 终态FAILED EXIT恢复 | 默认保持FAILED；专门核验、授权、留痕后才能处理剩余义务 | 禁止仅改状态、重置次数或换generation重新发单 |

**非终态持续重试不等于恢复终态FAILED。** 动态基线修复、连接恢复、差额消失、到了退出时间或重新请求退出，都不能自动恢复历史FAILED EXIT交易。

### 1.1 两种手动操作

- **普通个人交易**：直接在IBKR买卖，默认归个人，不改变策略lot；不要求提供外部成交逐笔证明。
- **主动提前退出DoxAgent策略**：用户明确授权Codex操作指定交易组，走本方案管理入口；Executor真实成交、费用与收益进入现有策略账本。

MARGIN例子：策略LONG10、个人原持仓0；用户自行在App SELL10后实际净持仓0。未明确替策略销账时，仍保留策略LONG10，个人残差为SHORT10；策略退出时仍可SELL10并形成实际净空。这是普通个人交易的归属语义，不应自动消掉策略lot。

已经在IBKR替策略平仓时，仍须核实实际成交并修正对应lot，不能自动猜意图。现有adjust_lot只修数量，不自动补齐人工损益/费用；不能用它替代新提前退出入口的真实订单链路。

## 3. 动态个人基线：宽松、可靠、无个人成交证明负担

范围键为**实际账户ID＋conId**；LIVE/PAPER不共享，SMART/OVERNIGHT不拆成两份归属。

```text
A = 可信券商快照的实际有符号净持仓
S = 同账户、同合约策略有效成交净额＋有符号lot调整
L = 全部相关策略lot的 Σ(sign × remaining_qty)
P = 个人/外部持仓残差 = A - S
```

保留execId family最新修订；数量用有限Decimal，个人碎股不取整，策略订单仍为整数股。

### 3.1 允许自动更新的条件

只要快照可信、策略成交和lot自洽，没有已知未结策略订单、成交缺口或其他明确异常，就允许更新P。差额幅度、方向、跨零或缺少外部成交明细，都不是阻断理由。

复用现有数据检查：

1. 账户、连接代次及positions快照正确、请求完成。不完整快照不猜0；完整全持仓快照中未返回该conId可按0处理。
2. 同合约无已知未知提交、撤单未确认或已报告未入账成交。当前确定未发送的PREPARED不自阻塞；已有活动订单先走原状态机。
3. S与L自洽，无已知execution_event_gaps、超额退出unattributed_qty等真实缺口。历史普通失败日志不是永久挡板；明显生产策略引用无法匹配，不能默认为个人。
4. 存在已知同合约策略成交/修订/lot调整与快照竞态时，丢弃不一致快照，在原调度中重新同步。没有此证据时不额外等待。

**不要求逐笔外部成交证明，也不因“无法证明数量差额来源”拒绝初始化或更新基线。** 已知历史成交遗漏、恢复不完整或账本矛盾时才阻断相关合约；不为每次个人变化重新核对全历史。

已持久化、已完成对账的历史策略订单复用既有结论。history_complete=False不一律禁止正常交易；仅当存在明确未决订单且恢复依赖缺失历史时继续等待。history_complete=True也不是永久全历史完整证明。

对拆股、强制减仓、历史遗漏，优先沿用已知异常、订单对账和账本检查。不新增按数量比例/方向猜企业行为的模型；无异常证据时不因无法逐笔解释而阻塞。接受极少数不可观察事件无法完全识别的边界。

### 3.2 轻量实现与审计

优先修改_position_check，复用有效成交和调整读取，得到A、S及lot自洽结果，通过现有检查后计算P。P不同或首次建立时才更新execution_position_baselines[account:conId]。

基线及轻量审计在同一现有本地事务提交；用现有te_events/JSON记录旧/新P、A、S、账户/conId、job、快照时间和原因。不新增表，不声称识别具体个人成交，重复检查不更新at或重复写日志。

保留正常同步和缓存。必要时仅为原_sync_fresh补同步边界/已入账水位元数据，用已知事件判断同合约竞态；不逐单扫描全部历史、不建持久化凭据服务。提交前复用原lot余量、未结attempt和明确变更检查；准备期间确有相关变化时才作废未发送PREPARED并重新核对。

健康路径不新增券商请求、固定等待、双次同步、全量历史扫描或个人流水追踪。严格恢复材料只在第6节使用，不能变成普通订单的“归属完整性审批”。无法匹配的明确生产策略事件沿用现有gap处理；不把DA-TEST/DA-WHATIF等非生产引用误判为策略缺口。

不拆“先平个人、再开策略”两张单，不改策略数量、对冲方向和配仓。A=0或S=0不代表各lot平仓，不据此释放策略资金/名额。EXIT只退出自身lot余量。

CASH继续原已结算现金、不可正股卖空、SHORT替代与整数股规则；动态P不授予新能力。本轮不新增原版的CASH负残差专用拦截、EXIT库存专项核验或虚拟借股模型，也不按券商净额截断lot来伪造退出完成。实际可卖/资金约束由既有Executor及IBKR检查处理，余量如实保留。

个人与策略仍共用券商资金、保证金和借券能力。P变动不增加策略额度，也不把个人盈亏算为策略收益；虚拟归属不等于券商账户实物隔离。

## 5. 受保护的策略提前平仓入口

### 5.1 对象、授权及幂等

增加轻量管理命令`group-exit`，绑定execution/group ID、预期账户、request_id、actor及MANUAL_EARLY_EXIT原因。Codex必须获得用户对明确目标组的授权，不能只凭ticker猜测目标。

请求前展示目标Case、账户、主/对冲lot余量、EXIT状态及未结委托；应用事务中再读最新对象。这里是指定管理操作的对象确认，不是正常交易新增审核。不能改账户、改方向、扩大数量或重放ENTRY。

相同request_id及相同内容返回同一结果；同ID不同对象拒绝。客户端超时、SSH丢回执、重启后仍按原ID确认，不重复创建订单或换代。原业务exit_reason可保留，人工请求原因和actor独立留痕。

### 5.2 执行路径

1. 读取目标组、lot、ENTRY/EXIT及相关未结attempt。已清零且无待核对旧单时幂等返回已完成，不能把CLOSED重新改成CLOSING。
2. 目标任一腿有FAILED EXIT时，普通提前退出请求整体拒绝并提示FAILED_EXIT_REQUIRES_REVIEW；不得顺带恢复或先退出另一腿来绕过专门核验。
3. 已有活动EXIT或撤单确认中，复用原订单；未结ENTRY则请求阻止继续新增开仓，沿原路径撤单/对账，迟到成交仍承担退出责任。不得直接清零状态或新建替代单。
4. 有ts_positions时复用ExitRepository.request_exit的版本和证据机制，并扩展允许原因MANUAL_EARLY_EXIT；没有该受管记录时复用groups.request_exit请求全组退出，不强制启用滑动止盈或建立第二套仓位。
5. 正常Executor先退出主仓、再退出对冲；沿原限价、等待、撤单、无限轮次及未知提交恢复处理。真实成交、费用、收益和lot归属均走原账本，不以管理请求成功冒充成交成功。

### 5.3 交给唯一Writer，不绕开Executor

优先复用Runtime现有持久操作与回执。当前ticker控制submit只支持监控类动作，不能把组退出伪装成PAUSE/RESTART；也不能在Executor持锁时用CLI抢锁直接改任务。

若现有操作类型不便扩展，最小落点为现有runtime_values中按request_id保存管理请求/回执，由现有Executor配置/管理维护回合有界消费。无需新服务、新表或独立订单队列；每回合处理少量待应用请求，已处理记录不反复扫描，所有订单继续是原te_jobs/te_attempts。

Writer在同一事务内完成请求幂等校验、退出意图和应用回执落盘；崩溃后重读回执，不能再下单。日常提前退出无需频繁停止整个Executor。

**禁止Codex直接调用IBKR下单后再adjust_lot补账。** 新入口必须走正常策略订单链路，避免人工退出损益和费用遗漏。

### 5.4 用户已经在IBKR代平仓

核实成交、账户/合约、方向、数量与lot归属，以及旧策略委托是否仍可能成交，确认后使用现有人工修正流程。部分代平只改部分lot；对冲未清不能整组CLOSED。

目标已FAILED时，核验后走“不发单、修正归属”的完成分支，不能先READY再补账。仍有未知旧单时先核对、必要时取消已知策略委托，不能清零账本后放任旧单成交。人工费用/损益未补齐时单独说明，不伪造策略自动成交。

## 6. 普通EXIT与终态FAILED EXIT严格分离

### 6.1 普通EXIT及归属等待

正常EXIT继续原自动执行、撤单、重新报价、持续重试和对账。暂时归属缺口在step通用失败累计前分流到非终态RECONCILE_REQUIRED等；复用原调度退避，不因三次归属检查永久FAILED，不需要人工恢复审核。

归属等待不增加ENTRY真实失败预算、不冒充连接故障；ENTRY仍受300秒时效、意图过期、禁交易日及部分成交责任约束。已发送但未明订单优先核对，不创建替代单。明确账户/权限/合约拒绝继续原处理，不统统改成无限等待。

真实已知缺口未解就不发新单；现有同步及账本恢复一致后非终态任务直接继续。历史普通失败日志不是永久挡板，真实event gap修复成功才可清理，不因净额相等就删除。此流程不加载第6.3节恢复材料，不增加普适人工核查。

### 6.2 禁止自动恢复终态FAILED

**删除原版扩大FAILED EXIT自动恢复白名单的设计。** 不论历史FAILED原因是否像短暂故障，recover_failed_exits均不得自动改READY/RECONCILE_REQUIRED并重新发单，也不得通过generation+1绕过核验。

调整该函数及调用方：移除终态自动发单恢复职责；如保留函数，仅返回/展示待处理项或推进无新增发单权限的旧单核对。发布不得批量恢复历史FAILED。允许接收旧单回调、补齐成交与费用，但缺口消失不授予新单权限。

封闭resume_exit(identity, reason)简单重置：改为仅由已核验恢复请求调用的内部步骤，旧CLI/内部调用不能只传reason就READY。最终准备/提交入口拒绝仍属FAILED任务的新增订单，防止组推进、request_exit、旧定时任务或重启间接复活。

job已FAILED但attempt未明时，沿既有回调/同步核对原attempt，必要时取消该已知订单；维护回合可有界选择这类未结attempt，但不能调用可能新增订单的完整_step。优先保持job FAILED，只推进attempt对账，前端继续提示失败和未明旧单；不得靠临时改成可调度状态偷渡新单权限。

若普通EXIT原本靠“先FAILED、再被恢复器拉起”才能持续重试，应在正常分支内保留非终态剩余义务，不能保留终态自动恢复后门并称其为正常重试。实际拒单导致的终态FAILED不在此豁免。

### 6.3 Codex受保护恢复入口

恢复命令为`group-resume-exit`，查询对象与回执使用`group-exit-status`。必须取得对目标FAILED EXIT剩余义务的明确恢复授权，绑定request_id、账户、交易组及失败代次或任务版本；不得与普通提前退出命令混用。

**以下严格核验仅用于终态FAILED恢复。** 允许在此异常管理路径取得必要的最新券商同步、历史订单/成交证据，不扩展到正常ENTRY、EXIT和个人基线变化。

| 核验项 | 处理 |
| --- | --- |
| 目标及失败原因 | ID、实际账户、合约和lot归属正确；权限/路由/资金等障碍已处理或明确可执行，不靠重置字符串 |
| 原订单与迟到成交 | 相关旧策略单、撤单、实际成交及更正已核对；没有open order不等于历史未成交 |
| 是否人工代平 | 结合用户明确说明和实际成交核实；A=0、P=A-S成立、lot非零均不能单独证明是否仍需退出 |
| 人工全部代平 | 修正lot、结束义务，不恢复发单；人工费用/损益缺失另行注明 |
| 人工只代平部分 | 先修正已平部分，核验后仅恢复剩余lot |
| 确认未代平 | 券商记录、策略账本及授权相符后恢复真实余量；虚拟抵消时不要求实际净仓等于该lot |
| 证据缺失/矛盾 | 保持FAILED/待人工处理，不吸入个人基线；“用户未提及”不能作为未代平证明 |
| lot清零/版本变化 | 返回已完成或核验失效，不恢复旧余量 |

保存一次核验的范围、时间/订单证据摘要及目标lot数量/任务代次，Writer应用前作轻量本地版本比对。相关事件、数量变化或核验期间断连使证据不再可信时，拒绝旧请求并重新核验；不建设全局审批令牌系统。

授权消费、状态调整和审计回执同事务提交。同request_id重试只返回原结果，不再次增加generation或建立第二张单。确有现有恢复语义需要时，generation只能在本次核验获准后调整一次，未结旧attempt绝不靠换代遗忘。

确认已人工代平且lot已经核实修正为0时，可用MANUALLY_CLOSED核验分支确认完成：不发单、保留持久闩锁并记录已人工结清；若未来lot被重建为非零，闩锁仍阻止重新发单。

核验确认剩余义务后仍由正常Executor发单。订单已SUBMITTING，即使回执丢失也只能对账原单；若后来进入新的终态FAILED，前次授权不自动覆盖，需要针对新失败版本再次核验。任何入口不得恢复ENTRY。

### 6.4 前端明确展示FAILED EXIT

复用执行详情/交易组卡片，由te_jobs、te_lots投影最小exit_summary：MAIN/HEDGE的EXIT状态、原因、剩余股数、是否有状态未明旧单、requires_manual_review。扩展现有DTO和卡片，不新建页面或诊断服务。

只要对应EXIT为FAILED，明确显示 **“FAILED EXIT／退出失败，需人工处理”**，即使ENTRY为FILLED、组为OPEN/CLOSING也不能掩盖。lot为0但仍有旧单待核对，保留待处理提示，不能假装全部完成。

普通RECONCILE_REQUIRED显示“退出对账中”，不贴FAILED人工审核标记。不提供绕过核验的一键重试。管理请求成功、订单成交、费用收益已结清分别显示；费用迟到仍用原pending/provisional机制。

## 7. 最小修改范围与实施顺序

本节为本轮实施范围和顺序；实际结果见实施与验收报告。

| 范围 | 必要改动 |
| --- | --- |
| executor.py | 动态P、轻量已知竞态保护、普通归属等待；FAILED禁新单与旧attempt对账分离 |
| repository.py / recovery.py | 原归属读取及审计；关闭终态自动恢复，封闭简单resume；管理请求幂等回执 |
| groups.py / ExitRepository、schema | MANUAL_EARLY_EXIT原因及组退出封装；已完成/FAILED/重复请求保护，主后对冲不变 |
| 现有CLI/管理入口和Executor维护回合 | 两种明确不同的操作，共用Writer及现有操作/JSON回执，不开放直接券商发单 |
| ibkr_session.py（必要时） | 仅补回调conId/同步来源元数据，不改正常请求次数/序列 |
| 现有Read投影/DTO/Case执行卡 | FAILED EXIT摘要、原因与剩余量，契约/展示回归 |
| 现有交易测试、changelog | 实施后补定向回归与变更记录；实施时追加定向回归及变更记录 |

实施步骤：

1. 先补正常/等待/FAILED边界回归，封住recover_failed_exits、简单resume_exit和其他间接复活入口。
2. 实现动态P及普通归属等待；健康路径零额外券商请求，仅在P真正变化时审计落盘。
3. 封装提前退出与受控恢复管理入口，复用原组请求、Writer及幂等回执；授权与核验范围分开。
4. 接入FAILED EXIT后端摘要和前端提示，验证ENTRY/组状态不掩盖失败。
5. fake broker、隔离样本回归，后续按授权PAPER验证；不借本方案授权LIVE测试、批量恢复或旧意图重放。

不重写资金、配仓/对冲、整数股、滑动止盈、正常退出时点、W1/W2/W3、ENTRY三次机会及过期规则。不新增服务、独立订单状态机、个人流水跟踪、全量回填或普适审批。

## 8. 边缘、高风险与验收矩阵

以下为设计验收矩阵；本轮已执行的具体测试与尚未实盘验证的边界以实施报告为准，不将设计矩阵等同于逐项真实券商成交验收。

| 场景 | 验收判据 |
| --- | --- |
| 个人同向加减仓，无外部成交明细 | 可信快照/自洽策略账本下更新P，不查个人流水或额外等待 |
| 个人LONG15、策略SHORT20 | 一张SELL20，lot=-20、实际=-5；退出BUY20后个人+15 |
| 个人SHORT、策略LONG及两向跨零 | 按完整虚拟lot交易，不按净持仓裁剪 |
| 实际或策略净额为0 | 不清各策略lot，不释放原预算/名额，保留退出责任 |
| 多个策略共享ETF、方向相反 | 各lot独立，一组退出不FIFO误销另一组 |
| 个人直接SELL策略LONG的实物股票 | 不擅自销策略lot；MARGIN原退出仍可能形成实际净空 |
| 差额大、方向反转、无法逐笔证明来源 | 无明确异常时更新P，不建数量阈值或来源审批 |
| 已知拆股/强减/历史策略成交遗漏 | 沿现有异常处理，不用P掩盖；不可观察极少数事件接受边界 |
| 未知提交/部分成交/撤单未确认 | 原订单继续对账，不更新P吞掉成交，不发替代单 |
| Filled/Cancelled先到、成交后到 | 补齐已知成交，非终态等待，不按0误归属 |
| 同步/报价期间相关策略成交修订或lot调整 | 原快照/准备量失效，原路径重同步；无相关变化不加请求 |
| 历史查询不可用、当前已完成对账 | 正常路径继续，不全历史扫描；明确依赖缺失历史的未决单等待 |
| 未知生产策略引用或unattributed>0 | 真实gap阻断相关归属；不误伤普通手动、测试、WhatIf引用 |
| LIVE/PAPER、不同路由、个人碎股 | 账户/conId隔离；Decimal保留碎股，策略订单整数 |
| 净额EXIT增加实际敞口 | 不加EXIT WhatIf/专项资金审查；沿原风控提交，拒绝后保留余量 |
| CASH实际资金/库存/卖空限制 | 原能力及券商风控处理；不加负P专项审批、不截断lot假装完成 |
| 授权提前退出正常交易组 | 对象正确，原Executor主后对冲，真实成交/费用/收益归原组 |
| 提前请求重复、回执丢失或重启 | 同ID同内容返回同结果，订单不重复；同ID不同对象拒绝 |
| 无ts_positions的正常组 | 复用groups.request_exit，不强制滑动止盈状态 |
| 已有EXIT或未结ENTRY时提前退出 | 复用旧单；停止新增ENTRY并核对迟到成交，不额外重复平仓 |
| 提前请求指向CLOSED/零lot | 返回已完成，不重开组、不发单 |

| 普通归属缺口多于三次 | 保持非终态等待，不增加真实失败预算，不进入FAILED审核；解决后继续 |
| 历史FAILED遇到P修复/连接恢复/定时器 | 保持FAILED，不自动READY/换代/新增发单 |
| 历史FAILED已人工全部代平 | 核实成交与归属后修正账本，不恢复发单 |
| 历史FAILED仅人工代平部分 | 先修已平部分，核验后只恢复真实余量 |

| FAILED实际净仓0、虚拟lot非0 | 不据此断定人工代平或仍需退出，核实成交与授权后决定 |
| FAILED旧单未知或有迟到成交 | 无新单权限下继续对账，不能换代遗忘或放弃旧单 |

| ENTRY FILLED、组OPEN/CLOSING但EXIT FAILED | 前端明确失败原因、主/对冲余量和人工处理提示 |

### 8.1 必要回归和性能验证

固定fake broker样本对比正常调用次数/数据库写入计数，在同环境比较耗时分布；不增加常规券商调用、固定等待、每轮日志或全历史扫描。FAILED专门核验调用只计入该异常管理操作。费用未回报保留原pending/provisional，不伪造已完整入账。

## 9. 整体Review与交付判据

核心边界：**正常路径仅处理现有可观察异常；终态FAILED EXIT重新发单必须经过专门核验与授权。**

- 动态P不要求个人逐笔证明，不猜不可观察异常。
- 主动提前退出走正常Executor，完整记录策略成交、费用和收益，不用直接IBKR发单加adjust_lot的捷径。
- 接受虚拟净额退出的边缘资金风险，不增正常EXIT专项预检。
- 非终态归属等待自动接续；终态FAILED默认锁定，修复不复活历史任务，未明旧单仍完成对账。
- 前端明确FAILED及剩余责任，管理请求成功不等于成交或费用结清。

实施验收须同时满足以上五点及正常调用、延迟、写入无显著增加。不得通过恢复旧ENTRY、扩大FAILED自动恢复白名单、全局关闭保护或给所有正常交易加审核来通过验收。

后续发布不批量拉起历史FAILED，需要恢复的目标逐个走受保护入口；回滚保留真实订单、成交、lot调整和管理审计，未确认旧单状态前不以简单状态重置代替安全回滚。
