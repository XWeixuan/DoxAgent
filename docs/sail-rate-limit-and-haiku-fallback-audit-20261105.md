# Sail FP4 限流、Haiku fallback 与 OpenRouter 消耗排查

排查日期：2026-11-05；全程只读生产数据及配置，额外各一次Sail/Haiku最小真实探测，未改生产配置。

## 结论

**是：当前锁定的Sail FP4端点，已从发布初期较可用变为长期大面积无法分配容量，四节点大部分轮次实际由Haiku完成。明确复现到的原因是Sail上游共享容量池不足，而非OpenRouter余额用尽或本端异常高并发。** 不把这一结论扩大为DeepSeek模型在所有provider不可用。

必须区分：昨天19:49左右才完成模型切换；昨天全天的大部分时间R2/R3还在Haiku。切换后R1也仍固定用Haiku，且R1输入很大，因此“Haiku token占比高”本身不能单独证明fallback；本次用逐轮主备回执证明了fallback比例。

## 明确的429原因

19:40左右从当前生产key发一个小型、全字段required的strict Schema请求：

```json
{
  "status": 429,
  "provider": "Sail Research",
  "provider_error_code": "no_asap_capacity",
  "limit_source": "upstream_provider_shared_pool",
  "retry_after_seconds": 180
}
```

Sail约0.85秒返回429；紧接着同一key对Haiku Vertex Global请求返回200，约1.00秒。该探测不含大量Policy或历史事实，不是长上下文才触发的问题。11月4日发布前探测也保存了相同no_asap_capacity/shared_pool原因。

能确认的是本次明确返回Sail共享池容量来源。生产adapter历史上只把HTTP429记成provider_rate_limited，没有保存完整metadata，7次流错误也只记录通用stream error；因此不能逐条追溯1687次429是否100%同一细分原因。结合时间趋势、当前探测和此前同类探测，持续共享池容量不足是最有证据的主要解释。

|路径|调用次数|输入token|输出token（含推理）|已报告费用USD|
|---|---:|---:|---:|

|Haiku R2/R3备用与重试|1,713|16,184,239|1,966,058|$1.98251|

- Haiku占发布后已记录输入+输出token约97.8%；其中Haiku自身token约86.9%来自R1。R1负责全量事件/Policy召回，本轮没有切到DeepSeek。
- R1约112,165,870个输入token命中缓存，占其输入约94.4%；token数量很大不等于全部按未缓存价收费。
- 另一方面，Sail失败确实让1695个R2/R3轮次落到Haiku，已报告费用约1.98美元；主调用已报告约0.24美元。Haiku全部路径已报告约4.93美元，占这批OpenRouter已报告费用约95.3%。
- 昨日北京时间完整窗口5334次调用，发布前就有3440次；昨天全天token分布不能当成发布后主备比例。
- 拒绝请求、流错误可能没有usage或完整账单；不把缺失费用当作经过证实的零。本表不包含其他工作流、离线测试、尚未落库的请求及其消费。

## 当前机制和建议

当前主调用发生429后立即转Haiku，正好解释主轮次PENDING_RETRY与备用OK并存；不会等待Sail的180秒Retry-After，也不会再次尝试同一轮的主模型。切换状态会持久化，重启后不重复该轮主调用。

但**每个新的Case/轮次仍会尝试Sail**，没有端点级跨Case冷却/熔断，因此共享池持续无容量时会继续产生429噪声。这并不证明并发失控，却造成一次无效请求的开销与等待。

建议按优先级：

1. 生产稳定性优先时，先恢复已有openrouter_haiku_high为四轮主配置；或在重新测试一个有稳定容量的DS端点后切换。当前Sail FP4不适合当可靠主端点，继续充值/换OpenRouter key缺少对症证据。
2. 若继续保留Sail为主，增加轻量的端点级冷却：429后按Retry-After窗口让新轮次直接走既有备用并记录“跳过主端点”原因；到期少量探测，恢复后再启用。不要让Case排队等180秒，也不要把跳过伪造为已付费失败尝试。
3. 补齐错误可观测性：安全记录provider_name、provider_error_code、limit_source、Retry-After/上游request ID；SSE error也保留同类字段。不要把secret、完整请求或不必要上游原文写入日志。

本轮只排查，没有修改模型、并发、fallback、重启或发布任何生产变更。Sail/Haiku各一个真实探测使用现有生产凭据，未落业务Case、未发交易。

官方说明：OpenRouter区分额度、预算及请求速率限制，额度/预算可通过key API和error.metadata核查；provider错误应保留上游metadata。参考 [限额文档](https://openrouter.ai/docs/api_reference/limits) 和 [错误说明](https://openrouter.ai/docs/api_reference/errors-and-debugging)。
