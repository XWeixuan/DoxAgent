**当前看板的巨大差距主要是共享维护/恢复长尾与样本分母的组合，并非已经证明某些Ticker日常固定慢十倍。**

- 800—975秒级长尾集中在11-18约13:18—13:31Z的共同中断/恢复窗口。已有Research数据库VACUUM回执明确记录Scheduler、Worker等9个owner暂停，停完到重新启动约767秒，13:30:53Z Worker恢复。不同Case可能在首个分支派发前、两个分支之间，或模型都返回后等待恢复，因此这些时长都落入非模型余量。
- 另一个100—200秒级群集中在11:34—11:44Z的应用发布/恢复期，IONQ受影响较多。精查一条表明：模型任务进队后约1.5秒便开始，真正的大段等待在READY/派发之前及READY之后到正式job创建之间；不是Haiku/Luna的推理时间，也不是Web Search搜索量。
- **14:00Z之后的651个有效样本，十Ticker均值已收敛为2.78—5.74秒，最大单案18.32秒。** 这个时段观察支持“近期巨大排名差距主要由异常时段暴露造成”，不等于长期已无资源/调度问题。

## 2. 指标口径与样本

现行派生公式为：

> 非模型调用延时 = decision_effective_at − Runtime Case.created_at − 该区间内非Operations模型调用区间的并集长度。

它包含W1/W2之间的编排空档、W3上下文/Thread准备、调度与配额等待、模型请求之外的重试退避、重启/维护停机、最后结果到交易判定生效的持久化与释放等待。Operations在决策之后，不计入；消息抓取到Runtime接纳前的源延时也不计入。

W1/W2并行、W3 A/B并行均只能扣并集，不能相加；一支返回后另一支仍在模型调用中，这段仍有模型覆盖，不能把它全部当非模型等待。反之，一支已结束、另一支尚未真正发起，空档属于非模型。失败请求本身的在途时间会扣除，失败之后未发请求的等待不会扣除。

模型区间对W3采用Worker SDK派发到返回的客户端边界，不能把该KPI解释为严格的“无LLM CPU时间”：SDK内部工具等待等也可能已经包含在被扣除区间。本文不另创一套生产KPI，也不拿`w3_model_seconds`粗跨度直接相减。

指标只在REALTIME Case已有W3决策、生效锚点及完整模型计时条件时产生；没有样本不等于0。当前968条有效值，并不代表全部消息都进入W3。候选固定取Runtime最近3500行，再筛至11-17 07:00Z之后，最老候选为11-16 19:00:45Z，覆盖本次两个语义日的已存在Case。共读到2896个REALTIME且有Read摘要的Case，其中2248条有有效非模型指标，其他648条不填0。

2248条逐Case按原始区间复算，最大绝对误差小于0.000001秒。此处未发现能解释Ticker差距的“并行调用被重复扣除”错误。看板快照自身标记STALE，当前watermark并无明显积压；历史Runtime投影缺口17207仍存在。本结论针对可读、有完整计时的近期Case，不把缺口解释为已修复或不存在。

## 5. IONQ为什么仍偏高：发布恢复期的派发空档

`case_3447426a96d546d5a141e10a68897e8c`非模型203.88秒，其中首次W3前201.60秒、最后W3返回到生效2.28秒。A/B都成功，没有失败重试。

- 11:39:14 Case接纳；11:39:35主Trade阶段接纳；A/B阶段11:39:59、11:40:08分别接纳。
- 两个私有槽位11:40:24建立；11:40:40、11:40:45 READY。槽位操作启动回执分别约5.45/8.00秒，不是180秒的SDK启动。
- 正式任务却到11:42:47、11:42:48才创建，距READY约127/122秒；入队到Worker实际开始约1.54/1.97秒，开始到SDK派发再约0.1秒。
- 所以把约3分钟都归为“Worker队列慢”不成立；主要空档在任务创建前的编排/恢复段。更不能归因于这个Ticker需要更多新闻检索，因为该段还没进入决策模型。

同一时段IONQ另有约197.8、201.7、202.4秒Case，INTC/NBIS/MU也有100—190秒样本。发布回执记录Worker11:39:33恢复、Scheduler11:40:35恢复，与这批Case跨过的恢复窗口相符；这比“IONQ数据更多”有更直接的证据。

**尚未证明的是READY后这122—127秒具体由哪个调度步骤消耗。** 本轮针对历史窗口读取当前容器日志未取得对应trace；旧日志不可得不等于当时没有锁或调度等待。现有持久回执足以定位到正式job创建之前，但不足以进一步区分effect恢复租期、上下文准备、数据库写门等待或轮询。不要把其中一个未经确认的候选写成确定根因，也不宜据此改Ticker专属并发。

## 7. 建议与边界

1. **保留现行端到端KPI，同时解读样本数、中位数/P95与异常时段。** 不删除真实停机等待，也不把冷启动/发布恢复冒充日常Ticker特性。若后续要改页面，轻量增加样本数/尾部提示即可，本轮不实施。
2. 先解决共享服务的维护与恢复体验，优先于Ticker特调；数据库压缩等owner暂停应标明业务空窗，避免其影响被误诊为模型变慢。
3. 后续若正常时段仍出现READY已就绪、job迟迟未建立的自然Case，再用现有boundary timing沿“阶段接纳→READY→job创建→SDK派发”精查。当前不为已消失的历史窗口新建harness、常驻采样器或重跑付费模型。
4. 本轮的逐Case复算没有发现当前非模型派生公式造成的系统性Ticker偏差。没有据此宣布全链路永远正确，也没有将历史缺失值填0、修改过滤阈值或上线任何修复。
