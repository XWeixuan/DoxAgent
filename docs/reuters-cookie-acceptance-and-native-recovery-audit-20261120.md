# Reuters Cookie 接受性与正常会话恢复：双线复盘、实证和定向方案

日期：2026-11-20（北京时间）；机器回执为 UTC。证据：`eval/reuters_session_mechanisms_20261120/`，并引用上轮 `eval/reuters_session_acceptance_20261119/`。本轮不把供应商回执、Cookie 写入、站点接受、正文可读和持续可用混为一件事。

## 一、先纠正上轮解释中的两个过强结论

**上轮成功不是“只打开 API 页面就恢复”。** 代码复盘表明，它还包含隔离上下文、该上下文的正常设备检查、Cookie 转移、持久化上下文请求、重载、正式 Verify 等多个操作。两身份都成功具有实证价值，但不是入口单变量实验，不能据此证明存在“API 专属 Cookie”或把跨上下文凭证转移当正常恢复主线。

**上轮 HTML 对照取到的“最终 Cookie”不等于已知200时携带的 Cookie。** `cookie-context-control.json` 中，干净上下文文档200时携带指纹 `cbfafa…`，20秒后读取的是 `77b5d1…`；中间搜索API200的 Cookie ExtraInfo 证据不完整。将后者用于原持久化上下文后得到 HTML200/API401，因此不能断言“同一个已被搜索API接受的 Cookie 换上下文后失败”。这项对照混入了 Cookie 自身更新，入口差异、Cookie代次和生成环境仍有混杂。

这也是本轮实际修正取证代码的原因：CDP ExtraInfo 可能先于 requestWillBeSent 到达。原收集器只缓存含验证码 Cookie 的早到事件，导致“明确没带Cookie”与“没有采到完整请求头”都显示为空数组。历史空数组不具有缺 Cookie 的证明力；有实际指纹匹配的拒绝样本仍有效。

## 二、方向一：第三方结果为何不被接受

### 2.1 已证实的失败位置

1. 上轮两次 EZ 原 Chrome 校验均返回 HTTP200、JSON键只有 `cookie`；`errorId`、`view` 没有明确值。供应商 step2/3 的 errorId0/ready 证明其执行完成，不证明 Reuters 已认可。
2. 结果写入后，紧接的实际 Chrome 请求携带相同指纹，domain/path正确，无 blockedReasons，无重复 DD Cookie。两次 EZ 的首次拒绝已发生在 **HTML根文档**，搜索API尚不必发出；不能只笼统记为“后续搜索401”。
3. 首个受保护响应带 `x-datadome: protected`、CloudFront LambdaGeneratedResponse；服务端在该拒绝响应中再设置下一代 Cookie。已证实的顺序是 **结果送达 → 拒绝 → 更新Cookie**，不是“结果先被本地覆盖所以拒绝”。
4. EZ 结果生成后立即应用并发出请求；没有证据支持靠延长或缩短应用等待修复这些即时拒绝。旧Challenge的服务端有效期则没有被证明，二者不同。
5. 未观察到这些失败样本先有真实受保护200、然后才重新拒绝。它们应归为 **首次业务接受失败**，不能记为“已通过后复发”。

这排除了上述具体样本的纯写入丢失、未发送、domain/path范围错误、重复Cookie、请求前覆盖以及登录层生成401。它没有证明所有历史个案都不存在这些问题。

### 2.2 Cookie 本身究竟能说明什么

DataDome 官方说明：`datadome` 是同时用于客户端、服务端检测的加密数据；`ddSession` 仅在 sessionByHeader 启用时作为本地副本。Cookie不是可在客户端解析的“通关布尔值”，也不能凭长度、字符格式或存在性判定已通过。官方同样描述了拒绝响应更新Cookie的机制。[Cookie与存储说明](https://docs.datadome.co/docs/cookie-session-storage)、[Protection API](https://docs.datadome.co/reference/validate-request)

本轮当前两身份：DD Cookie 长度128、domain `.reuters.com`、path `/`、非HttpOnly、SameSite Lax，浏览器到期时间约一年后；`ddSession` 不存在。因此 **浏览器Cookie在10分钟到期**、**旧ddSession覆盖Cookie** 不符合这些当前现场。加密内容内部可能存在服务端时效/风险判断，客户端元数据无法排除它。

官方 Protection API 接收请求元数据，并由服务端返回允许或挑战决定；IP/UA匹配不等于所有上下文相同。浏览器客户端没有站点侧完整判定日志，因此目前不能将401进一步认定为某个密文字段无效、答案质量差或某条规则命中。[服务端判定接口](https://docs.datadome.co/reference/validate-request)

### 2.3 旧付费对照还缺什么

- 实验脚本确认了当前归属的可见 iframe 与 `/captcha/` 路径，却没有冻结一个“题面实际有效、非RETRY/拒绝页”的完整前置证明。`t=fe`、iframe200都不足以证明旧Challenge可用。旧现场可能已拒绝，这是输入有效性的缺口，不应算供应商答案质量结论。
- EZ文档示例有明确提交回执，而实测仅Cookie；不同响应结构的含义需要供应商按任务回查。当前Linux Chrome153与完整语言/请求环境是否完全属于其支持范围，也没有得到供应商确认；不能仅因UA字符串被接受就假定整个执行环境等价。[EZ接口文档](https://ezcaptcha.atlassian.net/wiki/spaces/IS/pages/36372655)
- EZ两次最终验证请求已经由原Chrome发出，仍失败。因此 **验证HTTP客户端TLS不同** 不能单独解释所有失败；Provider计算结果的上下文是否一致、Challenge是否仍有效、返回Cookie是否已经代表接受，仍待区分。
- 本轮没有额外发起付费测试或重新应用历史Cookie；既有生产Solver按原私有配置自然运行。最新自然账没有新的 ready/APPLIED，不能伪造一条新的供应商端到端成功链。

### 2.4 可以实际落地的分层判定

沿用现有 APPLIED，不新增业务状态机；仅给诊断派生结果加清晰含义：

| 证据 | 诊断结论 |
|---|---|
| 验证接口返回Cookie | `CHECK_RETURNED_COOKIE`，接受性未知 |
| 读回匹配且真实请求带同一指纹 | `COOKIE_DELIVERED` |
| 首个非缓存受保护请求401且DD证据充分 | `REJECTED_AT_FIRST_PROTECTED_REQUEST` |
| 先真实200/业务契约成立，再401 | `ACCEPTED_THEN_RECHALLENGED` |
| 没有完整Cookie请求头事件 | `COOKIE_OBSERVATION_MISSING`，不能认定没带 |
| 仅缓存200、缺少请求、控制断开 | 证据不足，与站点拒绝分开 |

供应商对账应提交现有任务ID、时间、UA/出口绑定、脱敏首个响应和“校验仅返回Cookie”的结构。只有供应商/站点侧证据才能进一步说明加密结果为何不被接受；客户端不能通过改写Cookie内容推断修复。

## 三、方向二：正常会话恢复是否真实、为何反复失效

### 3.1 上轮成功顺序与可推断边界

Main：UTC23:29:08 干净上下文实际API文档401，约6.2秒后原生流程产生真实API200；23:29:29 Cookie写入持久化上下文；其真实API请求200，重载后的根文档和API继续200；23:29:57 正式 CRAWLER READY/BODY FULL。

Backup1：23:33:39 文档401，约5.7秒后实际API200；23:34:00 写入后持久化API200/7条，根文档及API200；23:34:32正式 READY/FULL。均不是缓存200、不是付费结果，也不是人工解题。

这证明当时原持久化Chrome/出口能接受某个由原生会话形成的Cookie，排除了“这个Profile永久不能访问”的强断言。没有证明固定入口是唯一原因、所有第三方Cookie必错，或这种恢复能长期保持。人工22:05的成功属于旧Main，与新Main的付费实验也不是严格同Profile配对。

### 3.2 18小时自然账是更强的“无需打码可恢复”证据

初始审计窗口 UTC2026-11-18T23:29:57 至2026-11-19T18:03:51（北京时间19日07:29至20日02:03）：

- Main 2,003、Backup1 1,766次 CRAWLER SUCCESS采集回执；正式正文共11条FULL（Main 4条、Backup1 7条）。这不是完整QUERY周期数，也不是已经排除浏览器缓存的网络访问数。
- 存在多轮 `fresh_probe` 真正业务恢复；对应时间窗没有新的 Provider ready/APPLIED。后续完整账截至UTC18:42，19日零点后有24个非superseded的Task以fresh_probe结束，不能把这些都算成第三方解码成功。初始审计中自然生产7笔Solverify作业失败于deadline，另17笔为未购买事件结束；失败费用未知不算0。
- 每身份恢复后的新阻断通常在约10–12分钟；按Task结束口径，可观察的阻塞至恢复中位数约77–78分钟。此时间是“首次探测成功”的上界观测，受10分钟探测间隔影响，不是已证明的服务端固定封禁时长。
- 同时有5384次CRAWLER队列延期及48次BODY队列延期。上轮短窗口的恢复不能延伸为18小时稳定可用。

### 3.3 找到一个可解释、可修的内部升载机制

当前真实配置：每身份 max_concurrency2、基础间隔1500ms；恢复保护300秒、保护间隔10000ms，再用300秒对 **间隔** 线性插值。

| 恢复后秒数 | 既有代码间隔 | 理论最大启动数/分钟 |
|---:|---:|---:|
| 0–300 | 10000ms | 6 |
| 360 | 8300ms | 7.2 |
| 420 | 6600ms | 9.1 |
| 480 | 4900ms | 12.2 |
| 540 | 3200ms | 18.8 |
| 600 | 1500ms | 40 |

离线直接调用现有 `_identity_navigation_interval` 得到该曲线，没有修改生产频率。**间隔线性下降并不等于请求率线性上升**；最后一分钟启动能力从约19翻倍到40。历史新阻断前的采集成功回执分桶平均亦由每分钟约6上升到最后一分钟约33；最新Backup1样本最后一分钟40，随后实际401。这些回执可能包含缓存，不能直接称为同等数量的服务器请求。

这是内部升载行为与历史复发时点的明确吻合，是应优先验证的内部机制，不是已经证明的服务端根因。可能是实际网络速率、累计量、缓存到期或其他并行变化；当前历史账不能分离它们。

本轮实时取证发现搜索API有 `Cache-Control: max-age=300`，部分后续API200明确 `fromDiskCache=true`。缓存命中可能掩盖新的服务端拒绝，也会使“60秒执行一次采集”不等于“60秒取得新网络结果”。因此先补齐网络/缓存分账再调整速率；不得基于历史成功计数直接估计DataDome阈值，更不能通过关闭全局缓存或随机改查询参数来假装修好了时效。

### 3.4 旧页和真实会话必须分开

本轮被动DOM观测：当前原页 iframe 约1439×912、可见、中心命中 iframe，是真正覆盖内容的页面；根文档的历史 navigation200或后台已有搜索壳并不能说明解除。这排除了将当前所有阻断归为隐藏iframe误判。

但旧原页不会自动代表当前服务端接受性：既有恢复已在新业务页取得真实搜索200、结束旧Task；上轮最初也出现同一旧target衍生新待办而业务仍成功。必须分别记录原页阻断、同身份新业务请求及能力epoch，不能拿旧DOM独自推断整个身份不可用。

现有 `fresh_probe` 是同持久化Profile中的正常业务校验，不要求新Profile或跨上下文Cookie转移；它已经多次成功，是应复用的非付费恢复主线。其首次401/原生自动跳转/最终API200的Cookie代次仍应补齐，才能区别服务器重新接受与新原生检查生成有效会话。

## 四、本轮本地补丁与下一步执行边界

已修改 `solver_forensics.py`：

1. Cookie摘要增加SameSite、expires、长度，不记录值或尝试解密。
2. 无验证码Cookie的早到ExtraInfo同样进入原有8条缓冲；无关请求到达后清除缓冲，仍维持6条请求上限。
3. 增加 `cookie_evidence`，明确区分完整ExtraInfo、可见请求头及未观测。
4. 增加内存缓存事件及prefetch标志，避免仅凭 `fromDiskCache=false` 就误认为新网络接受；不改变浏览器缓存行为。
5. 新增本地事件顺序/缺失与明确空值/有界缓冲/元数据脱敏回归；成功路径不增加网站请求。

这些小补丁只改善证据准确性，不改变Cookie、Profile、出口、Provider、Challenge动作或业务频率。本轮未发布，避免把取证改进当成已经修好站点接受性。

建议后续按以下顺序落地，复用现有模块，不加常驻组件：

1. **补齐首次自然恢复的两端证据。** 在既有recovery probe事件中，每事件最多保存“首次拒绝”和“首次真实接受”两组有界WireEvidence；沿用相同incident指纹盐、instance/context/target与scope。Cookie原值不落盘，缓存200单列，记录实际来源为正常导航或自动重定向。只观察既有请求，不加探测次数。
2. **分离原页状态与能力恢复。** 在既有finish_recovery/CAS路径中，以新业务真实证据结束对应capability；历史原页保留不重置成功epoch，新的失败必须有新的物理请求或实际可见阻断证据。同一target的历史重开不能伪装成新站点事件。用“旧页有遮罩、新请求成功”的本地fixture回归，不靠关闭所有原页。
3. **先修调度均摊，再评估升载。** 将既有QUERY/TAIL单位按固定周期相位铺平、全局去重，公平分配给两个可用身份；已过期的同单位调度意图不补抓历史轮次。保留目标60秒，记录实际覆盖/遗漏。以请求启动率而非间隔曲线检查末段加速；任何新曲线先离线重放同一工作量，不能直接换成更快的早期增载、借此增加总量，或无限延长低速期掩盖失败。
4. **有限正式验收。** 当前首次接受失败与接受后复发分别计数；至少覆盖旧10分钟复发窗口的数倍，并核对全部QUERY周期和真实BODY。若外部拒绝仍在，仅靠调度不能承诺既定时效，应明确容量缺口，而非把“仍每60秒生成任务”当作“每60秒完成采集”。

本轮定长被动实验的最终网络与Cookie时间线、测试结果和收尾现状，追加于下一节；它们是自然对照，不冒充随机化Cookie有效性实验。

## 五、本轮捕获的无付费、无凭证转移恢复

第二段被动观察 UTC18:16:08–18:31:08（北京20日02:16–02:31）已捕获：

1. Main原页18:23仍有全屏验证码遮罩；其Cookie指纹 `a8d4cc…` 在18:14至18:23的多个快照中已存在，没有本轮Cookie写入。
2. 18:24:09，既有生产 `fresh_probe` 创建正常业务页，同一Profile/Chrome携带 `a8d4cc…`，根文档直接网络200，无该请求的重定向链、无 Set-Cookie。
3. 18:24:10，同一Cookie随搜索API请求发送，API为非缓存200，无该响应Set-Cookie。这条链 **不是必须先获得新Cookie或再过一次DeviceCheck才可恢复**。
4. 随后的正常业务页继续网络API200，Cookie之后又由浏览器原生流程更新；这不是第三方结果应用。本轮没有新Profile、换IP、清Cookie、重放旧结果或人工解题。
5. 该15分钟窗口记录Main52次未标记磁盘缓存的HTTP200（其中50次API、2次文档），23次明确磁盘缓存API200；Backup1有2次真实文档DataDome401。首组根文档/API有实际请求ExtraInfo、同Cookie发送及网络响应证据。观察器未覆盖内存缓存事件，不能将其余52条全部计为独立新网站接受；本地取证补丁已补这个缺口。

由此可以证实：**正常会话自行重新获得接受能力真实存在，旧原页不自动刷新不代表新业务仍被拒绝，恢复当刻也不必更换Cookie。** 尚不能证实同一Cookie此前已被服务器拒绝，因为其首次形成的完整网络链未采到；也不能从此直接判定服务端仅按时间解封。

第一段观察使用20秒枚举页面，漏掉了生命周期很短的恢复探测页，尽管有DOM快照却没有采到请求。这是观察器覆盖不足，不是“服务器没有发请求”。第二段改用Target创建事件及时挂接，已捕获真实回执。为检验这次恢复是否跨过旧10分钟复发点，仅追加一次7分钟被动窗口，不持续守候。

## 六、没有在“恢复一次”处停止：实际复发与负对照

- UTC18:24:12.595（北京02:24:12），Main正常业务探测恢复；UTC18:31:32.752又记录新业务页阻断，间隔 **440.16秒，约7分20秒**。新页是刚才成功使用的业务页，不是最早那张静止旧原页。

- 此次复发在300秒保护加300秒升载结束前，说明“固定10分钟过期”或“只在升载结束瞬间触发”都不成立。历史升载关联仍值得查，但不能当作唯一解释。
- Backup1 UTC18:37:22–18:38:05、Main UTC18:39:50–18:40:33，各执行 **一次**现有正常 Verify 对照。同Profile/同出口，不碰题目、不写Cookie、不换上下文。两组均 `BLOCKED / CONTENT_ERROR / http_401 / BODY NOT_TESTED`，原页保留，Viewer释放。单纯再开正常页或点Verify并不能随时恢复。
- 因而当前可以重复证明的是：正常业务会话有无需第三方结果的恢复能力，但恢复是条件性的、会再被拒绝。不能把它包装成已经可靠的“免费解码方案”。

## 七、确定性内部缺陷：已结束恢复的清理会重建人工Task

这是本轮另一个已定位到具体代码的根因，和外部401分开：

1. 当前Main旧事件在18:24:12.595结束，原人工Task已RESOLVED。
2. 约54毫秒后，同一旧target又生成 `automatic_verification_stalled` 的 `TARGET_LOST`；operation_id仍是已经结束的recovery_id，而不是新的业务请求。
3. `GovernanceRepository.save_recovery` 的人工升级条件检查HUMAN/manual_review_reason和旧Task状态，却没有排除 `value.phase == RESOLVED`。成功后的cleanup/probe元数据保存仍会进入这个分支。
4. 旧target已关闭时，直接创建幽灵TARGET_LOST；仍LIVE但所有权已结束时，还可能抛出OWNERSHIP_HANDOFF_FAILED，使清理无法完成。遗留人工Task又可能在进程重启的兼容迁移中重新变成阻断恢复。
