2026-11-12，北京时间。根据 `runtime-read-projection-performance-diagnosis-and-repair-plan-20261112.md` 执行。已发布 Projector；保持单进程、原有四源顺序，不按业务设置优先级，未重跑模型或交易，也没有重置 checkpoint、重建 Read、清空 gap 或暂停 GC。

## 实际修复

1. **历史缺口恢复减负。** 使用既有批内源 reader，不再逐事件建立连接；合并 CLI 和 tick 的两个恢复入口；每5秒一次、最多20条、250ms合作预算。只对实际开始尝试的项更新 attempts，长期失败采用有上限的退避，所有原始 gap/exception pin 保留。
2. **早解析与薄输入。** 增加仅供 Projector 使用的解析入口，事件内共享解析结果。完整证据读取与历史 JSON subtype 兼容保持；冻结上下文第一次解码后仅保留方向和状态所需的薄字段。缓存最多64项、16MiB，事件获取独立小对象，避免跨事件修改。保留 POLICY_TRADE 的 pinned condition/decision、W3 execution state 与 follow-up。
3. **减少无效写事务。** 只合并原本已经确认 `serving_skipped` 的连续坐标；下一条成功业务事件或轮末持久化。未处理业务事件、错误、崩溃边界不会被跨越。保留正常业务事件单次原子提交和实体/贡献水位。
4. **执行依赖从当前态读取。** 按既有索引查 `object_current`，避免经过历史兼容视图。未改变执行业务、成交或费用语义。
5. **发现并修复更深的冷启动全量反向同步。** 第一轮发布触发了原来就存在的 `sync_business_facts` 全量恢复：先把大量 Read 业务事实装入列表，再写回 Runtime，首轮消费被阻塞数分钟，RSS上涨到约2GiB。未将这种重启后积压当作可接受状态；随即追加修复并再次发布。

冷启动修复按现有索引每次最多取16个完整 revision，保留同revision的所有行；使用既有 `v2_transport_gc_state` 存放小型进度，不增加服务、队列或新数据库。Projector每轮同步预算250ms，未同步完整时不推进源 ACK。重启起点只能来自“之前已完成事实同步后写入的 consumer ACK”所覆盖的索引 receipt，不能拿当前 head 假装已复制。保留当前态与过往事实用途、命中撤回和快照重建语义。

新增每分钟的 event load/map/ingest、整轮墙钟/CPU、repair 聚合时间。实际数据表明事件本身已经较快，因此本轮没有进一步引入业务事件微批、大事务、多 writer 或内容注册架构改造，也没有修改持久性配置来换性能。
