## 发布方式与兼容迁移

后端、Site 从精确提交通过标准 `storage_release.py build` 构建，复用批准的依赖层。Web 在本地从该提交的 Git archive 构建并取得静态产物；因生产内存紧张及完整镜像传输缓慢，改为传输约 496KiB 的静态资源包，在服务器复用原运行 nginx 镜像形成新的应用层。静态文件逐一校验 SHA-256，运行镜像记录新代码提交，不在生产执行 pnpm 构建。

生产组件通过标准 release manifest/deploy 发布，保留原 secrets、挂载、角色命令及回滚版本。没有把应用源码临时覆盖进旧容器。

首次增量迁移遇到旧 Bus 持续持写，`BEGIN IMMEDIATE` 超时并退出，原始失败日志保留。随后在发布窗口停止旧 Bus、BODY、scheduler、projector、maintenance 和 transport-maintenance，重试后 Bus/Read 增量迁移成功；更新消费者后再由新生产者接管。新增表/字段保持兼容，回滚代码不需要删除业务数据表或用旧备份覆盖实时数据库。

Chrome Supervisor 不重建，保留物理 Chrome、profile、Cookie、出口与人工页面；CPU 相对权重通过原 Compose 配置及运行参数更新生效，不以重启浏览器实现调度优化。
