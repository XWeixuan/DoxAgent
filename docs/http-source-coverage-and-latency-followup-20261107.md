# HTTP 迁移覆盖与长尾延迟专项排查

统计窗口：2026-11-04 09:30 至 11-05 16:00 America/New_York，即 UTC 11-04 14:30 至 11-05 21:00。网站对照探测在北京时间 11-07 凌晨进行。沿用首轮统计窗口，不把网站后来出现的文章算作窗口内新发现。

## 结论

此前“延迟改善”的判断需要增加覆盖率约束：确实存在 HTTP 返回成功、但漏掉部分消息的情况。已修复 Canary 的陈旧列表与伪精确时间、Salesforce 内容类型缺失、NSF 置顶稿解析缺口、TechNews 上午时间解析，并将 TechNews 改为轻量官方 API 与原 HTML 的并集；CRN 改用已验证的固定 HTTP 出口。外部源身份、ticker 订阅与既有 BODY 流程保持一致。

ETNews 和 TechNews 的选定长尾不能归因于十几分钟的 DoxAgent 排队：四个典型案例首次形成候选后，0.14–0.34 秒完成总线接纳。历史回执没有保存当时的 HTTP 正文，因此不能断言这些文章在之前每次响应中都不存在，也不能把鲜活 Date 或 CDN MISS 当作无源站缓存的证明。ETNews 与 DoD 没有找到值得新增抓取路径的明确内部问题，本轮停止对其做推测性改造。

## 证据与口径

- 对齐代码中的实际栏目、HTTP 入口、RSS feed、解析器与内部单元，逐一或每批两个网站进行抓取和解析重放。
- 以当前官方 feed/公开 API 中发布时间属于窗口的文章构造参考集合，再查生产 `live_origins` 的来源级身份。查 URL 的大小写百分号编码和解码变体，避免把编码差异直接算成漏抓。
- 参考集合会受 feed 长度和后续分类、发布时间、URL 修改影响；“参考集合全部找到”仅证明这组已知文章，不宣称历史全站 100% 覆盖。
- `inputs.observed_at` 可证明特定文章内容指纹首次形成业务候选的时间；不是原始 HTML 证据。负向查询也不能排除曾以不同标题/摘要出现。
- `captures` 确认接纳后清空 payload；常规请求记录保留状态、时钟、缓存头和校验结果，不保留 HTML/JSON 原文。部分超过 48 小时的候选/抓取记录已按既有策略清理。当前网页重放和历史原文证明严格区分。
- `live_articles.input_ref` 会因后续更新变化。长尾使用首轮冻结导出中的 capture_id 回查首次回执，避免用当前最新修订的时钟替换首次发现。

### Canary：新鲜响应包裹陈旧内容

当前 `/articles?_dox_poll=...` GET 返回 200，Date 新鲜、Age 38 秒，但最新文章停在 11-04。HTML 的分页链接还保留 `11-04 09:05 UTC` 对应的旧 `_dox_poll` 值；更换查询参数和增加排序参数仍返回旧内容。窗口内四稿的 URL 在该响应正文中完全不存在：

- `top-clean-energy-wins-midterms`，11-04 22:30 UTC。
- `virtual-power-plants-grid-ai-bust`，11-05 05:01 UTC。
- `revolution-wind-fully-operational`，11-05 15:00 UTC。
- `pge-2b-cut-in-grid-investments`，11-05 17:00 UTC。

同一列表只读 POST 返回 `Cache-Control: no-store`、`CF-Cache-Status: DYNAMIC`，能解析上述四稿及更新文章；重复探测仍成立。切换为 POST，并禁止从旧 GET checkpoint 携带条件缓存请求头。

列表所有卡片统一标记当天 12:00，而 RSS 中这些稿件的具体时间各不相同。这是日期展示占位值，原来当作 EXACT 会触发 30 分钟实时窗口错误过滤。改为 DATE，后续仍由原 BODY 流程取得真实时间；不会拿占位时间继续计算精确延迟。

这同时说明仅靠 Age/Date 检查不能识别源站渲染缓存。没有把这个个案扩展成全站逐篇抓正文的常驻校验，避免增加轮询负担。

### Salesforce：posts 不等于原 feed 的全部文章

`/news/feed/` 包含 `sf_linked_content`，但迁移后仅调用 `/wp/v2/posts`。窗口内 `Double recall: Inside the Agentforce Memory update`（11-04 18:00:30 UTC）不存在于普通 posts 返回中，生产也无该来源记录；官方 `sf_linked_content` 接口能返回它。

增加 `sf_linked_content` 与 `sf_press_release` 两个独立内部单元，和普通 posts 共用 Salesforce feed 订阅入口、同一外部企业软件官方源；不新建碎片化消息源。沿用既有分单元调度、共享站点 HTTP 约束、URL 去重及失败显式 RSS fallback。SAP/Workday opt-out 的订阅语义保留。

### TechNews：上午静默漏解析及入口覆盖

旧正则要求小时为两位数；网站实际使用 `9:55`、`0:00`。只要列表还有其他能解析的文章，整个轮询仍然成功，上午条目被静默跳过。窗口参考集合缺失的 20 篇均发布于台湾时间 06:00–09:43。对应 UTC 11-04 22 点至 11-05 01 点，每小时都有 120 次两个栏目合计的物理轮询，不是休眠造成的缺口。

取回当前分页中的对应卡片，20 个缺失 URL 全部能复现“旧正则不匹配、修复后匹配”。这证明解析机制有确定性缺陷；没有历史原文，不能补造它们当年首次进入每次响应的时刻。另一篇 `91% 企業正在自研 AI 工具，但不到半數擁有成熟戰略` 在官方 API 和有效正文页中存在，但当前栏目 HTML 分页未列出它，不能仅靠修正小时正则保证与官方分类集合一致。

最终每个栏目合并官方 WordPress `posts` API 与原 HTML 列表，分类 ID 93648（半导体）、19819（AI）来自实际页面 class 和完整 API 分类字段交叉验证。使用 `per_page=40&context=embed`：

- 覆盖复核发现 API 单入口只包含当前半导体网页的 13/15 篇，两个网页独有样例的分类字段也不含 93648。API 不能直接替代原入口。最终每栏目两次轻量 HTTP 请求，仍归属于原来的一个独立单元，在同一个 12 秒预算内完成并集合并；共同文章优先采用 API 秒级时间。两个响应都验证后才记成功，任一失效均明确标失败并回退 RSS。
- API 每次约 71–72 KB，网页约 173–177 KB；合计约 244–249 KB/栏目/轮，比原 HTML 增加约 40% 的带宽，以保留覆盖。没有新增浏览器或常驻任务，CPU/内存仍为轻量 HTTP 与解析开销。旧 WP 4.7 忽略 `_fields`，所以不采用会返回完整正文的普通 view 响应（40 条约 344 KB）。
- embed 的 `date` 是台湾本地时间，不提供 `date_gmt`；显式按 Asia/Taipei 转换并保留秒，午夜样例有回归测试。
- 不下载 API 的完整正文，不把摘要当作 FULL；BODY、发布去重和 ARTICLE_ONCE 更新语义沿用原流程。当前半导体 HTML 15 篇与 API 40 篇合并为 42 篇，原 15 篇全部保留，其文章键和正文更新指纹全部一致，不会仅因列表时间从分钟变秒而重新下载正文。

### CRN：固定低成本出口修复

同一 JSON 入口 Direct 返回 Cloudflare 403，增加查询参数仍失败；固定 `us-standard-5` HTTP 出口下 cloud/security/data-center 三组均可解析 50 条，且覆盖当前各自 feed 的已知窗口文章。多次重复请求正常。将这三组改用该固定出口，不引入浏览器、身份轮换或拒绝后自动换出口。

**ETNews：** 历史响应 Date 新鲜，无可见旧 Age；当前原 GET、带分钟参数 GET、只读 POST 的列表文章集合一致。页面的新闻列表由服务端输出，检查 inline 脚本及 common.js，未发现用于替换该栏目最新列表的前端 API；其 AJAX 为收藏操作。当前正文发布时间 02:07:17 UTC，与列表分钟时间差 17 秒，不能解释 19 分钟长尾。当前 feed 的 9 篇均有来源记录。可排除已观察到的采集后排队，未找到可以重放的长尾解析错误；无法进一步严格区分源站缓存、分类索引迟到与文章标称时间早于实际公开时间。没有为了“看起来做了优化”增加 nonce/POST/浏览器链路。

**TechNews：** 这两篇长尾发布于台湾时间下午，不受一位小时错误影响。历史列表响应为 CloudFront MISS、Date 新鲜；这可以降低“边缘旧缓存”的可能性，但不能排除源站缓存。`major-transformation` 的官方 API `date_gmt=06:23:50`、`modified_gmt=06:45:19`，首次抓取距修改仅 47.764 秒，支持“发布后更新/栏目索引变更”这一解释，不能证明修改前没有公开。`surge` 当前修改时间为次日，不能替代首次公开时的证据。普通 GET 与 POST 当前没有新鲜度差异。API 补充覆盖与避免下载完整正文的成本收益已证实，但不能据此承诺网站自身 20 分钟长尾会全部消失。

**DoD Releases：** 第二例 Article 4641125 的标称时间 11-04 17:00:25、首次发现 17:11:10.590，延迟 10.76 分钟。两例均有连续成功轮询；第一例新鲜 Date、`no-cache,private`，接纳耗时 0.292 秒。当前官方 feed 的 5 篇窗口稿均有记录，没有发现解析/接纳缺口。未保留历史响应正文，不能把 10–16 分钟明确归为 DNN 源站缓存或发布操作顺序；按要求完成少量案例核查后停止扩展开发。

## 验证、发布与边界

修复后的真实响应离线重放、时区/午夜、只读 POST 不复用 GET validators、delta 去重、Salesforce 内部 feed opt-out、CRN 固定路由、失败 fallback 的 UI/台账一致性均有回归。合并当前 main 的其他发布后，相关四组测试首轮 187 项通过；补充双入口覆盖与故障回归后最终 190 项通过。

在生产网络中以独立进程加载候选代码，不写生产 checkpoint、不接纳探测文章：CRN/Canary、NSF/TechNews HTML、Salesforce 和最终 TechNews embed 各运行三轮。首轮解析正确，后续未变文章不重复输出；最终 TechNews API 分别 40 条，与原 HTML 合并后为 42/40 条；三轮无失败，后续两轮没有重复消息。生产曾被其他发布重建，导致一次探测退出 137；当前容器 OOM=false、cgroup oom_kill=0，重建后已重跑通过。

本轮没有执行人工历史补发，也没有把旧文章发布时间改成当前时间。恢复后列表自然重见的文章仍走原 DATE/EXACT 接纳与 BODY 流程；修复后新增的迟到来源记录不计为原统计窗口覆盖成功。不修改接纳时间预算、ticker 监测词、正文质量标准或 Chrome 身份。Aviation Week 的既有历史缓存不稳定问题仍由显式失败 RSS fallback 保护；本次两个典型入口当前缓存 Age 为 27/4 秒，不把瞬时成功当作已消除长期问题。

首轮于 UTC 19:33:59 发布 4ee65abf 的 API 主入口版本；随后最终覆盖检查发现 API 独有分类集合不能替代 HTML，已补充双入口并集修正，不把首轮单入口当作最终验收通过。最终发布回执与观察结果见下方追加记录。原始响应仅用于本轮诊断，未新增常驻全量响应存储。
