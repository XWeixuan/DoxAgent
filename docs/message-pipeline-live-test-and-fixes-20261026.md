## 已确认问题和处理

### 1. 浏览器回退抛公共程序异常，不能解释成网站拒绝

真实 Microsoft Fabric 失败页隔离重放复现 `AttributeError: 'dict' object has no attribute 'append'`。SiteAccessBrowserReader 把物理访问 trace 的 `stage_timings` 字典覆盖到正文流水线的阶段列表，后续 append 直接失败。该问题影响进入浏览器回退的多种站点。

修复：物理指标改用 `site_stage_timings`，原始 Site Access trace 保留；流水线 `stage_timings` 继续为列表。正文异常记录 job/source 和堆栈。HTTP→浏览器、HTTP→浏览器→Reader 适配器组合通过回归；生产修复后该异常消失。原 Microsoft Fabric 样例继续执行到真正的网络/访问失败，未被伪记为 FULL。

### 2. 源级获取较快，控制写入与 writer 排队却占用大量时间

实测 HTTP/浏览器内请求常在 0.1–2 秒完成，但轮次可能达到二三十秒以上。初始请求前等待约 5–50 秒。共享源逐 ticker 的开始、结束和 roster 处理制造多次串行排队，纯读也曾经过 writer。

修复：纯读使用独立有界 read lane；共享轮次开始/结束合并，词表 roster 一次快照，准备阶段合并短事务。轮次末尾的 poll state 与 run ledger 原子合并，源级 roster 状态投影共用一条连接和事务。2/20 ticker 都不增加应用排队次数；两者同时回滚的故障测试通过。

writer 从 `Condition.notify_all` 改为定向唤醒下一位 Future，保留单 writer、优先队列公平性、取消后的提交排空，修复“被取消 waiter 尚未清理就交接”的竞态。接纳短片参与采集同级排队，避免源账本长期挤压接纳。WAL 模式只在仓库初始化设置，不在每次短连接上重新协商。

### 3. 原始列表反复带回大量旧候选，接纳吞吐不足

最显著样例是 `nbis_official_actor_rss` 每次约 930 项。该源实际走 ticker 接纳路径。列表大多是明确过期候选；接纳仍按每片少量输入逐次处理，叠加 writer 等待，队列持续增长。原始候选数包含重复和旧条目，不能称为“新增新闻数”或“正文失败数”。

修复：共享与 ticker 两条路径统一在准备阶段复用现有年龄规则，对确定过期且未发布条目每片最多推进 256；真实候选仍最多 16。完整 capture 不裁剪，collected/filtered 计数、游标与 checkpoint 保留。明确过期 DATE 使用原本的日期规则；今天/昨天、未来、UNKNOWN_FIRST_SEEN 和 CLOSED_SWEEP 保持原处理。已发布文章保留更新核查；提交时再次检查准备期间是否新发布，有变化则重准备，游标不前进。

被过滤旧条目仍批量保存最早 first_seen，避免后续来源日期降级为未知时变成“新新闻”。接纳复用既有两个准备槽，并行处理不同 capture 的准备，数据库保持单写入者。分发文章集合由每篇重读/重写改为每片一次快照。

### 3.1 重复 capture 在接纳排队之后才去重

对同一 ticker 抽查连续 16 个等待轮次：NBIS 的 930 项数组、Finnhub 的 94 项数组、Newswire 的 40 项数组各自完全一致；Barron’s 的 16 次输入只有 2 种数组，Yahoo 只有 2 种。原始 capture 必须保留，但相同输入无需重复执行整个接纳过程。

补充精确输入复用：仅作用于同 binding/unit、source/binding 版本、bootstrap、接纳 policy 和完整消息数组都一致的实时 ticker capture。父输入完成时，每次最多复用 64 个处于等待状态、且捕获时间位于父输入处理窗口内的重复 capture。每轮原始载荷、实际请求和采集时点保留，单独记录 reused_from；部分已处理的轮次只复用未处理后缀，保留原收据、任务 ID 和首次接纳时点。复用轮次不增加正文成功或发布数。变化的原始 payload、摘要、版本、bootstrap、未来捕获、历史 sweep 以及共享分发 run 不合并。已处理后的未来轮询仍会正常触发到期复查。

已有积压通过有界、低优先级的输入哈希元数据回填处理，不删除 capture、不改 checkpoint 或订阅。回填共 13025 条，耗时 170.661 秒，剩余未索引等待项为 0；生产首轮复测等待 capture 已由约 1.33 万降至 7612。最终效果见下方固定窗口。

### 4. 已有任务或失败重试窗口内的重复输入仍反复展开旧正文

原处理完成正文、身份及队列对象构造后才返回“相同任务已存在”。重复成本占用接纳，而没有新增下载/发布。

修复：在原输入指纹、policy、scope、语言一致且存在对应持久任务的条件下，用标量收据提前返回。覆盖 queued/running/retry_wait，以及未到下次复查时点的终态任务。输入变化、策略变化、重试到期和历史补采继续原流程。此收据表示输入已经持久处理，不表示正文 FULL，也不推进任何虚假成功率。

### 5. 同一稳定文章 ID 的出版商 URL 与转发 URL 形成不同正文键

实际 Yahoo 样例：相同稳定文章 ID 早已有 Fool 出版商全文，之后列表给出 Yahoo 分发 URL，正文缓存另建键并记为 new_article；最终发布去重会指回原 Raw，但此前下载和失败负载已发生。

修复：仅在已有发布身份/上下文证明的情况下，将 URL 变体关联原 FULL/SHORT_FULL 正文记录；保留 scope、语言、内容 hint 和到期复查检查。重要输入变化仍重新获取，30 分钟到期不会被 URL 变化续期。旧文章新键回填原 first_seen，标记 prior_publication，缺正文的已发布文章归 recheck。ARTICLE_ONCE 继续更新原消息和修订，不再次触发下游发布。

### 6. BODY 没有前台可领任务时仍争用数据库 writer

复测出现 BODY 暂无新执行、队列主要为旧文章 recheck 的阶段；recheck 按原压力门禁暂停，但领取循环仍开启写事务探测，部分调用超过一秒。

修复：先只读探测到期前台任务或过期租约；无工作立即返回。增加与“暂不执行 recheck”谓词匹配的部分索引，避免扫描复查积压。真正领取仍在写事务里再次查询、认领和恢复租约，空探测之后的新任务由下一轮发现。保留原资源门禁，未强制增加 BODY 负载。

### 7. 休市补采反复空轮次与延期边界丢失

到期检查发现 GlobeNewswire `TAIL:SWEEP` 每约 5 秒重复运行。生产游标里各查询 `done=true`，但缺少 `head_at`；原调度强制 tail-only，从第 2 页开始，完成条件却要求首页证据，造成永远无法完成且可能遗漏第 1 页。Reuters 的补采延期也丢弃了 Site Access 提供的约 60 秒重试时点，统一在 5 秒后重试，并不断追加 UNKNOWN 覆盖记录。

修复：冻结窗口缺首页证据时先取得第 1 页，保留已有尾页游标和完成证据；之后正常完成或继续未完成尾页，不能直接把旧游标改成完成。延期沿用 provider 的 retry_not_before，缺失时使用原绑定周期；无进展不追加页覆盖，有进展仍持久保留任务/游标。此补丁在临时开关到期后发布，不重开临时实时采集。

### 8. 容器正常替换遗留长租约

最后一个 CEG 补采任务的 updated_at 为 05:21:29.073，早于新容器启动 05:21:29.771，原 owner 已随旧容器移除；其 30 分钟租约仍有效，导致恢复等待。正常取消原代码未捕获 CancelledError，未将自己的 claim 交还队列。

修复：正常关闭时释放自己的 fenced SOURCE_SWEEP claim，保留 capture、checkpoint、正文任务和失败计数，按原短交接间隔恢复；崩溃和其他 owner 的租约约束不变。对这一条已确认旧 owner 的生产任务单独核验 token/owner/时间后恢复并写审计，未全局清理运行任务。取消与恢复回归 11 项通过。

## 正文验收口径纠正

本轮最初看到 6 个首次出现的正文键、5 个 FULL；不能据此声称真实新文章成功率达到 83.3%。进一步按 canonical Raw 和既有发布流追踪，5 个 Yahoo 键对应此前已发布的旧文章。新键并不等于新文章，`work_kind=new_article` 的旧分类也不可靠。

已确认的新文章样例为 HuggingNews，首次捕获 02:12:56，正文取得 FULL 于 02:25:02，INTC/NBIS 发布约 02:25:05/07。首次发现至发布约 12 分 9 秒，说明当时主要卡在接纳队列；正文实际完成与发布间隔是秒级。另有最后窗口 BE 的 Google News 新样例取得 FULL。周末新文章样本不足，不能将少量样例或缓存复用当作“稳定超过 80%”的验收。

修复公共异常后仍有真实失败：MarketWatch 的 `no_authenticated_profile_available`、Investing 的 `login_required`、通用发布站点的访问组合不可用/重定向阻断，以及 Reuters 的人工挑战待处理。这些与程序异常分开统计。MarketWatch 当前要求认证，配置中虽然包含 Dow Jones 身份，也不能把 Barron's 可用直接认定为 MarketWatch 订阅已验证；本轮没有绕过认证或把摘要降级为完整正文。
