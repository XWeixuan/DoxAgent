# Yahoo Finance 消息源现状勘察

勘察日期：2026-10-31。依据：生产代码、采集数据库、Site Access 记录及公开列表/RSS 实测。本轮仅排查与记录，未调整采集代码或生产配置。

## 1. 当前采集方式

消息源 ID 为 `yahoo_finance_news`，按 ticker 订阅，实际分为三个内部任务：

| 任务 | 作用与当前方式 |
| --- | --- |
| `HEAD` | HTTP 获取 Yahoo ticker RSS，解析文章及 `pubDate`。 |
| `SUPPLEMENT_HEAD` | 使用 Playwright 和已有 `yahoo-main` Chrome 身份补充页面列表。常态复用已验证页面，通过页面内同源 `fetch` 取得 HTML 后解析；必要时走页面导航等恢复路径。 |
| `TAIL:YAHOO_TIME` | 为页面卡片补查精确发布时间，每次最多检查 3 篇；查到时间后输出文章。 |

RSS 与页面补充独立调度，并非仅在 RSS 失败时才启动页面采集。九个原有 ticker 配置周期为 30 秒，IONQ 为 60 秒。`page_network_ncp` 是沿用的结果标签，不代表实际必然调用 `/xhr/ncp`。

固定统计窗口：北京时间 **2026-10-31 00:00—03:00**，即 UTC 2026-10-30 16:00—19:00，属于 10 月 30 日美股交易时段。

| --- | ---: | ---: |
| 成功轮次 | 3,324 | 3,419 |
| 失败轮次 | 96 | 1 |
| 调度等待平均值（相邻快照） | 约 0.05 秒 | 约 0.05 秒 |
| 单轮执行平均值，含失败（相邻快照） | 约 0.71 秒 | 约 1.08 秒 |

耗时指标取自同次勘察中截至约 03:02 的相邻快照，非固定窗口的逐项重算。对应 Site Access 成功访问中，3,443/3,447 次复用了页面锚点，约 99.9%。轮询成功表示取得并验证了列表，不表示发现了新文章，也不表示列表覆盖完整。

固定窗口内，已入库的 34 条 ticker 消息记录全部标记为 RSS 召回；扩展到美股开盘至北京时间 03:00，RSS 为 70 条、页面路径为 7 条。记录数包含同一文章对应多个 ticker，不是独立文章数；结果标签也不能完整还原每篇文章最早出现在页面卡片中的时刻。

这 34 条消息的“发布时间至首次采集”平均约 8 分 58 秒，中位数约 8 分 49 秒，16 条超过 10 分钟，最大约 25 分 36 秒。该时间差不能直接视为一次轮询执行耗时。

00:03—00:08 左右存在 RSS 集中超时，成功采集间隔最长约 5—6 分钟；同期页面补充基本正常。该段超时的底层原因尚未确定。

## 3. 页面覆盖与发布时间处理

### 页面覆盖

- 常态同源 fetch 路径解析返回 HTML 中已有的新闻卡片，没有继续翻页或加载更多来证明覆盖完整。
- 当前 HTML 卡片解析仅接受 `finance.yahoo.com` 下以 `.html` 结尾的文章链接；`/m/…` 包装链接会被跳过。
- RSS 与页面不是等价列表。本次公开页面即时实测：INTC 页面 12 条、RSS 18 条，仅 1 条标题重合；MU 页面 12 条、RSS 19 条，有 11 条重合。此为勘察时的公开响应样本，不是历史生产页面逐轮快照。
- 列表存在推荐、持续更新内容和非严格时间倒序排列，不能仅凭列表位置判断发布时间。

### 精确时间与补查

精确时间取自接口 `pubDate` / `providerPublishTime`、文章 JSON-LD `datePublished`、`article:published_time`，或此前验证过的时间缓存。相对时间及 URL 数字不会被推断为精确时间。

本次 INTC、MU 共 24 张 HTML 卡片均未提供 `<time datetime>`。当前页面主轮询设置 `max_probes=0`：未知精确时间的卡片进入 pending，由独立任务访问文章补查；缓存有效期为 24 小时。补查每次最多 3 篇，单篇请求设有约 6 秒超时，但没有“一两分钟内必然完成”的保证。

复查时，10 个 ticker 中 9 个页面 pending 队列为空，INTC 有 1 条；未观察到普遍积压十分钟的补时间队列。

固定窗口内另有 15 次补时间任务记为 `UNPROVEN_LISTING`。当前成功判定要求有效列表请求证据，而纯时间补查可能仅访问文章或命中缓存，存在任务职责与台账判定不匹配。该计数不能直接解释为时间抓取失败或消息丢失。

## 4. 时间、去重与其他消息源

去重主要依赖文章身份等信息，精确时间不是去重的必要条件。时间还用于接纳判断：精确时间实时消息采用 30 分钟新鲜度窗口，补扫需要判断所属时间区间。首次发现的历史文章不能单靠去重识别为过期。

公共处理链支持 `EXACT`、`DATE`、`UNKNOWN_FIRST_SEEN`，因此“必须补齐精确时间才输出”不是总线的统一硬性要求，而是 Yahoo 页面路径的额外限制。

| 来源 | 已检查到的处理方式 |
| --- | --- |
| Yahoo | 专用 pending 队列及 `TAIL:YAHOO_TIME` 补查任务。 |
| Barron's | 原生接口通常直接提供时间；缺精确时间的卡片报错或跳过，没有同类补查队列。 |
| Investing | 读取列表时间；缺字段卡片可能跳过，没有独立补时间任务。 |
| InvestorsHub | 支持精确时间或日期级时间，没有同类队列。 |
| 科技、国防、能源、企业 IR 等适配器 | 按具体来源支持精确时间、日期，部分支持首次发现时间；未发现 Yahoo 式独立补时间队列。 |

## 5. 判断及证据局限

常态调度和单轮访问耗时较短，但存在一次 RSS 集中超时。页面补充的覆盖范围、链接过滤及精确时间门槛共同限制了它抢先发现并接纳消息的能力。

“页面每轮成功”不等于“RSS 中的文章已提前被页面发现”。不能将十分钟以上差距主要归因于补时间，也不能全部归因于 Yahoo 上游收录延迟。历史台账未保存每轮完整卡片及未定时卡片首次出现时间，暂不能逐篇拆分上游可见性、页面覆盖遗漏与时间补查的贡献。

主要代码入口：

- `src/doxagent/message_bus_v2/news_adapters.py`：Yahoo 路径选择及消息映射。
- `src/doxagent/message_bus_v2/yahoo_sources.py`：RSS、页面卡片及时间补查。
- `src/doxagent/site_strategy/origin_listing.py`：同源 fetch 与卡片过滤。
- `src/doxagent/message_bus_v2/collection_plane/worker.py`：采集执行与列表证据判定。
- `src/doxagent/message_bus_v2/admission.py`：时间接纳规则。
