# 开仓失败三次后永久废弃：修复记录

北京时间 2026-10-21。

## 问题确认与纠正

连接恢复能恢复已有仓位的退出义务，不能证明旧开仓信号仍有交易价值。上一轮将两笔较早信号恢复后成交列为业务恢复成功，判断有误。它们没有超过 semantic-day 截止时间，不代表仍有足够交易时效性。

真实 badcase：

- INTC `trade:case_0b5a60b35b174fbfa3f15a067d76a832`：修复前 job.failures=712，后于恢复连接后成交 198 股。
- MU `trade:case_fef78df457004eff92e0b4704f5970cd`：修复前 job.failures=337，后于恢复连接后成交 10 股。

证据为 `eval/trade_delivery_audit_20261021/pre-repair-ledger.json` 与 `final-ledger.json`。本次再读生产时没有其他未完成 ENTRY，已有两笔仓位仅保留各自原定 EXIT；没有反向交易来撤销真实成交，也不把已成交账本改成零成交失败。

## 根因

旧实现对 ENTRY 的异常重试没有三次失败的终止分支，主要依赖语义日过期。上一轮加入账户冷却后，瞬态异常仍持续重试，且恢复连接后只检查 expires_at。

另有两个可绕过路径：共享账户冷却使部分 ticker 不直接调用 API，自己的 failures 不增长；提交订单和取消后再次准备订单会把通用 failures 重置为 0。

## 修复后的行为

1. **ENTRY 默认三次执行失败即永久停止开仓。** 独立持久化 entry_failures 与 entry_abandoned_at；成功提交、连接恢复、进程重启和重复 intake 均不能解除废弃。已有累计失败达到上限的待执行 ENTRY 在启动或执行入口直接失败，无需先访问券商。
2. 共享账户连续失败达到三次时，同一账户下已经等待的 ENTRY 也立即废弃，包括尚未到 due_at 的任务，避免 ticker 轮流绕过账户故障。冷却期间只检查状态、不访问 API的跳过不计为一次失败。
3. 未发送的 PREPARED 作废并释放额度；确定未成交的 ENTRY 写 `entry_result=FAILED`、`entry_reason=ENTRY_FAILURE_BUDGET_EXHAUSTED`。Job 的 DONE 表示终态，result=FAILED 表示未执行成功，沿用现有契约。
4. 已发送但结果未知的订单永久禁止再追加开仓，但保留原订单对账、撤销余单的职责；不能在券商尚未确认时伪造“未成交”。部分或迟到成交保留真实数量、原 owned lot 和 EXIT。
5. 实际发单前，在同一数据库写事务中检查任务终态、废弃标记、持久失败预算及账户故障预算，并把 PREPARED 改为 SUBMITTING。废弃与发单竞争时不允许把 NOT_SENT 恢复为 SUBMITTING；已经进入发送过程的原单继续对账。
6. **EXIT 不受三次开仓失败上限影响**，仍按账户级 2/5/10/30/60 秒逐步退避，此后每分钟恢复一次。确定身份/权限/参数错误仍保留原来的显式错误处理。

无需新服务、队列、策略配置或数据库迁移；保留现有订单类型、价格、配额、出入场时间和 Policy 消费规则。

## 验证

67 项交易、资金周期、恢复、投递、Read 结果与执行投影测试通过；Ruff 和 whitespace 检查通过。

新增回归覆盖：三次连接失败后恢复仍不下单；337/712 次历史失败在任何 API 调用前终止；共享账户失败传递给尚未到期的等待任务；冷却跳过不消耗失败预算；重启和重复 intake 不复活；已发送/部分成交只对账撤销、不补仓；最终发单竞态阻断；提交成功不清零开仓累计失败数。既有 EXIT 持续恢复与低频 API 回归继续通过。
