# Runtime 批量失败排查与修复（2026-11-09）

## 已确认的失败

当前语义日从 2026-11-09 07:00 UTC 开始。首次数据库快照（约北京时间 20:40）共有 508 个 Case：281 COMPLETED、82 FAILED、119 PENDING_W3、26 RUNNING。失败数会随实时消息继续变化。

82 个终态失败均发生于 W3，而非最近切换 Luna 的 W1R2/W2R2：

| 根因 | Case 数 | 证据及修复 |
| --- | ---: | --- |
| 上下文目录顺序变化被误判为冻结内容变化 | 66 | 全部 66 例逐字段比对：快照内容摘要、版本、时点均相同，仅派生 `snapshot_catalog` 顺序不同。新绑定规范排序；旧绑定在内容完全相等时继续使用原 manifest 字节、摘要、token。真实内容变化仍拒绝。 |
| Codex 上游持续 429 | 14 | Worker 07:11—08:45 UTC 共记录 130 次包含 HTTP 429 的失败调用，包含其他成功恢复 Case 和二阶段调用。原账户暂停只识别 usage_limit，未识别这种 429，Case 耗尽三次重试。扩展现有机制：429 暂停 60 秒，之后仅一个 Case 探测；不扣业务重试次数。原额度耗尽仍暂停 15 分钟。 |
| 活动任务字典在 await 期间变化 | 2 | Worker 原始堆栈定位 `jobs.py:_capture_identity`，遍历 `_active` 时异步读取磁盘，调度器同时增删。改为遍历快照，并在写身份前确认任务仍活动。 |

W1/W2 中 Sail R3 的流式错误由既有 Haiku fallback 接管；它增加延迟，但本次快照中不是上述终态失败的来源。保留现有模型配置、提示词、Schema 与业务路由。

## CPU 与存储

8 核主机初查负载 12.9—14.6，内存可用约 9GB、Swap 接近占满。短采样 CPU 仍有约 20% 空闲。Runtime 日志存在 SQLite 写入等待及短写忙重试，可能放大队列和绑定回执落盘间隙；但三个已确认根因分别有确定性复现或原始上游错误，不能通过“CPU 紧张”统一解释。

CDECR executor 也存在初始化库写锁导致重启的独立现象；这不等于本次 W3 Case 失败根因。不得因本次修复擅自恢复旧交易信号、改写已经提交的交易或更换研究模型。
