## 为什么前一周多数正常、这两天集中发生

**409 是条件触发的恢复缺陷：首次绑定成功后，本地绑定回执还必须成功落盘。正常路径不重建目录，所以潜在排序缺陷可以长期不显现。** 近期 SQLite 争用频繁打断这个落盘步骤，才把大量 Case 推进有缺陷的重绑定路径。

实证来自 MU Case `case_2bc7f9990ecb4199931443acc971cfcf`，全部时刻为北京时间：

1. **19:58:15.268—19:58:15.322**，Worker 上下文绑定成功，耗时 **53.154ms**。Worker 原 manifest 的落盘时间与该时段吻合。
2. 绑定之后，Scheduler 唯一紧接的持久化步骤为保存 `w3_context_v2`。该 phase 于 **19:58:46.739** 以 `OperationalError` 退出，绑定回执没有留下；这符合现有 30 秒 SQL 写重试预算。该 Effect 本轮累计 journal.begin 等待 **42.68 秒**、20 次 begin 异常。
3. 下一次从已经冻结的 manifest 恢复，JSON 键顺序已规范化；Worker 已有原绑定，目录数组顺序却不同，出现 409。后续重试继续同样失败，最终 20:03:48 Case FAILED。
4. 本轮修复后，同一原输入连续两次 HTTP 200，原 token、原 manifest 摘要不变。这验证了失败转换条件，而不仅是根据错误文字猜测。

数据库留存状态也支持这一差异：

| 语义日 | 已构造第一阶段上下文 | 缺少本地绑定回执 | 留存的上下文错误字段 |
| --- | ---: | ---: | ---: |
| 11/02—11/06 合计 | 4,656 | 0 | 0 |
| 11/07 | 7 | 2 | 2 |
| 11/08 | 167 | 42 | 42 |
| 11/09，21:00 左右快照 | 351 | 110 | 104 |

当日在途 Case 尚未完成绑定也会计入“缺少回执”，所以最后一行不是 110 个失败。错误字段可能保留在已恢复行里，也不等于终态 FAILED 数。前一周虽然没有上下文 409，但 11/02、11/03 分别仍有 2、5 条字典错误；因此“完全正常一周”与现存记录并不完全一致。

近期的放大条件：

- **周末突发集中。** 11/08 的 280 个 Case 都是 CLOSED 模式，集中在 15:06—15:48 北京时间，212 个路由 W3，单分钟峰值 103。11/09 15:07—15:43 又有 305 个 CLOSED Case，其中当小时 221 个路由 W3，且与 REALTIME 入站重叠。这个模式与日内逐条消息不同。
- **维护工作重叠。** 11/08 语义日有 211 条 SUPPLEMENTAL、11 条 SWEEP 维护任务；11/03—11/05 分别只有 2、2、0 条 SUPPLEMENTAL。11/07 上线的 O2 自动恢复/迟到交接机制及周末后继工作，是值得继续缩减读放大的负载参与者；不能只凭计数将 O2 修复认定为 409 的代码引入项。
- **历史压力不是仅凭今日负载反推。** 11/08 21:03 左右的原观测已有主机 load 45.62 / 77.25 / 99.14、Swap 使用 2,046/2,047MB；同期 O3 也有 SQLite 派发前写锁失败。该记录早于 22:08 的 O2 r4 修复，排除了“r4 上线才制造整场事故”的说法。
- **当前存在可量化的读放大。** 发布后 15 秒 GIL 采样中，204 个样本约六成落在 Case 模型重建及原生 JSON 编解码。主要调用链是 W3 Effect 为检查 Sweep 门槛先完整读取 Case，以及 O2 构造每条原子事实时重新完整读取来源 Case。单条冻结输入平均仍约 1.5—1.7MB：11/08、11/09 没有较前一周显著膨胀，不能把本次事故归因于新一轮输入尺寸异常。
- **形成反馈循环。** 锁等待导致 Effect 重试；每次重试又读取/解码大 Case、争用短写和阶段状态，进一步拖慢绑定回执和已完成结果的消费。当前已修复其中“临时写锁问题升级为永久 409”的关键环节，账户级 429 暂停也避免继续放大模型重试。

“SQLite 争用 → 绑定回执缺失 → 重绑定目录变化 → 409”的链路有逐 Case 直接证据；各负载参与者的独立因果占比尚未通过控制实验分离。15 秒 GIL 采样不能等同于全机 CPU 占比，不能声称某一服务独自制造了全部压力。下一步最小优化点是只读 Sweep 门槛所需标量、只读 O2 所需来源字段，避免每次为了少量字段完整解码冻结研究材料；这些属于后续吞吐优化，未混入本次三个故障修复。
