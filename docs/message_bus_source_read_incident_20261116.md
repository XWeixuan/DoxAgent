# 消息源读取失败修复记录（2026-11-16）

## 故障与根因

请求 `f5d0b52a00954d3188d3e8a94dacfa16` 对应生产环境
`/api/doxagent/v2/message-bus/source-catalog`，日志为 `INTERNAL_ERROR`。
这不是前端旧构建：在容器内用生产 Read 数据直接调用统计代码，同样触发
`article_samples.py` 的 `datetime.fromisoformat(None)`。

跨消息源去重接管同一篇文章时，`live_deliveries` 可能更新为新消息源，
但输入属于 baseline/rejected 时没有首次发现时间。Read 当前对象因此没有时间锚点；
文章抽样索引却仍保留旧消息源的条目。抽样程序通过旧索引找到当前对象，
既没有校验当前消息源，也没有检查时间锚点，导致整个目录和 ticker 统计失败。
生产候选中确认 20 个这类失配。

另外，恢复统计后复现 BE 消息列表独立的 `504 QUERY_TIMEOUT`。
分页本身约 0.03 秒，正文状态补充约 3.43 秒。原查询的生产执行计划选择
`current_kind_revision(kind,valid_from)` 范围扫描，再过滤本页 ID；
只显示 20 条消息仍可能扫描大量标准消息记录，超过 3 秒请求预算。

## 最小修改

1. 抽样时同时校验当前消息源和真实存在的首次发现时间，不用旧索引时间或
   `created_at` 猜测缺失锚点。原有每源最多 20 个候选的边界不变。
2. 投影更新时，首次发现时间被清空的 delivery 同步删除抽样索引条目，避免继续制造旧索引。
3. 一次性维护脚本只检查实际绑定源的最近候选，删除 20 个失配索引，复查为 0。
   不删除或回填历史文章、正文、交易及 Runtime 数据。
4. 消息列表正文状态查询改由当前页的消息 ID 驱动，分两步查标准消息和文章状态；
   先查 current，仅对缺失项按同一视图水位查 history。最多四个批量精确查询，
   沿用已有身份索引，不增加索引、轮询、任务、缓存或持久化状态。
