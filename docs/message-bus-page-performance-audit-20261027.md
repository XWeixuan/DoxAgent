# 消息总线页面加载缓慢：问题排查与指标取舍报告

日期：2026-10-27，北京时间。生产采样约02:13–02:21；业务语义日为2026-10-26。

本轮是只读排查：核对代码、提交历史、实际运行镜像、生产日志、SQL执行计划，并对生产读库做串行、有截止预算的分项读取。没有修改产品代码、配置、数据库结构或数据，没有重启、部署、删数，也没有运行整页并发压测。报告中的修复项均为待决策建议。

## 1. 结论

**新增的历史统计是重要诱因，但不是唯一根因。当前是“重统计进入默认请求 + 每来源重复计算 + 模块一起成败 + 消息列表选错索引 + 主机I/O压力”叠加。仅在界面上隐藏几个指标不能解决问题。**

| 问题 | 证据与影响 | 确认程度 |
| --- | --- | --- |
| 状态接口仍扫描旧轮询状态历史 | `poll_window()`先查语义日内的poll状态版本，再在Python过滤近30分钟；INTC/MU均触发3秒预算中断。这部分旧均值/P95在新cadence存在时已不作为界面主指标展示 | 生产复现、执行计划确认 |
| 全局与逐来源重复计算实际周期 | `/status`和`/sources`各自调用`poll_cadence()`；后者单次实测2.785秒，还未包含卡片组装 | 生产复现、代码确认 |
| 每来源“当天新增”误用完整统计接口 | INTC有效来源31个，前端逐源并发调用完整`/metrics`，每次额外计算正文cohort和上期指标，却只取`published_revisions` | 代码确认，访问日志确认真实逐源请求 |
| 一个慢模块拖住其余模块显示 | status、metrics、sources合用一个`Promise.all`和一个Query；任一失败，本次整组成功结果不能发布，首次来源卡片和其他KPI也会缺失 | 代码确认 |
| 消息列表自身存在低效读取路径 | 前21条消息选择`current_kind_revision`后排序；原查询4.441秒后中断，诊断性使用已有`current_page`索引2.070秒成功 | 生产复现、执行计划确认；时间受I/O波动影响 |
| 全机存储/内存等待放大慢读 | 8核主机load约48.84，I/O PSI some avg60=80.43%、full=66.77%，swap已用约1.8GiB | 当时真实快照；不能当作全天均值 |
| 额外上下文写锁与认证等待 | 前30分钟日志有14次read-context STORE_BUSY、12次排队超时，以及2次约10秒AUTH_UNAVAILABLE | 日志确认；认证外部失败的具体原因未进一步确定 |

原有的“周期新增消息数”和基础源状态本身不重：INTC样本约0.014–0.043秒。**有价值的指标大多可以保留，主要应改变它们的取数方式和进入首屏的时机。** 极端I/O压力下，轻查询也会变慢，MU同类桶查询另一次耗时2.169秒。

## 3. 页面究竟发了什么请求

默认消息流、当前交易日模式，在没有可复用前端缓存、所有阶段成功推进时：

1. 页面当前周期context与消息流ALL context：2个请求。
2. minute模块再建context：1个请求，随后并发请求status、metrics、sources：3个。
3. 消息列表首批：1个请求，之后才启动SSE及可见消息的正文读取。
4. 来源列表成功后，daily模块再建当天context：1个请求，随后对N个source各发一个完整metrics。

**合计N+8个普通请求。INTC的N=31，即39个，不含SSE、逐消息正文、重试、续页。** 周期ALL时两个页面context可能合并，不能一律按39个算。minute整组首次失败时daily尚不会启动；如果此前已经成功取得来源，后续刷新仍可触发daily扇出。

每个可见分钟会重跑minute和daily；两者又设置窗口重新聚焦时刷新。定时器自身有防重入，并非无限轮询漏洞，但这些触发会反复产生上述工作。minute和daily请求函数没有向ApiClient传递React Query的取消signal，切换标的后旧请求也不保证立即取消。

还有两种“一起成败”：

- status、metrics、sources中任意一个失败，首次其余成功结果也不能更新到界面；消息列表是独立Query，并非代码上必须等待KPI，但会争用相同读池。
- 所有来源当天统计也合用`Promise.all`；一个来源失败，当批其他来源的计数也不会作为新daily结果展示。

实际Web访问日志采样前20分钟：metrics返回200共169次，503共10次、504共5次；包含MU约30种、SNOW约25种不同source_id的metrics请求。这确认了逐源取数在真实用户请求中发生，并非只存在于静态代码。

代码：`frontend/v2/src/pages/message-bus.tsx:148–233`、`:334`；ApiClient恢复重试在`frontend/v2/src/core/api.ts:263`起。GET遇到指定暂时性错误还可重试两次，并有约20秒恢复窗口，进一步拉长可感知等待；不能把一个SQL的3秒预算理解为整页最多等3秒。

## 4. 哪些SQL真正慢

下表来自同一线上读库、正常投影继续运行时的串行分解。测试使用函数实际取数与NativeContent解码，预算一般3秒；不经过公网认证、浏览器渲染和共享读池排队。不同阶段的数字不能相加推导整页固定时长。

| 分项 | INTC墙钟耗时 | 实际CPU耗时 | 结果与说明 |
| --- | ---: | ---: | --- |
| 基础源状态聚合 | 0.043s | 0.017s | 成功 |
| 当前日原有消息/正文尝试桶 | 0.025s | 0.013s | 成功 |
| 上期桶 | 0.014s | 0.008s | 成功 |
| 某来源仅原有桶计数 | 0.034s | 0.009s | 成功 |
| 同来源完整metrics | 0.799s | 0.101s | 成功；约0.753s耗在额外文章JOIN，即便该来源没有返回cohort文章 |
| 当日新文章正文cohort | 0.894s | 0.225s | 成功；后续热读完整metrics曾为0.323s |
| 旧poll状态近30分钟统计入口 | 3.057s | 0.240s | SQL_INTERRUPT，尚未进入后续cadence |
| 来源实际周期统计 | 2.785s | 0.226s | 成功，但只剩极小请求预算余量 |
| 31来源绑定分页，不算cadence | 0.880s | 0.008s | 成功，包含当时元数据读取等待 |
| 31张源卡片，不算cadence | 0.558s | 0.236s | 成功，93次身份SQL读取 |
| 消息前21条，原计划 | 4.441s | 0.010s | 中断；另一轮也在4.114s中断 |
| 相同消息头查询，指定已有current_page | 2.070s | 0.006s | 成功，21条；不是已上线修复或稳定耗时保证 |
| 近7日正文cohort | 5.786s | 0.014s | 中断 |
| 全保留窗口正文cohort | 3.172s | 0.012s | 中断 |

墙钟明显大于CPU，说明这次不只是“Python算得复杂”，大量时间花在存储/调度等待。SQLite进度回调只能在继续执行时检查截止时间，I/O阻塞时3秒预算可能被超出，API还有硬超时处置。

### 4.1 status里有一笔当前界面不优先显示的历史成本

`api_v2/bus.py:214`无条件执行`poll_window()`。`news_timeliness.py:95–143`先查current/history中的`native:poll_states`：SQL按语义日筛选并按版本排序，**近30分钟筛选在SQL返回后才做**。历史分支没有按固定水位筛掉已失效版本，是为重建历史轮询样本，不等于普通快照查询。

执行计划为current分支使用`current_kind_revision(kind,valid_from)`，history分支使用`objects_day`后临时排序。`LIMIT 4000`只是结果数量上限，不代表最多读取4000条记录/页，也不能阻止前面的筛选、JSON读取、排序成本。

紧接着又计算新`poll_cadence()`。当前前端优先显示cadence的“实际刷新间隔”；旧mean/p95只是兼容fallback。因此，**直接移除这段旧窗口重建、改用现有轻量最近耗时，可能不损失用户当前主要看到的字段，却省掉一个已复现超时的步骤。** 若要保留旧窗口历史统计，应进入按需诊断，不能继续暗藏在基础状态读取中。

### 4.2 cadence有索引，但仍被重复调用并读取较多明细

当前/历史的poll时间表达式索引真实存在，不能诊断为“全部没有索引”。但每次cadence仍读取schedule和poll run/capture payload、解码并重建周期。

- INTC有662条当前schedule；一次来源cadence样本中，仅schedule读取耗时约2.097秒。
- status与sources分别计算同一ticker、同一近30分钟窗口的cadence，只是一个汇总、一个按binding分组，没有共享计算结果。
- sources的cadence计算不依赖本页返回多少来源，配置模式每页20个来源也会执行整个ticker的cadence；配置界面没有展示这些cadence字段，属于额外无用计算。
- 代码设有schedule 4,000、runs/captures 16,000的结果上限，这是安全限制，不保证固定时间。当前INTC仅`native:poll_captures`的current记录已达51,289条；这些是技术收据，不能等同于51,289篇新闻。

### 4.3 新正文指标改变了完整metrics的成本

`bus_metrics.metrics()`原有部分走预聚合桶，本轮确认线上桶标记和索引可用。但末尾无条件调用`body_cohort()`。

cohort先将article_observation与全局article_body_results按canonical身份关联、DISTINCT去重，读取payload后计算成功/失败/待完成，再查关联body_attempt的网络尝试与复用。固定水位落后于持续写入的head时，通用`snapshot_table()`会生成current/history UNION；本次计划出现`MATERIALIZE o`、`MATERIALIZE b`、`SCAN b`、`SCAN o`、`TEMP B-TREE FOR DISTINCT`。这部分不是简单的计数桶读取。

各来源当天计数只需一个桶值，却反复执行这个完整函数，是最直接的浪费。即使删除页面“正文复用”一行，只要后端仍调用完整`body_cohort()`，主要JOIN成本仍在。

### 4.4 消息列表也有独立问题，删KPI不能保证恢复

`repository.page()`当前分支只在case等部分场景指定读取索引，message没有指定。线上无`sqlite_stat1`统计表，本次优化器选择：

```text
原计划：SEARCH current_kind_revision (kind=? AND valid_from<?)
        USE TEMP B-TREE FOR ORDER BY
诊断：  SEARCH current_page (kind=? AND ticker=?)
```

原路径先按类型/版本找记录，再过滤ticker、排序；已有`current_page(kind,ticker,sort_key,id)`能按该标的页面顺序读取。只读对照确认其具有实质影响。统计表缺失是优化器缺少信息的事实，不能据此断言所有查询都因它变慢；也不应为了本页直接全库ANALYZE或盲目再加一组大索引。

## 5. 排队、锁、认证分别卡在哪里

当前真实限制：读worker **2个**，等待队列16，排队预算**3秒**，普通查询执行预算3秒，详情5秒。最近一次发布已把排队预算从1秒调整为3秒；当前仍失败，继续延长等待不能消除重复工作。

采样前30分钟API失败日志（失败计数，不是请求失败率；成功请求未在同一日志中完整记录）：

| 路径 | 查询预算超时 | 排队超时 | 其他 |
| --- | ---: | ---: | --- |
| status | 37 | 5 | — |
| metrics | 5 | 12 | — |
| sources | 5 | 4 | 1次hard_timeout |
| messages | 16 | 3 | 1次hard_timeout |
| read-context | — | 12 | 14次STORE_BUSY、2次AUTH_UNAVAILABLE |

- `QUERY_TIMEOUT / SQLITE_INTERRUPT`：已经获得worker，但未在查询预算内完成。
- `capacity_timeout`：等worker超过预算，执行耗时是0，用户通常看到“读取服务繁忙”。不能全部解释成该请求SQL很慢。
- `STORE_BUSY / SQLITE_BUSY`：read-context最终需要`save_token()`，通过短写事务保存固定水位；GET并非全程无写入。重复context增加争写机会，日志中实际约2秒后失败。这与只读SQL的I/O慢是两种机制。
- `AUTH_UNAVAILABLE`：发生在交给读池前，两个样本约10.0/10.6秒。代码认证缓存未命中时访问外部认证/权限服务；本轮未探测该外部服务，不能把这两次失败归因于指标SQL，也不能认定认证服务持续故障。

日志还记录少量SSE child_ValueError/client_cancelled，不足以单独认定具体根因，不把正常用户取消视为服务故障。本轮未用未知原因填补结论。

全机快照：8核、内存约15.24GiB，可用约3.22GiB；swap约1.75GiB/2GiB已用。CPU PSI some avg60约7.95%，I/O some/full avg60约80.43%/66.77%，内存some/full约28.17%/25.74%。这是明显存储与内存争用场景，不能用“已经升级8核”排除资源问题。当前serving SQLite文件约16.90GB；该大小不含所有NativeContent文件，**没有证据将整个体积增长都归因于本次页面指标**。

## 6. 哪些指标值得留、哪些可以移出首屏

以下“成本”按当前取数实现评估，不代表指标本身必须昂贵。建议优先解决共同请求结构，再决定界面删减。

| 指标/内容 | 能帮助决定什么 | 当前代价与口径 | 建议与删除代价 |
| --- | --- | --- | --- |
| 消息流、正文按需展开 | 实际收到什么、如何处理 | 列表有索引路径问题；正文已有可视区按需机制 | **保留，优先修列表读取路径**；不能靠删KPI替代 |
| 连续运行时长、源正常/异常数 | 服务是否运行、哪些源出错 | 当前状态、轻量聚合 | **保留**，从重timeliness计算中拆开 |
| 周期新增及环比 | 今天/近几天有多少正式发布 | 已有预聚合桶，正常样本很轻 | **保留**，不应为其附带正文重算 |
| 每来源当天新增 | 哪个源实际产出、是否值得保留 | 指标轻；当前逐源完整metrics使其变重 | **建议保留，改一次批量按source汇总**；若愿意删除可直接取消整组daily请求 |
| 最近成功、配置间隔/倒计时、上次结果/错误、采集距今 | 某源是不是停了、是否需要干预 | 当前poll状态；卡片有逐条身份读取，但无需历史周期扫描 | **保留**；阶段耗时悬浮信息也无需独立重算 |
| 新文章正文成功率及成功/失败/待完成数 | 是否“有标题但拿不到正文”，包含未发布失败文章 | canonical文章去重；关联当前ticker、全局首次观察时间落在选定周期，排除legacy/ineligible；当前实现中高成本 | **有价值，建议保留但按需/较低频独立读取**，不阻塞消息和基本状态。若删除，会失去对未成功发布文章的质量观测 |
| 网络成功数、正文复用数 | 区分网站失败与缓存复用，适合排障 | 同cohort额外body_attempt查询；不等于新文章成功率 | **可移到按需详情或删除**；须同步去掉相应后端查询，保留cohort主率仍有JOIN成本 |
| 全局近30分钟实际刷新均值/P95 | 看采集是否按节奏发生 | 由多个采集单元的fresh gaps聚合，不等于每个源配置周期；多单元源权重更高 | **优先移出默认首屏**，保留诊断入口；只保留全局一个均值可能掩盖某源长时间失效 |
| 逐源实际间隔、最长空窗、兑现率/缺轮 | 区分“配置60秒”与“实际几分钟”，发现源掉队 | 有业务价值，但当前重复重建技术时间线，成本高 | **建议按需诊断保留**；若需要常驻，应一次计算同时提供汇总和逐源结果，不按卡片重算 |
| 旧“近30分钟单次轮询耗时”兼容统计 | 旧版本展示请求耗时，不代表真实采集间隔 | 当前status的已复现主要阻塞，界面已有新口径优先 | **优先取消默认计算**；保留卡片现成的“上次轮询耗时”即可 |
| 候选待接纳/异常数 | 区分采集成功与接纳/发布积压 | 当前来自近30分钟capture，不是全保留窗口积压；候选也不是唯一文章 | **值得保留概念，需写清窗口**；不能把当前数值当总积压。不要为此在首屏再扫描全历史 |
| 待覆盖查询/待核验时间 | 某源还有哪些覆盖工作未完成 | 来自当前checkpoint，本轮未发现其为主要瓶颈 | **可保留**，没有必要连同高成本历史指标一起删 |

口径提醒：`body_cohort()`没有应用消息路由筛选，消息新增数会按route过滤。选TRADE等路由时，不能将正文率理解为同一路由的正文率；它也不是“本ticker第一次看到的文章”，而是关联文章的全局首次观察窗口。cadence的截断/eligibility_unknown字段没有在当前主界面充分提示。保留这些诊断指标时需要保留口径/缺失信息，不能用0补未知。

## 7. 可供选择的简单修复边界

**推荐：保留业务产出与质量信息，把工程诊断统计移出默认加载；先改请求和SQL路径，不新增另一套存储系统。**

### 方案A：最小、容易维护（推荐）

1. 消息列表、基本状态、消息计数、来源列表分别加载和报错；继续使用明确固定水位，不用`Promise.all`整组丢弃成功结果。
2. status取消旧poll_window重建；sources（含配置页）不默认计算cadence。保留当前状态、最近成功、上次耗时、倒计时、错误。
3. 每来源当天新增改成一次读现有桶并按source归并；不调用N次完整metrics。不需要回填新表。若决定删掉此字段，则删除daily请求链，成本更小。
4. 保留新文章正文成功率，但独立按需加载，或仅在其模块展示时低频读取；网络成功/复用移入详情或取消。不能只在JSX藏字段而保留无条件SQL。
5. 修复message分页选择已有有序索引的问题，保留同样的MVCC/排序/续页语义；验证current与history两个分支，不添加非必要大索引。
6. 复用同ticker/同周期/同水位可复用的context，接入已有取消signal，避免切换后的旧查询继续占资源；不为了减少GET写入取消水位保护。

这样保留核心业务判断，牺牲的是默认界面的精确周期诊断。不是关闭后台采集、正文补全或删除原始证据。

### 方案B：周期诊断也要保留

在方案A上加一个“诊断统计”按需入口：一次读取同时返回整体与逐来源cadence；必要时使用短时、有界缓存，缓存键包含ticker和统计窗口/水位，并显示统计时点。不让它重新进入首屏共同等待链。此方案需要额外维护一个可选读取结果，但仍不需要新建长期历史指标库、Redis或定时全库扫描。

### 方案C：最少指标

在A上取消新文章正文cohort、网络/复用、实际周期与兑现率，仅留消息计数和当前状态。这能进一步减少重查询，但会失去“没拿到正文、没发布出来的文章失败”与“名义周期正常但实际掉队”的观测。若这些信息平时不用，删除是合理取舍；消息分页、批量计数和模块隔离仍应修，不能只删展示。

不建议作为主要修复：继续加worker或延长超时、让首屏启动更多后台精确计算、立即全库建索引/ANALYZE、靠删业务数据减库、为本页另造指标平台。现有2个读worker已经被磁盘等待拖慢，盲目增加并行可能进一步放大争用。

## 8. 为什么上次验收通过，几小时后还会复发

10月26日恢复报告记录57/57成功、最慢1.863秒，是当时的真实结果，本轮没有证据否认。但核对其`eval/production-recovery-20261026/http_probe.py:46–55`：每个ticker创建两个context后，并发读取sources/status/metrics/messages四个模块，随后换下一个ticker。

它没有重现实际前端逐source的N个metrics请求、minute/daily刷新、重新聚焦、逐消息正文，也没有证明长期高I/O压力下稳定。sources使用默认分页20，前端消息流请求limit100。此外，当前重统计没有变成稳定的小摘要，数据规模与机器等待持续变化；先前能在3秒内完成，不代表始终能完成。

后续验收应针对真实默认请求图：确认每来源当天计数只发一个批量请求；切换标的能取消旧请求；可选诊断失败不阻止消息与基本状态；当前/7日/全部窗口均按相应策略处理；覆盖可见分钟刷新与重新聚焦。记录成功与失败、排队与执行耗时、同期I/O压力，不能只取一轮成功结果。本轮没有登录浏览器做页面计时，也没有将直接函数耗时写成用户端整页加载耗时。
