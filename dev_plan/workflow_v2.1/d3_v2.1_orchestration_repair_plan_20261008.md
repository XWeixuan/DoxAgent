# Document3 v2.1 编排修复方案：Pilot 后根因诊断与实施边界

日期：2026-10-08。状态：**待实施方案，本轮没有修改业务代码、prompt/skill，也没有启动新 Pilot 或部署。**

依据：冻结需求 `d3_v2.1.md`、`document3_v2.1_contracts.schema.json`、既有重构实施方案、MU SDK Pilot 的 `PILOT_ANALYSIS.md`，以及本轮本地工作树中的实际实现。当前代码包括 Pilot 期间及 10 月 7 日已经发生的修复；结论不等同于生产部署状态。用户本轮的明确决策优先于 Pilot 报告中的旧建议：采用 **5 个目录一批**，不实施关系图分组；将参考、直接编辑和补研分离；GLOBAL 只承担 Planning 与 Integration。

## 1. 修复目标与不变边界

本轮拟实施的不是再添一个 Review，而是纠正线程职责、文件交接和 Integration 调度的根源问题，同时收敛已修补代码中的局部缺口。

1. Shell、OPEN 负责 Discovery 与 Build；GLOBAL 只负责 Planning、Integration，保持 N+2 个线程和 owner 内串行 waves。
2. 原始上游资产、主研究接纳池 B、已接纳补研稿和候选稿均能通过明确路径读取；读取一个对象不意味着重新处理它。
3. 由 agent 显式产生待编辑、待补研决定；宿主只做结构接纳、路由与有限调度，不根据 `relations`、标题或引用推断经济影响。
4. 主审查、补研后复核、最终写入均按最多 5 个待处理目录组成一批；累计 Review 保持串行，唯一补研轮不变。
5. 仅有明确待编辑请求才调用 final_write。健康、无需改写的补研稿已经可以作为 Consolidation 候选，不必再复制成一份 final 稿。
6. 保留 B 的默认 retain、完整 Policy 写入、宿主 ID/Condition 规范化、显式集合替换及局部失败保全；不修改最终 PolicySet V3、MAINTAIN Patch 或下游交易合同。
7. 正式 v2 默认、legacy prompt/skill 路由、foundation 已合入 o3.md 的注入方式均不切换。MAINTAIN 继续单节点，仅承接共享材料、SDK 权限及恢复方面的修复。

不建设知识图谱、共享事实数据库、语义影响传播引擎、自动经济审核或新的研究阶段。不因为报告过旧、可选资料缺失、某条补研未完成，就阻塞全部健康稿件。prompt/skill 内容由另一会话处理，本方案只改宿主合同和技术任务上下文。

## 2. 更细化的根因诊断

### 2.1 核心偏差：线程清单被误用为研究路由

`inputs_v21.py:222` 的 `topology.owners` 同时列出 Shell、OPEN、GLOBAL。`orchestrator_v21.py:509` 对整个 owners 集合做 Discovery；`normalize_agenda()` 接受集合内任意 owner；`_build():321` 又按同一个集合路由。这不是一个 prompt 问题：即使 agent 完全正确，GLOBAL 已经先被派了 Discovery；若 Planning 填 GLOBAL，宿主也会合法化并执行。

`RunnerV21.turn()` 只注入当前 phase 的技能，其机制本身合理。但由于错误调度，GLOBAL 先后获得 Discovery/Build 技能及相关历史文件，持续线程的业务认知被污染。现有 SDK 回归还以 GLOBAL 的 Discovery → Planning → Build 为正常路径，证明错误已进入测试预期。

**诊断：S0001 路由修复有效，但 owner 集合的职责边界仍错。必须分别表示“线程存在”与“可承担研究”。** 不能只在 prompt 告诉 GLOBAL 不研究，也不能只过滤首次 Discovery 而保留 Agenda/Build 漏口。

### 2.2 问题 2：材料交接仍没有完整的可读闭包

跨 owner Discovery 文件现已在 `_turn():200` 注入 Build/Integration，解决了部分 Lead 原句不可读。剩余主要机制如下。

| 场景 | 当前行为 | 后果 |
|---|---|---|
| 主 Review 跨批比较 | 当前批全文 + 全池路径/ID/标题索引 | 看得到其他对象存在，读不到其完整 Conditions/calibration，无法可靠判断重复与边界 |
| 补研参照原稿 | Build 没有显式传入 B、主 Review 及其映射；依赖本 owner 历史 | 跨 owner 或原路径未投影时，ref 存在但正文不存在 |
| 补研后复核 | 当前批全文 + B 的轻索引 + 累计 Review | 对照其他原稿/补稿仍依赖记忆，容易重复叙述缺口 |
| final_write | 当前批材料和部分 owner 历史 | 需要比较的其他版本、Result、已有候选缺少统一权威入口 |
| 源报告及路径 | manifest 的 available 主要表达源资产已取得 | agent 会将“当前 owner 原路径不存在”误读成源材料丢失 |
| 最终集合决策 | Consolidation 的 `review_frozen` 取 `run.review` | 新补研后复核已经改变处置，最终决策却收到主 Review 的旧决定 |

这里需要提供的是**已接纳、完整、正确版本的文件**，不是把 Review 加长或要求模型额外搜索。全池索引只供导航，不能作为跨稿判断的事实依据。上游 Q3/Q4 时点错位另需显式展示资产身份/时间，但本轮不重写上游，不生成未经来源验证的“最新事实快照”。已有 Build Result、研究说明及可追溯抓取成果可被后续节点复用。

### 2.3 问题 3：物理目录被切成过多串行调用

`policy_batches():49` 先按 wave 目录分组，然后在每个目录内部执行 20 条/128 KiB 切片；没有把多个目录合成一批。MU 的主审查 11 批、补研后复核 21 批、final_write 21 批因此并非业务需要。

本轮离线探针：6 个各含一稿的目录生成 **6 批**，预期新规则应为 **2 批**。文件可按需读取后，正文大小不再是把同一目录拆成很多模型请求的理由。

**决策：改成最多 5 个焦点目录一批，目录是调用组织单位，不再被解释为关系边界。** 不实现 Pilot 报告 §8.1 的小型关系组；跨目录关联由完整只读材料及编辑请求表达。

### 2.4 问题 4：引用被误当作实质影响

`orchestrator_v21.py:697` 将主 Review 全部 `relations.policies` 与补研 Topic 全部 `ref` 并入 affected，再加入所有补研稿。MU 因此把 23 主稿 + 15 补研稿全纳入 21 批复核。

`relations` 可以只是比较、覆盖讨论或建议；`ref` 可以只是参考材料。代码无法从这两个字段判断 B 是否真的需要变更。当前 Review 又只有 `relations / research_requests / coverage_notes`，缺少“已有依据、后续应编辑什么”的持久交接位置，导致直接修改被挤入补研，或只存在线程记忆中。

**决策：移除基于 relations/ref 的 affected 扩张。新补研稿作为复核焦点；确实要编辑的旧稿由 agent 写入最小 edit_requests。** 不新增语义 diff 分类或代码侧“实质改变”判断器。

### 2.5 问题 5：final_write 把确认保留也当成编辑任务

当前 `final_write:748` 有补研时沿用 affected，没有补研时取全部 B。这样即使只需 retain，也会调用模型并运行 Pilot 复盘。MU 的 21 批 final_write 仅得到 18 候选，若干批没有新稿。

`Consolidation:791` 已把补研接纳稿直接加入候选池，证明 final_write 不是补研稿进入最终交易的必经步骤。真正需要的是待编辑清单，而不是再次确认每份稿。

**决策：final_write 只调度有效 edit_requests；零请求则零 final_write。** 没有编辑请求不等于跳过集合决策，Consolidation 仍执行一次，明确保留、增加、替换、退休、覆盖和剩余缺口。

### 2.6 问题 6：后期时间差有多项可确认宿主成本，但不能全部归因

Pilot 补研后复核墙钟约 51 分 36 秒，研究+复盘累计约 32 分 25 秒；final_write 墙钟约 57 分 57 秒，累计约 22 分 55 秒。差值包含恢复、调度、文件操作及其他未单独计时窗口，**不能直接宣布这些分钟全部由某个哈希循环造成**。

已确认的代码成本：

- `_build()` 每 wave 先接纳一次，再在所有队列结束后遍历原始文件接纳一次，重复读取 run/draft ledger 和写入规范稿。
- `accept_policy()` 使用 `state.drafts(run_id).get(path)`，单对象查询变成全 ledger 反序列化；Runner 恢复每个历史路径也再次读取全 ledger。
- Runner 每个正常 Turn 都重建全部 owner 历史，并按 task key 复制 borrowed 正文、生成独立全量 context_index。
- 每 Turn 前后 `inventory()` 对整个 owner 目录递归读取 SHA；历史 attempt、审计、索引副本越多，成本越大。
- `_write_view()` 每 Turn 前后读取全 run/tasks/drafts，将包含全部 prepared 正文的 run 再写入 v21_state.json。
- Pilot `_protected()` 在研究后复盘前后将全部非 audit 文件读成内存字节字典。这个保护有必要，当前实现的重复复制成本没有必要。

**决策：先建立可归因计时，再同时落实单次接纳、稳定正文引用、增量装配、定点 ledger 查询和轻状态视图。** 不靠取消输入校验或移除 Pilot 复盘提速，不承诺未经实测的节省比例。

## 4. 合同与三类对象：实施时唯一口径

### 4.1 只新增最小编辑请求，不重做 Topic/Policy 合同

在 `schema_v21.py` 添加：

```python
class EditRequest(WorkModel):
    policies: list[Text] = Field(min_length=1)
    instruction: Text

class Review(WorkModel):
    relations: list[Relation]
    research_requests: list[Topic]
    edit_requests: list[EditRequest] = Field(default_factory=list)
    coverage_notes: str
```

`policies` 优先填 **已接纳稿规范 ref/path**，可包含多个对象；`instruction` 用一段文字记录要改什么、已有依据和预期处置。无需新增 priority、风险分数、证据证明字段、操作枚举、独立审批、状态机或编辑单 ID。

同改 `document3_v2.1_contracts.schema.json` 的 Review 定义和 EditRequest 定义，使设计合同与运行合同一致。新生成的 Review schema 展示该字段和空列表默认值，技术 task 要求 agent 显式输出 edit_requests（无编辑为 []）；不为了这个新增字段把历史 Review 变成全局接纳失败。保留 Topic 四字段和最终 PolicySet/Consolidation/MaintenancePatch 合同。

| 对象 | 表示方式 | 触发什么 | 不触发什么 |
|---|---|---|---|
| 参考材料 | task 中 policy_catalog/read_mapping；Topic.ref；relations 中讨论对象 | 按需读取完整正文 | 不生成补研 wave、post 复核批或 final_write |
| 待直接编辑 | Review.edit_requests | final_write 写完整候选稿 | 不开启补研；不立即覆写 B |
| 待补研 | Review.research_requests，沿用 Topic 四字段 | 唯一补研的 Shell/OPEN Build wave | ref 中所有 B 不自动变成待编辑或待复核 |

三类不是互斥的“Policy 类型”。A 可以既需要补研，又已有一项独立确定的编辑；这时分别记录，post Review 根据补研结果维护最终待编辑清单，不要求所有编辑都等待新证据才能成立。

### 4.2 累计 Review 与补研议程的权威性

主审查各批接续前一份已接纳 Review，返回的是**累计**对象。最后一份健康累计 Review 为主审查权威；失败批保留此前健康累计值，并记录该批未审，不读取工作区遗留 review.json 假装本批成功。

待补研 Topic 的内容和 owner **只来自累计 Review.research_requests**。为了兼容现有 `supplement_agenda.json` 输出，可继续接受其中 waves 排序/组合，但它不能新增或覆盖 Review 中的 Topic。按 Topic 名称精确映射，未知项诊断后忽略，遗漏项按既有 max 3/同 owner 规则补齐；没有健康议程文件时由宿主结构化构造默认 waves。不增加一个补研 Planning 调用。

补研派发前持久化并冻结 Agenda/hash/一次性标志。post Review 的 research_requests 表示补研后仍未解决的问题，**不能再次触发研究**，最终进入 remaining_gaps。已派出的原始请求保留在冻结补研 Agenda，不需要另加研究请求状态字段。

post Review 沿用主 Review 已确定编辑并根据新材料更新。以最新健康累计 Review 为 pending 清单权威：显式 [] 可以表示编辑决定已撤销或不再需要；宿主不追加已经撤销的旧指令。仅对历史/兼容载荷“字段缺失”保留此前 edit_requests；不要先用模型默认 [] 抹掉“缺失”和“主动清空”的区别。累计请求重复以规范化值去重，不根据相似文字做语义合并。

`effective_review = post_supplement_review（若存在健康累计值）else main_review`。final_write 和 Consolidation 必须读取同一 effective_review。

### 4.3 路径和身份解析

编辑目标可使用完整 ref/path；兼容 Policy ID 时，仅唯一匹配才能自动解析。如果 B 和补研稿沿用了同一 Policy ID，不得随便选最后一个文件：要求 agent 指定 path，记录局部歧义并保留其他健康编辑请求。缺失/越界目标只降级该请求，不阻塞全部编辑。

源 ref/path 是跨任务身份；owner local_path 是物理读取入口。不得把借入的内容哈希文件名写成业务 ref，不得靠标题解析对象身份。多版本同 ID 可以在只读材料池共存，不能在索引构造时按 ID 去重而丢旧稿。

## 5. GLOBAL 职责与 owner 路由改造

修改 `inputs_v21.py / validation_v21.py / orchestrator_v21.py / runner_v21.py`。

1. `topology.owners` 保留全部线程的兼容清单；新增 `research_owners`，仅 Shell 槽位和 OPEN。route_aliases 继续映射 Shell 合法别名。
2. INITIALIZE Discovery 只遍历 research_owners。GLOBAL 第一个业务调用应是 Planning；不为 GLOBAL 生成 Lead 文件。
3. normalize_agenda 接收 research_owners，不再把 GLOBAL 当合法研究槽位。无效 owner（包括裸 GLOBAL）按冻结需求退至 OPEN并记录诊断；实际 Shell 与保留名冲突时使用限定别名，不把 GLOBAL 协调线程伪装为 Shell。
4. `_build()` 只查研究路由。入口再次进行轻量 owner/phase 校验，防止旧 Agenda 或绕过归一化的调用把 GLOBAL 派进研究。
5. Runner 在文件物化/Worker 请求前验证 owner 与 phase：GLOBAL 允许 planning/integration；research_owners 允许 discovery/build；既有 MAINTAIN 专属调用保持 maintain。校验失败为该错误任务的调度错误，不污染线程再等待模型纠正。
6. GLOBAL 仅注入 role/common、当前 Planning 或 Integration skill；phase 切换仍可保留它先前合法协调阶段资产。Shell/OPEN 不注入 Planning/Integration skill。schema 文件属于合同参考，不等同于将全部阶段业务 skill 注入。
7. 技术 task 明示 allowed_research_owners、别名与 owner_shell。继续保留不同 owner 并发、同 owner 串行及现有 concurrency 上限，不新增全局 wave barrier。

不能从已污染的旧 GLOBAL thread 删除一个文件就声称心智修复。新验收 Pilot 必须新 run/新线程；旧 MU 研究和回执全部保留作为证据，不把 GLOBAL 旧研究重命名 OPEN 冒充新拓扑结果。

## 6. 全文只读参考池与上下文投影

### 6.1 紧贴当前文件/ledger 实现，不新建业务资料服务

在 Orchestrator 内增加小型 helper：`policy_reference_context(run_id, stage)`。从已接纳 ledger/checkpoint 取得规范 Policy、Result 和权威 Review，生成参考文件清单及目录导航。Runner 承接内容哈希稳定物化，不按每个 batch 再复制一遍。

每条 Policy 索引至少含：`ref / local_path / policy_id / title / sha256 / source_round / source_directory`。同一 source_ref 原稿与规范稿的含义必须明确：agent 业务比较读取**宿主已接纳规范稿**；原始 task 输出/SDK snapshot 另存审计，不替换原始证据。JSON 保留完整 transmission/match_scope/ref/所有 activation_conditions 和 calibration，不能只输出节选。

所有可读取 canonical ref 都有 read_mapping。policy_catalog 的 local_path 必须是该 owner 工作区实际存在的文件，不能是别的 owner 绝对路径或仅 root workspace 路径。可以用 `context/.../references/<content_hash>.json` 稳定保存 Policy 全文；沿用现有 borrowed 机制也必须使索引与实际入口一致。哈希对应规范 JSON 内容，source Directory 则沿用原稿 wave，不以内容哈希目录决定批次。

### 6.2 各阶段材料集合

| 阶段 | 当前重点 | 必须可读的只读参考 |
|---|---|---|
| Planning | 本批 Lead 和累计 Agenda | 全部健康 Discovery 文件、冻结原始上游、manifest/D2 引导 |
| 主 Build | 当前 wave Topics | 全部健康 Discovery、上游原件；Topic refs 的实际映射；历史 PolicySet 如存在 |
| Integration 主审查 | 当前 5 目录的 B | **本轮全部已接纳 B 完整 JSON**、全部主 Result、累计 Review、主 Agenda、共同上游 |
| 补研 Build | 本 wave research_requests | 全部 B 完整 JSON、主 Review、主 Result、Discovery/上游；尚未生成的补研稿不假装存在 |
| post Review | 当前 5 目录的新补研接纳稿 | 全部 B + 全部补研完整 JSON、两轮 Result、主/累计 post Review |
| final_write | 分配到本批的 edit_requests | 全部 B + 补研 + 已接纳 final 候选、对应 Result、effective_review |
| Consolidation | 一次最终集合交易 | B、全部健康补研/final 候选、effective_review、两轮 Agenda/Result、缺口和局部失败收据 |

`batch/focus_directories` 只限制当前应作出交付的焦点，不限制只读视野。主审查第一次调用前，即完成 GLOBAL 的全 B 物化与路径验证；后续批复用。跨批覆盖、合并、重复、边界判断必须读取相关全文，不增模型/研究调用，不把全部正文内联进 SDK prompt。

### 6.3 可用性与源信息

分开记录 source availability 与 owner projection 状态：源已取得、缺失、未配置、截止后不可用；投影位置、投影失败及内容 hash。源码中报告 artifact 取得失败时要有局部 manifest/diagnostic，不只保留一句无对象 warning；空文件保留真实 bytes/状态，不一概写成“缺失”。Event 为空与未配置尤其要区分。

不是每个历史 citation 都有本地存档。只保证**已提供材料集合**的完整正文可读；外部 URL/未随源资产交付的引用要标明可外查/当前无存档，不伪造闭包。引用不存在只影响该对象的判断与 gap，不构造全局失败门禁。上游 manifest 原字节和冻结哈希保持原样，新投影描述另存派生导航。

## 7. Integration 调度：5 目录、一次补研、按需编辑

### 7.1 目录计数与确定顺序

改写 `policy_batches()` 或替换为 `directory_batches(items, directories_per_batch=5)`：

- 规范 `.../<wave>/policies/*.json` 的目录归属为 `<wave>`；已接纳顶层 Policy 归该 wave，不因路径风格再拆目录。
- 按冻结 Agenda 的 wave ordinal、owner 槽位和源 path 稳定排序，不依赖数据库返回顺序或 set 遍历。
- 每批最多 5 个焦点目录，每个目录的焦点对象保留完整，不再使用 20 Policy/128 KiB 把该目录分成额外模型调用。
- 大材料仍通过索引和分页读取，不用 prompt 全量内联解决。末批可以不足 5 个目录。
- 主 B 为空但存在待汇总 Topic/缺口时保留一次空焦点主 Review，用于形成 Review/gaps；post/final 无工作则零批，不能由通用 `[[]]` 默认制造确认调用。

### 7.2 新调度顺序

```text
Shell/OPEN Discovery → GLOBAL Planning → Shell/OPEN Build → 冻结 B
→ GLOBAL 主 Review（B 焦点目录，5 个一批，全 B 只读）
→ 从累计 Review 冻结补研 Agenda → Shell/OPEN 唯一补研
→ GLOBAL post Review（仅新补研目录，5 个一批，B+补研全可读）
→ 解析 effective_review.edit_requests
→ GLOBAL final_write（有待编辑才调用，5 个编辑归属目录一批）
→ GLOBAL Consolidation 一次 → 宿主结构替换 → staged F
```

不再生成“relations/ref 扩张后受影响池”。已有运行视图若保留 affected_paths 字段，改作兼容展示，不能继续用它驱动调度；新视图显式展示 `post_review_focus / pending_edit_targets / reference_count / pending_research_topics`。

### 7.3 A/B 场景的精确处理

1. 补研 A 要参考 B：research_request.ref 指向 A/B，两份全文可读；B 不新增 post 重点批、不自动进入 final。
2. A 补研确认原边界成立：post Review 记录判断，健康 A 进入候选池；B retain，无需 final。
3. A 补研实质改变 B 边界或 A/B 重复：post Review 显式新增 edit_request，policies 指向确实要处理的稿，instruction 说明合并/修改依据；final 处理一次，Consolidation 显式交易。
4. B 已有材料足以修正：主 Review 直接写 edit_request，research_requests 不为此添一项；没有其他补研也照常 final 改 B。
5. 仅补研不足以闭合：post Review 记 remaining request/gap，不再补研，不为“确认仍未知”调用 final。保留健康 B，不把未决问题悄悄改写成 COMPLETE。

### 7.4 编辑请求分批与跨目录合并

编辑请求的首个合法目标 path 是调度归属，其 wave 目录为 anchor。按最多 5 个 anchor 目录组批，**同一个编辑请求只派一次**；其余 targets 作为这次请求必须处理的关联全文，即使来自其他目录，也不因此再跑一批。task 明示本批 edit_requests、focus_directories、related_targets、只读参考索引和允许的候选输出前缀。

这个规则解决“合并 A/B 跨目录时各批都重复写一个合并稿”的问题，不需要关系图或强行把全池连成组件。其他独立请求仍按它自己的 anchor 派发；后批可读取前批已接纳候选。累计请求应由 GLOBAL 避免矛盾，宿主仅对完全相同请求去重，不凭语义判断哪个编辑正确。

纯退休/保留决定可直接由 relations/coverage 支撑 Consolidation 的 replacements，无需先写一份没变化的 Policy；只有需要完整新候选才记录 edit_request。新补研健康稿可直接选择，不能要求每条补研输出在 final 又生成一份。

### 7.5 最终候选与交易

候选池 = 健康补研接纳稿 + 健康 final 接纳稿；B 默认保留，但候选不自动进入 F。Consolidation 的 `before` 仍解析 B 中 Policy ID，`after` 指向健康候选路径；保留现有交易结构和局部失败规则。

final 不改 B 原件、不写部分 JSON Patch。需要继承既有身份时查完整主 B/补研/历史 PolicySet；规范化 ID 后发布到候选参考池。改写无效应留下可定位诊断和未完成编辑，不把 accept_policy 返回的旧稿 fallback 伪装成本次编辑已经完成。

main/post/final/Consolidation 读取本次 task 的已接纳输出/snapshot，**禁止以共享当前路径的旧文件充当失败新批输出**。支持累计值保全，但来源 task_key/hash 必须清楚。Consolidation 使用 effective_review 以及最新候选索引，修复当前主 Review 回退错误。

## 8. 文件接纳、ID 与有限恢复的整合修复

### 8.1 一次 wave 接纳

先解析所有认可的 Result 文件名（results.jsonl、result.jsonl、result.json、results.json），逐条结构接纳。健康重复记录按 canonical 值去重；同 Topic 真冲突只标记该 Topic，不覆盖健康其他 Topic；首选文件损坏不会阻断备用文件的健康记录。JSONL 坏行保持局部隔离。

统一 inheritance map，传入完整 Policy；只在来源明确时沿用 Policy/Condition ID。保留既有 null/new ID 分配和逐 Condition 局部保全，不新增语义相似性 ID 推断。补研接纳、final 接纳、重放采用同一入口。

### 8.2 Pilot Planning 恢复

- 成功 Planning task 不重跑；重建累计 Agenda 时从它的接受快照恢复，下一失败批继续。宿主保存最新健康累计值，不使用失败遗留当前文件。

不用通用修复服务、无限自动重试、清空 owner 或改冻结上游。旧 MU run 已完成，不对它实施新拓扑回滚；其历史错误保留。

## 10. 性能改造：可测量、增量、保留完整性

### 10.1 必须记录的执行时间
