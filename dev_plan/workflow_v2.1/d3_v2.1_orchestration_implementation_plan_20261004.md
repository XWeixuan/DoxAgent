## 4. 入口、版本和隔离

### 4.1 版本冻结

```text
入口 orchestration_version：v2（默认） / v2.1（显式）
Published v3 schema_version：document3.v3
Published v3 workflow_version：document3.v2.1
通用 Worker workflow_version：codex_document3_v1（保留）
ResearchLane：DOCUMENT3（保留）
Projection：document3.runtime_projection.v5
Projection consumer_contract：persistent-runtime.v2.condition-policy.v1
publication target：staged（V21 本轮唯一提交目标）
```

v5/consumer_contract 是本文规定的输出接口版本，不表示已有 consumer 支持它。旧 Projection v4 和旧 consumer 的升级/缓存逻辑不改；新版生成函数也不调用旧 `assert_runtime_projection_compatible` 来判断 v5。

### 4.2 显式接口

service builder 增加 `orchestration_version="v2"`；V21 返回新 orchestrator。旧调用不传新参数，行为不变。

新 INITIALIZE 接口至少接受：ticker、as_of、run_id、document2_run_id（可空）、source_global_run_id（可空）、event_library_version（可空）、additional_materials（冻结文件描述列表）、node_assets（可空的外部资产绑定）。

新 MAINTAIN 接口至少接受：ticker、as_of、run_id、base_policy_set_version、maintenance_feed/其冻结文件、event_library_version（可空）、node_assets。base 必须显式指向 staged v3；不从旧 current 猜测新版基线。

CLI 增加 `--orchestration-version v2.1`、`--as-of`、`--source-global-run-id`、`--base-policy-set-version`、`--materials-manifest`、`--node-assets-manifest`。document2_run_id 对旧入口仍必需，对新入口可空。V21 不提供 active/promotion 开关。

示意命令（资产就绪后的显式入口，本轮不执行真实模型）：

```powershell
uv run python -m doxagent.workflows.codex_document3.cli initialize --orchestration-version v2.1 --ticker MU --document2-run-id <published-d2-v21-run> --as-of 2026-10-04T00:00:00Z --node-assets-manifest <later-assets.json>
uv run python -m doxagent.workflows.codex_document3.cli maintain --orchestration-version v2.1 --ticker MU --base-policy-set-version <staged-v3-version> --as-of 2026-10-04T08:00:00Z --node-assets-manifest <later-assets.json>
```

### 4.3 run 绑定

V21 Pinned run_id 采用独立 `d3v21-` 前缀，哈希输入包括 ticker、orchestration_version、schema_version、UTC as_of、明确的上游 run/版本及额外材料清单摘要。已有旧 Pinned 哈希不改。

随机 run 的第一次 PREPARE 固定输入身份；重入时核对 run/ticker/mode/version/as_of/上游与材料绑定，之后只恢复冻结文件。`force_new` 若日后提供，必须创建新 run，不覆盖不相容旧 run。

不得因为 root run 已保存四文件就先返回“完成”；先查 staged commit receipt，验证同版摘要和实际 staged 对象，再返回或补全未完成的发布步骤。

## 5. 新业务合同与 schema 构造

### 5.1 附件原结构直接落模型

`schema_v21.py` 为附件每个 definition 定义对应模型：Lead、Topic、NotSelected、Agenda、ResearchResult、Relation、Review、Replacement、Coverage、RemainingGap、Consolidation、Calibration、ConditionDraft/Condition、PolicyDraft/Policy、PolicySet。

Published 数据字段维持附件：Policy 中没有 decision/source_refs；Condition 有 decision、trigger_layer、criterion、calibration；PolicySet 有 as_of、workflow_version、可空 D2/Event 快照对象。ref 缺失落为空数组，不能用空串、假 URL 或假 Gap 引用填满。

工作输入忽略并记录无害额外注解；Published 输出只序列化正式字段。读取时先识别可读部分，再构造最小正式对象；禁止对整个 scan/results/PolicySet 做一次 strict validate 后丢掉全部同级记录。

草稿 ID 初次可以缺失。Published ID 必需且唯一。Schema 只保证字段类型与可执行结构，不附加投资语义规则。

### 5.2 Worker 返回与工作文件分开

Worker final_response 使用小型技术 receipt（如 completed、notes），只用于审计；业务产物由工作文件决定。schema 描述仅解释字段、读写路径和交付位置，不写新的研究方法。

工作文件 JSON Schema 从新版模型产生，放入 run context。Responses 的 strict schema 只作用于小型 receipt；无需把全部 Policy/Agenda 塞进模型 final_response。

### 5.3 两个明确的工程扩展

1. `ConsolidationV21` 增加可选 `publish_empty: bool=false`：仅表达空集替换的明确提交意图。非空集合不要求该字段；它不添加投资分类。失败空集不能由 COMPLETE 文案自动推导为允许清空旧活动集。本轮记录该意图，但不执行活动切换。
2. 单节点维护定义 `PolicyPatchSetV21`，见第 14 节。附件未给维护 patch，需在 runtime model 中补齐，不覆盖用户附件。

其他计数、阅读进度、分配表、重试次数都属于宿主状态或 Pilot 投影，不加到 Agent 业务文件里。

内部另定义 `RunResultV21` 与 `StagedHandoffV21`：返回mode、业务完成状态、run_id、policy_set_version、staged标记、四文件/manifest定位和缺项摘要。缺产物/未提交时version可空；NOOP返回base版本。它们不冒充旧Document3Bundle的活动published handoff，root真值由V21 run/commit状态读取，通用NodeAttempt/ThreadRecord继续用于执行审计。

## 6. 输入冻结和材料取得

### 6.1 D2

新版正式入口优先读取 `document2.v2.1`。按 Published 元数据取得原始 bytes并核对 ticker/size/hash；这是身份完整性检查，不是研究成熟度检查。源 snapshot 不完整时，局部 Shell/Unit 按原始记录切片并报告缺项，不能因某条业务记录坏而丢掉其他 Shell。

不把 v2 文档机械补字段变成新 D2。V21 如显式收到旧 v2 D2，将其保留为完整、标注原版本的共享历史材料；不把旧 core_question/proposition/possible_occurrence伪装成新版语义。没有正式 v2.1 Shell 时，OPEN/GLOBAL 路线仍可执行，并报告 topology 不可用。

保留 State/Baseline/Factors/Gaps 原文；baseline 可空；不生成 Gap coverage denominator。Discovery/selection/resolution sidecar默认不注入。显式提供时只按过程材料标注，不能当正式现实/传导结论。

### 6.2 D1 与共享材料

source_global_run_id 显式给定时优先使用；未给且有正式 D2时，从其 source_global_run_id继承。读取实际 GlobalResearchBundle、PublishedDocument/Artifact 原文：所有可用报告、Future Nodes、Entity Map/Relations、已取得的实体/事件/外部材料和 Reference View完整落盘。

参考 D2 input loader的读取与校验代码，但不调用其整个 `load()`：该函数要求 C1/C3/C5齐全并会查询 optional providers，不符合本轮局部可用及不重查冻结输入的要求。D3仅复用必要读取方法/小型工具，不修改 D2 loader行为。

additional_materials 只接纳调用者明确提供的现有文件/Published artifact描述，包括通用催化等；没有配置或没有对象就记录 NOT_CONFIGURED/ABSENT。宿主不为“完整材料层”自行发起额外 Narrative/Web/数据研究，也不制造占位研究。

### 6.3 时间

as_of 一次固定为有时区的 UTC timestamp；拒绝含糊的无时区时间参数。每项材料另存 source_run_id、artifact/版本、hash、原始业务 as_of和 published_at（可空）。Published时间可晚于研究cutoff，不能据此擅自抬高cutoff；明确业务信息晚于cutoff的材料标为不可用于本轮。Event未指定版本时只接纳可确认符合截止的快照，不能悄悄读取更新head。

冻结后所有恢复/Pilot延续都从 run目录取得原文，不再调用 provider。材料可选且缺失不阻断业务；已明确取得的冻结 bytes发生hash冲突则为完整性故障，不能伪装成ABSENT。

### 6.4 三层投影

- topology：Shell/Unit名称、scope、boundary/horizon、基本公司简介及资产目录，不含全D2正文。
- current研究：完整Shell；需要收窄时完整Unit＋Shell头＋sibling目录。禁止拆Unit内部四类研究资产。
- shared：非D2材料完整原文，全部节点可读取同一组版本；task.json只列定位，不要求每turn自动全文内联。

完整单条Policy和Condition不截断。若一条记录已超过装载参考预算，单独成批并保留完整文件，不剪掉calibration。

## 7. 工作区与 owner 会话

### 7.1 复用现有工作区类别

```text
主 run
  context/document3/v21/
    task.json / input_manifest.json / topology.json
    d2/shell-0001.json ...
    shared/...                         # 完整冻结材料
    schemas/...                        # 宿主产生
  output/work/v21/
    discovery/<owner_slot>.jsonl
    discovery/<owner_slot>.late.jsonl
    agenda.json
    research/<owner_slot>/<wave>/results.jsonl + policies/*.json
    review.json
    supplement_agenda.json
    supplement/<owner_slot>/<wave>/...
    final/policies/*.json
    consolidation.json
  artifacts/document3/checkpoints/...  # 宿主接纳快照、主池索引、ref位置映射
  output/final/...                     # 四文件展示副本
  artifacts/document3/releases/<version>/... # 四文件正式版本
```

相对ref统一以主run为根。原方案中的inputs/work/output映射到现有context/output/work/artifacts，不改 Worker顶层规则。主run的业务输入不可改，发布API仍只发布artifacts文件。

### 7.2 每个 owner 一个工作区

用现有 `workspace_run_id` 与 `persistence_run_id` 分离模式：主run存事实与耐久记录；Shell各自一个owner工作区，OPEN一个，GLOBAL一个。owner工作区ID从主run身份与slot生成，不使用任意经济名称拼路径。仍是N+2逻辑会话，不创建逐Policy/逐Topic线程。

每个工作区只接纳该owner当前任务的输出到主run。输入、他人Policy、已冻结Agenda/B和先前交接副本只读；对它们的本地改写不被接纳。源文件名可以保持规范root相对路径，存在物理路径差异的借阅材料用task中的 `{ref, local_path}` 映射指明，不修改其业务来源含义。

task结束后宿主：读取允许目录 → 局部解析 → 分配身份 → 保存主run接纳快照 → 保存任务终态。更新后的已分配ID工作副本回填owner，供后续任务使用。主run不供研究Agent直接写入。

这样可复用 `(owner_workspace_run_id, O3 role)` 的ThreadRecord，避免扩展agent_role为任意Shell名或修改所有通用thread表。owner工作区与thread_id关联可从ThreadRecord取得，run状态只持久化owner槽位与工作区位置，不重复存第二套会话真值。

### 7.3 路由

业务Topic.owner仍用实际Shell名称或OPEN；内部slot为`shell-0001`/`open`/`global`。遇到Shell同名或名称等于OPEN，拓扑目录同时公开可区分的路由别名，原name/scope保留；歧义owner不由代码猜经济归属，送OPEN并报告。正常唯一Shell直接按原名路由。

同一owner加async锁，任何时刻一个turn；任务之间沿用session。thread_resume明确不可用时，下次有限技术尝试开新session并重装该任务文件，不新增总结Agent。

## 8. 单一宿主状态与恢复主键

`state_v21.py` 沿用同一个SQLite设施，增加三张小表，不把整个业务稿塞进数据库：

| 表 | 内容 |
| --- | --- |
| `codex_document3_v21_runs` | root run身份、mode/as_of、phase、owner工作区定位、冻结agenda位置/hash、主池位置/hash、supplement_dispatched、最近review/consolidation/commit receipt位置 |
| `codex_document3_v21_tasks` | `(run_id,phase,round,owner_slot,ordinal)` 主键；status、attempt_count、worker job/attempt位置、接纳manifest位置、有限错误摘要 |
| `codex_document3_v21_draft_ids` | `(run_id,canonical_policy_path)` 的首次policy_id与条件分配记录、最后接纳snapshot；不存经济匹配键 |

所有更新在短事务中完成，网络/Worker调用不持数据库锁。通用NodeAttempt继续存执行审计；不能用其“节点全局attempt_number”替代每任务总预算。Generic WorkflowCheckpoint如需展示，仅由这里的阶段状态派生，不再独立决定wave是否完成。

任务status采用内部PENDING/RUNNING/COMPLETED/PARTIAL/FAILED/CANCELLED；不进入Policy业务schema。attempt_id包含完整task主键摘要＋attempt序号，防止不同owner同节点碰撞。

恢复先核对输入及已接纳snapshot，再看任务：终态不重新dispatch；已接纳文件不重新分配ID。RUNNING且Worker已有耐久完成receipt时先接纳其文件；没有完成receipt的中断任务才在剩余预算内续跑同目录。同一任务最多两次技术尝试，恢复不会重置计数。

已完成产物丢失/污染时，从宿主接纳snapshot恢复；连snapshot也坏则记录完整性错误，不能重跑终态任务冒充原成果。局部未成功产物不影响其他owner。

## 9. Discovery、Planning与主研究调度

### 9.1 Discovery

新增节点值：`d3_o3_discovery`、`d3_o3_global_planning`、`d3_o3_research_build`、`d3_o3_global_integration`。旧枚举值保留，新路径不调用它们；MAINTAIN仍为一个维护节点。

冻结N＋OPEN个Discovery任务，按max_parallel_owners调度。每个owner写Lead JSONL；不预创建空业务产物作为“完成证据”。逐行读取坏行隔离，可读行完整保留。空文件可以表示已完成且无发现；不存在文件表示缺产物。

第一次接纳的初始scan保存immutable snapshot。后续新线索写`.late.jsonl`，同Lead模型；宿主不把它们自动排进当前主Agenda。失败owner终态后其他任务继续，GLOBAL看到其具体缺项。

scan/results的规范源文件保留原始行序、空行和坏行；`#L<n>`始终指向该原文行号。宿主解析视图记录原行号，不把过滤坏行后的新顺序写回同一路径。late采用单独文件并在接纳时保存版本snapshot，已引用的历史行不因后续追加或恢复被重编号。

### 9.2 Planning

等全部Discovery任务终态后才dispatch。按owner扫描批次读取并累计Agenda草稿，最后一次全局选题/整理完成才冻结可调度Agenda。

分批数量由输入bytes与owner边界确定并在Planning开始固定；不是每读一个owner就启动Build。若小规模一次可读，只有一次Planning turn。正常Planning结果先做局部结构修正，冻结结果及宿主调度队列同一次状态提交。

选题内容不由宿主生成；允许Topic承接多个Lead，允许OPEN和Shell互相分配。Lead未被交代只提醒；不自动升级为Topic。

具体修正：

1. 重复wave引用同Topic，保留首次有效调度。
2. 所选Topic漏排，按其owner加队尾，默认每组3个。
3. wave混owner，按既有owner拆队列且保持相对次序。
4. owner不存在/歧义，送OPEN并报告。
5. wave引用不存在Topic，隔离该引用，不创建Topic。
6. Topic同名且内容完全相同，可去掉字节等同重复；同名不同内容则隔离该歧义Topic及其引用，交GLOBAL可见缺项，不偷偷择一或合并经济含义。

Planning失败使用最近可读草稿完成上述修正；连草稿也没有则冻结空Agenda、保留全部scan进入Integration，仍只有一次补研机会。不得因此启用一套代码选题fallback。

### 9.3 Research & Build

从冻结Agenda分出owner队列；每个owner按其wave顺序运行，不同owner并行。同owner完成wave1立即可跑wave2，无全局wave序号栅栏。

每wave一个业务turn，交付results JSONL与独立Policy drafts。每Topic一条结果；policies为空合法，notes保留结论/局限供GLOBAL处理。results缺行或Policy缺文件均按实际缺项记录，仍接纳同wave其他完整成果。

完成的Policy/Topic在turn内先保存是文件checkpoint，不产生额外评审turn。晚发现只记late；技术失败最多一次额外尝试，业务unresolved/诊断不重试，不无限续wave。

默认参数：topics_per_wave=3、max_parallel_owners=3。前者只用于漏排补队和分组参考，不是拒收Planning合理并组的硬门槛。

## 10. Integration、唯一补研和最终收敛

### 10.1 主池 B 与完整读取

所有主Build任务终态后，将实际可读取主稿冻结为B，包含完整JSON和宿主索引；孤立可读Policy也保留，但Topic结果缺失仍可导致PARTIAL。原工作稿与接纳snapshot都保留。

轻索引直接从稿件投影policy_id/title/transmission/match_scope、Condition的id/decision/layer/criterion及文件位置，不由模型另写摘要取代事实。

默认同owner/wave成批，每批最多20条Policy、序列化正文参考上限128 KiB；超过就减小批次，超大的单条独立成批且不截断。装载参考128 KiB同样用于Planning分批。所有批次列表在阶段开始冻结，防止恢复后重切导致重复阅读。

GLOBAL每批读取完整Policy，包括calibration，写累计review。借阅其他Policy从完整文件取得。批次结束接纳最近可读review快照；某批失败保留既有记录并结束该批，其余批继续，未完成全局整合标PARTIAL。

### 10.2 唯一补研

主池扫描结束后，GLOBAL在Integration内将research_requests收敛成supplement_agenda；不重跑Discovery/Planning链。最后一个扫描turn可完成这个工作，避免强制额外空turn。

在分发第一项之前：先保存冻结计划与hash，再以事务持久化`supplement_dispatched=true`和位置。标记一旦成立永不自动回退。若写标记后崩溃，恢复继续这份计划尚未dispatch/尚未终态的任务。

有请求但无可读supplement计划：记录缺项，不让代码依据review自动进行业务选题。本轮可以零补研，不因“必须有一次机会”强制创建任务。

补研沿用Build，独立目录，同owner串行，不能改B；计划冻结后不接受新任务。补研中出现新方向进入remaining_gaps。没有第二份supplement计划，也不回到主轮加wave。

### 10.3 增量整合与最终写稿

补研结束后仅展开新增产物、明确引用的受影响B稿和已有待判关系；保留整池轻索引。关系引用可帮助定位，代码不作传递闭包式业务merge。

GLOBAL可按受影响组分批写final drafts，最后写一次consolidation。待写组在该子阶段开始固定，写稿不递归生成新研究任务。这个过程仍属Integration，不新增Compile/审计节点。

分批任务由实际已有的有限review记录、补研结果和待比较稿件定位构成；宿主只分装读取材料，不从关系记录自动生成merge组。小规模一次finalization turn即可写稿与清单；大规模先按冻结材料批次写候选稿，最后一次同节点turn只收敛最终替换/coverage清单。无需另造模型输出的final_task_plan业务台账。

无consolidation时F=B，覆盖状态仅报告真实调度/结果，不宣称全局去重和覆盖已完成；有最近可读consolidation则局部解析与应用，坏记录隔离。

## 11. ID、Condition隔离和集合替换算法

### 11.1 ID分配

policy_id在宿主第一次接受文件时分配，生成UUID并在同一SQLite事务保存路径映射；重试/恢复只读映射，ID不由title、direction、ref、criterion或calibration哈希生成。已有有效映射后文件重写保持policy_id；另一文件显式继承某旧ID时必须在最终替换/维护上下文里能证明该旧对象存在。

初稿缺condition_id时分配C1/C2…；已有Condition更新需带回宿主已分配ID。新Condition缺ID可从该Policy曾分配最大序号后分配；不按criterion或数组顺序猜测既有Condition身份。已接纳文件的ID可从工作副本与snapshot读回。

在首次接纳后，若整份改写丢失全部旧Condition ID而无法表达身份连续性，保留上个可读版本并记结构缺项；不把“重新按文本匹配”当修复。完整upsert明确省略旧Condition则是移除操作，不等于代码机械消费它。

合并由GLOBAL显式选择保留一个旧policy_id或省略以取新ID；拆分最多一个新文件继承一个旧ID，其余新分配。主/补/最终稿可暂时存在候选ID重叠，不能因此在工作期丢稿；最终F必须唯一。

### 11.2 局部读取

先读取Policy顶层必要文本，再逐Condition校验decision/layer/criterion/reference_state/trigger_boundary；坏Condition隔离，至少一个完整Condition即可接纳Policy。不能补LONG、猜boundary或把缺baseline变成默认现实。

重复Condition ID且内容相同保留一份；相同ID不同内容不任意择一，隔离该冲突ID的全部候选，其他Condition继续。重复policy_id冲突在最终集合/替换组处理；错误稿保留原文、定位和原因。

### 11.3 replacements两阶段提交

输入B、所有可读候选文件、consolidation.replacements：

1. 解析每条before/after，before仅可指向B中的主稿；after仅可指向当前run已接纳候选文件。
2. 在应用前一次找出before重叠、跨组after路径/最终ID冲突；冲突相关组全部失效，不按列表顺序裁决。
3. 每组检查before可定位、after完整可读取、最终身份与保留稿不冲突。任何一项不成立整组不执行。
4. 基于全部成功组计算F；未被成功替换B稿保留，补研/最终稿未进入after不加入F。
5. 保存规范化执行清单摘要与F快照，再提交assembly状态；恢复按该快照补后续发布，不重复执行替换。

如果新发现冲突使某组退回、原before恢复后又与其他组after撞ID，则将这些关联冲突组一起撤回，直至没有新的结构冲突；这是有限的集合一致性计算，不是经济merge、研究循环或另一次Agent修复。

before/after均空只记无作用记录，不触发操作。after为空可移除；before为空可新增。合法单独组失败不影响其他独立组。

## 12. Coverage与发布状态

coverage_map从最终consolidation.coverage/remaining_gaps/summary＋实际任务缺项生成。记录Topic去向而非旧Gap数量闭环，文件定位解析成F中的正式ID；已被替换的路径不再被默认为仍在F。无法解析的coverage映射保留缺项，不编造覆盖。

宿主可以给GLOBAL事实性初始去向；最终语义覆盖由GLOBAL确认。host不分析notes/summary关键词判断投资意义。

COMPLETE的结构条件：必需任务进入可接受完成状态、每个主/补Topic有结果与最终coverage处置、最终整合有可读结论、没有实际未解决缺口/丢失可执行产物/替换冲突。result空Policy＋coverage空Policy＋GLOBAL未留该Topic缺口可以正常闭合。Agent写PASSED/COMPLETED不替代这些事实。

PARTIAL的事实条件：缺任务/文件/结果、不可执行遗漏、全局整合未完成、替换冲突或remaining_gaps。某研究方向/layer缺失、ref暂不可读、候选未选等提示不单独改成PARTIAL，也不自动重试。

初稿文件损坏造成实质遗漏可标PARTIAL；研究后主动移除无效候选且有最终处置，不因历史坏候选原文仍存在永远PARTIAL。没有最终结论时不能靠宿主补默认“研究不成立”关闭Topic。

## 13. 四输出、Projection与staged提交

### 13.1 Projection v5

由F唯一生成，头部携带ticker、policy_set_version、as_of、Published时间及新schema/consumer合同。

```text
每条Policy索引：policy_id、title、match_scope、transmission
每条Condition：condition_id、decision、trigger_layer、criterion、完整calibration、condition_revision
```

condition_revision为宿主对该条件执行字段（decision、trigger_layer、criterion、完整calibration）的规范序列化摘要。它是Projection技术字段，不进入附件Published Condition；不参与稳定ID。未修改条件revision保持不变，另一条件重校准不改变它。修改ref/title本身不机械重新开放交易入口。

本轮只验证纯投影中的完整字段、条件身份和revision独立性。后续R1可取中性索引，R2可取完整条件；本轮不调用或改写它们，也不实现condition claim、排序或最终交易选择。

### 13.2 本地staged存储

在D3 repository增加 `save_staged_v3(run_id, policy_set, projection, release_manifest)`、`get_staged_v3(ticker,version)`、`get_staged_v3_by_run(run_id)`。InMemory测试与SQLite正式staged实现同合同。

SQLite用一张专属 `codex_document3_v21_staged_sets` 表保存ticker/version/run_id、主JSON/Projection及四输出摘要/正式位置；唯一约束run_id及ticker/version。复用现有version reservation；预留版本参与统一递增，因此旧正常发布可按既有规则跨过已预留序号。允许版本有间隔，不追求连续。

首次预留以本地已有版本/所有预留、显式base版本、读取到的现有活动版本为下界取max＋1；该下界随run身份冻结。旧 `reserve_version` 默认行为不改，新staged预留方法可复用其事务实现并传入下界。远端正式版本若以后并发增长，由后续正式启用的base CAS处理；本轮不宣称本地staged序号已在远端保留。

不将v3写入旧 `codex_document3_policy_sets.is_current=0` 后期待旧解析器“碰巧不读到”；独立staged表避免旧history/metadata/serializer误解新对象。它不是另一套活动存储或新对象服务，只是本轮隔离提交区。

无论settings当前是sqlite/hybrid/postgres，新版staged写入使用已配置本地SQLite；上游现有repo/storage可以只读。不给Postgres/Supabase新增远端数据写入/迁移，不镜像staged到旧投影器。

### 13.3 提交顺序与恢复

1. reserve_version一次，固定published_at，保存F/coverage摘要及版本receipt；恢复复用时间，不重生成内容。
2. 从同一F生成document3.json、runtime_projection.json、coverage_map.json、document3.md，写该version artifacts目录。
3. 检查四文件可读取、引用版本一致、hash与manifest一致；Markdown也展示as_of/coverage，不独立取中间稿。
4. 复用workspace.publish对该目录做checksum-addressed release；保存正式位置及摘要。
5. 同一个SQLite事务存staged对象和commit receipt，幂等重入比较内容；摘要不一致报immutable conflict。
6. root run记完成/staged；返回发布结果及位置。每个前序步骤均可按耐久receipt补做，不dispatch业务节点。

活动current、journal visibility、O4 enqueue不执行。只有四文件真实可用后才写staged完成receipt。保留现有workspace/source-run导出能力，所有研究ref源文件先接纳到主run并在checkpoint manifest记录；不能发布后删除这些依据而只留下悬空ref。

### 13.4 空集

失败造成空F：保存合法PARTIAL/staged结果供检查，`publish_empty=false`，不清空旧活动集。

完整研究明确空处置：可以保存合法COMPLETE空集；需要替换已有集合为空时GLOBAL显式提供publish_empty=true。该意图及结构闭合保存到receipt，未来启用才能应用。本轮不实现promotion，也不以空集数量作为全局失败门槛。

INITIALIZE始终新研究生成F，不掺入本轮未研究的旧Policy填数量；旧previous_set只供只读参考及明确身份取舍。

## 14. 单节点MAINTAIN的可执行合同

### 14.1 输入与调度

V21 maintain显式读取指定staged v3 base，冻结它的JSON/hash、as_of、完整O3MaintenanceFeed、Reference View Delta、可选Event ref及可定位研究依据。没有新Event版本但存在Trade/BADCASE/W3 gap也可运行；缺可选Event ref不让真实feed被旧NOOP条件挡掉。

base coverage从同版staged release中的coverage_map读取并核对hash，与主JSON一并冻结；不能只读PolicySet后假定过去remaining_gaps为空。

同一run只调度一个MAINTAIN任务，使用独立维护owner工作区；允许同任务有限技术重试/新session恢复，不扩为初始化四节点。保留当前maintain模型/effort配置；不因为新架构改模型默认。

无delta、无removed事件、无Trade/BADCASE/W3 gaps/candidates且没有显式维护任务时NOOP，保存处理receipt，不调用模型。其他情况进入MAINTAIN，由模型判断是否产生实际patch。

### 14.2 Patch模型

```text
PolicyPatchSetV21
  base_policy_set_version: int
  event_library_ref: EventLibraryRef | null
  upsert_policies: PolicyDraftV3[]
  retire_policy_ids: string[]
  remaining_gaps: RemainingGap[] = []
  summary: string = ""
```

upsert是完整Policy，沿用现有增量思路，不引入第二套Condition patch协议。已有Policy带稳定policy_id；已有Condition带condition_id；新增对象允许宿主首次分配。

不要求旧source_refs，不读取policy.decision。新/旧schema不得混入同一集合。旧v2.2 base拒绝作为V21维护对象并给明确版本错误；不能靠字段搬运完成旧集合重研。旧默认MAINTAIN仍在旧入口运行，不影响线上现状。

### 14.3 局部更新与保护

- base version/hash必须与冻结对象相符；这是对象绑定，不是质量闸门。
- 坏upsert隔离，该Policy保留base版本；其他独立upsert/retire继续。
- 同Policy既upsert又retire、重复且不一致upsert：该对象操作组不执行，保留base并PARTIAL，不让全patch失效。
- 已有Policy的某Condition更新坏：有明确condition_id时保留该条件base内容，接纳其他完整条件改动并PARTIAL；新坏Condition只隔离。没有可定位ID则不猜旧对应。
- 完整upsert合法地省略一个旧Condition表示主动移除；不会因为同Policy另一个条件在feed中触发就由代码代删。
- 明确合法retire可移除整个Policy；未知retire ID只报告。所有明确合法retire导致空集可以staged提交，保留显式退役证据。
- 纯内容等同upsert、未知retire、空patch不凭空产生新版本；记录处理receipt即可。

宿主不消费/重新开放任何Condition，只生成新的独立condition_revision；实际消费状态在后续消费者任务实现。

### 14.4 元数据、状态和恢复

Event ref可空，语义为本次实际可用快照，不允许猜版本。若完整维护已处理新Event ref但无Policy变更，保存一次metadata-only staged版本以推进对应来源/as_of；同base重复执行从receipt返回同版本。单纯重复feed/同来源且无实质维护变更则NOOP，新的时间参数本身不制造版本。

从base继承未解决缺口；patch.remaining_gaps给出本次维护结束后的最终缺口列表。若base有缺口但patch未交付这一字段，沿用旧缺口并PARTIAL，不默默清空。Agent显式给空数组可作为本次关闭处置，宿主不按summary文本判断经济正确性。

实现必须在注入模型默认值前保留原字段存在性，或检查Pydantic `model_fields_set`；不能让 `default=[]` 消除“未提供”与“显式清空”的区别。

接纳snapshot保留原始patch及字段存在性；恢复时不能仅用包含所有默认字段的model_dump重新解析，否则会把原本未提供的缺口字段误认为主动清空。

可读patch但仍有缺项输出PARTIAL；无可读patch且无可恢复snapshot输出DEGRADED，旧base保留。COMPLETE不得仅因为apply_patch执行成功；它要求本次维护文件齐备和最终缺口处置闭合。

恢复：先读已提交staged receipt；否则读已接纳patch snapshot完成确定性提交；只有未完成MAINTAIN任务才续run。不会重复dispatch已终态维护，也不会重复增加policy_set_version。正式DailyClose/Persistent maintenance调用者及records processed状态本轮不修改。

## 15. 技术失败、依赖与权限边界

### 15.1 失败分类

网络/进程/传输/timeout明确技术失败：同task最多一次额外尝试，保留目录与已经完成文件。SDK回复缺失/不合schema不自动增加业务研究尝试，先按文件接纳。

文件可读性/字段缺项：局部隔离或保留最近可读snapshot，不起修JSON Agent，不为经济unresolved重试。鉴权、unsupported model、schema请求错误、路径逃逸、lease丢失、已冻结输入污染、宿主存储写失败为系统问题；记录有限终态错误，不能宣称成功或伪造研究。owner局部技术失败不阻断其他owner。

### 15.2 prompt/skill依赖

代码支持后续外部node_assets manifest，声明role/common材料与Discovery/Planning/Build/Integration/MAINTAIN对应业务资产位置，并随run冻结hash。旧prompt/skill不能被新节点直接当作正确研究资产，也不能从旧Compile文件名推断新Build语义。

本轮不创建这些业务资产。真实Worker显式V21入口若缺所需资产，在dispatch前返回清晰的依赖错误；不静默退回旧研究节点。此检查仅是实际文件依赖，与业务质量或研究充分性无关。

离线测试用Fake Worker和测试临时文件/资产定位，不生成仓库业务prompt。正常transport指令仅指定task、schema、输入路径、写目录和receipt，不承载隐藏研究方法。

### 15.3 Data MCP

Discovery/Build/Integration注册为O3角色，并从现有Data MCP目录取全部可用只读接口；不只照抄O1的现有工具并集。保留已有市场适用性、工具注册有效性和能力签名边界，不扩入Message Bus/源配置写操作。

Planning为空工具集合；MAINTAIN保留现有O3维护权限上限，本轮不借维护迁移扩大来源操作权限。何时调用由后续skill决定，本轮不硬编码“某Topic必须调用某数据工具”。
