# Document2 v2.1 重构前代码勘察发现

勘察日期：2026-10-03（Asia/Shanghai）。需求依据：同目录 `d2_v2.1.md` 全文。代码基线：当前工作区，HEAD `eb5bb328d62abe29583e65bbac1794db5dacf8b7`，包含既有未提交修改。

补充勘察：2026-10-03，针对需求新增 §§38–42 的 O0 Research Topology 重构。第 13 节记录补查证据及修订结论；其中 Shell `name/scope/boundary/ref`、Unit `name/scope/horizon/ref` 的新版定义取代早期章节仍使用的 `core_question/boundary_rule/proposition` 目标示意。最新实施边界为基于 v2 的局部编排与 schema 改造，prompt/skill 本轮不修改；第 11–12 节中的 prompt 改写和全栈展示建议只是完整业务迁移影响，不是本轮实施清单。

本轮范围是需求理解、静态代码勘察和现有离线测试验证。未修改业务代码，未调用真实研究模型，未读取或修改生产数据库，未部署。方案中 INTC、C5 的具体研究质量判断来自需求文档，本轮没有独立复核对应生产研究原文，不能据此声称已证实具体 badcase 的发生率。

## 1. 核心结论

这次重构是 D2 的研究职责和 D2→O3 契约重构，不是增加一个字段或调整几段提示词。

当前 D2 的正式业务结构是 `State + Realization Factors + Potential Gaps`。Factor 包含待兑现的条件/执行门槛和未来观察接口；Gap 包含具体未来事件及其最低识别证据。尽管 O3 已有禁止机械复制 D2 的提示，这些字段仍容易把研究导航提前压缩为下游触发边界。v2.1 要建立 `Reality + Default Expectation + Causal Model + Revision Space`，由 O3 独立研究具体现实变化首次产生可交易预期差的位置。

已有基础可以大量复用：O0 分支发现与评审、完整 Shell 逐轮交接、Shell 间并行、每轮持久化、失败 Shell 隔离、PARTIAL 发布、来源 lineage 和只读 Published 输入。需要实质新增的是 O1 前置 Discovery 的两次独立调用与冻结交接，以及候选覆盖闭环；需要实质替换的是正式 ontology、旧观察/识别字段及其消费者。

四项必须先讲清楚的事实：

1. **现有 Gap 方法并非完全没有开放探索。** `gap-research.md` 已要求 evidence-led 与 possibility-led 两套探索、外部 actor、模型挑战，明确反对只复述 State/Factor/Future Nodes。当前缺口是探索位于 State/Factor 之后、候选池只在模型推理中形成、无独立冻结与取舍记录，最终仍收敛为可识别 occurrence。
2. **现有 ID 多数已经是自然语言语义名称。** `_id → name` 是统一字段契约，不是从 UUID 改成自然语言；O0 的临时候选 handle 与 runtime 的 attempt/artifact/run ID 是另一层身份，不能一并删除。
3. **当前执行不依赖同线程。** 编排器保存和传递 thread ID，但 Runner 提交 Worker 时强制 `thread_id=None`；现有 agent/skill 的“同线程累积理解”表述与真实执行不符。
4. **不能只修改 D2 writer。** O3、W3、读模型都直接解析旧 `Document2Document`，前端和 API wire schema 也依赖旧字段。若仅写出 v2.1，业务消费者会失败，或在宽松解析下丢失新字段。

## 2. 为什么要这样改：业务因果与责任边界

| 现有倾向 | v2.1 目标 | 解决的问题 |
| --- | --- | --- |
| State 同时维持 actual、管理层/卖方/市场隐含预测的当前快照 | 保留当前事实及已存在计划的身份；独立研究未来默认路径 | 避免把“今天有人这样预测”与“可合理采用的默认未来判断”混为一谈 |
| Factor 可以是 condition、constraint、execution gate | Factor 是相对稳定的机制；current_status 是传导链当下运行状态 | 避免把“客户是否最终采购”直接变成机制主体和等待条件 |
| impact + structural_role 粗略表达影响 | mechanism + 自然语言 materiality_context + scope_boundary | 解释链内变量的相对重要性、尺度和当前边际作用，不要求所有环节同时变化 |
| Gap 是一个可识别的未来 occurrence | Gap 是具有独立经济意义的 revision theme，内含不同 implication 的 possibility branches | 防止按客户/产品/月份拆出大量表面不同、实质相同的事件 |
| recognition_criteria、observability 提前说明要看到什么 | 从 D2 移除交易/匹配边界，O3 针对现实 case 研究 | 降低 D2 conclusion leakage 与 downstream realization 等待倾向 |
| 先研究内部 State/Factor，再开放发散 | 先 Full Scan，再 Selection，再研究事实和机制 | 减少 internal-company bias，使研究能主动补齐外部新方向所需 facts |
| 临时候选池不可审计 | 保存 Scan、Selection、Late Additions、Resolution | 区分“没想到”“想到后淘汰”“深入后合理并入/舍弃” |

Baseline 的作用不是证明完全 priced in，也不是伪造精确卖方 consensus。它描述当前信息能合理支持到哪里、普通 progression 是什么、尚未延伸到哪里。`open_frontier` 是普通预期的边界，不能偷换成足以交易的边界。

Materiality Context 的作用不是多写一段“这个因素很重要”，而是解释当前哪一个变量更能改变结果，哪些变量只是时点、质量、辅助或下游确认。Gap 的 revision_logic 保留轻量经济路径，不能恢复为严密的 A+B+C 触发 checklist。

## 3. 当前真正相关的实现入口与边界

### 3.1 主目标是 Codex Document2，而非 legacy Document2

目标实现位于 `src/doxagent/workflows/codex_document2/`，提示资产位于 `prompts/codex_v2/document2/`，正式版本当前是 `schema_version=document2.v2`、`workflow_version=codex_document2_v1`。

仓库同时保留 `src/doxagent/workflows/document2/`、`src/doxagent/models/documents.py` 等旧工作流/模型，以及大量 legacy canonical/promotion 测试。它们不是本需求所描述的 O0→O1 Shell workflow。不能根据 Document2 同名就同时重构旧 promotion、belief-state、resolver 体系。

主要入口：

- 正式 ticker 初始化：`ticker_initialization/research_adapter.py:352`，D2 读取 D1 依赖与 O2 pinned version，传入 initialization ID 和冻结 research cutoff。
- 独立研究 lane：`dashboard_api/research_lanes.py:123`、`:336`，启动 D2、复用已发布完整 run，配置 Worker、模型、并发、重试、发布存储。
- O2 精确版本启动器：`codex_document2/pinned_runner.py:28`，以 D1 run、ticker、Event Library version/hash 生成稳定 run identity；允许复用已发布 PARTIAL。
- 人工/离线 Pilot：`pilot/document2_case_builder.py`、`document2_coordinator.py`，另有自己的阶段依赖、context 构造与 schema 选择。

本地 `codex_document2/orchestrator.py` 的既有未提交 diff 仅把默认模型从 `gpt-5.6-luna` 改为 `gpt-6-luna`。本轮按现有工作区读取，没有覆盖该修改。正式入口还会显式传入配置模型，不能把构造器默认值当成生产实际模型结论。

### 3.2 当前流程

```text
Input Preparation：冻结 Published D1 + optional Narrative/Event Library
  ↓
O0 Candidate：C1 / C3 / C5 / 可用时 Narrative，分支并行
  ↓
O0 Synthesis：临时 Shell、候选归属及未分配候选
  ↓
Domain Review：C1 / C3 / C5 分支评审
  ↓
O0 Finalization：最终 Shell/Unit Seeds 和完整 topology
  ↓
O1 Per Shell：State → Realization → Gaps → Finalization
  ↓
Assembler：成功 Shell + 所有 Shell Outcomes + 引用重映射
  ↓
Publish：Document2 JSON、citation manifest、摘要 Markdown、最终 Shell/Seeds
```

Shell 使用 semaphore 控制并发，每个 Shell 在锁内完成自己的四阶段；不同 Shell 通过 `asyncio.gather(return_exceptions=True)` 汇合。默认 Shell 并发 2，正式入口可由 `codex_d2_max_concurrency` 配置。O1 不启用 subagent。方案保留这套粒度是合理的，无需引入额外 Agent 类型或跨 Shell 全局串行研究。

证据：`orchestrator.py:79`、`:202`、`:414`、`:727`；`codex_runtime/schema.py:66`。

## 4. 输入和真实 context 勘察

### 4.1 Input Preparation 已具备的大部分资产

`inputs.py:231` 起的 `Document2InputLoader` 要求 Published Global Research、匹配 ticker、存在 handoff；读取 C1/C3/C5 原文并核对 SHA256。`GlobalResearchInput` 已保存 reports、entity_relations、future_nodes、horizontal_collection 和来源 artifact IDs。

- C1/C3/C5 报告中的旧 `O#` 引用被限定为 `D1-O#`；Entity/Future/Horizontal 中的嵌套引用也会处理。
- Horizontal Collection 是可读取到的 program-collection bundle；读取不到则为空，不阻断研究。
- Narrative 读取最新 completed report，按 cutoff 检查七天窗口；过新或过旧不作为可用输入，失败转成 UNAVAILABLE。
- Event Library 只读 Published Reference View。普通读取会排除晚于 cutoff 的 head；pinned 读取可以按版本读取并支持 hash/published_at 校验。正式 initialization 入口目前只传 pinned version，精确 pinned launcher 还传 hash/time。
- 默认 cutoff 是 D1 published_at；显式 requested_as_of 可保留早于 publication 的研究 cutoff，同时记录 warning。publication time 不等同于 evidence time。

`orchestrator.py:380` 的 prepared-input artifact 可在恢复时重用；新 Discovery 应使用这一份已冻结输入，不能在每次重试时重新取最新 Narrative 或 Event Library。

### 4.2 O1 实际交接内容已很完整

每轮 O1 收到：完整 `canonical_shell`、完整 `o0_finalization` topology、research cutoff、D1 publication time、完整 global research、Narrative、Event Library、turn。

这意味着 Discovery 所需 D1、Future Nodes、Entity Relations、Horizontal、全局 Shell topology 已有数据通路，可复用；不存在必须新建 Entity 服务或新增上游 agent 的理由。可用 Event Library 的完整 payload 目前每轮都重新注入，并非只在第一轮出现。

证据：`orchestrator.py:786-799`、`:935`；`inputs.py:205`。

### 4.3 已证实的 context mismatch

**O0 Event Library mismatch：** `candidate-discovery.md` 声称参考 Event Library，但主流程 `_common_context()` 仅含 ticker/as_of/Future Nodes/Horizontal；`_run_candidate()` 未加入 Event Library。Synthesis/Review 复用同一 common，也不能靠其中拿到 Event Library。方案指出的 mismatch 在当前主流程可复现于代码阅读。

**Pilot 与主流程不一致：** bootstrap case builder 的 common 确实带 `event_library`，但其值固定为 NOT_CONFIGURED，并不实际读取 Published Reference View。普通 source-attempt Pilot 可复制真实冻结输入，不能把 bootstrap 路径与其混为一谈。v2.1 Discovery 的正式验证至少需要一个实际注入可用 Event Library 的 case。

**线程理解 mismatch：** agent `o1.md` 和 Realization/Gaps/Finalization skills 假定 same thread；`runner.py:168` 的 Worker request 却设 `thread_id=None`。包括 domain review，也只是读原研究、传入旧 thread ID，实际 Worker request 仍新建线程。v2.1 应以显式 context 为业务事实，并清理这些提示；无需为兑现旧措辞新增 hidden-thread continuity。

证据：`orchestrator.py:656`、`:927`；`pilot/document2_case_builder.py:373`；`runner.py:151-175`。

## 6. O1 编排、过程工件与恢复的重构影响

### 6.1 历史解释：一个业务 Stage，两个真实 Turn（已修正）

> 2026-10-04 补充：以下“六次调用、两个独立 attempt/node”的建议是上一轮错误解释，不能继续用作目标契约。用户已明确 Open Discovery 为单节点、一次节点级调用，在调用内部冻结 Scan 后继续 Selection。当前实现、SDK/Worker/Pilot 能力和直接可执行的修复见 [Open Discovery 单节点勘察与修复方案](d2_open_discovery_single_node_repair_plan_20261004.md)。原章节保留以说明不对齐的来源。

目标同一 Shell 的正常路径是六次模型调用：

```text
Discovery Full Scan → 冻结 Scan → Discovery Selection
  → State + Baseline → Realization + Materiality → Gaps + Possibilities
  → Finalization + Discovery Resolution
```

当前正常路径四次调用。应为 Scan 与 Selection 提供独立 attempt/artifact/durable identity，不能在一次模型响应中让“完整扫描”与“筛选”同时完成，或仅把 checkpoint 当提示词要求。

可以由同一个 O1 role 完成两次调用，但程序必须区分各自完成状态、output model、恢复位置。`CodexD2Node`、`ShellResearchStage` 当前没有 Discovery，`completed_order` 是手写 ordinal map，`_failed_stage` 也只有四阶段。这些都是明确改点。

### 6.2 当前 Shell-only 输出无法承载新 sidecar

四次 O1 都用 `output_model=ExpectationShell`。Runner 解析、重新序列化后才保存 snapshot，`AgentModel.extra=ignore`；通用 `ingest_model()` 也会尝试删除 forbidden extension fields。因此把 discovery resolution/late additions 临时塞到 Shell 的额外字段里，有可能被机械丢弃；也不能要求它们进入最终 Published Shell。

建议最小契约：Scan/Selection 使用各自独立 typed output；研究回合在需要追加 late additions 时用明确结果 envelope 或独立受控 sidecar 读回；Finalization 结果显式携带完整 canonical Shell 与 resolution，拆分保存。具体 envelope 名称未由需求指定，但必须先定下来，不能依赖模型随意写额外字段。

### 6.3 文件写出不等于冻结

`codex_worker/workspace_store.py:112` 只保证 `context/`、`published/`、`attempts/<id>/input/` 已有内容不可变；一般 `artifacts/` 文件可覆盖。因此单纯写一个 `artifacts/open_discovery_scan.json`，还不能满足“Selection 不得重写”的承诺。

可复用现有 artifact metadata/SHA256 和不可变 attempt input：保存主 run 的原始 Scan，checkpoint 记录其路径/hash，Selection 输入冻结该 Scan 内容，恢复时校验。无需给全部业务文档新增复杂锁服务。**名称冻结指 candidate 的语义名称和原始内容冻结，不是第一次扫描永久封闭世界。** 后续方向写 late_additions，不回写原 Scan。

### 6.4 当前 checkpoint 粒度与一个恢复隐患

`ShellRunState` 记录 shell/workspace/thread/stage/canonical_path/snapshot_paths/event_library_injected/error；每轮保存 snapshot、覆写 `artifacts/shell.json`，再保存 bundle/checkpoint。恢复依赖 canonical_path 与最后 stage，阶段成功后跳过已完成阶段。`Document2Checkpoint` 另存 O0 artifacts、attempt→workspace 映射。

新增 Discovery 必须在 Selection 失败时保留成功 Scan；State/Gap/Finalization 重试不能重新扫描或重做 Selection；late additions 应保留前轮记录并允许幂等重入。

静态可见的既有隐患：`_restore_or_initialize_shell()` 在 canonical 读取/解析失败时退回空 Seed，却没有同步重置 `state.stage`；后面的 completed_order 仍可能跳过已完成研究，造成 Seed 与 checkpoint 不一致。这不是本轮已触发事故，但新版恢复设计应把“进度”和“对应工件可恢复性”联动，而不是继续默默跳过。

### 6.5 durable identity 不仅存在于 D2 checkpoint

初始化内 `@durable("d2")` 把 node + workspace_run_id + artifact_key 组成子步骤身份，成功 receipt 可直接解码返回；`ticker_initialization/substeps.py:223`。新版两 Pass 不得共用相同 durable key，也不能在同一已成功子步骤身份下无条件切换旧/新 output model。

`PinnedDocument2Runner` 的稳定 run ID 当前没有 D2 schema/workflow revision 或 cutoff；独立 lane 也会复用完整已发布 run。v2.1 验证要使用清楚区分的新 run identity，避免“已完成复用”直接返回旧 D2。是否升级 workflow identifier 与如何兼容旧 durable receipts 应显式决定。

### 6.6 Coverage Closure 应是有限完整性检查

程序可以核对：每个冻结 candidate 有 Selection；MERGE 指向存在的候选且无无效引用；每个 DEEPEN 最终有 resolution；late additions 有去向；需要 destination 时存在对应最终名称。不要把材料不完整、低概率、引用 unresolved 或缺少精确 materiality 数字新增成阻断理由。

MERGE/PARK 的理由已经由 Selection 保留；需求明确必须 closure 的是 DEEPEN。候选吸收到 Factor、并入 Gap、研究后影响不足、相邻 Unit 承担，都是有效结果，不能强制每个候选生成一个 Gap。

## 7. Assembler、引用和发布现状

### 7.1 引用链可复用，但遍历范围必须重写

Runner 将当前 attempt 的裸 `O#` 限定为 `D2REF:<attempt>:O#`，保留 D1、URL、DoxAtlas 来源；Assembler 统一映射成最终 `【cite:O#】` 并保存 citation manifest。未解析/无效引用非阻断，citation status 与业务 COMPLETE/PARTIAL 是独立维度。

但 `assembler.py:178` 的 `rewrite_shell()` 只遍历 State Values、Factors、Gaps 的 `citation`，不处理 Shell/Unit/Parameter，也不存在 Baseline。`citation→ref` 后必须覆盖所有正式来源字段，否则 Baseline 等新来源不会被纳入最终 manifest。过程 sidecar 保留自身 provenance；不能为了“统一 ref”把 candidate→resolution 的审计关联变成正式 ontology 链接。

注意 `ref` 是来源字符串列表；没有必要新造 state_refs/factor_refs/baseline_refs/discovery_refs。来源命名空间仍需保留，因为不同 attempt 的 O1 不是同一个来源。

### 7.2 发布不等于所有过程工件进入 Published D2

当前 `publish_refs` 白名单只包含正式 document/citation/markdown、最终 Shell、最终 Seeds；普通 turn snapshots 没有自动进入 Published release。可以沿用这一隔离：Discovery 工件作为过程记录被登记、恢复、审计，但不成为 O3 的正式研究输入。

如果过程记录需要远端备份，应区别“可留存/可查询”和“作为 Published D2 正式内容”。目前只在 Worker 子 workspace 保存 sidecar 会遗漏主 run 的恢复/审计通路，建议同步主 run artifact 并纳入 checkpoint。

`render_document2_markdown()` 目前只输出 proposition/horizon 与各对象数量，是摘要而非完整研究报告。v2.1 应至少加入 Baseline 数量和新版名称；是否扩展为完整可读报告是独立产品选择，不能将现有摘要误称为完整 D2 内容。

### 7.3 失败与 PARTIAL 语义应保留

成功 Shell 才进入正式 shells；失败 Shell 在 outcomes 保存 seed、阶段、错误码。所有 Shell 完成且非空才 COMPLETE；零 Shell 是 PARTIAL；current 只在 COMPLETE 时为 true。bounded retry 后可隔离 TRANSIENT/FORMAT/SHELL 失败；invalid request/schema、权限、lease、路径完整性等系统错误不能伪装为研究 PARTIAL。

初始化/精确 pinned launcher 允许复用 PARTIAL；D3 接受 Published PARTIAL 并把 failed shells 排除出 Gap coverage 分母。因此新增 Discovery 的局部失败需要进入同一可见 outcomes，不能默认把整个 run 阻断，也不能把未完成候选覆盖静默记为完整 Shell。

证据：`orchestrator.py:219-260`、`:329-367`、`:1172`；`errors.py`；`codex_document3/inputs.py:105-138`。

## 10. 方案落地前必须明确的技术契约

这些是可确定范围内的实现细节和真实冲突，不是要求追加审批或扩大研究 ontology。

1. **Published envelope 是否保留 run/source identity。** §31 的示意未列 document2_run_id/source_global_run_id，但 W3、下载、D1 lineage 都需要它们。建议作为非 ontology provenance 保留；若移到 handoff，必须有等价可用的 reader 通路。
2. **O0 不大改与 name 统一如何接边。** 可保持 O0 算法和临时 handle，调整 final seeds 的规范名称，或在 Seed→canonical Shell 边界转换。不能保留两个会漂移的业务名称真源。
3. **canonical name 的唯一作用域。** 建议 Shell 在 Document 内唯一，Unit 在 Shell 内唯一，Parameter/Value/Factor/Gap/Baseline 在 Unit 内唯一；candidate 至少由冻结 Shell/Unit 上下文消歧。Selection/resolution 示意只写 candidate name，跨 Unit 重名时须用嵌套 Unit scope 消歧，不造 Candidate ID。name 是 identity，内容可修订但不能随措辞润色任意漂移。
4. **Finalization 与 late additions 的返回形式。** 需要明确 envelope/sidecar contract，保证解析、快照、receipt、重试后都不丢过程数据，而正式 canonical Shell 不混入它们。
5. **冻结与持久化承诺。** 原 Scan hash/path、Selection 绑定、最后成功 Pass、late additions 累积、Resolution 应有 checkpoint 引用；不能靠普通 artifacts 文件名宣称不可变。
6. **State 的当前快照与未来默认判断。** 管理层当下已发布计划保留在 State，模型自行推断未来默认路径进入 Baseline；不能把 source_role=MANAGEMENT 当成 market consensus。
7. **Gap 第一来源与新发现的协调。** 未在 Full Scan 出现但深化时发现的方向先进入 late_additions 再研究；不把“来自 Discovery”实现成封闭白名单，否则与 §30 开放追加冲突。
8. **范围删字段不延伸到 D3 Policy。** D2 的 source_refs/机械对象引用统一移除，不等于删除 D3 PolicySourceRef 的有效 provenance，或者废弃 runtime attempt/artifact identity。
9. **历史读取和 run 复用策略。** 旧文档不可覆写；新 run 不误复用旧 COMPLETE/旧 durable receipt；reader 能准确区分原生 v2.1 和旧 v2，必要的 adapter 只保持可读，不补造研究结论。
10. **failed Shell 诊断与完整性。** §31 outcomes 示例更精简，现有 read projection 依赖 seed/error_code。需选择正式 envelope 保留还是读模型另取诊断，避免失败 Shell 变成无标题/无法定位。

## 13. 补充：O0 Research Topology 重构勘察

### 13.1 最新需求改变了什么

需求 §§38–42 保持跨节点链路 `Candidate Discovery → Synthesis → Domain Review → Finalization → O1`，但将 O0 的产出从“完整预期命题”改成“值得维护预期的经济对象及其研究拓扑”。

- Shell 定义共享业务语境、参与者网络、基础数据和研究材料的容器；正式字段从 `shell_id/core_question/boundary_rule` 改为 `name/scope/boundary/ref`。
- Unit 是可独立修订的经济预期对象；正式字段从 `expectation_id/proposition/horizon` 改为 `name/scope/horizon/ref`，**不保留 proposition**。
- Shell scope 说明研究对象，boundary 只排除相邻业务域；Unit scope 说明持续研究什么。二者均不预设最终结果、完整传导链或排除条件。
- Candidate 的业务信息收敛为 `name/scope/why_material/ref`。
- Reversal、Open Catalyst、Multi-path、Independent Revision、Thesis Leakage 是后续语义研究/评审方法，不能在本轮编排代码中变成禁词校验、打分或阻断规则。

所以第 10 节原先提出的“保持 O0 seed 语义、仅做 name 接边”已经不足。应保留节点位置、角色、并行分支和持久化方式，同时更新各节点结果模型和交接字段。也不能将历史 proposition 机械改名为 scope 后宣称已经消除 thesis leakage。

O0 的多来源发现和 domain reviews 已有并行及逐分支 checkpoint，Synthesis/Finalization 串行，因此这里不需要新增 orchestration Stage，不需要拆更多 Agent，更不需要重建调度器。

### 13.3 可以保留的结构理念和真正的语义冲突

现有 `shell-synthesis.md` 已要求 common context core、因果关系不等于同 Shell、上下文共享不传递；这些与新增 O0 设计一致。需求并不是要求反向把所有 Shell 合并为宽泛 ticker 总论，也不是按“六个 Unit”机械拆分。

真正冲突在于当前所有 O0 方法都把 Unit 定义为 middle-level proposition，尤其 `shell-finalization.md:125-133` 明确要求 declarative expectation；`agents/o0.md:7`、`candidate-discovery.md:67`、`domain-review.md:22` 也采用命题定位。这不能通过修改字段名或删除几个词可靠修正。

本轮只读这些资产识别依赖，不修改它们；不在 Python、context 或 schema description 中暗中加入一套新的研究/评审指令。编排与 schema 的机械就绪、真实 Agent 研究语义就绪应区分验收。

### 13.4 Candidate 与 Review 的过程身份

当前主流程把来源名与分支临时 `candidate_id` 拼成 `C1:U1` 等 `candidate_ref`，防止跨来源同名 handle 冲突。Pilot 的 `_pilot_candidate_sets_context()` 独立实现同一逻辑；Domain Review 的 target 使用 `S# / <candidate_ref>`。

新版业务对象以 name 为 canonical identity，不妨碍保留必要的**过程定位**。可在编排输入中派生来源限定的 candidate_ref，不发布进 D2；Shell 的 provisional handle、feedback_id 也只是过程对象。不要因统一业务 name 而删除 attempt/run/artifact、durable key、review target 的定位能力；同样没有理由新建第二套业务 ID 系统。

如果 Candidate 输出移除 candidate_id，两处 helper 必须同步更新为基于 source+name 的定位，不能继续拼接 `None`。同一分支重复名称、跨来源相同名称，要分别按照作用域和原始来源处理，不能通过自动改名或文本相似度合并语义对象。

### 13.5 新增发现：O0 fallback 同样固化旧 thesis

`codex_document2/recovery.py` 在 Synthesis 不可用时，把每个 Candidate 独立保留为 provisional Shell，使用 `candidate` 作 core_question、`reason` 作 boundary_reasoning；Finalization 不可用时，把 candidate_ref 作 expectation_id、candidate 作 proposition，horizon 标为 UNRESOLVED。

因此仅改正常模型 schema 还不够，fallback 会继续生成旧结构；若删除 proposition 而不改 fallback，则它可能直接格式失败。局部重构要让 fallback 保留已经存在的 name/scope/ref，不从旧 reason 合成排他 boundary，不凭空推断研究结果；未知 horizon 继续诚实表达。Fallback 不能把临时 Shell handle 假装成最终业务研究域名称。

这里需要的是基于已有候选的可恢复结构，或者清楚可见的局部失败，不是新加一次“自动补 thesis”的模型回合。

### 13.6 O0 ref 与证据交接不能漏掉

当前 Candidate 的 references 和 Review 的 references 会在 Runner 中进行局部 alias qualification，但正式 citation remapper 只遍历 O1 Value/Factor/Gap 的 citation。Synthesis 的 ProvisionalCandidateUnit 不携带 Candidate 的 reason/references，Final Shell/Unit Seed 也无引用字段。

新版 scope 和经济对象选择同样需要 lineage；Candidate→Provisional→Final Seeds→O1 Shell 的 ref 应按同一语义沿途保留，不能让 schema 收敛顺便丢掉上游来源。Assembler 扩展 Shell/Unit/Parameter/Baseline 等正式 ref 的遍历就够了，不需要新增 ontology 对象互引。
