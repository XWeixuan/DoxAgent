# Document3 v2.1 重构前代码勘察发现

日期：2026-10-04。对象：当前本地工作树中的 Codex workflow Document3，包括 INITIALIZE、O3 日常 MAINTAIN，以及新合同成立所必需的消费接口。

本轮只做方案阅读、代码勘察和离线基线验证，不修改业务实现、prompt/skill，不调用真实模型，不部署。所有“当前”均指本地源码，不代表生产运行版本。工作树已有 D2 v2.1、Overview 等未提交修改；本文按这些修改后的实际代码勘察，不回退、不覆盖它们。

## 1. 总体结论与重构动机

已通读 `d3_v2.1.md`（含附录）和 `document3_v2.1_contracts.schema.json`，并以当前 D2 schema、D3 实现和消费代码交叉核对。

本次是研究入口、工作组织、决策对象和发布生命周期一起变化的重构，不能仅将三个旧节点重命名。当前主干是“D2 Gap → Path → Trigger Calibration → Policy Compile → Final Global Pass”；目标是“开放线索 → 全局研究议程 → owner 内有限 waves 深研并构建 → 跨批整合与唯一补研 → 集合替换发布”。

为何这样改，按方案及现有实现可归纳为：

1. D2 v2.1 的 Unit 是经济预期对象，Potential Gap 是 revision space，已不是交给 D3 映射成 trigger 的兑现命题。继续按旧 Gap 三元组驱动，会约束来源、放大字段映射，并遗漏 D1/Web/横向事件中的机会。
2. 早期 Discovery 不应提前承诺方向和交易边界；Global Planning 必须先看到各 Shell 与 OPEN，再决定研究投入和归属，避免按 Shell 局部选题后重复深研。
3. 独立 Compile 把实质边界研究与 Policy 表达分开，却要求多份台账保持同步。Build 应在真正研究中直接形成可交付的 Policy，跨 Shell 的取舍交给 Integration。
4. 中性 Policy 可容纳不同方向、不同层级的独立入口；方向属于 Condition。过去整个 Policy 一次性消费的逻辑不能照搬。
5. 完整原稿、文件交接和不重叠集合替换，能避免逐批覆盖总集时丢失差异，也避免补研改写稿与旧稿一起上线。
6. 一次冻结补研计划、有限技术重试和局部隔离，让不完整成果可见且流程有终点；COMPLETE 是已选工作完成与处置闭合，不是候选数、Policy 数或开放世界穷尽。

用户补充覆盖本文的 MAINTAIN 设计解释：**保留一个 O3_MAINTAIN 业务节点，沿用局部增量维护思路，适配新的字段、来源、Condition 方向及发布/恢复架构；不扩成初始化四节点链路。**方案第 18 节关于复用 Build/Integration，本文理解为复用契约和确定性组件，不据此新增 MAINTAIN 业务节点。

## 3. 当前 INITIALIZE 的真实拓扑

```text
读取 Published D2 v2 + Event Library Reference View + previous PolicySet
    → seed 全局工作区、按 Shell 切片、冻结 manifest
    → Shell 1 Calibration → Shell 1 Compile
    → Shell 2 Calibration → Shell 2 Compile → ……（串行）
    → Final Review 一次全局 turn（可直接改全部工作稿和台账）
    → recover/validate → stable ID assembly → publish → 可选 O4 enqueue
```

- `initialize()` 用普通 `for` 遍历 Shell；一个 Shell 两个 turn 后才进入下一个，没有 OPEN、GLOBAL owner、Agenda 或 owner 队列并行。
- 同一个 `thread_id` 连续传给所有 Shell/阶段；Runner 从 `(run_id, O3 role)` 加载和保存唯一会话。正常业务 turn 数约为 `2N+1`，不含准备/发布及技术重试。
- 当前“wave”就是一个 Shell 的整个 Calibration 或 Compile，不是 1–3 Topic 的有限研究批次。
- 前阶段以 completed_nodes、trigger_calibration_state、wave_state 和 worklist 多份记录判断恢复；校验失败会 reset 从 Calibration/Compile/Review 开始的节点集合。
- Final Review 获得 Shell 切片目录、全部 Policy 草稿和台账，可直接重写；没有主池 B 冻结、分批读取进度、累计 relations、唯一 supplement 标记或最终 replacement 清单。
- 声明 REVIEW_BLOCKED 会转提示继续 PARTIAL，但实际缺 Worklist、无可用 Stage-A、Worker 耗尽且没有当前 wave checkpoint 等仍可抛异常失败。

依据：`orchestrator.py:121,233,285,431,527,1584`；`runner.py:253,342,418,704`。对应旧拓扑回归：`test_initialize_runs_two_turns_per_shell_with_document2_slices`。

## 4. 上游 D2 接口与新输入投影

### 4.1 当前准备器并不兼容已存在的 D2 v2.1

`prepare_initialize()` 要求 D2 bundle 已 published、有 handoff、ticker 一致，并验证 PublishedDocument 大小/SHA256；不要求 D2.current，也不拒绝 PARTIAL。随后硬编码用 `Document2Document`（v2）解码，并构造 `(shell_id, expectation_id, gap_id)` 覆盖分母；failed shell outcomes 单列且不计入分母。

Runner seed、恢复输入加载和初始化 internal rerun adapter 也重复用旧 D2 parser/三元组。只改 preparer 不足以接通新版。

当前 D2 本地已有 v2.1 schema/六轮编排，但 staged、非 current，默认入口仍 v2。必须协调 D3 的版本入口和上游选择；不能认为读取一个新版文件就等于默认初始化已接新版。当前 D2 v2.1 有 State、expectation_baseline、realization_factors、potential_gaps 与 `name/scope/horizon/ref`；Discovery sidecars 不是正式 Published D2。

依据：`inputs.py:64`；`runner.py:115`；`orchestrator.py:1068`；`ticker_initialization/internal_adapter.py:183`；D2 `schema.py`、`assembler.py`、`pinned_runner.py`；同目录 `document2_current_implementation_for_d3_refactor_20261003.md` 为辅助索引。

### 4.2 当前研究资产装载不足

当前冻结业务文件仅 D2 JSON、Reference View、previous PolicySet、task，加 Shell 切片。未准备 D1 原文、Future Nodes、Entity Map/Relations、通用催化与其他完整共享材料；D2 内的 manifest 不是这些材料的实际正文。

新三层投影必须落地：全局 topology 轻目录、当前完整 Shell/Unit D2、同一组完整共享研究材料。D2 最细为完整 Unit，并保留 Shell 头与 sibling 目录；非 D2 材料不按节点隐藏或切 C1/C3/C5 片。需要从实际发布/冻结上游资产取得原文和来源时间，不靠会话隐式带入。

新 as_of 是 run 级冻结研究截止；当前 cutoff 传到 Worker/task，但不在 Published PolicySet 中，Event reader 在此入口也未按 cutoff 限制版本。需记录实际输入时间与可用状态，不能把 published_at 当研究截止或把旧材料重新标为新。

目标允许 D2 ref 为 null，而当前请求强制 document2_run_id、preparer 强制成功读取 D2。若实现目标中的无 D2 降级，应保留 OPEN/共享资产路线，并同步处理下面 W3/O4/activation 对 D2 的依赖；不能只把字段改 nullable。

## 5. 节点、线程和调度迁移

| 当前 | 新行为 | 工程落点 |
| --- | --- | --- |
| Calibration 提前给出方向/Trigger | Discovery 三字段 Lead | 逐行 parse、owner 独占文件、初始 scan 冻结、late 独立文件 |
| 无全局选题 | GLOBAL Planning | 全部 discovery 终态后才冻结 Agenda；分批读取仍是同一节点 |
| 每 Shell Compile | Research & Build | agenda 派生 owner 队列，默认 topics_per_wave=3、max_parallel_owners=3 |
| 单 O3 thread | N Shell + OPEN + GLOBAL | 逻辑 owner 映射到物理 session；同 owner 串行、不同 owner 并行 |
| 单 Final Review | Global Integration | 主池 B、轻索引、完整 Policy 分批读取、review 快照、最终 consolidation |
| 无补研合同 | 最多一份 supplement Agenda | 分发前耐久写 supplement_dispatched；恢复不得重置 |

同 owner 下一 wave 不等待其他 owner 的同序 wave；发现与主研究的汇合等待终态，不要求全部成功。混合 owner wave 按 owner 拆分、重复 Topic 首次调度、漏排所选 Topic 加队尾、不存在 owner 路由 OPEN，均为调度修正，不替 Agent 选题。

现有 SDK adapter 已调用 `thread_start`/`thread_resume`，具备底层会话连续性；但 D3 只有 O3 role 的一条 ThreadRecord，不具备多 owner 会话索引和恢复失败后的新 session 降级。不能直接把任意 Shell 名塞入严格的 agent_role enum；owner 状态需独立映射或明确扩展现有存储键。

现有 `@durable("d3")` 支持 durable_key，能复用父初始化的子节点/Worker receipt；新 key 必须区分 phase、主/补轮、owner、wave/batch 序号。当前单个 active_wave_key、节点级 attempt number 和全局台账不适合直接并行。ContextVar 提供执行上下文隔离，但不是共享工作文件隔离。

两个并行任务都不能拿全 workspace 前后 diff 推断“另一个 owner 的写入是本任务越权”；边界检查需按当前 owner 目录和宿主写入范围核对。初始 scan、agenda、B 的宿主冻结不能依赖 Agent 自觉不改。

依据：`runner.py:418,704`；`codex_runtime/schema.py:241`；`codex_worker/sdk_runtime.py:378`；`ticker_initialization/substeps.py:199,415`；`orchestrator.py:1633`。

## 6. 中间合同、ID 与最终替换

附件机器合同的根是 PolicySet；`$defs` 覆盖 RefList、Lead、Topic、NotSelected、Agenda、ResearchResult、Relation、Review、Replacement、Coverage、RemainingGap、Consolidation、Calibration、Condition/Draft、Policy/Draft。

- ref 缺省空数组；JSON Schema default 本身不注入值，adapter/model 要实现该默认。附件未普遍关闭 additionalProperties，不应照旧 whole-object strict parser 把无害额外注解变成全流程失败。
- Draft 仅 ID 可省；Published Policy/Condition 必须有身份、完整执行内容。宿主首次接受文件即分配 ID并耐久保存，不在最终 assembly 才重新生成。
- Topic 名称唯一、owner 可路由、wave 引用、结果对应、replacement 冲突等跨记录约束不是附件 JSON Schema 自动解决的，须做局部读取与调度修正。
- 当前 Policy ID 的生成/连续性键含 decision、title、source_refs；Condition 以 criterion 匹配旧 ID。新架构不能再依赖这些文本哈希：中性化、方向分拆、ref 开放会改变键，同 criterion 的双向条件也可能碰撞。
- 新身份应以首次接受的文件与持久化分配记录为恢复依据；同一文件重写保持 ID。合并由 GLOBAL 明确选择旧 ID/新 ID；拆分分配新对象 ID，保留 snapshot/替换历史，不另建 alias 图。

当前 assembly 汇集 `output/work/policies/` 下可读草稿，没有 B 与候选池区别。新 assembly 应严格实现 `F=(B−成功 before)∪成功 after`：未替换主稿保留；补研/GLOBAL 稿仅经 after 接纳；坏组保留 before，其余继续。

before 重叠组需先识别冲突，不能遍历时“先出现者成功”；after 文件缺失、ID冲突、同路径重复或与保留稿冲突，都应先整组确认后提交。relations 的 A-B、B-C 不可被代码做经济含义传递合并。覆盖路径最终解析成正式 ID，但来源存在不等于研究覆盖完成。

依据：`identity.py:16,22,32,54,80`；`assembler.py:24,65`；`orchestrator.py:1465`；方案第 9–14 节及附件 definitions。

## 7. 非阻塞处理：已有基础与实际差距

当前代码已有逐行恢复、坏记录隔离、Artifact 优先于回复声明、语义诊断提示化、immutable input/hash、有限 Worker 尝试。不能概括成完全硬 gate，也不能概括成全面非阻塞。

| 当前事实 | 新需求 |
| --- | --- |
| `_GLOBAL_FATAL_CODES` 仍含 SHELL_ZERO_POLICY、STALE_BASE | 删除每 Shell 至少一条 Policy 闸门；保留真实发布基线一致性 |
| 缺 Worklist/Stage-A 可使 Final Review 或 assembly 失败 | 无 Planning 时走最近可读 Agenda，否则空主研究进入 Integration |
| 一个 owner Worker 耗尽可上抛，停止串行父流程 | owner 终态隔离，已完整产物仍接受，其他 owner 继续 |
| `_policy()` 规范化 Conditions 后整体验证 Policy | 先逐 Condition 隔离；坏 Condition 不导致整份其余条件丢弃 |
| 缺草稿 policy_id 无法过旧 Policy 解析 | 首次接受可分配 draft ID，不伪造经济内容 |
| 语义/来源/中文占比等 findings 可令 PARTIAL | 提示性诊断不直接变必需研究失败；状态据实际任务/剩余缺口确定 |
| completed checkpoint 损坏可能 reset 前序阶段 | 明确恢复任务与冻结产物，避免因局部问题重跑所有终态任务 |

当前 `_finding(blocking=True)` 会把 fatal allowlist 以外的旧“blocking”调用降级；因此 Compile/Path 台账检查不是全部硬阻断，真正零 Policy gate 有代码和测试双重证据。新需求允许经济上不成立的 Topic 零 Policy 正常闭合，必须移除该约束，而非重命名。

Runner 独立运行默认各业务 turn max_attempts=2，恢复后 next_attempt_number 继续递增，新调用会再次给 offset预算；受管父初始化的 durable wrapper则将内部max_attempts改为1，并由耐久子节点控制外层重试。需分别核对两种入口，按同一任务耐久计算总技术尝试，避免恢复叠加预算；不为 unresolved、业务质量或提示重试。真实 lease/capability/路径逃逸、冻结输入污染、存储提交错误仍属系统完整性边界，不应用伪造空研究掩盖。

## 8. Runtime 消费是不可省略的适配范围

### 8.1 方向与命中

当前 Projection v4 仅 policy_id、match_scope、activation_revision、condition_ids、criterion，不含 title/transmission；R2 按 pinned version 回读完整 calibration，但 `_w2_detail_business_payload` 不包含 Condition decision/trigger_layer。新 R1 要中性 title/match_scope/必要 transmission；R2 必须给全部方向条件和完整 calibration。

当前 `RuntimePolicyProvider.decision(ticker,version,policy_id)` 返回 policy.decision；`_claim_first_policy()` 遍历 Policy IDs、取顶层方向并返回第一可 claim 的 Policy。只删除顶层字段会导致无法交易；随意补 LONG 则改变业务含义。必须基于命中的 Condition 方向进入既有最终决策接口，同时保留双向命中证据，不能靠遍历先后替模型选方向。

W2/W3 已有 matched_condition_ids，可复用身份归属基础，但仅有 Condition ID 记录不等于支持双向决策。

### 8.2 消费/重新校准

当前 Runtime activation 以 `(ticker,policy_id,activation_revision)` 唯一 claim；activation_revision 对全部 criterion/calibration 求哈希，W2 和 W3 都按整条 Policy revision 过滤 consumed。TradeOutput、selection、read lifecycle 也依赖它。

**明确风险：原样使用会在一条 Condition 触发后屏蔽同 Policy 的另一方向；而任一条件重校准又会改变整个 Policy revision，可能同时重新开放其他已消费条件。**新方案须处理受影响 Condition 的版本/可用性与反馈，保留与旧 revision 的历史对账，不能只把 claim SQL 多加一个字段就宣称交易闭环完成。

revision 必须包含实际决定新条件执行含义的字段；旧哈希未包含 Condition decision/trigger_layer，不能沿用作新双向身份。Policy ID、Condition ID 和边界 revision 作用不同：稳定身份不能随着 baseline 文本更新漂移，边界 revision 则需反映执行语义变化。

### 8.3 D2/current 与历史兼容

W3 PreparedContext 仍硬解码 D2 v2，并查 current Published D2；D2 v2.1 staged 非 current 意味着 D3 单独成功也不证明 W3 已接新输入。必须版本解码/版本绑定，不能混用新版 D3 与旧 current D2。Runtime coordinator、operations、version pin、ticker initialization runtime inputs 等也反序列化旧 Projection/PolicySet。

本轮建议范围是兼容输入输出、命中归属、消费和维护反馈，沿用 W1/W2/W3 研究职责；不扩写内部研究任务。旧 ALL 多条件不得无声转换 OR。

依据：`runtime_projection.py:37,62,122`；`persistent_runtime_v2/providers.py:46,93`；`service.py:89,106,737,1430`；`w3.py:141,203`；`repository.py:1171`；`trade_output.py:168`；`selection.py:152`。

## 9. O3 日常 MAINTAIN：保留单节点，完整适配架构

### 9.1 当前增量链路

```text
Daily/Persistent maintenance 冻结候选、Trade、BADCASE、W3 gaps
  → O2 更新 Event Library → Reference View Delta
  → 一个 O3_MAINTAIN turn → policy_patch.json
  → 结构读取/稳定 ID/upsert-retire → 发布新版本
```

`maintain()` 读取当前或指定 base_policy_version；无 Event ref 返回 NOOP；无 feed 且 Event版本不新则 NOOP；无 feed 且 Reference View空则 DEGRADED。提供 feed 时允许同 Event版本的 Trade/BADCASE/gap 驱动维护。Agent 收到 current_policy_set、delta、task 和完整 runtime feed，单 turn 写 patch。

Patch 目前是 `base_policy_set_version + event_library_ref + upsert_policies + retire_policy_ids`，upsert 是完整旧 Policy。空 patch NOOP；非空 apply_patch +1，默认置 COMPLETE，再按读取/校验 findings 标 PARTIAL。没有初始化那样的 task/input manifest 全套冻结与 WorkflowCheckpoint；candidate reservation 已发布时可恢复返回，但普通维护重试仍可能重新 seed/run，需更明确的幂等恢复。

Persistent maintenance 与旧 DailyClose 两个调用链均存在：前者 pin base、candidate publication并通过 journal checkpoint后提交可见版本；后者普通 maintain，完成后标记 daily records processed。不能只改其中一个入口，或混淆 repository.current 与 journal visibility。

### 9.2 本次应变与应保留

| 项目 | 适配要求 |
| --- | --- |
| 编排 | 保留一个 MAINTAIN；不新增 Discovery/Planning/Integration 维护节点 |
| 输入 | 保留 Delta + Trade/BADCASE/W3 gap；冻结 base/as_of，受影响原文可按新 ref 定位 |
| 内容 | 中性 title、transmission、ref；完整 Condition decision/trigger_layer/calibration |
| patch | 完整 v3 Policy upsert 可继续承载局部条件改动；不得将局部 condition patch 错当完整 Policy替换 |
| 条件维护 | 重校准受影响条件；另一方向不可机械删除，也不能不经研究假定永久有效 |
| IDs | 明确已有 Policy/Condition身份；新对象宿主分配；更新 baseline 不换稳定身份 |
| 局部容错 | 坏 upsert/Condition隔离；无可读补丁不清空旧集；保留未改条件 |
| 发布 | base CAS、candidate reservation、同版四输出和单次可见指针提交复用 |
| 恢复 | 复用冻结 feed与已完成产物，耗尽技术尝试后终态；不能重发/重复加版本 |
| 状态 | 区分空变更 NOOP、缺产物 DEGRADED/PARTIAL、明确研究处置 COMPLETE |
| O4 | 当前维护不创建 O4任务；本次保留，若涉及策略配置变化应走既有控制面 |

## 10. 发布、空集、可见性与恢复

当前 `_publish_policy_set()` 从一份 PolicySet生成四输出，写 `output/final`，复制 `artifacts/document3` 并 workspace.publish，再存 artifact/PublishedDocument，最后 publish repository或candidate。repository把主 JSON、Projection及 current切换放一个事务，已有 expected base CAS；SQLite具备跨连接耐久 version reservation和immutable candidate。

这提供可复用基础，但文件、PublishedDocument、Policy repository、bundle、journal visibility 并非一个总事务。中途失败可能留下已保存但未成为活动版本的工件；恢复需验证已提交版本与内容后补全 handoff，不能重新分配随机 artifact ID并多次提交。四文件一致性还应覆盖 coverage/Markdown，而非只依赖 DB中两列事务。

目标区分：

- 有可执行 Policy 的 PARTIAL可以发布。
- 首次研究全部失败或无可用 Policy：保存合法 PARTIAL供查看，保留已有活动集合。
- 完整研究明确退役全部：允许空集合发布。
- 初始化新 PARTIAL不混入未重研的旧 schema Policy填量。

当前 repository允许空 policies，不区分失败空集与研究退役；旧 INITIALIZE可能先被 SHELL_ZERO_POLICY挡住，零 Gap场景也不构成完整的空集保护。此区别须基于任务终态和最终处置证据实现，而不是 `if len(policies)==0: always reject` 或无条件切空。

当前 `PinnedDocument3Runner` 的身份哈希只含 ticker/D2 run/Event version，不含 as_of/新编排版本；initialize对已 published bundle早返回也不完整校验新请求绑定。新 schema/workflow/as_of要进入身份或强一致绑定，以免新架构复用旧 run。存储和request不能以“数据version已改”代替执行version隔离。

依据：`orchestrator.py:139,1787`；`repository.py:327,361,391`；`pinned_runner.py:15`；`ticker_initialization/research_adapter.py:401`；`persistent_runtime_v2/maintenance.py` 后续 journal提交链路。

## 12. 实施前应明确的工程决策与风险

以下不是本轮请求新增批准流程，是方案落地时需要写进合同和测试的细节。

1. **v3入口与旧v2.2只读策略。** 明确默认启用、父D2 v2.1选择、历史decode/展示，避免旧MAINTAIN写回新集合。prompt/skill本轮排除意味着工程完成后仍需对应资产才可做真实模型验收。
2. **Condition消费合同。** 明确命中方向、同时双向命中的最终决策、受影响条件重新校准和未受影响条件可用性；这是必要运行适配，不是可推迟的可视化工作。
3. **MAINTAIN patch v3。** 附件未定义；明确单节点完整upsert、部分坏记录保护、基线/空patch和元数据推进。
4. **owner命名。** 真Shell名若为OPEN或同名，需要宿主路由槽位区分并报告；不能改写经济scope或新增topic业务ID。Topic name稳定唯一；波次主键不依赖展示名文件路径拼接。
5. **新Projection合同。** 方案指定消费行为未指定新版本字面值；须显式选定并校验兼容，不能复用v4却改变语义。
6. **缺输入与系统完整性。** 可选D1/Reference等缺失应记不可用继续；读取hash冲突、lease丢失、写入失败不能伪装成研究未成立。无D2路线须同步处理下游强依赖。
7. **并行共享文件。** 只换成gather会引入单O3会话、全workspace diff、worklist、attempt ID的竞争；owner局部目录与宿主checkpoint必须先接通。
8. **PARTIAL和空集。** 提示提醒不应自动变全局闸门；但真实未完成调度、未整合、替换冲突要保留PARTIAL证据。失败空集不能覆盖旧活动集，显式退役空集不能一概禁止。

本轮未发现应否定四节点总体设计的逻辑冲突；上述问题是从旧实现迁移时必须解决的接边。不能把“保留旧consumer行为”“只改schema”“直接并行旧runner”当作完整实施。
