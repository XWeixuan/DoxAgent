# Document3 v2.1 编排重构方案

## 1. 版本、范围与最终决策

本方案冻结 Document3 INITIALIZE 的节点调度、输入投影、工作产物、交接协议、一次补研闭环、最小校验、恢复及发布合同。节点内部的研究方法和 prompt/skill 不在本文展开。

采用四种业务节点：

```text
Discovery → Global Planning → Policy Research & Build → Global Integration
线索发现   → 全局选题与分配 → Policy 深研与构建       → 全局覆盖整合
```

采用 N+2 条逻辑线程：N 条 Shell 研究线程、一条 OPEN 研究线程、一条 GLOBAL 协调线程。取消独立的纯 Policy Compile；其局部组织与字段编写并入 Research & Build，跨 Shell 协调并入 Global Integration。

只有一次可选的补研轮。补研可以包含多个预先冻结的 wave，但不能再生成第二份自动补研计划。

### 1.1 版本命名

“Document3 v2.1”是本次方案和编排版本，不回退当前文件已经使用的 `document3.v2.2` 数据合同。由于方向归属、来源结构等均发生不兼容变化，发布时采用：

```json
{
  "schema_version": "document3.v3",
  "workflow_version": "document3.v2.1"
}
```

版本严格按字符串识别，不按大小猜测结构。`policy_set_version` 继续使用现有递增发布版本，不重新从 1 开始。

### 1.2 三条实现边界

1. **文件承担事实交接，线程承担会话连续性。**恢复同一线程是优化，不是后续节点拿到事实的唯一办法。
2. **Agent 决定业务，代码决定调度和提交。**代码不生成 trigger，不做经济含义归并，也不判断边界是否足以交易。
3. **校验不阻塞工作流，不代表强行发布坏数据。**不可读取的局部产物隔离，其余继续；不存在无限修复、人工放行和全局语义质量闸门。

## 2. 完整调度拓扑

```text
PREPARE：冻结输入、建立目录和 Shell 切片
    │
    ├─ Shell A：Discovery
    ├─ Shell B：Discovery
    ├─ ……
    └─ OPEN：Discovery
              │ 所有已调度任务结束或有限失败
              ▼
GLOBAL：Planning，必要时分批读取发现产物，最后冻结 agenda
              │
    ├─ Shell A：Build wave 1 → wave 2 → ……
    ├─ Shell B：Build wave 1 → wave 2 → ……
    ├─ ……
    └─ OPEN：Build wave 1 → wave 2 → ……
              │ 所有主研究 wave 结束或有限失败
              ▼
GLOBAL：Integration 扫描各批完整 Policy，累计关系与覆盖缺口
              │
              ├─ 无需补研 ─────────────────────────────┐
              │                                     │
              └─ 冻结唯一 supplement agenda          │
                     │                               │
                  原 owner 线程执行有限补研 waves     │
                     │                               │
                  GLOBAL 读取新增及受影响部分 ─────────┤
                                                   ▼
GLOBAL：生成最终替换清单、必要的改写 Policy、覆盖结论
                                                   │
ASSEMBLE：应用替换、生成全部发布文件、原子切换发布版本
```

同一 owner 的 wave 严格串行。不同 owner 可并行，不设置“所有 owner 的 wave 1 都成功才运行 wave 2”的全局同步栅栏。

阶段间仅保留两次必要汇合：发现结束后全局选题；主研究结束后全局整合。汇合等待的是任务进入终态，不是全部任务成功或全部质量检查通过。

## 3. D2 v2.1 → D3 的输入合同

### 3.1 使用附件末尾修订后的正式拓扑

附件第 39、40 节覆盖第 31 节仍保留的旧示意。D3 正式读取：

```text
Shell
  name
  scope
  boundary
  ref[]
  units[]

Unit
  name
  scope
  horizon
  ref[]
  state
  expectation_baseline[]
  realization_factors[]
  potential_gaps[]
```

不再要求 `shell_id / expectation_id / gap_id`，也不继续把 `core_question / proposition` 当作新 D2 的必填字段。

Shell 仅决定研究上下文归属。Unit 是经济预期对象，不是已经规定好的兑现命题。

### 3.2 四类研究资产原样保留

| D2 资产 | D3 交接内容 | 不做的转换 |
|---|---|---|
| State | 参数口径、当前值、时间、来源身份及有效性 | 不转成未来 Condition |
| Expectation Baseline | baseline、ordinary_progress、open_frontier、time_scope、ref | 不冒充精确共识，不把 open_frontier 直接作为 trigger |
| Realization Factors | mechanism、current_status、materiality_context、scope_boundary、ref | 不转成“链条上所有变量必须一起满足” |
| Potential Gaps | name、why_live、revision_logic、possibility_space、ref | 不再读取已删除的 recognition_criteria 等字段 |

D2 的 baseline 可能为空，也可能只是有依据的默认未来路径；D3 不因缺少逐项 baseline 而拒收整个 Unit。

### 3.3 来源开放与工作归属分离

研究课题可以直接来自 D1、D2、Future Nodes、Entity Map、Event Library、通用催化资产或 Web 发现，不要求经过 D2 Gap 才能入场。

`owner` 只表示哪条逻辑线程负责工作，不是研究内容的来源限制。OPEN 发现的课题可以交给 Shell 线程；Shell 中发现的横向市场事件也可以交给 OPEN。

D2 的 open_discovery_scan、selection、resolution 等过程文件不作为正式预期研究默认注入。必要时可以作为候选发现或覆盖取舍的补充材料读取，但不能作为已成立的现实基线或传导结论。

### 3.4 时点与输入冻结

一次 run 使用一个 `as_of`，表示本轮研究截止时间。D1、D2、Reference View、Event Library 及其他资产按实际取得的版本冻结在输入 manifest 中；保留各资产自己的原始时间，不把较旧材料改标成最新。

本轮新 Web 证据以 `as_of` 为信息截止。中途不因为某线程查到新资料而单独抬高其 cutoff；`published_at` 也不能替代 `as_of`。

缺失的可选资产在资产目录中明确为空或不可用，继续运行，不伪造占位研究。D2 某个 Shell/Unit 不完整不阻断其他线程，GLOBAL 能看到具体缺项。

## 4. 上下文投影与线程管理

### 4.1 三层投影

**全局目录层**只放整个 ticker 的 Shell/Unit 名称、scope、boundary/horizon、研究资产目录、文件位置和必要的基础公司简介。不包含全部 State/Factor/Gap 正文。

**当前研究层**只放当前任务需要直接展开的 D2 正文。默认按当前 Shell 提供；当需要进一步收窄时，最细只按完整 Unit 切片，保留 Shell 头和 sibling Unit 目录，不再把 Unit 内部的 State、Baseline、Factor 或 Gap 拆开切片。

**共享研究材料层**保留 D1、Future Nodes、Entity Map / Relations、Reference View、Event Library、通用催化资产、实体/事件材料、外部来源及既有研究依据等冻结材料的完整原文，并原则上在各个业务节点均提供，不按节点做材料隔离，也不再为这些材料制作内容切片。Agent 是否实际读取和使用其中某项材料，由对应 skill 约束。

跨 Shell 的 D2 仍通过 Shell/Unit 定位读取；其切片规则与当前研究层一致，最细粒度为完整 Unit。

不截断单条 Condition 的 criterion/reference_state/trigger_boundary，也不把它们拆成互相缺失的输入。

### 4.2 各节点默认输入

| 节点 | 当前研究正文 | 共享研究材料 |
|---|---|---|
| Shell Discovery | 全局拓扑、当前 Shell 的 D2 切片 | D1、Future Nodes、Entity Map / Relations、Reference View、Event Library、通用催化资产、实体/事件材料、外部来源及其他冻结研究材料 |
| OPEN Discovery | 全局拓扑；需要读取 D2 时按 Shell/Unit 取得完整切片 | D1、Future Nodes、Entity Map / Relations、Reference View、Event Library、通用催化资产、实体/事件材料、外部来源及其他冻结研究材料 |
| Global Planning | 全局拓扑、发现线索；需要回看 D2 时按 Shell/Unit 取得完整切片 | 同一组完整共享研究材料 |
| Build | 本 wave 课题、原始线索、当前 Shell/Unit 的 D2 正文、已完成研究摘要 | 同一组完整共享研究材料，以及必要的既有 drafts / research results |
| Global Integration | 全局轻索引、当前批完整 Policy、累计关系记录、议程及结果摘要；需要回看 D2 时按 Shell/Unit 取得完整切片 | 同一组完整共享研究材料，以及任意原始 draft / research result |

各 D1 报告及其他非 D2 研究材料均以完整原文进入共享研究材料层，不设置 C1/C3/C5 等常用内容切片，也不因当前节点不同而隐藏材料。

Discovery、Build、Global Integration 开放 Data MCP 的全部可用接口。具体调用由对应 prompt/skill 约束：优先使用现有冻结材料与 Web Search；只有现有材料与 Web Search 无法提供所需数据，且能够明确判断 Data MCP 可提供该数据时，才调用 Data MCP。Global Planning 不因此新增 Data MCP 调用职责。

### 4.3 线程连续性与上下文恢复

不为换线程额外创建“记忆总结 Agent”。现有 discovery、agenda、results、review、consolidation 与原始文件就是显式恢复资产。逻辑线程数仍是 N+2，物理 session 可以因恢复而更换。

线程恢复不可用时启动同一逻辑 owner 的新物理线程，重新装载该任务所需的 D2 Shell/Unit 切片、共享研究材料和已经落盘的交接产物，继续尚未完成的任务。

## 5. 工作区与交付物

推荐保留以下业务产物类别，不继续维护多份含义重叠的 worklist/state/calibration 台账：

```text
inputs/
  manifest.json                 # 宿主维护的冻结输入目录
  topology.json                 # 宿主投影
  d2/shell-01.json ...           # 宿主切片；编号只是文件槽位
  d1/...                        # 原文与可用定位

work/
  discovery/<owner>.jsonl        # Discovery 输出
  discovery/<owner>.late.jsonl   # 有晚发现时才创建，同一 schema
  agenda.json                   # GLOBAL 选题和主 waves
  research/<owner>/<wave>/
    results.jsonl               # 每课题研究交接
    policies/*.json             # 单独 Policy drafts
  review.json                   # GLOBAL 累计关系与补研请求
  supplement_agenda.json         # 最多一份，与 agenda 复用结构
  supplement/<owner>/<wave>/...  # 与 research 相同结构
  final/policies/*.json         # GLOBAL 必要的最终改写件
  consolidation.json            # 最终替换和覆盖结论

output/
  document3.json
  runtime_projection.json
  coverage_map.json
  document3.md
```

源文件使用现有 artifact/workspace 体系。无需另建知识图谱、对象服务或向量库。

业务文件只由所属节点写；宿主负责 snapshot、格式读取、ID 分配、索引与发布。并行 Shell 不写同一份全局 JSON。

### 5.1 统一 ref

本版 D3 中间产物与 Policy 统一使用 `ref: string[]`，字符串为可追溯的冻结文件定位或外部来源 URL，例如：

```json
[
  "inputs/d2/shell-01.json#/units/0/realization_factors/0",
  "inputs/d1/C3.md#服务器需求",
  "work/discovery/shell-01.jsonl#L1"
]
```

JSON 路径、Markdown 节、JSONL 行号使用现有读取能力，不另建实体 ID。相对路径以本 run 的 artifact 根目录为基准，发布后依然可以经该 run 解析。

附件只列出了 D2 的 `ref[]`，没有给出底层元素完整类型；上述字符串形式是本版 D3 的选择，不宣称是 D2 已经实现的类型。输入 adapter 可把原有引用投影成实际 artifact 定位，并保留原始引用在冻结输入中。

`ref` 缺失默认按空数组处理并报告，不用伪造 D2 引用补齐。程序不因为某条 ref 暂不可读而阻断整条研究链。

## 6. Discovery：最小线索 schema

每个 JSONL 记录只有三个字段：

```json
{
  "name": "AI Agent的持久云端运行环境",
  "lead": "真实产品的执行环境出现变化，可能改变通用计算资源需求；当前尚需研究部署安排、资源净增量及目标公司的业务暴露。",
  "ref": [
    "inputs/d1/C3.md#新型工作负载"
  ]
}
```

`name` 用于识别和展示线索。`lead` 合并容纳现实变化线索、初步相关性和待解问题，不再拆出多套判断字段。`ref` 指向实际使用的材料。

不交付 direction、candidate_trigger、trade_sufficiency、minimality、judgeability、trigger_layer 或预设 boundary。已有事实可以自然写进 lead，但不需要给出准 Policy 才能进入下一阶段。

每条逻辑线程完成发现 turn 后，宿主保存不可变的初始扫描快照。后续不能重写这个快照；新增线索写入同 schema 的 `.late.jsonl`。晚发现不是新节点，也不会自动生成无穷调度任务。

## 7. Global Planning：研究议程 schema

```json
{
  "topics": [
    {
      "name": "AI Agent计算资源需求与CPU暴露",
      "owner": "计算产品市场",
      "brief": "研究运行方式变化可能影响的资源需求与供应商暴露，确定有哪些值得构建Policy的现实观察入口。",
      "ref": [
        "work/discovery/shell-01.jsonl#L1",
        "work/discovery/open.jsonl#L2"
      ]
    },
    {
      "name": "指数调整与被动配置事件",
      "owner": "OPEN",
      "brief": "研究该ticker可适用的指数变化事件、现有状态与可使用的消息边界。",
      "ref": [
        "work/discovery/open.jsonl#L3"
      ]
    }
  ],
  "waves": [
    ["AI Agent计算资源需求与CPU暴露"],
    ["指数调整与被动配置事件"]
  ],
  "not_selected": [
    {
      "ref": "work/discovery/open.jsonl#L4",
      "reason": "与已经选中的课题实质重复，相关材料已并入其研究范围。"
    }
  ]
}
```

每个 Topic 仅四个字段；不增加 topic_id、priority score、readiness 或 direction。

`name` 在本轮议程内唯一并在冻结后稳定。`owner` 使用真实 Shell 名称或保留路由名 `OPEN`，不是额外的业务 ontology。`brief` 是研究任务，不是必须证明的结论。

多个原始候选可以共同引用到一个 Topic。Topic 可以形成零条、一条或多条 Policy；一个 Policy 也可以承接多个 Topic。以上关系不再要求与 D2 Gap 一一对应。

`waves` 是 Topic 名称的二维数组。每个 wave 的 Topic 属于同一 owner；owner 从 Topic 记录读取，不在每个 wave 重复存储。数组位置足以定位调度单元，不增加 wave 业务 ID。

未被引用也未在 not_selected 交代的原始线索只产生覆盖提醒，继续调度；不能被自动视为已研究或已否定。

### 7.1 Planning 过大时

GLOBAL 按 owner 批次读取 scan，累计 agenda 草稿，最后完成一次全局选题和 wave 整理，才冻结可调度的 agenda。不得读完 Shell A 就立刻让其 Build 启动，否则尚未看到其他来源便完成了事实上的局部选题。

Planning 的分批读取属于同一节点，不新增“候选审计节点”。

## 8. Wave 分配与执行规则

### 8.1 默认分法

采用 **owner 内按共享研究背景合并课题，通常 1–3 个 Topic 一 wave**。相关 Unit 可共享 wave；一个复杂 Topic 单独占一 wave。既不按每个 Policy 拆线程，也不把整个 Shell 压进一个研究 turn。

工程初始默认：

```text
topics_per_wave = 3
max_parallel_owners = 3
```

前者是装载与分组参考，不是经济学门槛；强相关的少量课题可以由 Planning 合理并组。后者只控制并发资源，不影响 OPEN 是否执行或覆盖要求。

不设置每 Shell Policy 数量配额、LONG/SHORT 配额或层级数量配额。

### 8.2 主调度

1. 冻结 agenda 后，以 owner 分出队列，同 owner 按其在 waves 中出现的顺序执行。
2. 某 owner 完成一个 wave 后即可运行自己的下一个，不等待其他 owner 同序号 wave。
3. 一个 wave 对应一次 Build 业务 turn，turn 内可进行多次资料读取和工具调用。每次尝试使用现有有限的 turn 时间/工具预算；超时中止该尝试，不能等待文件出现而无限挂起。
4. 未完成的课题写出当前结果或由宿主记录缺项，进入全局缺口判断；不由 Build 无限续建 wave。

主轮 Build 的调度总量由冻结 agenda 决定。后续真正不同的新方向可记录到 late 线索，由一次补研机会统一处理。

### 8.3 轻量结构修正

同一 Topic 被重复排入 wave：代码保留首次调度，后续重复仅报告。已选 Topic 漏排 wave：按既有 owner 补入队尾并按默认批量分组。不存在的 owner：送至 OPEN 并保留提醒。一个 wave 混入多个 owner：按 Topic 已有 owner 拆成各自队列，保持原顺序；不重新判断课题内容。

这些是调度修正，不是选题或经济含义判断。代码不把未选候选自动升级为研究 Topic。

## 9. Research & Build：交接产物

### 9.1 一个 Topic 一条结果记录

```json
{
  "topic": "AI Agent计算资源需求与CPU暴露",
  "policies": [
    "work/research/shell-01/1/policies/01.json"
  ],
  "notes": "保留后续整合所需的研究结论、关键比较依据和重要取舍；这里不是思考过程逐字记录，也不再复述整份Policy。仍未解决的问题一并说明。",
  "ref": [
    "inputs/d2/shell-01.json#/units/0",
    "inputs/d1/C3.md#新型工作负载"
  ]
}
```

`policies` 允许为空。空数组可以表示研究后不应形成 Policy，也可能表示边界仍无法建立；区别由 notes 说明，GLOBAL 决定是否作为需要补研的缺口。

不要求输出 TRIGGER_READY、d2_boundary_sufficient 或一组“充分性已通过”的枚举。未发生新实质研究的字段映射不算完成研究，但这属于节点业务要求，不由宿主写成硬编码门槛。

### 9.2 Policy 文件

每份 Policy 独立保存，业务结构直接使用第 13 节的 Published Policy，不再有一套比 Published Policy 更复杂的 Trigger Calibration schema。

只在 ID 上保留草稿便利：草稿可以暂不填 policy_id/condition_id。宿主在首次接受该文件时分配，后续重写同一文件保持 ID。results 引用文件路径，因此不依赖 Agent 预先取得 ID。

首次分配后的工作副本可供后续节点读取。ID 不从 title、direction 或 calibration 的文本哈希生成，避免标题中性化或基线更新造成身份漂移。

同一 wave 的研究节点只写自己的目录。其他线程的 drafts 为只读；跨 Shell 改写留给 GLOBAL。

### 9.3 节点内 checkpoint

完成一份 Policy 后先保存完整 JSON；完成一个 Topic 后保存结果记录。建议使用临时文件后原子替换，避免一次截断破坏已经完成的 JSON。

这些保存只是耐久化，不触发额外的业务评审 turn。若 turn 中断，已完整保存的文件仍可提交，未完成部分不拖住下一阶段。

## 10. Global Integration：分批阅读与累计关系

### 10.1 主研究池冻结

主 Build 全部进入终态后，宿主收集可读取的主轮 Policy，形成不可变的主研究池 B。保留原始 drafts，不立即执行 merge。

宿主从实际 Policy 生成轻索引：policy_id、title、transmission、match_scope、Condition 的 id/decision/trigger_layer/criterion、文件位置。索引是投影，不由模型另写一份摘要作为唯一事实来源。

默认按 owner 和原研究 wave 分批读取，通常每批不超过约 20 条 Policy，并受上下文装载预算约束。单条 Policy 内容长时批量更小。

每批提供完整 Policy，包括所有 calibration；全局目录用于发现其他批次可能存在的相关对象，需要比较时再取其完整内容。不依赖模型只凭标题做最终合并。

### 10.2 累计产物 review.json

```json
{
  "relations": [
    {
      "policies": ["pol_A", "pol_B"],
      "proposal": "两条Policy可能描述同一观察入口；当前仍需比较具体边界，暂不删除任何原稿。"
    },
    {
      "policies": ["pol_B", "pol_C"],
      "proposal": "主题相关，但可能是不同层级的独立信息增量，不能仅因终点相同就合并。"
    }
  ],
  "research_requests": [
    {
      "name": "外部需求冲击的早期观察入口",
      "owner": "计算产品市场",
      "brief": "补充当前产物中尚未校准的外侧消息入口。",
      "ref": [
        "work/research/shell-01/1/policies/01.json"
      ]
    }
  ],
  "coverage_notes": "累计保留覆盖判断，不把已读部分压缩成一个替代原稿的新PolicySet。"
}
```

只有 GLOBAL 写这个文件；每批结束宿主保存最近可读快照。relations 是待判关系，不是马上执行的操作指令。

A 与 B 相关、B 与 C 相关，不自动推出三者应合并。代码可以帮助调出关联材料，但不能自动做传递闭包式的业务 merge。

未写入 relations 的 Policy 不意味着没看过。阅读进度由调度器记录，不给每条 Policy 增加 reviewed=true 等字段。

## 11. 唯一补研轮

### 11.1 触发与冻结

GLOBAL 完成主研究池的覆盖扫描后，才确定是否需要补研。需要时，将 research_requests 收敛为一份 `supplement_agenda.json`，复用第 7 节的 topics/waves 结构，不重新跑 Discovery 与 Planning 全链路。

调度器在分发任何补研任务之前持久化 `supplement_dispatched=true` 和计划位置。本标记在恢复、重试或模型输出变化后均不能自动重置。

### 11.2 “一轮”的准确含义

一轮是**一份冻结计划的一次有限执行**。它可以包含多个 owner、每个 owner 多个有限 wave；不是强迫全部缺口挤进一个 turn。

执行期间不接受自动追加到该计划的新任务。补研中再发现的新方向保存为剩余缺口，不触发第二份 supplement_agenda，也不绕回主轮重新排 wave。

技术失败的有限重试仍属于同一个已调度任务，不算新补研轮，但必须计入同一任务的尝试次数。

### 11.3 补研输出与后续处理

补研沿用 Build 输出，写入独立 supplement 目录。它可以提出新增 Policy 或对旧 Policy 的替代草稿，但不能直接修改或删除主研究池 B。

补研结束后，GLOBAL 只实质展开新增产物及受影响的原稿/关系组，同时保留整个 Policy Set 的轻索引。不得要求再全量重做一遍所有 Shell 的深研。

补研稿默认只是候选，只有被最终替换清单接纳才进入发布集合；不能把“旧稿+新改写稿”机械并列全部上线。

## 12. 最终一致收敛：替换清单而不是顺序 merge 链

### 12.1 consolidation.json

```json
{
  "replacements": [
    {
      "before": ["pol_A", "pol_B"],
      "after": ["work/final/policies/combined.json"],
      "reason": "同一观察入口，整合为一条具有独立方向条件的Policy。"
    },
    {
      "before": [],
      "after": ["work/supplement/open/1/policies/01.json"],
      "reason": "接纳补研形成的新观察入口。"
    }
  ],
  "coverage": [
    {
      "topic": "AI Agent计算资源需求与CPU暴露",
      "policies": ["work/final/policies/combined.json"],
      "note": "说明该课题最终覆盖的入口与仍保留的限制。"
    }
  ],
  "remaining_gaps": [
    {
      "name": "另一个重要外部变量的比较锚",
      "reason": "一次补研后仍未建立可用边界，本轮不继续追加研究。"
    }
  ],
  "summary": "对整套覆盖的最终判断；不是全开放世界已穷尽的保证。"
}
```

`after` 和 coverage.policies 使用 Policy 文件定位，宿主发布时解析成正式 ID。coverage 覆盖全部已进入主研究或补研的 Topic；未选线索仍保留在 agenda 和扫描快照中。

coverage 可以由宿主预填事实性去向供 GLOBAL 修改，但拆分、合并后的实际语义覆盖由 GLOBAL 确认，不能把“存在来源关系”自动当作“已完整覆盖”。

### 12.2 替换语义

每项 replacement 表示一次完整集合替换：

```text
一条 → 一条：改写
多条 → 一条：合并
一条 → 多条：拆分
若干条 → 空：移除
空 → 若干条：新增
```

不新增 action enum、merge_group_id、权重或优先级字段。

最终集合为：

```text
F = (B − 全部成功替换的 before)
    ∪ 全部成功替换的 after
```

未被替换的主稿自动保留。补研稿和 GLOBAL 改写稿未出现在 after 中，不自动进入 F；其去向应在 coverage/remaining_gaps 或备注中说明，缺失只报告。

### 12.3 一致性与失效处理

同一主稿不能出现在两项最终 replacement 的 before 中。关系记录可以重叠，但最终执行清单必须由 GLOBAL 先收敛成不重叠替换组。

例如 A-B、B-C 两个待判关系，最终可以决定合并 A/B、保留 C；也可以比较后统一处理 A/B/C。但不能让代码按先后顺序自动执行两个相互覆盖的 merge。

每项 replacement 先确认 before 可定位、after 可读取，且应用后身份不冲突，再整体应用。若该组不完整，整组不执行，保留原 before；其他独立组照常执行，并将失败组写入剩余问题。冲突组不采用“谁先出现谁获胜”。

这是局部结构提交，不是经济质量审核。绝不出现先删旧稿、随后才发现新稿不存在的半次替换。

### 12.4 不要求一个大输出 Turn

GLOBAL 可以在同一 Integration 阶段分批写受影响的最终 Policy 文件，最后完成 consolidation 清单。待处理组是主扫描和一次补研后形成的有限集合，不由每次写入再递归生成新组和新研究轮。

不要每完成一批就用新 merge_vN 覆盖整个主池并丢弃旧信息。

### 13.1 完整结构

```json
{
  "schema_version": "document3.v3",
  "workflow_version": "document3.v2.1",
  "ticker": "EXAMPLE",
  "policy_set_version": 14,
  "as_of": "2026-10-03T08:00:00Z",
  "publication_state": "PARTIAL",
  "document2_ref": null,
  "event_library_ref": null,
  "policies": [
    {
      "policy_id": "pol_example",
      "title": "关键任务结果与后续商业执行能力",
      "ref": [],
      "transmission": "该任务的不同结果通过能力确认或执行风险变化影响后续商业预期；各方向机制及触发边界分别校准。",
      "match_scope": "该任务的准备、执行结果、异常及对后续执行安排的相关消息。",
      "activation_conditions": [
        {
          "condition_id": "C1",

          "calibration": {
            "reference_state": "该事件所在层级的当前现实及已建立的默认预期。",
            "trigger_boundary": "相对上述基线，该方向独立成立的最低有意义变化。"
          }
        },
        {
          "condition_id": "C2",

          "calibration": {

            "trigger_boundary": "独立校准的SHORT边界，不由LONG边界取反生成。"
          }
        }
      ]
    }
  ],
  "published_at": "2026-10-03T09:00:00Z"

```

以上仅为结构示例，不是经过研究的可交易 Policy。

### 13.2 字段约定

PolicySet 元数据由宿主填写。`document2_ref` 与 `event_library_ref` 沿用实际可用的既有快照对象，缺失时为 null；不为填满对象编造 run_id/hash。全部其他输入的版本保存在 run 的 input manifest，不再每条 Policy 重复。

Policy 保留 policy_id、title、match_scope、activation_conditions；`source_refs` 换为统一 `ref[]`，新增 transmission。Condition 保留 condition_id、criterion、calibration；decision 从 Policy 下沉，新增 trigger_layer。

Published 可执行 Policy 至少有一个可读取的 Condition。decision 只接受 LONG/SHORT；trigger_layer 只使用 OUTER/MIDDLE/INNER。它是粗位置标记，不承担 DAG、依赖关系或执行优先级。

除上述方向、层级、发布状态和版本外，不增加业务分类枚举。ref 可以为空。其余新业务字段按完整 schema 交付；不完整记录按第 15 节局部处理，不阻断整个发布。

### 13.3 对已有运行语义的必要更新

同向 Conditions 仍为独立充分的替代入口；不同方向不要求同时存在，也不要求对称。不得继续读取 policy.decision 或用缺省 LONG 补它。

Policy 本体是中性的观察与决策范围，**不能再把“一条 Condition 触发”解释成“整个 Policy 的所有方向永久消费完毕”**。当前基线受影响时，应重新校准受影响条件；另一方向不能因为归在同一 Policy 就被机械删除，也不能不经重校准永久有效。

transmission 是预先研究的联系，不是所有环节都必须被新消息证明的隐藏 AND。INNER 不等于财报事件；财报可作为基线来源，但财报交易不因 INNER 覆盖要求而重新进入可交易集合。

## 14. ID、Runtime 投影与发布产物

### 14.1 最小身份

只保留有明确运行用途的 policy_id、condition_id。研究线索用文件定位，Topic 用名称，wave 用数组位置；不增加 path_id、candidate_id、transmission_node_id、merge_id。

policy_id 由宿主在首次接受 draft 时分配，至少在本 run 和后续对同一 Policy 的维护中稳定。condition_id 在 policy 内唯一，运行时使用 `(policy_id, condition_id)`。

最终重写同一观察范围可保留 ID；合并由 GLOBAL 显式选择保留的旧 ID 或采用新 ID；拆分需要为新对象分配新 ID。源 snapshot 及本次替换记录保留历史去向，不新增运行时 alias 图。

### 14.2 runtime_projection.json

完全由最终 document3.json 生成，不允许 Agent 独立写一份可能不一致的 Runtime Policy。

R1 使用中性 title、match_scope、必要的 transmission，不以顶层方向过滤。R2 接收被召回 Policy 的全部方向 Conditions 和完整 calibration，避免只投影预判方向后重复出现反向漏判。

W2 的命中归属于具体 Condition。两个方向同时满足时保留双方命中证据，交由既有最终决策流程处理；schema 不用优先级、净分数或顺序覆盖来替运行时选方向。

本方案只规定消费接口的必要兼容，不重写 W1/W2/W3 内部研究任务。

### 14.3 其余输出

`coverage_map.json` 由 consolidation.coverage、remaining_gaps、summary 和调度器记录的实际缺失拼合，文件定位解析为正式 Policy ID。没有最终 coverage 结论时，可以输出事实性已完成/未完成情况，但不得伪造“全局覆盖已评估”。

`document3.md` 是最终 JSON 和覆盖结论的展示投影。所有输出来自同一份 F、同一 policy_set_version 和 as_of，不分别取不同阶段稿件。

## 15. 最小、非阻塞 checkpoint 与校验

### 15.1 只保留四处业务 checkpoint

| checkpoint | 保存内容 | 不做什么 |
|---|---|---|
| Discovery turn 结束 | 初始 scan 的冻结快照 | 不要求线索达到交易充分性 |
| Planning 结束 | 可调度的主 agenda | 不要求每个 Gap 均有 Policy |
| 每个 Build wave 结束 | 已完成 Policy 与 results | 不按 Trigger 数、方向数、层级数打分退回 |
| Integration 每批/最终结束 | 最新 review；最后 consolidation | 不新增逐 Policy 审计 Agent |

Policy 文件和 Topic 结果在 turn 内逐项保存就是微型 checkpoint，不再额外输出 Stage-A state、wave_state、worklist progress 等多份业务进度表。

上述 checkpoint 同时作为断点恢复点。运行中断后，宿主从最近可读 checkpoint 恢复当前任务；已经进入终态的前序节点、owner 或 wave 不因恢复而重新执行。

### 15.2 校验仅分两类

**结构可读性：**文件能否解析；最小对象结构是否可被下一阶段或 Runtime 消费；引用的输出文件是否存在；本轮ID是否可区分；替换清单是否结构一致。

**提示性诊断：**来源无法定位、候选未交代、所选 Topic 未返回、某个方向或层级显著缺失、比较锚可能不完整等。诊断不产生 BLOCKED/PASSED 闸门，不强制触发重做。

代码不检查“有两个季度就违规”“必须存在 OUTER”“至少多少 Policy”“baseline 需要多少个数字”等投资语义，也不硬编码非财报事件分类来做关键词删除。

### 15.3 故障处理合同

| 情况 | 处理 |
|---|---|
| 一行 scan/result JSON 损坏 | 保留可读记录，隔离坏行，继续 |
| 一个 Condition 无法供 Runtime 读取 | 隔离该 Condition；其他完整 Conditions 保留 |
| 一个 Policy 顶层不可读取，或无剩余可用 Condition | 不进入本次可执行集合；保留原工作稿与原因 |
| ref、计数或非执行性进度信息缺失 | 提醒或由宿主计算，不退回整阶段 |
| 模型回复声称完成，但产物缺失 | 按实际文件记录缺项；不相信完成措辞 |
| 模型回复异常，但已保存完整产物 | 接受完整产物；缺失部分仍可标 PARTIAL |
| 一个 owner 的 turn 失败 | 结束该任务并继续其他 owner；进入全局可见的缺项 |
| GLOBAL Planning 无可读结果 | 使用最近可读议程；连议程也没有时主研究为空，带原始 scan 进入 Integration，仍只允许使用一次补研机会 |
| GLOBAL 整合批次或最终清单失败 | 保留最新可读累计记录；没有可应用的最终替换时使用可读主研究池，明确全局整合未完成并标 PARTIAL，不假装完成去重或覆盖评估 |
| 最终某一替换组结构不成立 | 整组不应用，原稿保留；其他组继续 |
| 补研后仍有缺口 | 留 remaining_gaps，进入发布，不再循环 |

重要区别：**继续工作流不等于给坏记录补一个猜测的 decision、boundary 或 baseline。**

### 15.4 重试上限

不为业务质量、unresolved 或提示性诊断自动重试。

网络、进程、传输等明确技术失败，沿用宿主有限重试，默认最多一次额外尝试；它继续相同任务和工作目录，不新建业务 wave。尝试耗尽后标记终态并继续。

不增加“修 JSON Agent”“恢复审计 Agent”或无限 repair loop。纯文本代码围栏等无语义包装可由宿主去除；缺失业务内容不由代码制造。

## 16. 最小运行状态与恢复

沿用现有 SQLite/运行状态设施，只需在逻辑上记录：

```text
当前 phase
owner → physical_thread_id
已结束的任务及有限尝试次数
supplement_dispatched
主 agenda / supplement agenda / 最近可读产物位置
```

任务用现有 run 标识加 `(阶段, 主轮或补研, owner, wave序号)` 定位。它是调度主键，不进入业务 schema。

不要同时再维护 processed_gap_count、unprocessed_path_count、completed_shell_ids、path_dispositions 等可从任务和文件推导的多套完成状态。

明确支持断点重跑与恢复。恢复时，已结束任务不重跑，已完成文件不重新分配 ID。运行中断的任务从最近可读 checkpoint 在同一任务主键和工作目录下继续；若当前 turn 无法继续，则允许重跑当前未完成任务，技术失败的尝试次数仍受第 15.4 节限制。重新提交同一个完成产物不能导致重复增加 Policy。

同一物理线程不同时执行两个 turn。线程恢复不可用时新建物理线程，但复用逻辑 owner、任务主键、最近可读 checkpoint 和现有交接文件。恢复或断点重跑不得重新生成已冻结的 agenda、不得重置 `supplement_dispatched`，也不得重复执行已经完成的 replacement。

## 17. 发布状态与发布提交

### 17.1 COMPLETE / PARTIAL

`COMPLETE` 表示本轮已经选中的工作完成并有最终覆盖处置，没有未完成的必需调度任务或未解决的本轮补研缺口。它不表示开放世界已穷尽，也不要求全部候选都形成 Policy。

明确研究后不成立、经济意义不足或不适用的课题，可以以零 Policy 的研究结论正常关闭。因事实/边界未建立而仍需后续处理的课题进入 remaining_gaps，对本轮标记 PARTIAL，但不阻塞。

技术缺项、不可执行的遗漏、未完成的全局整合或替换冲突也进入 PARTIAL。状态由实际任务和最终剩余问题决定，不由 Agent 的 PASSED 口号决定。

### 17.2 原子发布

先在新版本目录内生成 document3.json、runtime_projection.json、coverage_map.json、document3.md，完成最小可读取检查后，再一次切换活动版本指针。不得先切主 JSON，再慢慢生成对应 Runtime 投影。

有可执行 Policy 的 PARTIAL 可以正常发布。首次初始化全部失败、没有任何可用 Policy 时，保存合法的 PARTIAL 结果供查看，不把已有活动集合替换为空。经完整研究明确决定退役全部 Policy 的空集合，则可以通过显式最终处置发布为空；它不同于失败造成的空输出。

发布写入本身失败时保留旧活动版本、记录终态错误，不进入无限等待，也不宣称新版本已经上线。

初始全量重构的 PARTIAL 集合不自动掺入“本轮没研究到的旧版 Policy”来填数量，避免不同时点、不同 schema 混用。

| 独立 Policy Compile | 取消；局部研究表达归 Build，跨 Shell 协调归 Integration |
| Final Review | 改为分批覆盖扫描、累计关系、一次补研分配、最终一致收敛 |
| D2 Gap 强制 Path 校验 | 删除唯一来源约束；改为开放 ref 和研究议程 |
| worklist / trigger_calibrations / calibration_state / 重叠 wave_state | 由 scan、agenda、results、review、consolidation 和宿主状态替代 |
| schema.py / JSON Schema | 新建明确的 v3 数据合同，保留 v2.2 历史读取 |
| Runtime Projection / W2读取 | 适配 Condition.decision、完整双向 Conditions 和 transmission |
| coverage_map | 从 Gap 数量闭环改为研究课题去向与真实剩余缺口 |
| stable IDs / artifact发布 / 恢复 | 保留确定性能力，适配新生命周期 |

v2.2 旧稿只读兼容。可在内存投影中把顶层 decision 下沉用于展示或旧结果回放，但不能仅靠结构搬运就宣称完成中性化、双向覆盖、transmission 或新边界研究。本次 INITIALIZE 重新研究生成新集合，不机械给旧稿补反向 Condition。

MAINTAIN 至少必须同步适配新字段、来源及 Condition 级方向，不能继续写回 policy.decision 或强制 Gap 引用。本方案不另行重构 MAINTAIN 全链路；既有局部维护可复用 Build 与受影响范围的 Integration，不能在初始化迁移后继续由旧 serializer 覆盖新文档。

## 19. 工程验收场景

这些是调度和数据合同测试，不是新增研究质量闸门。

1. D1/Web 产生但无 D2 Gap 的课题可以通过发现、排 wave、Build 和发布全过程。
2. OPEN 与 Shell 同时发现的候选可以合并为一个课题，不重复安排深研；原线索仍可追溯。
3. 5 个 Shell 中一个失败，其余与 OPEN 继续；全局最终输出明确 PARTIAL，而不是永久等待。
4. selected Topic 漏排 wave 会被补入队尾；未选候选不会被代码擅自升级。
5. 单 Policy 支持 LONG C1/C2、SHORT C3；R1 中性召回后 R2 能看到全部方向和 calibration。
6. A-B 与 B-C 的待判关系不会被代码自动合并成 A/B/C；冲突替换组不执行且其他组照常发布。
7. 合并后只出现一份最终 Policy，不同时发布主稿和补研改写稿；拆分后的课题覆盖有明确最终去向。
8. 补研阶段恢复、技术重试或再发现缺口，均不能触发第二份补研计划。
9. Context 重建后仍能从 agenda/results/review 和原文恢复，不依赖隐藏会话记忆；不把完整 D2 注入每个节点。
10. 某个 JSON 或 Condition 损坏，不丢弃全部同级成果；程序不猜测缺失的交易方向或边界。
11. Runtime 投影与主文件始终属于同一发布版本，不出现新主文件配旧投影。
12. 初始研究失败造成的空结果不清空旧活动集；明确退役产生的空结果可以按最终处置发布。

## 20. 方案收束

本次编排只增加一种业务节点类型，不增加独立专家网络和审计网络。关键交接压缩为：

```text
scan：发现了哪些值得研究的线索
agenda：哪些课题交给谁、分几批研究
results + policies：研究得到了什么和真正可交付的规则
review：跨批次有哪些待协调关系与覆盖缺口
consolidation：最终替换哪些稿件、保留什么、还缺什么
```

早期不预先定型，深研按有限课题批次投入，整合不丢失原始差异，补研有且仅有一次机会；所有业务检查都不能把流程拖入无穷回路。
