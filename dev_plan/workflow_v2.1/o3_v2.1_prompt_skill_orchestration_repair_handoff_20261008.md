# O3 v2.1 编排修复同步说明：供 prompt/internal skill 会话使用

日期：2026-10-08。配套：[编排修复方案](C:/Users/WEIXUANXIE/Desktop/DoxAgent/dev_plan/workflow_v2.1/d3_v2.1_orchestration_repair_plan_20261008.md)。

**本说明已按 2026-10-08 本地实际实现更新；代码已实施，不代表正式启用或部署。** 本轮未修改 prompt/skill；正式默认仍是 v2，旧版资产在 v2.0_legacy。另一会话应结合本说明适配新资产；本轮新 SDK Pilot 与验收结果见配套验收记录，内容侧仍需联合验收。原 `o3_v2.1_prompt_skill_orchestration_context_20261006.md` 对 GLOBAL 研究、affected 和 final 分批的旧描述须按这里纠正，其他未涉及的 Policy 业务原则仍保留。

## 1. 最重要的变化：GLOBAL 不是研究 owner

冻结设计是 N 个 Shell 研究线程 + OPEN 研究线程 + GLOBAL 协调线程：

| 阶段 | 执行 owner | 职责和交付 |
|---|---|---|
| Discovery | Shell、OPEN | 从材料发现 Lead，交付 Lead JSONL |
| Planning | GLOBAL | 汇总 Lead、建立 Topic/waves/not_selected，交付累计 Agenda |
| Build/唯一补研 Build | Shell、OPEN | 研究当前 Topics，交付完整 Policy 草稿及每 Topic Result |
| Integration 主审查/补后复核/最终写入/Consolidation | GLOBAL | 跨稿判断、记录编辑与研究请求、根据已有成果写候选、最终集合交易 |
| 日常 MAINTAIN | 既有单 MAINTAIN 调用 | 完整 upsert/retire 和 gaps；不改成多节点流程 |

原实现让 GLOBAL 做 Discovery，又允许 Planning 把 Topic.owner=GLOBAL，进一步执行 Build，导致相关指导被污染。新宿主已取消这些任务，不给 GLOBAL 注入 Discovery/Build skill。GLOBAL 第一个业务调用是 Planning，持续 thread 内只延续协调工作。

Topic 仍只有 `name / owner / brief / ref` 四字段。owner 只能选 task 中允许的 Shell 名/槽位/限定别名，或 OPEN。不能因题目跨 Shell、需要全局视野、属于平台机会就填 GLOBAL；这类研究应交给 OPEN，GLOBAL 保留全局议程与最终整合职责。无效 owner 宿主会退 OPEN并记诊断，agent 应主动输出合法路由。

这不是禁止 GLOBAL 在 Integration 使用其获授权的必要核实工具，而是禁止它承担独立 Discovery/Topic Build。需要委派的补研由 research_requests 交给 Shell/OPEN，仍只有一轮。

## 2. 读取范围和处理范围必须分开

主 Review 会获得本轮**全部已接纳主 Policy 完整 JSON**的只读参考池。不是只有当前批正文和其他稿标题；索引中的每份稿都有 ref、ID、版本来源、SHA 和可读 local_path。补研后 GLOBAL 还能读取全部补研稿、两轮 Result 和后续已接纳候选。

每次请求有明确当前 batch/focus_directories，主审查、post Review 和 final_write 最多 5 个焦点/编辑归属目录一批。批次只规定“这一轮要重点交付什么”，不限制读取其他稿。跨批覆盖、合并、重复或边界判断必须读取相关完整 Conditions/calibration，不能以标题索引、累计 Review 摘要或记忆替代正文。

使用 task 的 `policy_catalog` 和 `read_mapping` 找实际 owner 工作区文件。业务 ref 是规范来源身份，local_path 是读取位置；它可能是哈希命名的派生 JSON。不要猜另一 owner 的路径，不把派生文件名当业务身份，也不要把物理原路径不存在一概上报为源资料丢失。

实际索引使用轻量总导航 + 每材料独立索引：task.context_reading.sources 给出对应材料的 index_path/read_context 路径。先选择材料，再用该材料的读取器；不要把总导航 JSON 当作单份内容索引传给读取器。全文始终可直接从 read_mapping 读取。此处复用公共读取器，未改变 D2 的索引语义。

Result 的推荐聚合文件是 results.jsonl，也兼容 result.jsonl/result.json/results.json。实际 Pilot 证明每 Topic 独立 result_*.json 也是符合原交付结构的合理形式，因此宿主还接纳同 wave 顶层 result/results 后接下划线或连字符的 JSON/JSONL（例如 result_auto.json）。新技术 task.result_delivery 明确给出 preferred_path 和可接纳命名/目录范围；优先按这个声明交付，避免隐含文件名约束。均按 ResearchResult 结构逐条验证、同 Topic 重复去重，真冲突局部诊断；不会把目录里任意 JSON 当成 Result。policies 仍指实际合法 wave 内 Policy 路径，不填 ID。

共享原始 D2/Global 等材料仍冻结；材料标明源时间/版本及可用性。已有 Result、可追溯研究记录可以复用，不能把不同上游时间伪称为最新统一快照。没有被交付的历史 citation 存档不会凭空存在：无存档、外部 URL、未配置、已发布但空、投影失败须区分，按实际情况报告限制。

## 3. Review 要区分三个对象

| 对象 | agent 如何表达 | 宿主如何执行 |
|---|---|---|
| 参考材料/关系说明 | Topic.ref、relations、只读 catalog 中相关稿 | 提供全文供比较，不据此再调度稿件 |
| 已有依据，待直接编辑 | 新增 Review.edit_requests | 留到 final_write 生成完整候选，不开启补研 |
| 尚缺关键事实，待补研 | Review.research_requests，沿用 Topic 四字段 | 冻结后由 Shell/OPEN 完成唯一补研 |

`relations` 保留原合同：对象列表和 proposal，表达比较、覆盖、合并建议等。**提到 B 不意味着 B 受补研影响；ref 引用 B 也不意味着 B 需要重处理。** 如果关系判断确实要求新文本，必须显式记一项 edit_request，不能指望宿主从 proposal 的自然语言推断编辑任务。

某对象可以同时有一项已经确定的编辑和另一项未决补研，不必把一切修改都绑到新研究。直接编辑请求保存的是后续要改什么，当前 Review 仍不能覆写 B。

### 3.1 新增的最小字段

Review 继续输出 `relations / research_requests / coverage_notes`，增加 `edit_requests`，无编辑时写 []。

```json
{
  "relations": [
    {
      "policies": ["output/work/v21/research/OPEN/0001/policies/a.json", "output/work/v21/research/S0001/0002/policies/b.json"],
      "proposal": "A 与 B 共享比较基准，当前仍各有独立观察边界。"
    }
  ],
  "research_requests": [],
  "edit_requests": [
    {
      "policies": ["output/work/v21/research/OPEN/0001/policies/a.json"],
      "instruction": "按已经读到的原始材料纠正 A 的对象范围，保持独立观察边界；现有证据足够，无需新补研。修改完整正文及受影响条件，其他成立条件保留。"
    }
  ],
  "coverage_notes": "B 仅作比较参考，不需要修改。"
}
```

policies 至少一个对象，优先使用完整已接纳稿 ref/path；instruction 是一段明确的编辑要求，保存依据与预期处理，防止跨阶段丢失。没有固定操作枚举、打分、审批、编辑单状态或多层证明字段。

多份稿合并可放同一个 policies 列表，写清改什么；同 Policy ID 的 B/补研版本都存在时必须用 path 指定版本。纯保留或退休可由最终集合交易表达，不需要先造一份内容未变的稿。宿主不做经济意义上的“相似稿自动合并”。

### 3.2 主 Review 和 post Review 都是累计交付

每批读取上一份健康累计 Review，保留前批已经成立、尚待完成的编辑和研究请求，更新当前重点对象。不能只交付本批片段而丢掉前批决定。

主审查最后累计 `research_requests` 是补研内容的权威。若保留补研 Agenda 文件输出，它只能安排这些 Topic 的 waves，不另造一套研究请求，不改变它们的内容/owner。宿主可结构化补齐遗漏的 waves，不增加补研 Planning。

post Review 对补研稿作判断，同时维护最终待编辑清单。原编辑决定若因新证据不再需要，可以明确撤销；显式 edit_requests=[] 表示当前没有待编辑任务，不能一边清空字段一边仅在 coverage_notes 暗示“以后还要改”。未解决的 research_requests 留作 gap，不会开启第二次补研。

final_write 和 Consolidation 都读取**最新健康的 post Review；没有 post 时读取主 Review**。不再出现 final 用新判断、集合交易回到旧主 Review 的情况。

## 4. 用 A/B 场景理解新工作方式

**A 需要补研，B 是比较基准。** research_request.ref 可以同时指 A/B。研究 owner 读取 B 全文，研究 A；B 不因此进入另一批补研或 post 重点审查。A 的新稿在 post 中被复核，B 全文仍可随时读取。

**补研 A 后确认 B 无需改。** 保留关系判断和覆盖说明即可，不记 B 的编辑请求，不要求 final 再确认 B。健康补研 A 本身就是候选，Consolidation 可以显式采用。

**补研 A 真正改变 B 的边界、合并结论，或证明 A/B 实际重复。** post Review 明确写 edit_request 指向需要处理的 A/B，说明新证据如何改变处置。final_write 再生成完整候选，Consolidation 明确选择 before/after。这个实质影响判断由 agent 作，宿主不从引用数量推断。

**B 用现有材料就能修正。** 主 Review 直接记录 edit_request，不为了以后能改稿而伪造一个 research_request。final_write 编辑 B；如果没有其他待补研项目，本轮不发补研。

**A 的方向仍不能成立。** post Review 明示未决事实与 gap，不再发第二轮研究，不用重复确认型 final 来掩盖没有新结论。健康 B 可以保留；缺口不代表全部结构交付失败，也不代表规则已达到业务就绪。

## 5. final_write 与 Consolidation 的边界

final_write 只处理被分配的 edit_requests。有请求才调用，没有请求就直接进入一次 Consolidation。跨目录编辑/合并请求以首个合法目标目录作为调度归属，其他目标全文一并提供；同一个请求只派一次。task.batch 展示调度锚点；related_targets 展示本批全部显式编辑目标；edit_requests 是待执行的完整指令和目标清单，policy_catalog 是可读取的参考池。新技术 task.edit_task_contract 明确这些含义。后批可以读取前批已接纳候选，避免重复改稿。

如果修改 A 的边界同时需要改 B，主/post Review 应把 A、B 一起列入该 edit_request.policies，不能只在 instruction 暗示 B 也须修改。实模 final 曾自行补写关联原州激励稿来协调双向条件，并在最终集合中显式选用；这是 agent 的内容协调补救，不是宿主按引用自动扩张范围。写技能时应消除这种交接歧义，提前完整表达编辑目标。

final_write 输出仍是**完整 PolicyDraft JSON**，写 task 声明的候选前缀，不能覆写 B/只读参考稿，不交部分 patch。不修改现行 Policy 字段：policy_id、title、ref、transmission、match_scope、activation_conditions；每 Condition 仍含 condition_id、LONG/SHORT、OUTER/MIDDLE/INNER、criterion、reference_state/trigger_boundary。宿主负责新 ID 分配及合法继承；沿用已接纳身份时不要无故丢掉原 Condition ID。同 ID 多版本并存时，宿主优先按编辑目标 path 选择继承版本，同时认可其他已接纳版本中存在的 Condition 身份；这仅保留身份来源，不自动合并新稿经济内容。新增 Condition 仍省略 ID，不能自编未存在的显式旧 ID。

候选池包含已接纳补研稿和 final 候选；它们**不会自动进入最终集合**。Consolidation 仍输出现行 replacements/coverage/remaining_gaps/summary 等合同：before 对应 B 的 Policy ID，after 对应健康候选 ref/path；默认保留 B，新增/替换/退休由显式交易决定。

没有新文本需求的健康补研稿可直接作为 after；无需复制到 final。纯退休可使用合法空 after 交易；保留无需写无变化副本。未完成编辑、局部接纳失败和残留研究问题须反映到 coverage/gaps，不把旧稿 fallback 宣称为编辑已完成。

agent 负责经济覆盖、对象边界、合并/拆分、方向和条件质量；宿主只校验字段、路径、身份、可消费性和集合交易。结构验收成功或 PARTIAL/COMPLETE 标签不能替代真实消息可命中性判断。

## 6. Event Library、MAINTAIN 和 Pilot

正式服务已有 Published Event Library Reader 接线。配置 root/market/版本后，agent 读取冻结的已发布 Reference View，通过共同材料映射获得完整文件；它不访问写库，也不承担 Event Library 维护。NOT_CONFIGURED、请求版本不存在、空 Reference View 是不同状态。
