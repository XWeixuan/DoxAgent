# Document2 v2.1 重构方案

## 1. 重构目标

Document2 v2.1 的核心目标，是把 D2 从当前带有较强 **Pre-Policy Generation** 倾向的研究产物，调整为真正供 O3 使用的 **Expectation Research Model**。

D2 不再提前定义“什么未来事件满足什么条件才算预期差成立”，而是向 O3 提供四类研究资产：

1. **State**：世界现在是什么状态。
2. **Expectation Baseline**：基于当前信息，哪些未来发展已经属于当前默认预期路径，继续正常推进本身不足以构成新的 surprise；当前默认预期最远覆盖到哪里。
3. **Realization Factor**：在当前模型中，为什么这些 State 会导致 Unit 的结果，即相对稳定的因果结构、传导机制及其 Materiality Context。
4. **Potential Gap / Revision Space**：未来世界可能发生什么变化，使 State、Factor 或整个 Unit 的当前判断需要被修订。

四者时间和业务职责严格区分：

```text
State
= Current World

Expectation Baseline
= Current Default Expectation of the Future

Realization Factor
= Stable Causal Structure of the Current Model

Potential Gap
= Future Changes That May Revise the Current Model or Expectation
```

O3 在此基础上独立完成：

```text
开放世界现实场景研究
→ 当前预期校准
→ earliest tradable boundary
→ message observability
→ comparator
→ Policy
```

D2 不再提前完成最后这一层判断。

---

# 3. Expectation Unit 总体结构

Document2 v2.1 的核心 Unit 结构调整为：

```text
Expectation Unit

name
proposition
horizon

State
Expectation Baseline
Realization Factors
Potential Gaps
```

Schema 示意：

```json
{
  "name": "...",
  "proposition": "...",
  "horizon": "...",

  "state": {
    "parameters": [],
    "values": []
  },

  "expectation_baseline": [],

  "realization_factors": [],

  "potential_gaps": []
}
```

---

# 4. State

## 4.1 定义

State 只回答：

> **截至当前 research cutoff，真实世界处于什么状态？**

State 可以是：

- 数值；
- 区间；
- 时间；
  -方向；
- 阶段；
- 已有证据状态；
- 明确的管理层计划或行业链状态。

State 不回答：

- 为什么这件事重要；
- 下一步什么才算兑现；
- 哪一阶段值得交易；
- 什么未来事件能够改变预期。

当前 D2 已经能够较好地区分实际状态、管理层计划和产业链状态，例如 INTC 中同时保存 DCAI 实际指标、客户采用阶段和管理层制造执行计划。

这一基本能力保留。

---

## 4.2 State Schema

```text
state
  parameters[]
    name
    definition
    value_type
    ref[]

  values[]
    name
    parameter
    source_role
    value
    previous_value
    time_scope
    as_of
    validity_state
    ref[]
```

### `parameters.name`

参数名称，同时为 canonical identifier。

例如：

```text
DCAI服务器单位出货同比变化
```

### `definition`

定义业务口径。

负责避免：

- 不同财务口径混用；
- 公司指标与行业指标混用；
- 总服务器与非 AI 服务器混用；
- 内部 Foundry 与外部 Foundry 混用。

### `value_type`

继续用于结构化存储：

```text
NUMBER
RANGE
STAGE
TIME
DIRECTION
EVIDENCE
...
```

这是数据表达类型，不承担业务分类意义。

### `values.name`

一个当前 State Value 的自然名称。

例如：

```text
Q2 FY2026服务器单位出货同比增长
```

### `parameter`

直接使用对应 Parameter 的名称。

不再使用 `parameter_id`。

### `source_role`

继续保留，用于区分这个 State 本身是什么身份，例如：

```text
ACTUAL
MANAGEMENT
INDUSTRY_CHAIN
```

这是 State 语义，不属于 ref 分类。

### 不增加 `semantic_boundary`

v2.1 不再增加此前讨论的 `semantic_boundary`。

状态的业务含义如果需要解释，应在 Parameter definition、Factor 研究或 Gap 的 Possibility Space 中自然体现。

避免 State 再承担下游 trigger 语义。

---

# 5. Expectation Baseline

## 5.1 定义

Expectation Baseline 是 Unit 层面的独立未来预期研究。

它回答：

> **从当前已经知道的现实出发，未来什么发展目前已经可以合理视为默认路径或普通 progression，因此仅仅继续按照这个方向推进，本身不足以被视作一个新的 surprise？**

以及：

> **这个默认预期最远覆盖到哪里，哪些更进一步的状态尚未被当前信息合理纳入？**

它不是：

- 当前 State 的摘要；
- Factor 的 current status；
- 管理层 roadmap 的机械复述；
- 精确的卖方 consensus；
- 对“priced in”的绝对判定。

C5 已经表明，在很多情况下无法得到可靠的完整卖方预期、估值分解和 revisions，因此其当前 Market Anchor 只能被视为条件性判断，而不是唯一市场共识。

因此 v2.1 不要求构造虚假的 Market Consensus。

Expectation Baseline 的目标更弱、但更可操作：

> **确定当前信息已经能够把正常预期推到哪里。**

---

## 5.2 Baseline 不是一一对应结构

Expectation Baseline：

- 不要求每一个 State 都有一个；
- 不要求每一个 Factor 都有一个；
- 不要求 State / Factor / Baseline 一一映射。

一个 Baseline 可以横跨：

- 多个 State；
- 多个 Factor；
- 一个较大的 Unit 预期主题。

每个 Unit 只研究真正会影响后续 surprise 判断的少量 Baseline。

不追求数量完整。

如果无法形成有依据的未来默认判断：

> **可以不生成该 Baseline。**

不强制输出 `UNKNOWN`。

---

## 5.3 Expectation Baseline Schema

```text
expectation_baseline[]
  name
  baseline
  ordinary_progress
  open_frontier
  time_scope
  ref[]
```

### `name`

该预期基线的自然名称。

例如：

```text
14A外部客户导入默认路径
```

### `baseline`

描述当前已经能够合理采用的未来默认判断。

例如：

> 14A 已进入开发与潜在客户评估阶段，当前公开路线仍指向后续客户设计承诺和更长期 HVM；继续出现普通设计评估与生态推进属于既有路线的延续。

必须满足：

> **写的是未来判断，而不是当前 State。**

### `ordinary_progress`

说明在该 Baseline 下：

> 哪些未来变化仍主要属于当前默认路径的自然延续。

例如：

- Intel 再次重申已有路线；
- EDA/IP 生态继续扩大；
- 尚未形成商业 commitment 的更多设计评估；
- 已公布项目继续按既有阶段推进。

这个字段直接帮助 O3 区分：

```text
ordinary progress
vs
expectation revision
```

但它不代表这些事件在任何情况下都绝对没有交易价值。

如果消息在规模、时点或其他方面带来超出现有路径的新信息，O3仍可重新研究。

### `open_frontier`

Expectation Baseline 最重要的字段。

回答：

> **当前默认预期尚未合理延伸到哪里。**

例如：

> 当前 Baseline 尚不能推定具名大型客户已作出 production-level design selection、形成有经济约束力的产能 commitment，或已进入可重复的商业量产。

它只确定：

> **当前普通预期的边界。**

它不规定：

> 哪一个 frontier state 足以触发交易。

后者由 O3 研究。

### `time_scope`

Baseline 适用时间范围。

### `ref`

统一来源。

---

# 6. Expectation Baseline 的研究方法

Expectation Baseline 在 **State Research** 阶段完成。

顺序为：

```text
Current State
+
C1/C3/C5已有研究
+
明确管理层计划
+
可靠外部市场研究
+
必要Web Research
↓
判断未来默认路径
↓
ordinary progression
↓
open frontier
```

重点不是回答：

> “市场精确认为概率是多少？”

而是：

> “截至现在，哪些未来进展已经不需要一个新的特殊解释就能够被当前信息支持？”

C5 对 DCAI 的研究例如指出，当前价格若要保持，需要 DCAI 的经营改善不只是单季 ASP/mix，而能够发展为更持续的经营路径。

D2 可以据此形成条件性的 Baseline，但不得升级为：

> “市场确定认为服务器单位一定会增长。”

---

# 7. Realization Factor

## 7.1 定义

Realization Factor 严格定义为：

> **在当前模型中，为什么这些 State 会导致 Unit 的结果——即相对稳定的因果结构和传导机制。**

它不再定义为：

> 一个尚待兑现的未来问题。

Factor 应具有一定稳定性。

即使明天出现新消息：

> 这个机制本身通常仍然成立，只是它当前所处状态、重要性或作用强度可能改变。

---

# 8. Realization Factor Schema

```text
realization_factors[]
  name
  mechanism
  current_status
  materiality_context
  scope_boundary
  ref[]
```

相比当前版本，字段明显收敛。

---

## 8.1 `name`

Factor 自然名称，同时作为唯一业务标识。

例如：

```text
超大规模客户采购与工作负载分配
```

---

## 8.2 `mechanism`

解释相对稳定的经济传导。

例如：

> 超大规模客户对 Intel 平台的生产选择、工作负载分配和采购安排，决定 AI 基础设施总需求中有多少能够转化为 Intel DCAI 单位；客户可以继续保持合作关系，但将主要增量计算内容分配给其他 CPU、GPU 或自研架构，因此广义 AI 基础设施增长不能直接等同于 Intel 单位需求增长。

`mechanism` 应当回答：

```text
A 为什么能够影响 B？
中间哪些变量真正连接两者？
```

而不是问题式：

> 客户是否能从资格转成采购？

---

## 8.3 `current_status`

Factor 继续自行维护当前研究状态。

这一字段保留。

它不是 State 的机械复制，而是：

> **根据多个 State 和相关研究，当前这条传导链实际运行到什么程度、当前主要约束在哪里。**

例如：

> 当前已有多家 hyperscaler 和系统厂商的平台协作与部署信号，但客户采购约束性、Intel 在实际系统中的产品内容和部署规模仍不透明，因此“AI基础设施需求→Intel单位量”的传导已经存在入口，但强度尚无法按客户直接量化。

这是一个：

> **causal-state synthesis**

而不是单一事实。

因此有独立价值。

---

# 9. Materiality Context

## 9.1 定义

Materiality Context 不只是回答：

> “这个 Factor 对 Unit 有多重要？”

更重要的是回答：

> **在这条因果链内部，各个关键变量相对于最终结果分别有多重要，当前哪个变量真正具有边际决定作用，哪些变量只是辅助或结果性指标。**

它帮助 O3 避免：

```text
任何变量发生变化
→ 都被当作同等重要
```

也避免：

```text
所有变量都要变化
→ 才敢触发
```

---

## 9.2 Schema

Materiality Context 保持为一个自然语言研究字段：

```text
materiality_context
```

不继续拆成：

```text
marginal_role
offsets_and_substitutes
economic_scope
...
```

避免重新制造复杂 checklist。

但其 internal skill 必须要求内容尽量覆盖三类判断：

### 经济尺度

有哪些可用的：

- 收入；
- 单位；
- 客户规模；
- 产能；
- MW；
- wafer；
  -订单；
- 利用率；
- 业务占比；

能够帮助理解这条机制可能影响多大范围。

有就提供。

没有就不制造伪精度。

### 链条内变量的相对重要性

明确哪些变量目前是：

- 主要限制因素；
- 强传导变量；
- 更多影响时间而非最终规模；
- 更多影响结果质量而非方向；
- 更接近 downstream realization。

这些不需要结构化枚举输出。

应当自然说明。

### 当前边际条件

说明当前为什么某一变量的变化：

> 现在特别重要，或者其实边际作用有限。

例如：

> 如果当前服务器需求已经超过 Intel 可供产品，则额外需求增长首先增加 backlog，而未必直接增加短期出货；相比之下，能够解除实际 good-unit 或后端瓶颈的变化对近期交付可能具有更高边际作用。

这种信息是 O3 校准某条具体消息 Materiality 的重要背景。

---

## 9.3 `scope_boundary`

说明这个 Factor 解释到哪里为止。

例如：

> 本 Factor 只研究客户采购和工作负载向 DCAI 单位需求的传导，不负责解释 Intel 制造供给能否满足订单；后者属于供给执行 Factor。

用于防止 Factor 不断膨胀。

---

# 10. Potential Gap / Revision Space

## 10.1 定义

Potential Gap 回答：

> **未来世界可能发生什么变化，使 State、Factor 或整个 Unit 当前判断需要被修订？**

它的研究入口不是：

```text
State逐条向后推
Factor逐条向后推
```

而是：

```text
Unit整体预期
+
Open Discovery
+
外部Entity Network
+
当前业务模型
+
开放世界变化
↓
Revision Themes
```

因此 Potential Gap：

> **不能默认从 Factor 生成。**

Factor 是校准和解释材料。

Open Discovery 才是 Gaps 的第一来源。

---

# 11. Potential Gap Schema

最终收敛为：

```text
potential_gaps[]
  name
  why_live
  revision_logic
  possibility_space[]
    name
    implication
  ref[]
```

只保留真正有独立研究价值的字段。

---

## 11.1 `name`

一个足够宽、具有独立经济意义的未来修订主题。

例如：

```text
个人Agent与持久云端任务改变服务器通用计算需求
```

而不是：

```text
Muse用户增加导致Intel订单增长
```

也不是：

```text
AI需求变化
```

Gap 应处在：

```text
宽到可以容纳多个现实发展路径
但窄到拥有清楚的经济研究含义
```

---

## 11.2 `why_live`

回答：

> **为什么现在值得把这项未来可能性放入 Revision Space，而不是纯粹脑暴。**

例如：

> 已经出现真实的持久云端 Agent 产品与运行模式，使“个人用户长期占用云端计算环境”从抽象设想变成值得研究的新需求来源；但实际资源消耗和供应商受益尚未确定。

这里只证明：

> 这个方向值得研究。

不判断：

> 是否应该交易。

---

# 12. `revision_logic`

原来的：

```text
revision_target
+
research_frame
```

合并为一个：

```text
revision_logic
```

它回答两个彼此不可分割的问题：

> **当前哪项判断可能因此需要修订？**

以及：

> **从这个变化到 Unit，大致沿什么研究逻辑传导？**

例如：

> 当前 AI 基础设施需求研究主要围绕 hyperscaler 集中式训练、推理和传统云工作负载；如果个人 Agent 形成持续、大规模的云端后台任务，则服务器通用计算需求来源和单位资源模型可能需要上修。研究应重点判断实际使用是否创造净新增计算负荷，以及这些负荷由何种架构和供应商承接，而不能从用户数量直接外推 Intel 出货。

这已经提供：

```text
未来变化
→ 为什么会修订当前判断
→ 大致研究路径
```

但不形成 Factor 那种密集、严谨、全链路的因果模型。

---

## 12.1 Gap 的传导刻意保持轻量

`revision_logic` 不应该扩张成：

```text
新应用
→ 用户量
→ Token
→ CPU utilization
→ VM density
→ hyperscaler capex
→ server orders
→ Intel content
→ shipment
→ revenue
```

这种完整链条属于后续 O3 或相关 Factor 的深入研究。

D2 Gap 只需要建立：

> **这个方向为什么可能修改当前预期，以及最核心的研究链是什么。**

通常 2–4 个经济环节已经足够。

---

# 13. `possibility_space`

这是新版 Potential Gap 的主要发散资产。

它回答：

> 同一个 Revision Theme 未来可能以哪些**经济含义真正不同**的方式发展？

Schema：

```text
possibility_space[]
  name
  implication
```

不再维护：

```text
recognition_cues
progression_map
variant_id
...
```

---

## 13.1 `name`

直接描述一个未来可能状态。

例如：

```text
用户扩张并伴随持续云端计算负荷显著增加
```

或者：

```text
用户增长但资源共享和调度效率抵消大部分单位计算需求
```

名称本身就是 identifier。

---

## 13.2 `implication`

说明：

> 如果现实向这个方向发展，对当前 Unit 判断意味着什么？

例如：

> 说明个人 Agent 不只是应用层采用增加，而可能形成持续的新型服务器计算负荷，从而扩大现有 DCAI 需求模型需要覆盖的需求来源；但仍不能直接推出 Intel 获得相同比例的增量份额。

它不规定：

> 什么证据必须同时出现。

O3再根据具体消息研究。

---

# 14. 为什么移除 `recognition_cues`

旧 D2 最大的问题之一，就是：

> 一旦提前告诉模型“未来要看什么”，这些研究提示极容易在 O3 中重新变成 Activation Condition。

新版 Possibility 已经提供足够明确的经济意义。

例如：

> “用户增加但单位资源消耗下降”

O3自然可以针对真实 case 去查：

- 使用数据；
- 运行架构；
- 资源占用；
  -供应链信息。

D2 不需要再把显而易见的 investigation checklist 固化进 Schema。

这也是降低 D2→D3 conclusion leakage 的关键。

---

# 15. 不再维护 Progression Map

同理，D2不再为 Foundry、客户资格、采购等对象统一输出：

```text
evaluation
→ qualification
→ booking
→ shipment
→ repeat shipment
```

因为这再次容易变成：

> 后一阶段比前一阶段更值得交易

的隐性暗示。

这些阶段如果本身已经是当前世界的重要状态，应进入 State。

如果某种阶段变化未来可能修改预期，则进入 Possibility Space。

O3负责研究：

> 哪个状态在当前具体背景下第一次具有足够交易意义。

---

# 16. 新增 O1 Open Discovery Stage

现有 O1：

```text
State
→ Realization
→ Gaps
→ Finalization
```

v2.1 调整为：

```text
Open Discovery
→ State
→ Realization
→ Gaps
→ Finalization
```

只新增一个业务 Stage。

Open Discovery 内部包含两个连续 Pass：

```text
Full Scan
→ Checkpoint
→ Selection
```

不再新增更多 Agent 类型。

仍由 O1 完成。

---

# 17. Open Discovery 的职责

它只回答：

> **从整个 Unit、外部网络和开放世界来看，未来有哪些方向值得后续研究，因为它们一旦发展可能显著改变这个 Unit 的预期？**

它不做：

- State 研究；
- Factor 研究；
- Materiality 精确判断；
- Policy trigger；
- 最终 Gap 编译。

它只负责建立：

> **candidate research directions。**

---

# 18. Open Discovery 输入

每个 Shell 的 Discovery 应显式获得：

```text
当前 Shell / Unit Seeds
全部最终 Shell topology
D1 C1
D1 C3
D1 C5
Future Nodes
Entity Map / Relations
横向行业指标
Narrative Research（如有）
Event Library（如有）
research cutoff
Web Search能力
```

注意：

> Event Library 应真正进入这一阶段的 context。

避免当前 O0 skill 写“参考 Event Library”，但实际 O0 context 并未注入的类似 mismatch。

同时当前 Runner 实际不复用 hidden thread，因此：

> **v2.1 不依赖 thread continuity。**

每个阶段需要的研究资产都必须通过显式 context / checkpoint 传递。

---

# 19. Open Discovery Pass 1：Full Scan

第一轮唯一任务：

> **尽可能形成完整的 Candidate Research Direction List。**

此轮禁止：

- 删除；
- 排序淘汰；
- 因数据不足而不写；
- 因为“看起来暂时不如内部业务确定”而放弃；
- 提前把候选合并成 Gap。

先把想到的全部方向显式化。

---

## 19.1 Full Scan 的发散原则

Agent 不按固定 taxonomy 输出。

但 internal skill 至少从三个角度思考：

### Unit → Outside World

问：

> 即使目标公司本身什么都不做，外部世界发生哪些变化仍可能显著改变这个 Unit？

用于防止 internal-company bias。

### External Network → Unit

从：

- 最终用户；
- 客户；
- 平台；
- 供应商；
  -竞争者；
- 基础设施；
- 金融；
- 监管；
- 技术替代；
- 商业模式；

向 Unit 回看。

Entity Map 是这个视角的重要研究材料，但不是候选范围的封闭目录。

### Model Challenge

问：

> 当前 Unit 隐含了哪些关于需求来源、资源消耗、客户行为、竞争结构或价值归属的假设？未来有什么变化可能让这些假设本身失效？

这一视角专门发现：

> 当前 State / Factor 体系没有提前建模的新路径。

---

# 20. Full Scan Schema

这是过程级 Artifact，不发布进 Document2：

```text
open_discovery_scan

shell
units[]
  name
  candidates[]
    name
    change_hypothesis
    relevance
    live_basis
    ref[]
```

### `name`

候选研究方向名称。

也是 checkpoint 后的唯一 identifier。

### `change_hypothesis`

未来世界可能发生什么变化。

只描述研究方向。

不写完整触发条件。

### `relevance`

为什么这可能改变 Unit。

保持简洁。

不做密集传导研究。

### `live_basis`

为什么它现在值得进入候选，而不是纯脑暴。

### `ref`

统一来源。

---

# 21. Full Scan Checkpoint

第一轮结束必须先写：

```text
open_discovery_scan.json
```

作为冻结 checkpoint。

一旦完成：

> **后续 Selection 不允许删除或重写原 Candidate。**

只能：

- 保留；
- 合并；
- 暂停深入。

这样可以审计：

> Agent 到底有没有想到某类外部重大可能性。

否则如果模型在脑内：

```text
想到
→ 觉得难研究
→ 删除
```

我们永远无法区分：

> 没想到

和

> 想到了但错误淘汰。

---

# 22. Open Discovery Pass 2：Selection

第二个 Turn 读取完整冻结 Scan。

逐 Candidate 添加过程决策：

```text
open_discovery_selection

candidate
decision
merge_into
reason
research_focus
ref[]
```

这里 `candidate` 和 `merge_into` 直接使用 Candidate 名称。

没有 Candidate ID。

---

## 22.1 `decision`

允许三个运行态：

```text
DEEPEN
MERGE
PARK
```

这是流程控制状态，有明确程序意义，不属于业务 ontology 枚举。

### DEEPEN

值得进入后续 State / Realization / Gap Research。

### MERGE

与另一 Candidate 属于同一个经济 Revision Theme。

例如：

> Muse持续云任务

与：

> 另一 Personal Agent 的持续后台云执行

如果真正修改的是同一需求模型，可以在后续合并研究。

### PARK

目前没有足够理由深入。

典型原因：

- 潜在影响明显过小；
- 与 Unit 关系过弱；
- 没有任何现实依据；
- 被相邻 Shell 更完整覆盖；
- 与更广 Candidate 重复。

PARK 仍留在 checkpoint。

---

# 23. Selection 的取舍原则

最重要的是：

> **先按潜在经济意义选，不按数据容易不容易获取选。**

不能出现：

```text
某OEM采购变化
→ 信息完整
→ DEEPEN

新型Agent workload
→ 很多变量未知
→ PARK
```

如果后者真实发生后可能显著改变整个 Unit 的需求模型，它反而更值得 DEEPEN。

Selection 主要判断：

### 是否可能改变 Unit 的主要判断？

### 是否代表一个与其他候选不同的经济修订来源？

### 是否已经有足够现实基础值得投入后续研究？

### 研究粒度是否与潜在经济影响基本匹配？

不设：

- 外部 Candidate 最低数量；
- 内部/外部固定比例；
- 每个 Factor 必须几条；
- 每个 Entity 必须几条。

---

# 24. State Research v2.1

输入：

```text
Shell / Unit
+
Open Discovery Scan
+
Selection
+
全部研究上下文
```

State 阶段仍然优先研究 Unit 本身需要的当前状态。

但 Selected Discovery 同时告诉 State：

> 哪些开放方向可能需要补充当前世界状态。

例如 Open Discovery 识别：

> 持久个人 Agent 云端计算需求

State 可以研究相关：

- 已出现的运行方式；
- 当前行业 workload 状态；
- 当前服务器约束；
- 必要的现有参与者状态。

不是等 Gap 阶段才第一次发现：

> “原来我缺这些 facts。”

State 阶段同时输出：

```text
State
+
Expectation Baseline
```

---

# 25. Realization Research v2.1

输入：

```text
State
Expectation Baseline
Selected Discovery
```

任务：

> 建立当前 Unit 的相对稳定因果模型。

产出：

```text
Realization Factors
```

每个 Factor 必须包含：

```text
name
mechanism
current_status
materiality_context
scope_boundary
ref
```

Open Discovery 在这里的作用不是：

> 要求每个 Candidate 都对应一个 Factor。

而是：

> 检查当前因果模型有没有漏掉重要外部传导机制。

如果一个 Candidate 深入研究后发现：

> 这其实已经是当前模型真实存在并相对稳定的一条因果机制，

应吸收到 Factor。

如果它仍然只是：

> 未来可能改变当前模型的变化，

继续留给 Gap。

---

# 26. Gap Research v2.1

Gap Stage 的输入：

```text
Open Discovery Scan
+
Selection
+
State
+
Expectation Baseline
+
Realization Factors
```

生成顺序固定为：

```text
Selected Discovery Directions
↓
结合 Baseline 判断当前预期边界
↓
结合 Factor / Materiality 判断经济意义
↓
归并 Revision Theme
↓
展开 Possibility Space
↓
Potential Gaps
```

明确禁止：

```text
for factor in factors:
    generate gaps
```

也禁止：

```text
for state in states:
    predict next state
```

因为这会重新制造：

> 内部细节越拆越细，开放世界变量越来越少。

---

# 27. Gap Research 最终字段

每个 Gap 仅输出：

```text
name
why_live
revision_logic
possibility_space
ref
```

### `name`

宽度合适的 Revision Theme。

### `why_live`

为什么这个未来变化值得现在研究。

### `revision_logic`

这个变化会重写当前什么判断，大致为什么能够影响 Unit。

它可以自然包含：

- 当前 Baseline 的相关部分；
- 相关 Factor；
- 当前 State；

但不维护任何机械对象引用关系。

### `possibility_space`

至少包含真正有不同经济含义的未来分支。

不追求数量。

不应通过：

- 换客户名字；
- 换产品名字；
- 换月份；

制造表面多样性。

### `ref`

支持整个 Gap 的统一来源。

---

# 28. Research Finalization v2.1

Finalization 不重新研究完整 Shell。

主要负责四类工作。

## 28.1 Semantic Boundary Review

检查：

### State

是否混入未来判断或 Trigger。

### Expectation Baseline

是否只是重复 State；

是否把 management plan 冒充 market expectation；

是否把“公开过”等同于“完全 priced in”。

### Factor

是否还是问题式 future condition；

是否把最终结果等待链写进 mechanism；

Materiality Context 是否真的解释了链条内部变量的重要性，而不是泛泛说“这个 Factor 很重要”。

### Gap

是否重新变成：

```text
A + B + C
→ 才算成立
```

或者：

```text
某客户
→订单
→shipment
→revenue
```

这种 pre-policy。

---

# 29. Discovery Coverage Closure

Finalization 同时生成过程级：

```text
open_discovery_resolution
```

Schema：

```text
candidate
resolution
destination
reason
```

不需要 ID。

### `candidate`

Full Scan 中冻结的 Candidate 名称。

### `resolution`

说明最终怎样处理。

可以自然语言输出：

```text
形成独立Gap
并入某Gap
吸收到Factor
研究后认为影响不足
由相邻Unit/Shell承担
...
```

不必再造状态 enum。

### `destination`

如果进入最终 D2，则填写：

- Factor 名；
- Gap 名；
- Unit 名；

直接使用 canonical name。

### `reason`

简短说明。

Finalization 必须保证：

> 每一个 DEEPEN Candidate 最终都有明确 resolution。

不允许静默消失。

---

# 30. 后续阶段发现新方向怎么办

Full Scan checkpoint 冻结的含义是：

> 原扫描结果不能回头修改。

但不代表后续研究不能发现新的重要方向。

如果 State / Realization / Gap 深化过程中发现明显不同的新开放方向：

> 追加到过程 Artifact 的 `late_additions`。

最小结构：

```text
late_additions[]
  name
  discovered_during
  change_hypothesis
  reason
  ref[]
```

然后正常纳入后续研究。

这样既保持：

> Full Scan 可审计

又不把开放世界探索冻结在第一次扫描上。

# 36. v2.1 最核心的行为约束

整个重构最终应该围绕六条 invariant。

### 1. State 不预测未来

```text
State = Current World
```

---

### 2. Baseline 只描述当前默认未来路径

```text
Expectation Baseline
= What Can Already Be Reasonably Expected
Without New Special Information
```

不是精确 consensus，也不是 State 摘要。

---

### 3. Factor 必须是稳定机制

```text
Factor
= Why the World Produces the Unit Outcome
```

不再以“未来是否兑现”为主语。

---

### 4. Materiality Context 重点研究链条内部的相对重要性

不是：

> 这个 Factor 很重要。

而是：

> **这条链里，现在究竟什么变量最能改变结果，什么变量只是辅助、时间项或 downstream result。**

---

### 5. Gap 必须来自 Open Discovery，而不是 Factor enumeration

```text
Open World
→ Revision Theme
```

不是：

```text
Factor
→ Next Step
→ Gap
```

---

### 6. Gap 可以研究得具体，但不能提前选择交易边界

D2可以告诉 O3：

> 世界可能怎样变化，以及这些变化有什么不同经济含义。

但不能告诉 O3：

> **必须发生到哪一步才值得交易。**

这条判断权完整留给 Document3 / O3。

---

# 37. v2.1 最终业务定位

重构完成后，Document2 的定位可以正式改成：

> **Document2 负责建立某 ticker 的动态 Expectation Model：描述当前现实、当前默认未来路径、实现这些预期的主要因果结构与经济重要性，并开放研究可能改变当前模型的未来现实空间。**

Document2 不负责：

> 把这些未来空间提前压缩成可交易触发器。

Document3 / O3 则负责：

> **从 D2 提供的 Reality + Expectation + Causal + Revision Space 中，针对真实 actor 和现实信息生产规律，研究哪一种未来变化第一次已经相对于当前预期产生足够大的 tradable expectation delta，并把它编译为 Runtime 可执行 Policy。**

这就是 `document2.v2.1` 与下一版 D3/O3 之间应建立的新业务 contract。

# 38. O0 Expectation Construction 重构

Document2 v2.1 同时调整 O0 的 Expectation Construction，但**不改变现有跨节点编排链路**：

```text
O0 Candidate Discovery
→ O0 Synthesis
→ Domain Review
→ O0 Finalization
→ O1
```

重构仅发生在各节点内部的研究目标、prompt/skill 和 schema。

当前 O0 的主要问题不是 Shell / Unit 数量，而是过早把研究对象写成完整因果命题。例如当前：

> Intel计算产品需求与供给转化

以及：

> Intel 能将非 AI 企业及云服务器的平台周期、客户订单和有效产能兑现为可重复的服务器单位出货与交付；约束缓解后，结果不主要依赖稀缺分配、ASP 或高端组合……

已经提前规定了需求→订单→供给→重复出货的路径，并附加了 ASP、组合、替代架构等验证要求。后续 O1 因而天然围绕这一窄命题展开，而不是重新建立该业务领域的 Expectation Model。

v2.1 将 O0 的职责重新限定为：

> **构造 Research Topology，而不是提前构造完整 Expectation Thesis。**

即：

- Shell 定义一组 Unit 为什么应共享研究上下文；
- Unit 定义一个值得持续维护预期的经济对象；
- State / Baseline / Factor / Gap 的具体判断全部留给 O1。

# 39. Shell 语义与 Schema

## 39.1 Shell 定义

Shell 是：

> **一组共享主要业务语境、参与者网络、基础数据和研究材料的 Expectation Units 的研究容器。**

Shell 本身：

- 不是一个预期命题；
- 不表达 bullish / bearish；
- 不定义完整因果链；
- 不提前规定“什么才算兑现”。

Shell 名称应采用**稳定、宽口径、名词化的业务研究域**。

例如当前 INTC：

```text
Intel计算产品需求与供给转化
→ 计算产品市场

Intel经营盈利与指引持续性
→ 经营业绩与指引

Intel商业Foundry客户与先进封装转化
→ 商业Foundry与先进制造

Intel可信国防制造客户转化
→ 国防可信制造

Intel现金转换与资本融资
→ 资本、现金流与融资
```

当前五个 Shell 的整体业务分区基本可保留，主要需要移除名称和定义中的 outcome / conversion bias。当前 Foundry Shell 例如已经在 O0 seed 中提前列出设计导入、资格、订单、产能预订、出货和收入整条路径，这类内容应由 O1 后续研究，而不是成为 Shell identity。

## 39.2 Shell Schema

原：

```text
shell_id
core_question
boundary_rule
```

调整为：

```text
name
scope
boundary
ref[]
```

### `name`

稳定的业务研究域名称。

### `scope`

简洁说明：

> **本 Shell 研究哪些经济对象、市场或业务活动。**

例如：

> Intel 数据中心、企业与云服务器、PC 和边缘计算产品的终端需求、客户与平台采用、工作负载与架构分配、竞争格局及产品级供给环境。

`scope` 不得提前规定：

- 最终结果必须是什么；
- 哪些变量必须共同成立；
- 哪种解释需要被排除。

### `boundary`

只说明：

> **哪些相邻业务域明确不属于本 Shell。**

例如：

> 外部 Foundry 制造、独立先进封装业务、合并盈利和公司资本融资由其他 Shell 维护。

Boundary 不再承担详细的研究方法和因果路径约束。

# 40. Expectation Unit 语义与 Schema

## 40.1 Unit 定义

Expectation Unit 是：

> **一个可以被独立维护、持续研究和修订的经济预期对象。**

它回答：

> **“我们持续对什么形成预期？”**

而不是：

> “我们当前认为这个对象最终会怎样兑现？”

因此 Unit 名称也应使用**研究对象式表达**，而不是完整 thesis。

例如：

```text
Intel AI基础设施客户采用与DCAI出货
→ AI基础设施与DCAI需求

Intel PC与边缘计算需求及供给转化
→ PC与边缘计算需求

Intel非AI服务器需求与供给兑现
→ 企业与云服务器需求

Intel多季度经营盈利改善持续性
→ 经营盈利

Intel近端经营指引兑现
→ 近端经营指引

Intel商业先进制程Foundry客户转化
→ 商业Foundry

Intel经营现金转换支撑资本投资
→ 现金流与资本开支

Intel股权融资与资本计划充足性
→ 融资与资本结构
```

Unit 应足够宽，可以容纳：

- 多个 State；
- 多条不同 Factor；
- 正反方向的不同 Gap；
- 当前尚未进入研究框架的新型 Catalyst。

但又必须能够与 sibling Unit 独立发生重大 expectation revision。

例如 AI 基础设施、PC、非 AI 服务器可以分别出现完全不同的周期和事件，因此适合作为独立 Unit。

## 40.2 Unit Schema

原：

```text
expectation_id
proposition
horizon
```

调整为：

```text
name
scope
horizon
ref[]
```

### `name`

该经济预期对象的稳定名称。

### `scope`

一句话说明该 Unit 持续研究什么。

例如：

> AI 基础设施需求以及 Intel DCAI 产品在相关客户、平台和工作负载中的需求与业务暴露。

不写：

> 必须形成重复出货；

> 不得主要依靠 ASP；

> 客户资格必须转成采购。

这些属于 O1 的 Factor / Baseline / Gap 研究。

### `horizon`

保留，表示该对象自然的业务观察周期。

不得把 Horizon 写成需要走完的 realization chain。

# 41. O0 Agent 执行约束

跨节点编排保持不变，仅修改现有 O0 Candidate Discovery、Synthesis、Domain Review 和 Finalization 的内部任务。

O0 Candidate Discovery 不再优先寻找完整 `candidate proposition`，而应识别：

> **哪些经济对象值得作为独立 Expectation Unit 长期维护。**

候选研究重点包括：

```text
name
scope
why_material
ref
```

Synthesis 的核心任务则从：

> 相近命题归并成 Shell

调整为：

> **将 Expectation Unit candidates 按共享研究上下文组织为 Shell。**

判断两个 Unit 是否应该属于同一 Shell，主要考虑：

- 是否共享大量业务语境和实体网络；
- 是否复用相同基础研究和数据；
- 是否具有相近的行业/公司运行背景。

不能仅因为两条 Unit 属于同一因果链，就强行放入同一 Shell。

Domain Review 与 Finalization 继续沿用现有节点位置，但重点审查以下结构问题：

1. **Reversal**：如果 Unit 明天出现完全相反的变化，其名称是否仍然成立？
2. **Open Catalyst**：出现当前没有预见的新外部 Catalyst 时，能否自然进入某个 Unit？
3. **Multi-path**：Unit 是否能够容纳多条不同 Factor 与相反 Revision Space，而不是只允许一条预设兑现路径？
4. **Independent Revision**：Sibling Units 是否真的可以独立发生重要预期修订？
5. **Thesis Leakage**：Shell / Unit seed 是否提前出现了本应由 O1 研究得出的完整传导链、质量判断或排除条件。

特别警惕：

```text
能否……
转化为……
兑现为……
不主要依赖……
而不是……
只有……才……
```

这些表达不是机械禁词，但如果大量出现在 Shell / Unit seed 中，通常意味着 O0 又开始提前构造 thesis。

# 42. O0 与 O1 的新职责边界

Document2 v2.1 最终将两层职责固定为：

```text
O0
= Where to Research

决定：
研究哪些经济预期对象；
哪些对象共享上下文；
各自研究范围和相邻边界。
```

```text
O1
= What We Currently Think About Them

通过：
Open Discovery
→ State
→ Expectation Baseline
→ Realization Factor / Materiality
→ Potential Gap / Revision Space

建立真正的动态 Expectation Model。
```

因此 O0 不再输出高度限定的完整 Proposition。

**Expectation Unit 的具体“命题状态”不再由 O0 的一句 proposition 承担，而由 O1 后续形成的 State + Baseline + Factor + Gap 整体表达。**

这样既不改变当前 O0→O1 的跨节点编排，也能解除当前 Shell / Unit seed 对后续研究空间造成的过早收缩。
