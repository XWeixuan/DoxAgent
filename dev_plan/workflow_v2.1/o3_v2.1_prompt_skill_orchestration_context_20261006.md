## 1. 需要建立的新业务认知

O3 把研究与现实变化转化为预先研究、可被未来新事实判定的决策条件。D2 是重要研究基础，但不是唯一发现入口，也不是一张必须逐项编译成 Policy 的 Gap 清单。D1、开放来源、实体关系与事件材料都可以提出研究主题；Topic 与 Policy 是多对多关系，研究后可以不形成 Policy。

新版 **Policy 是中性的观察与决策范围**，表达 `transmission` 与 `match_scope`；交易方向下沉到每个 Condition。同一 Policy 可以只有 LONG、只有 SHORT，也可以同时具有两种方向；不得再写顶层 `policy.decision`，不得默认补 LONG，不能把同一 Policy 的所有 Conditions 理解成支持同一个方向。

Condition 应是经过现实校准、仍有未来增量、单独成立即可支持自身方向的完整观察入口。同向条件可以是替代入口，不要求所有条件一起成立。`transmission` 说明预先研究的经济联系，不是要求新消息逐环节证明的隐藏 AND。触发某个 Condition 不意味着另一方向自动失效或永久有效；维护要判断受影响的基线和边界。

`trigger_layer` 是 OUTER/MIDDLE/INNER 粗位置标记，不是依赖图、执行顺序或优先级。INNER 不等于财报事件，不能为填层级覆盖而引入财报交易。代码只限制层级枚举，并不代替 skill 判断层级、信息增量、重要性、方向稳定性或交易充分性。

## 2. 节点、会话与本次任务

| 节点 | 应承担的工作 | 正式业务交付 |
| --- | --- | --- |
| Discovery | 开放发现值得进一步研究的变化，不提前构造准 Trigger | Lead JSONL；可另交迟到发现 |
| Global Planning | 合并研究主题、选择投入、分配 owner 与 wave；brief 是研究问题，不是必须证明的结论 | 累计完整 Agenda |
| Policy Research & Build | 对分配的 Topic 做实质研究、现实校准和边界构建；局部组织与字段编写都在这里完成 | 每 Topic 一条 Result + 独立完整 Policy JSON 文件 |
| Global Integration | 跨 owner 比较、覆盖判断、一次补研安排、最终必要改写与集合收敛 | 累计 Review、可选补研 Agenda、最终 Policy 候选、Consolidation |
| MAINTAIN | 基于明确的新版 base 与维护材料修订已发布条件；保留单节点 | 一个完整维护 Patch |

初始化有 N 个 Shell owner、OPEN、GLOBAL。Shell owner 持有该 Shell 的研究背景；OPEN 承担开放或不能明确归属的研究；GLOBAL 负责全局协调，也有自己的 Discovery，并可被分配 Build。各 owner 有独立工作区/thread，同一 owner 的后续任务顺序执行、通常延续 thread；不同 owner 可以并行。**共享角色 O3 不等于共享一个全局会话。**

全部 Discovery 终态后才 Planning，主 Build 结束后才 Integration。Planning 和 Integration 可以在同一节点内分批多次调用，不能把节点名理解为“一次调用完成全部工作”。读取本次 `node`、`stage`、`round`、`batch/topics`、`final_batch` 和先前累计文件；新任务合同优先于旧会话记忆。恢复可能只重放已保存成果，不会让模型重新研究全部内容。

取消独立 Trigger Calibration→Policy Compile 链，不输出旧 Stage-A 台账。Integration 的 review、post_supplement_review、final_write、consolidation 是同一业务节点的不同任务，不是新增独立 Agent。

## 3. 材料可见性与文件执行方式

各新节点原则上共享完整冻结研究材料：可用的 D1 报告/资产、Future Nodes、Entity Relations、原始 D2、Event Reference View、额外材料和既有 PolicySet。Shell 任务另收到当前 Shell 的完整局部投影；全局 topology 提供 Shell/Unit 的范围与边界目录。新版 D2 Unit 保留 State、Baseline、Factors、Gaps 的完整模型，不只给 Gap 摘要。缺 D2 时仍可运行 OPEN/GLOBAL；旧版 D2 作为历史共享材料，不伪装成新版 topology。

按本次 `read_mapping` 将业务引用映射到实际可读文件。跨 owner 的原稿可能位于借用路径，不能根据引用自行猜本地路径，也不能假定能进入其他 owner 或宿主的根工作区。当前 Integration 的轻索引只有路径、Policy ID、标题，**不能仅凭标题判断经济合并**；本批完整 Policy 与以前实际读过的内容才是比较依据。需要的跨批原稿若未映射，说明缺材料，而不是虚构其边界。也不要假定每次 review 都已附带全议程、全量 Result 或所有其他 owner 的正文。

缺失/不可用材料与“没有相关变化”不同。Event View 不是完整世界状态，未记录不证明事实不存在；D2 PARTIAL 也不自动否决研究。遵守本次 supplied cutoff，区分材料发布时间、事实时间和本轮信息边界；不把旧报告 as_of 改成当前时间。

Planning 没有 Data MCP 研究权限，应基于发现和已有材料编排课题。Discovery/Build/Integration 使用只读研究权限，不能操作监控、抓取配置或外部业务状态；实际可用工具以任务为准，不能在资产中承诺未授予的工具。节点不允许自行派发 subagent。

真实业务产物通过**文件**交付。先读取工作区 `AGENTS.md`、common、当前节点资产、任务及适用 schema；仅写 `output_paths` 指定的文件/目录。冻结输入与已接纳原稿是只读材料，不修改它们。完整 Policy 完成后及时保存，再保存 Topic Result；不要等全部研究结束才一次写入。最终回复是技术回执 `{"completed": true, "notes": "简短执行说明"}`，不是业务 JSON/PolicySet。程序按实际文件接纳，口头“已完成”不能替代文件。

## 4. 初始化的中间交付合同

以下是实际字段目录。未注明的业务标量为字符串；标为非空的字段不可用空串填充。JSONL 每行一个对象，JSON 文件为一个完整对象；空集合使用 `[]`。

| 对象/文件 | 字段与用途 |
| --- | --- |
| Lead，Discovery 的 `<owner>.jsonl` | `name, lead, ref[]`；name/lead 非空。ref 是来源定位或 URL。不交方向、Trigger、充分性通过标签 |
| Agenda，`agenda.json` | `topics[], waves[][], not_selected[]`；Topic 为 `name, owner, brief, ref[]`，前三者非空；NotSelected 为 `ref, reason`（非空）。waves 的元素是 Topic 名称 |
| Result，每 wave 的 `results.jsonl` | `topic, policies[], notes, ref[]`；topic 非空；policies 是该 Topic 对应的完整 Policy **文件路径**；零结果交 `policies: []` 并说明理由 |
| Review，`review.json` / `post_supplement_review.json` | `relations[], research_requests[], coverage_notes`；Relation 为 `policies[], proposal`，policies 是相关 Policy 定位/ID，proposal 非空；research_requests 使用 Topic 结构 |
| 补研 Agenda，`supplement_agenda.json` | 与主 Agenda 同结构；没有独立新 Discovery 链。未交可读补研 Agenda 时，宿主可从 Review.research_requests 构造一次补研议程 |
| 最终清单，`consolidation.json` | `replacements[], coverage[], remaining_gaps[], summary, publish_empty`；Replacement 为 `before[], after[], reason`；Coverage 为 `topic, policies[], note`；RemainingGap 为 `name, reason`。reason、topic、gap 文本非空；publish_empty 是布尔值，默认 false |

文件位于本次任务指定的 `output/work/v21/...`。主研究与补研目录分开；每 wave 中 `policies/*.json` 保存 Policy。初始 scan 不改写；Build/Integration 新发现可写本次指定的 late JSONL，结构仍是 Lead。不要把后续发现塞进原扫描文件。

Planning 每批输出的是**截至本批的完整累计 Agenda**，不是追加 patch；后一次可读 Agenda 替换此前累计版本。Review 也应累计保留跨批关系、研究请求和覆盖判断。Topic 名称在冻结后稳定，owner 使用真实 Shell 名称或 task 提供的路由名（OPEN/GLOBAL 等），同一 wave 归同一 owner；不要自行发明业务 owner。宿主会拆混 owner wave、补排遗漏 Topic、过滤未知 wave 名称；同名冲突 Topic 会隔离，不会自动选第一条。

每个选中 Topic 都应交可辨识的 Result，不能用 Policy 文件代替结果处置。允许一个 Topic 零条/多条 Policy、多个 Topic 共用一份 Policy；notes 保留结论、比较依据、取舍和未解问题，不要求逐字思考过程。空结果可以是“不应构建”，也可以是“暂无法建立”，应明确区分。

## 5. Policy、身份与最终集合

每份 Policy 草稿使用以下业务结构，**不是字段 patch**：

```json
{
  "policy_id": null,
  "title": "中性的观察与决策范围",
  "ref": [],
  "transmission": "该观察变化怎样传导到目标公司的预期",
  "match_scope": "应召回和判断哪些主体、事件与现实状态",
  "activation_conditions": [{
    "condition_id": null,
    "decision": "LONG",
    "trigger_layer": "OUTER",
    "criterion": "一个单独成立即可支持此方向的完整可判定现实条件",
    "calibration": {
      "reference_state": "当前现实及比较锚，区分已知与未知",
      "trigger_boundary": "相对比较锚，什么新增信息达到所选边界"
    }
  }]
}
```

这是字段示例，不是经济内容模板。title/transmission/match_scope/criterion/两个 calibration 字段均非空；至少一个可读 Condition。decision 仅 LONG/SHORT，trigger_layer 仅 OUTER/MIDDLE/INNER；ref 为字符串数组，可空。没有旧 source_refs、Policy 顶层方向、路径图、trigger 数量、阶段“充分性已通过”等字段。

首次新对象省略或置空 ID，宿主分配 Policy ID 与 Policy 内 Condition ID；后续以宿主接纳、带 ID 的版本为准。重写同一对象显式保留旧 ID；新增 Condition 不编造 ID，交由宿主分配。不能按标题相似自行猜身份。完整重写必须带回仍要保留的 Conditions，代码不会替你自动字段合并；不要把旧 Conditions 全部去掉 ID 重新编号。拆分的新对象用新身份，合并如需继承，明确选用一份可继承的既有 Policy ID。

主研究形成不变集合 **B**。补研稿和 final_write 稿只是候选，**不会因存在文件就自动加入最终 F**。Consolidation 是对 B 的显式集合替换：`before` 使用 B 中 Policy ID，`after` 使用补研/最终候选文件路径。未在成功 before 中移除的 B 原稿默认保留；删除是非空 before + 空 after；新增是空 before + 非空 after；改写/合并/拆分写清两边。after 缺失不会先删除 before；相互重叠的替换组会一起失败回退。A–B、B–C 有关系不等于三者必须传递式合并。

最终 Coverage 的 policies 也是**文件路径**，由宿主解析为实际 F 的 ID；不是直接填写 ID。覆盖全部主研究与补研 Topic；无 Policy 的合理结论用空 policies + 清楚 note，未解决问题进入 remaining_gaps。补研只有一次，补研后仍有研究请求或迟到发现，明确处置/保留 gap，不设计第二轮递归。要关闭迟到线索，保留该线索实际 `文件#L行号` 引用与对应 Topic 处置，不能只口头说已覆盖。

宿主从 F 生成最终 `document3.json`、`runtime_projection.json`、`coverage_map.json`、`document3.md`，Agent 不独立写另一份正式 PolicySet/Projection。主 JSON 为 `document3.v3`、workflow `document3.v2.1`，包含 ticker/version/as_of/publication_state、可空实际 D2/Event 引用、完整 policies、published_at；元数据由宿主填写，不能编 run/hash。COMPLETE/PARTIAL 反映实际交付与未解缺项，不是投资正确性认证。

## 6. 单 MAINTAIN 的实际合同

MAINTAIN 以明确 staged v3 base 为准，可见 `base_policy_set.json`、`base_coverage.json`、完整 `maintenance_feed.json`、`delta.json` 及本轮共享材料。没有新 Event 也可能因 Trade/BADCASE/gap 等材料运行；完全无实质维护输入可由宿主直接 NOOP，不调用 Agent。不能假定 base 就是线上 current。

只写任务指定的 `maintenance_patch.json`：

```text
{
  base_policy_set_version: 本次base版本,
  event_library_ref: 实际可用引用或null,
  upsert_policies: 完整Policy对象数组,
  retire_policy_ids: 明确退役的既有Policy ID数组,
  remaining_gaps: 维护后仍未解决的{name, reason}数组,
  summary: 维护结论
}
```

upsert 完整替换该 Policy，未列入操作的 Policy 保持 base；不能只交变动字段。修订既有 Policy/Condition 保留身份，新 Policy/Condition 不指定虚构 ID。删除部分 Condition 通过完整 upsert 中明确不再保留它表达；退役整份 Policy 使用 retire。不得因一方向发生变化就自动清除另一方向。

同一 Policy 冲突 upsert，或同时 upsert/retire，会隔离操作并保留 base；坏的既有 Condition 按显式 ID 尽量保留 base，不意味着 Agent 可以省略必要内容。remaining_gaps **未提供**表示继承 base，**明确 []**表示全部关闭；资产应显式交代维护后的真实缺口，不能机械输出默认空数组。Event 引用仅能使用冻结或 base 的实际快照。无实际变化不发新版本；缺 patch/错误 base 为 DEGRADED，不发布虚构修复。

## 7. 校验与 skill 质量纪律的界线

代码检查文件可解析性、最小字段/枚举/非空、可用 Condition、身份唯一、Policy 路径存在、Topic Result 与最终 Coverage 的可辨识性、替换组结构及只读输入完整性。scan/result 坏行、坏 Condition、坏操作组局部隔离，其他成果继续；工作模型容忍额外字段，部分列表逐项抢救，但额外业务字段不成为正式合同，不能靠它传递必要语义。最终技术回执使用自己的严格小 schema，与业务文件 schema 不同。

程序不判断交易充分性、Trigger 最小性、经济传导正确性、主体重要性、比较锚真假、是否应合并、非财报交易边界或方向配比。不设每 Shell Policy 数量、LONG/SHORT 数量、OUTER/MIDDLE/INNER 覆盖配额；不按关键词替你删除财报事件。不要把这些要求写成“代码保证”，也不要为了看似完整填虚构数字或条件。

ref 为字符串数组，可使用冻结文件定位、`文件#L行号`、明确保留的上游引用和来源 URL。保留来源与时间语义，不凭空重编号/拼 run ID；O3 没有 O1 的 Scan 工具 SHA 提交合同，也没有同等的引用闭合硬校验。来源不充分时要写清未知与适用范围，不把“ref 可空”理解成无需证据。

局部继续不等于无视缺项：没有文件、Topic 缺结果、coverage 指向 F 外、保留稿存在结构缺失或仍有 gap，会影响 PARTIAL。已保存成果可在回执异常时接纳；不可依靠重试无限补齐业务。不要在 prompt 中要求额外 BLOCKED/PASSED 闸门、逐 Policy 新审计节点或宿主自动完成研究。

## 8. 改写资产与不必写入的实现知识

现有 `prompts/codex_v2/document3/` 的 o3、AGENTS、foundation、initialize_trigger_calibration、initialize_policy_compile、initialize_final_review、maintain 及旧 schemas 仍含旧合同，例如“Policy 单方向”“Stage-A→Compile”。它们不是新版可直接使用的说明。新版 Runner 显式绑定外部 `node_assets`：**role、common、discovery、planning、build、integration、maintain**；初始化只要求前六份，维护要求 role/common/maintain。role 落为工作区 AGENTS，common 可承载 foundation，四初始化资产与 maintain 可组织节点 prompt/internal skill。宿主只装载绑定文件，不自动搜索根目录中的新版 skill，也不会 fallback 到旧 Compile。资产如何拆文件，需保证实际绑定内容/可读附件完整，不能只写一个不存在的 skill 路径。

因此与 ChatGPT 沟通应同时携带本说明和业务需求方案：明确中性 Policy、Condition 方向与校准、开放发现、累计规划、实质 Build、全局集合替换、唯一补研、单维护；给出本节点真实输入和交付 schema。不要直接复用旧 AGENTS 的统一 task/输出路径、旧 Worklist/Calibration 台账或旧最终回执。

不必把 SQLite 表、锁、幂等键、内部 task hash、版本 reservation、Worker receipt 存储和发布 manifest 算法写成 Agent 工作。只需把恢复机制翻译成：**读本次任务与已接纳文件；保留既有身份；及时保存完整成果；不改冻结输入；只写允许位置；不假定重复调用意味着重新开始。**本说明未改 prompt/skill 或业务代码，未进行真实研究/部署验收。

核对依据：当前 D3 `schema_v21.py`、`inputs_v21.py`、`runner_v21.py`、`orchestrator_v21.py`、`validation_v21.py`、`runtime_projection.py`、service 版本分派及实际旧资产；业务语义依据 `d3_v2.1.md`。以当前文件合同为准，不将方案中的推荐目录、较丰富索引或预期材料装载误称为已实现能力。
