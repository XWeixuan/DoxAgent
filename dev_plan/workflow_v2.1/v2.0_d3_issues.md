# O3 历史问题与防回归清单

## 一、当前仍存在或容易复现的问题

### 1. Trigger 过晚 / Full-confirmation bias

O3 容易把“交易充分”理解成“结果已经被充分证明”，继续等待第二个季度、第二个客户、重复 shipment、收入、利润、份额等后续确认。

典型错误形态：
```
新事件
+ 运营结果
+ 财务兑现
→ 才触发
```

真正应判断的是：**哪一个最早的新事实已经产生足够大的 expectation delta。**

特别警惕 persistence 被当成提高置信度的通用工具，而不是被交易变量本身确实需要持续。历史上这一偏差曾达到大量 Condition 等两个季度/两个窗口的程度。

---

### 2. W2 Comparator Contract 未完全闭合

Policy 必须让 W2 可以直接执行：
```
新消息中的 new value/state
vs
Policy 中明确的 comparison anchor
→ trigger boundary
```

容易复发的半成品包括：

- “高于正常水平”但没有正常值；
- “低于原计划”但没有原计划；
- “交期缩短”但没有当前交期/状态；
- “Runtime 自行比较历史数据”；
- comparator 与新消息不是同一 variable / unit / semantic dimension。

这是直接影响 Runtime 可用性的最高优先级问题。

---

### 3. Market Expectation Calibration 不充分

`reference_state` 不能只回答“现实现在在哪里”，还要搞清楚：

> **市场已经预计下一步走到哪里？**

容易混淆：
```
current reality
known company plan / roadmap
market expectation
```

三者并不等价。

如果 market prior 不清，O3最容易退化成等待完整商业兑现，因为它不知道“走到哪里才算真正超预期”。

---

### 4. Transmission uncertainty 被 target-company realization 替代

外部客户、平台、竞争者、监管事件发生后，O3容易继续要求：
```
外部事件
+ 目标公司获得/失去订单
+ shipment/share/revenue变化
```

才确认方向。

正确区分是：
```
exposure / transmission 不清
→ 研究 exposure

而不是
→ 等最终 outcome
```

如果 D2 和现实 exposure 已经建立了稳定传导，外部事件本身可以形成可交易 expectation revision。

---

### 5. Synthetic Message / Cross-holder / Disclosure Granularity

Condition 有时要求多个独立 information holders、不同阶段或不同时间的信息同时存在：
```
平台BOM
+ 供应商allocation
+ 客户订单
+ 目标公司财务结果
```

“理论上一篇综合报道能把它们写在一起”不代表它们构成一条自然消息。

还需要检查：

> 信息拥有者现实中是否通常会公开到 Policy 要求的粒度。

尤其警惕 customer-specific order、internal allocation、workload-level procurement 等理论存在但现实很少公开的数据。

---

### 6. Aggregate Actor / Materiality 被数量替代

O3容易用：

- “至少两个客户”
- “两个平台”
- “两个季度”
- “20%供应商”

替代真正的 economic materiality calibration。

应区分：
```
Economic breadth
≠
Anti-noise confirmation
```

一个大型 actor 可能已经足够 material；两个小 actor 未必够。

看似精确的数字也要警惕 pseudo-precision：阈值必须有经济依据，而不是为了让 W2 好判断而随手选择整数。

---

### 7. Natural Composite 膨胀

Natural occurrence 的设计方向正确，但容易再次被滥用为 confirmation bundle：
```
事件
+ 市场响应
+ target outcome
```

都写进一个 Condition。

Natural Composite 更应对应：

> **同一次决定、合同、规则、交易、规格或生产状态。**

“处于同一经济因果链”并不足以成为同一个 occurrence。

---

### 8. OR Grouping / Hidden OR / Additive vs Sequential

同一 Policy 的 OR Conditions 必须是真正的替代路径。

持续检查三种关系：

- **Alternative**：任一个发生都消费同一个当前决策边界；
- **Additive**：C1 后 C2 仍产生新的独立交易 delta → 应拆 Policy；
- **Sequential**：C2 是 C1 的后续 realization → 通常保留更早 Trigger。

同时警惕 Criterion 内部用“A 或 B”隐藏本应独立的 OR Conditions。

---

### 9. 模糊程度词与不可观察 Comparator

“明显、重大、显著、大规模、实质、高位、正常”等并非绝对不能使用，但必须能由 W2 得到比较锚。

优先：
```
明确数值
→ categorical business boundary
→ unresolved
```

而不是保留一个无法判断的程度词。

---

## 二、历史存在、目前基本修复但必须防回归的问题

### 1. D2 机械映射

历史上 O3 曾直接采用：
```
candidate_trigger = possible_occurrence
current_state = Unit State
recognition_criteria → downstream evidence
```

甚至大量 Criterion 与 D2 `possible_occurrence` 完全相同。

D2 是 revision space 和 research prior，不是 Policy 字段模板。

---

### 2. Calibration 整层失效

历史最严重版本曾出现：

- `criterion == trigger_boundary`：40/40；
- 40 个 Condition 只有 16 个不同 `reference_state`；
- Unit/Shell summary 批量充当 Condition baseline；
- `qualifying_evidence` 全部使用统一模板；
- D2 `recognition_criteria` 大规模重新进入 evidence 字段。

这类现象一旦重新出现，通常说明 Agent 又开始做字段映射，而不是 Calibration。

---

### 3. Workflow 批量生成捷径

曾真实发生：
```
Stage A 临时脚本批量生成 Paths/Triggers
→ Compile 再用脚本字段直映射
→ Final Review 沿用前序结果并 PASSED
```

所以必须持续防止任何 Python / JS / shell 临时脚本批量生成或改写业务语义。

程序只能服务 deterministic 操作，不能替代逐 Path / Candidate / Policy 的研究判断。

---

### 4. Single Condition 作弊 / Hidden Conjunction

历史版本为了满足“Single Condition优先”，曾把多个独立事实塞进一个 C1：
```
BOM下降
AND 订单下降
AND 库存上升
```

只是写成一句话。

这不是真正 Single Condition，而且现实中往往不存在一条消息同时满足。

---

### 5. 过度修正为 Multi-condition Explosion

解决 hidden conjunction 后，一度走到另一个极端：
```
一个自然事件
→ 被拆成 C1/C2/C3/C4
```

甚至 actor、scope、period、magnitude 都被当成独立 Boolean predicates。

结果 Condition 表达极不自然、伪人感很强，并且多数 Policy 在现实中无法触发。

历史教训：

> Condition 单位应是自然完整 occurrence，而不是最小逻辑原子。

---

### 6. Prompt Harness 过重导致自然推理失真

曾同时引入：

- Causal Layer；
- Predicate Decomposition；
- Minimal Predicate Set；
- Actor-State checklist；
- Message Production checklist；
- 多级 Quality Gate。

每项单看合理，但整体让 Agent 开始“完成检查表”，而不是理解为什么 Policy 要这样设计。

后续任何大改都应警惕：

> **方法论越多，不等于研究质量越高。**

---

### 7. `match_scope` 两个极端

历史上先出现过：

**过窄：**\
几乎只召回已经达到 Activation 的 official messages。

随后又矫枉过正：

**过宽：**\
每条 Policy 都机械写入“计划、讨论、资格、配置、订单、采购、库存、价格、成本……”等通用 taxonomy。

正确状态是：

> Policy-specific 的 high-recall retrieval envelope，宽于 Activation，但仍围绕同一个 reality surface。

---

### 8. Official-only / Source Authority bias

曾把“现实可披露”误解成“必须公司正式公告”。

这会漏掉：

- 客户；
- 供应商；
- 监管；
- 可信 sourced reporting；
- 行业数据。

判断的是：

> 哪个 source 对该事实有真实 authority 和正常信息生产能力，

不是统一 official-only。

---

### 9. Actor Granularity 两个极端

早期经常生成：

> “多个核心客户同时……”

现实中很难作为单一消息出现。

后来又过度拆成：

> “一名可识别客户……”

但没有真正研究该 actor 当前 state。

正确原则：

> actor-specific 与否由 **current state / next boundary / disclosure / ticker delta** 是否不同决定，不由主体名称数量决定。

---

### 10. Schema 过重与字段多重定义

历史版本 Foundation、Stage Skill、Compile 对同一字段反复定义，导致模型自行取交集；同时 `qualifying_evidence / activation_summary / activation_mode` 等字段增加认知负担和重复表达。

曾直接诱发：
```
criterion = trigger_boundary
```

以及 evidence / recognition leakage。

防回归原则：

> 一个概念只有一个 canonical owner；Published schema 只保留真正有独立运行价值的字段。

---

### 11. Criterion 与 Calibration 职责混乱

历史上 Criterion 有时：

- 把当前 cutoff 的所有数字都塞进去；
- 或过度抽象成“高于市场预期”，但不给 comparator；
- 或把 economic transmission 解释写进事实命题。

应持续保持：
```
criterion
= Runtime判断的稳定业务事件

reference_state
= 当前直接比较起点

trigger_boundary
= 当前cutoff下的最低tradable surprise
```

---

### 12. 已成现实的 Future Trigger 未及时吸收

如果 Reference View / MAINTAIN 已证明某状态成为现实，却仍把它当未来 Trigger，就会形成 stale policy。

后续维护必须：
```
已发生状态
→ absorb into reference_state
→ 重新寻找下一项仍面向未来的 marginal boundary
```

而不是沿旧 confirmation chain 机械推进到更晚结果。

---

# 三、以后审计 O3 时最值得优先问的 6 个问题

1. **这个 Trigger 是第一次有交易意义的预期差，还是“等结果证明以后才交易”？**
2. **W2 是否真的拿到了同变量、同口径的 baseline 和 boundary，可以直接比较？**
3. **现实中真的会出现一条自然消息，以当前要求的粒度披露这个 Condition 吗？**
4. **是否因为 transmission 不确定，就错误等待 target-company 的订单/收入/利润兑现？**
5. **“两个客户/两个季度/多个指标”是真正 economic materiality，还是只是 confidence padding？**
6. **一个 Policy / Condition 是否只消费一次信息增量，还是偷偷混合了 additive / sequential events？**

只要这六问保持稳定，绝大多数历史问题都能在重新进入生产之前被发现。
