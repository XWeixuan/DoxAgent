# O0 v2.1 当前编排与 prompt/skill 改写上下文

核对日期：2026-10-04。依据当前本地工作区实现（包含尚未提交的 v2.1 修改），不是生产部署状态说明。本文只保留改写 O0 prompt/skill 所需的上下文；JSON 示例仅示意结构，不代表研究结论。

## 1. 职责与实际链路

设计目标：O0 构造 **Research Topology**。Shell 是共享研究上下文的容器，Unit 是值得持续维护的经济预期对象；具体 State / Baseline / Factor / Gap 判断由 O1 完成。

- Shell `name`：稳定、名词化的业务研究域；`scope`：研究哪些对象或活动；`boundary`：哪些相邻业务域不属于此 Shell。
- Unit `name`：稳定的经济对象名称；`scope`：持续研究什么；`horizon`：自然业务观察周期。
- 不在 seed 中预写方向性结论、完整兑现链、必须满足的条件或排除性解释。这是待改写 skill 要实现的语义要求，代码没有自动判定这些研究质量。

当前跨节点链路保持：

```text
C1 / C3 / C5 / Narrative（可用时）独立候选发现
    → O0 Synthesis
    → C1 / C3 / C5 独立领域审查
    → O0 Finalization
    → 按 Shell 交给 O1
```

候选分支均由 O0 执行，只是研究来源不同；审查分支分别由 C1/C3/C5 执行。候选分支之间、审查分支之间可并发，审查意见统一交给 Finalization，没有额外的互相辩论轮次。Narrative 不可用时跳过其候选分支。

**每次 Worker 调用实际创建新会话**，包括 Synthesis → Finalization、C1/C3/C5 Review。不要让 prompt 假设能自动记住上一轮对话或 D1 原线程；应以本次注入材料为依据。

## 2. 每个阶段真正拿到的输入

所有 v2.1 O0 阶段的 `context.json` 都包含：

| 字段 | 内容 |
| --- | --- |
| `document_schema_version` | `document2.v2.1` |
| `ticker`、`as_of` | 标的、信息截止时间（ISO 时间字符串） |
| `future_nodes` | D1 的未来节点 |
| `horizontal_indicators` | D1 横向指标集合，可能为空 |
| `entity_relations` | D1 实体关系 |
| `event_library` | 可选输入对象，含 `status`、`payload`、来源/时间等信息；不可用时不应假设存在正文 |

`event_library.status` 可能为 `AVAILABLE`、`ABSENT`、`UNAVAILABLE`、`NOT_CONFIGURED`。可选材料缺失本身不要求拒绝输出。O0 上下文使用 `as_of`，没有 O1 的 `research_cutoff_at` 字段；改写时应明确以实际注入的 `as_of` 为信息边界。

各阶段另有以下输入：

| 阶段 | 专属输入 |
| --- | --- |
| Candidate Discovery | `source_role` 为小写 `c1/c3/c5/narrative`；`primary_source` 为对应报告字符串（Narrative 是 JSON 序列化字符串）；`narrative_run_id` 仅 Narrative 分支有值，其他分支为 null |
| Synthesis | `candidate_sets`：按小写来源分组的完整候选输出，每条候选由程序追加 `candidate_ref` |
| Domain Review | `reviewer_role` 为大写 `C1/C3/C5`；`original_domain_report` 为本领域原报告字符串；`provisional_shells` 为整个 Synthesis 结果对象，包含未分配候选和 warnings |
| Finalization | `provisional_shells` 为整个 Synthesis 结果对象；`domain_reviews` 按大写角色分组，值为完整 Review 结果 |

**Synthesis 与 Finalization 不直接注入三份完整 D1 报告或完整 Narrative 报告**。它们依赖候选携带的 `scope/why_material/ref`、公共材料和审查意见；不要在 skill 中要求读取未提供的报告。`provisional_shells` 这个输入字段是对象，不是直接的 Shell 数组。

候选或审查发生允许降级的失败时，该来源可能从 `candidate_sets/domain_reviews` 缺席；缺席不是“没有问题”的审查结论，Finalization 不应声称已经吸收三份实际不存在的审查意见。

## 3. 四类 Agent 输出契约

实际每次任务都会提供 `output_schema.json`，以该文件为准。以下列出全部业务输出字段，四段 JSON 均为完整结构示例。

共同规则：所有对象字段都必须显式输出；列表没有内容时填 `[]`，不填 null；不添加 schema 之外的字段。字符串没有固定业务枚举，唯一例外是 Review 的 `reviewer_role`。O0 输出顶层不需要额外 `schema_version`。

### 3.1 Candidate Discovery：`CandidateDiscoveryResultV21`

```json
{
  "candidates": [
    {
      "name": "AI基础设施需求",
      "scope": "AI基础设施需求及公司相关产品的客户、平台和工作负载暴露。",
      "why_material": "该对象的变化可能显著影响相关业务的需求和收入预期。",
      "ref": []
    }
  ],
  "warnings": []
}
```

同一来源的候选 `name` 必须唯一。此阶段不输出 `candidate_id`、`candidate_ref`、`proposition` 或 `horizon`。

程序在交给 Synthesis 时追加：`candidate_ref = 来源大写 + ":" + name`，例如 `C1:AI基础设施需求`。跨来源同名候选会有不同 ref，程序不替 Agent 做语义合并。

### 3.2 Synthesis：`ShellSynthesisResultV21`

```json
{
  "provisional_shells": [
    {
      "shell_temp_id": "S1",
      "name": "计算产品市场",
      "scope": "计算产品的市场需求、客户采用、竞争及供给环境。",
      "boundary": "外部Foundry制造和公司资本融资由其他Shell维护。",
      "ref": [],
      "candidate_units": [
        {
          "candidate_ref": "C1:AI基础设施需求",
          "name": "AI基础设施需求",
          "scope": "AI基础设施需求及公司相关产品的客户、平台和工作负载暴露。",
          "why_material": "该对象的变化可能显著影响相关业务的需求和收入预期。",
          "ref": []
        }
      ]
    }
  ],
  "unassigned_candidates": [],
  "warnings": []
}
```

每条 `unassigned_candidates` 同样保留 `candidate_ref/name/scope/why_material/ref`，另加字符串 `reason`。

**每个输入 `candidate_ref` 必须恰好出现一次**：放入某个 Shell 的 `candidate_units`，或放入 `unassigned_candidates`；不得遗漏、重复或新增 ref。因此，语义相近的来源候选即使拟合并，也应保留各自候选记录，最终 Unit 合并交由 Finalization 落实；这里没有另一个“合并后 Unit”字段。

`shell_temp_id` 是过程定位用字符串（示例使用 S1，schema 不限定格式），不是最终业务身份。建议审查意见用它定位 Shell、用完整 `candidate_ref` 定位候选。候选文本忠实保留是 prompt 应说明的纪律，代码目前只校验 ref 覆盖，不校验逐字一致。

### 3.3 Domain Review：`DomainReviewResultV21`

```json
{
  "reviewer_role": "C1",
  "overall_assessment": "结构大体合理，但需澄清相邻Unit范围。",
  "targeted_feedback": [
    {
      "feedback_id": "F1",
      "target": "C1:AI基础设施需求",
      "issue": "与相邻Unit的研究范围存在重叠。",
      "reasoning": "两个对象可能重复覆盖同一客户需求研究。",
      "recommendation": "澄清各自研究范围，并保留可以独立修订的经济对象。",
      "ref": []
    }
  ],
  "warnings": []
}
```

`reviewer_role` 只能为 `C1/C3/C5`，应与本次输入角色一致。`target`、`feedback_id`、`issue`、`reasoning`、`recommendation` 都是字符串，没有操作枚举或结构化修改指令。Review 只给意见，不输出修订版 Shell。程序不强制校验 target 指向实际对象，因此 skill 应明确定位方式。

审查语义应围绕设计中的 Reversal、Open Catalyst、Multi-path、Independent Revision、Thesis Leakage，避免把审查重新变成对完整兑现命题的筛选。

### 3.4 Finalization：`ShellFinalizationResultV21`

```json
{
  "shells": [
    {
      "name": "计算产品市场",
      "scope": "计算产品的市场需求、客户采用、竞争及供给环境。",
      "boundary": "外部Foundry制造和公司资本融资由其他Shell维护。",
      "ref": [],
      "units": [
        {
          "name": "AI基础设施需求",
          "scope": "AI基础设施需求及公司相关产品的客户、平台和工作负载暴露。",
          "horizon": "未来数个季度的业务观察周期",
          "ref": []
        }
      ]
    }
  ],
  "finalization_note": [],
  "warnings": []
}
```

Shell `name` 在结果中唯一，Unit `name` 在所属 Shell 内唯一。`finalization_note` 是**字符串数组**。最终 seed 不保留 `shell_temp_id/candidate_ref/why_material`，也不输出旧 `shell_id/core_question/boundary_rule/expectation_id/proposition`。

Finalization 可综合意见拆分、合并、移动、重述或移除对象；代码没有要求最终 Unit 数量与候选数量相等，也没有强制逐条候选最终处置账本。重要结构决策可在 `finalization_note` 简述。O0 仅输出上述 seed；程序初始化空的研究明细，再把本 Shell 及完整 `o0_finalization` 交给 O1。

## 4. 引用、失败与验收边界

- `ref` 始终是字符串数组。保留收到的上游引用；新增 Data MCP 观察使用本次 `O#`，公共来源可用 URL，Narrative 来源可标记 `DoxAtlas:<source_run_id>`。下游收到程序限定来源的引用时应原样沿用，不自行重编号。引用不能解析不会单独阻断研究输出。
- Agent 返回一个匹配 schema 的 JSON 对象；正式运行的结果归档由程序负责，不需要自己编造运行标识或存储路径。
- 结构校验不代替研究质量：代码不强制对象数量、完整证据、非空 boundary 或 thesis-free 命名。不能把“通过 schema”当作“研究拓扑已正确”。
- 部分无法解析的 Synthesis/Finalization 输出可能触发程序保留性降级：前者把候选分别保留，后者沿用 provisional seed，`horizon` 设为 `UNRESOLVED` 并带 warning。这不是 Agent 应主动采用的正常结果，也不意味着已完成语义审查。候选/Review 没有同类自动业务兜底。
