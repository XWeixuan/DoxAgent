# O1 v2.1 当前编排与 prompt/skill 改写上下文

核对日期：2026-10-05。面向 ChatGPT 与研究资产作者，依据当前本地代码，不代表生产启用状态。本文区分**实际交付合同**与**需要 skill 建立的业务认知**；以每次任务的 `context.json/task.json/output_schema.json` 为最终依据。

## 1. 职责、阶段与会话

O0 提供 Research Topology：Shell 是共享研究上下文的容器，Unit 是稳定的经济研究对象。O1 为每个 Shell 建立动态 Expectation Model，其命题状态由 **State + Baseline + Factor + Gap** 整体表达，而不是沿用一句待兑现的 proposition。

| 阶段 | skill 应建立的认知与主要工作 | 实际交付 |
| --- | --- | --- |
| Open Discovery | 面向开放世界发现可能修订模型的变化；先完整发现，再决定研究投入 | 同一次调用内冻结 Scan，再交付 Selection |
| State | 当前现实与当前默认未来路径分开：State 描述当前世界，Baseline 描述无需新特殊信息即可合理期待的路径 | 完整 Shell，主要形成 State 与 Expectation Baseline |
| Realization | 稳定的因果机制；研究链条内谁是主导变量、辅助变量、时间项或结果项 | 完整 Shell，主要形成 Factors 与 Materiality Context |
| Gaps | 从开放发现形成仍然活跃的修订主题与可能性空间；不机械枚举 Factor 的下一步 | 完整 Shell，主要形成 Potential Gaps |
| Finalization | 整合一致性、修复结构与引用、明确发现候选的研究去向；不是额外的交易决策阶段 | 完整最终 Shell + 完整 Discovery Resolution |

同一 Shell 五阶段顺序执行，**共用同一个 O1 SDK thread**：首阶段创建 thread，后续阶段以新 request/task 在该 thread 内执行新 Turn；不同 Shell 各自持有独立 thread，可以并行。v2 的四阶段同样共享各自 Shell 的 thread。Open Discovery 的 Scan→Selection 仍在同一次 Worker/SDK Turn 内完成，不能拆成独立节点；工具往返可能涉及多次底层推理请求。

可以利用同一 thread 的历史研究认知，但每个新 task 必须读取本次输入与 schema，以最新 `canonical_shell`、冻结 Scan 和累计记录为业务依据，不以历史草稿覆盖它们。重试保留已取得的 thread ID；恢复复用原 Worker 或成功工件，不能假设每次恢复都会让模型重新做一遍。历史 O# 属于原 attempt，新增观察与权限按本次 task 重新绑定，不因共享 thread 而共享未限定的本地引用。

以上阶段分工是业务纪律，代码不按阶段禁止 Agent 修订其他研究字段。但输出始终只针对当前 Shell；兄弟 Shell 用于边界判断，不要求代写它们。不要让 D2 提前选择“必须发生到哪一步才值得交易”、Trigger、Policy 或投资动作；该判断权属于 O3。

## 2. 每个节点实际可见的研究材料

所有五阶段都收到：

- `canonical_shell`：当前完整 Shell；初始为 O0 seed 加空研究明细，后续为上一阶段返回的完整版本。
- `o0_finalization`：O0 的全部 Shell/Unit seed，供理解相邻业务边界。
- `global_research`：完整 C1/C3/C5 报告正文（`reports.c1/c3/c5`），以及 D1 的实体关系、Future Nodes、横向指标与来源信息。可以读取全部正文，不是只给 Candidate 摘要。
- `narrative_research`、`event_library`：可选材料对象。按 `status/payload` 判断是否有正文；`AVAILABLE/ABSENT/UNAVAILABLE/NOT_CONFIGURED` 不是研究结论。缺失不应被写成“没有相关事实”，也不要求拒绝交付。
- `ticker`、`document_schema_version`、`turn`、`research_cutoff_at`、`source_global_research_published_at`。信息边界是 `research_cutoff_at`；原报告发布时间不替代本轮截止时间。`turn` 为 `OPEN_DISCOVERY/STATE/REALIZATION/GAPS/FINALIZATION`。

后四阶段还收到冻结的 `open_discovery_scan`、`open_discovery_selection`，以及累计的 `open_discovery_late_additions`；已有处置时收到 `open_discovery_resolution`。这些是研究导航和审计材料，不是 canonical Shell 的字段。读哪些报告、何时补查证据，由各 skill 指导研究者决定。

Pilot 的业务材料与输出结构相同，并额外封存依赖 case 的输出供读取。正式运行返回 JSON，由程序归档；Pilot 按当前 task 写 `completion.json`。2026-10-06 起本地 SDK Pilot 由助手驱动：同一 Shell 的 O1 case 共享 Pilot 自己的 SDK thread，后续 case 是新的 task；不会接续正式生产 thread。各 case 仍有独立 workspace/权限，并从封存上游读取最新材料。每节点研究后另发 audit-only 复盘 task，记录问题及理解/写作/执行困难，不改变正式输出合同。历史人工 case 单独执行不自动搜索其他 case 的会话。不能把 Pilot 上游完整研究 envelope 直接当成 Shell，要读取其 `canonical_shell`。

## 3. Open Discovery：必须明确写进 skill 的特殊合同

### 3.1 中间交付：通过工具冻结完整 Scan

调用 `commit_open_discovery_scan`，参数为 `scan` 对象，其结构示例：

```json
{
  "shell": "计算产品市场",
  "units": [{
    "name": "AI基础设施需求",
    "candidates": [{
      "name": "客户部署方式变化",
      "change_hypothesis": "客户部署方式可能变化",
      "relevance": "可能改变该Unit的需求结构",
      "live_basis": "当前存在值得研究的线索",
      "ref": []
    }]
  }]
}
```

这是完整 Scan，不是逐条追加接口。必须覆盖当前每个 Unit 各一次；即使该 Unit 没发现候选，也保留 `candidates: []`。同一 Unit 内候选 `name` 唯一。**等待工具成功后**，以其返回的冻结 Scan 与 `scan_sha256` 为准继续 Selection；不得手工计算/编造 SHA，不得用 shell 写入或替换 checkpoint。

工具提供真实中间提交点，保留“想到但没有深入”的发现记录。Checkpoint 的 run/attempt/seed 等绑定由程序负责，Agent 不需要构造它。已冻结 Scan 不能改写；后续发现通过 Late Additions 保留。

### 3.2 节点最终交付：只交 Selection 与工具 SHA

```json
{
  "scan_sha256": "此处替换为工具返回的64位小写十六进制SHA",
  "selection": {
    "shell": "计算产品市场",
    "selections": [{
      "unit": "AI基础设施需求",
      "candidate": "客户部署方式变化",
      "decision": "DEEPEN",
      "merge_into": null,
      "reason": "值得深入研究其修订含义",
      "research_focus": "部署方式与需求结构之间的传导",
      "ref": []
    }]
  }
}
```

每个冻结 `(unit, candidate)` 恰好一条 Selection，不能遗漏、新增或重复。`decision` 仅为 `DEEPEN/MERGE/PARK`：DEEPEN 指深入研究，MERGE 指并入同 Unit 的另一候选，PARK 指暂不深入并保留理由；`research_focus` 是研究导航，不是交易门槛。非 MERGE 的 `merge_into` 必须为 null；MERGE 必须指向同 Unit 已存在候选，不能自指或成环。代码允许 MERGE 链，也允许最终并入 PARK，不强制合并终点为 DEEPEN。

最终 JSON **不再次返回 Scan，不返回 canonical_shell，也不输出程序内部的 checkpoint 聚合对象**。程序将冻结记录与 Selection 合成下游可见的完整结果。若 task/context 指定 `resume_from=SELECTION`，只沿用已有 Scan/SHA，不能重扫；source Pilot 即使原 context 早于 checkpoint，也应读取已存在的冻结记录继续 Selection。无候选时仍需提交含全部 Unit 的空候选 Scan，再返回空 `selections`。

## 4. 后四阶段：完整模型 + 两份过程交付

State、Realization、Gaps、Finalization 共用一个输出 envelope：

```text
{
  canonical_shell: 当前完整Shell对象,
  late_additions: 本阶段新增发现的数组,
  open_discovery_resolution: 本阶段给出的处置记录数组
}
```

上面是字段示意，不是可直接提交的 JSON。实际字段目录如下；没有另外一份 Markdown 研究报告或 patch 作为正式交付：

| 对象 | 全部业务字段（未注明的标量均为字符串） |
| --- | --- |
| Shell | `name, scope, boundary, ref[], units[]` |
| Unit | `name, scope, horizon, ref[], state, expectation_baseline[], realization_factors[], potential_gaps[]` |
| State | `parameters[], values[]` |
| Parameter | `name, definition, value_type, ref[]` |
| State Value | `name, parameter, source_role, value, previous_value, time_scope, as_of, validity_state, ref[]` |
| Baseline | `name, baseline, ordinary_progress, open_frontier, time_scope, ref[]` |
| Factor | `name, mechanism, current_status, materiality_context, scope_boundary, ref[]` |
| Gap | `name, why_live, revision_logic, possibility_space[], ref[]`；每个 possibility 为 `name, implication` |
| Late Addition | `unit, name, discovered_during, change_hypothesis, reason, ref[]` |
| Resolution | `unit, candidate, resolution, destination, reason`；`destination` 为字符串或 null，没有 `ref` 字段 |

State 类型对应关系：`NUMBER → {number: 数值, unit}`；`RANGE → {lower: 数值, upper: 数值, unit}`；`TIME → {point, start, end, precision}`（前三项可 null）；`STAGE → {stage}`；`DIRECTION → {direction}`；`EVIDENCE → {stance, strength}`。`previous_value` 可为 null，否则与 `value` 一样匹配 Parameter 的 `value_type`。

`source_role` 仅为 `ACTUAL/MANAGEMENT/SELL_SIDE/INDUSTRY_CHAIN/MARKET_IMPLIED`；`validity_state` 仅为 `CURRENT/SUPERSEDED/DISPUTED/RETRACTED`。不同来源的判断不要混成一个事实；Baseline 是默认未来路径，既不是 State 摘要，也不必伪装成精确共识数字。

**完整 Shell 替换上一版 Shell，不是自动字段合并。**必须带回仍然有效的已有研究和引用，否则会丢失。建议稳定保持 Shell/Unit 的业务名称；若修订结构，要显式处理候选归属与处置，代码没有自动重命名关联对象的能力。

Late Additions 只记录本阶段新发现，不需要复制全部历史；`discovered_during` 必须等于当前 `turn`。允许指向冻结 Scan、输入 Shell 或本次输出 Shell 中的 Unit。程序按 `(unit, name)` 累积，同键以新记录整体替换，不改原 Scan。开放发现没有在第一阶段结束后被封死，也没有要求每条新候选必须成为 Gap。

前面阶段可以逐步给 Resolution；程序按 `(unit, candidate)` 累积，但 **Finalization 的 Resolution 数组会替换全部累计处置**。Finalization 至少覆盖全部原 Selection 为 DEEPEN 的候选和全部累计 Late Additions（含本轮新增）。MERGE/PARK 不被强制逐条最终闭合，可按研究需要补充。Resolution 不要求候选全部变成 Gap：可以说明进入已有机制、形成修订主题、跨域归属、暂不能建立有效主题等实际结论。

`resolution` 是非空自由文本，不是枚举；`reason` 也是文本。非 null 的 `destination` 当前只能是最终当前 Shell 的 Unit/Factor/Gap 名称，或 O0 其他 Shell 的 Unit 名称。**Baseline、State Parameter、Shell 名称不能直接作为 destination**；此类去向可在 `resolution/reason` 表达，destination 设 null。跨域去向只记录归属，不会修改兄弟 Shell。

## 5. 哪些是代码校验，哪些需要 prompt/skill 保证

代码强制：严格输出 schema（字段全部显式输出、无额外字段；空数组用 `[]`，仅可空字段用 null）；Scan 身份/冻结 SHA、Unit 覆盖和候选唯一；Selection 精确覆盖与 MERGE 合法；Unit 内 Parameter/Value/Baseline/Factor/Gap 各类名称唯一，Value 引用存在的 Parameter 且类型匹配；Gap 内 possibility 名称唯一；Late Addition 归属与阶段合法；最终 Resolution 覆盖、唯一、文本非空及 destination 有效。

代码**没有**强制：每阶段必须填满其负责的列表、对象最小数量、每个 Gap 至少几条 possibility、候选逐一映射到 Gap、所有 State/Factor/Gap 必须有完整证据、State 不预测未来、Factor 必须稳定、Gap 必须开放而非机械枚举、不能泄漏交易门槛。这些是 skill 应建立的研究认知与质量纪律，不能称为“schema 已保证”。后续阶段也没有逐阶段字段只读锁。

`ref` 为字符串数组。保留上游限定来源的引用（例如 `D1-O#`、`D2REF:…`）；新观察使用本 attempt 的 O#，外部来源可用 URL，Narrative 可用 `DoxAtlas:<source_run_id>`。不要将旧 attempt 的 O# 冒充当前观察或自行重编号。无法解析的引用保留 warning，不单独否决研究；这不授权伪造可验证来源。

不确定应体现为清楚的未知、分歧、适用范围和时间语义，不要用 schema 合法但虚构的确定结论填空。Open Discovery 与后四阶段均没有自动生成业务结果的 fallback；失败可重试，不能依赖程序补齐研究。缺可选材料与缺必需交付不是同一类情况。
