# 五个 Massive Newswire 生产可靠性修复

日期：2026-11-13。使用 main 工作树，保留其他会话未提交内容、现有 Chrome/Profile、完整正文门槛、Massive 独立正则、消息身份和交易日接纳规则。

## 已确认机制与实施边界

1. **Business Wire**：原站文章GET403，只读POST同一原站文章200且完整；Reader401来自第三方Reader，不是新闻站登录失败。为正式和本地正文传输共用一个严格限定文章路径的HTTP请求选择函数，选择POST并去掉末尾重定向斜杠。继续复用现有预算、字节限制和验证；按 `bw-release-story` 正文区域抽取，不把JSON-LD teaser当全文。不新增浏览器或改列表协议。
2. **PR Newswire**：列表POST持续405，而GET200。改为GET并验证真实分页、首屏缓存与新稿时间；RSS失败兜底状态仍独立记录，不把RSS当HTTP通过。正文 `#continue-jump` 是指向已存在正文的手机端跳转导航，不是缺失正文。限制正文识别区域，排除这一已证实导航，保留实际展开/权限限制。不能对任意Read more全面放行。
3. **TMX Newsfile**：HTTP202含AWS WAF JS bootstrap；既有Managed浏览器等待自动验证后取得FULL。增加该域名的独立Managed站点策略，使用浏览器和有界正文就绪等待；保留原RSS列表。修复Massive正文强制覆盖策略，使显式Registry路径实际生效。响应状态采用观察到的最终主文档200，不伪造成功状态；继续记录最初202。
4. **ACCESS及共用分发**：当前旧PENDING已收敛，但正文完成后最长约40分钟。旧待办插在队尾，0.25秒轮次预算可在到达它之前退出，导致饥饿；每8轮保证一个最旧待办先处理，去重后继续新稿。保留当前时间预算和并发，不新增队列。Massive阴性/无正文分支不再预先进行无用的已发布文章查找，正例发布仍执行原去重。
5. **GlobeNewswire**：保留现有HTTP/RSS并行。审计必须按实际physical_run_id去重，分别统计HTTP、RSS、降级和缺口；以自然新增稿件发布时间→首次采集、正文完成、首次判定/发布衡量时延，排除启用初始批次和时间戳异常，不以轮询成功代替及时发现。

## 验证和发布

- 针对真实响应结构、POST范围/跳转、移动导航、策略不被覆盖、自动验证后主文档状态、旧待办在短轮次预算内推进补充回归。
- 先在正式容器走现有SharedContentExtractor验证失败样本，不直接往Bus发布测试消息。然后按精确SHA窄发布Collector/Site Access/Enrichment/Bus所需角色，保留Supervisor和Profile；默认recheck继续关闭。
- 只观察既有自然轮询和新稿，单列发布窗口错误、正文结果、完整性和分发等待；旧失败不批量补发、不重写历史。未出现新稿/正例或未覆盖分支如实保留未验收。
- 记录changelog，推送main，输出根因、改动、生产验收与残留问题。不给RSS、供应商成功或单篇canary赋予超出证据的结论。
