# W3 Elapsed 与短提示：影响面、根因及轻量修复方案

2026-11-19，北京时间。按用户最新要求修订：**启动时效优先，Elapsed 尽可能可靠，任何时间链路异常不得阻塞 W3、增加秒级非模型延时或触发专门技术恢复。** 本文前四节保留事故及历史窗口证据；第五节起替代上一版强制前置方案。开发及本地验收完成，详见[实施与验收记录](../../docs/w3-elapsed-nonblocking-implementation-and-acceptance-20261119.md)；未部署生产。

## 1. 结论和业务边界

这不是 INTC 特例，也不是单纯的日志问题。旧实现把参与模型行为约束的 Elapsed 当成“可选遥测”：一次零等待登记失败，就允许整个 Case 的模型分支不带时间上下文继续运行。数据库锁竞争只是触发条件；问题不是允许 W3 继续，而是**缺少共享内存兜底、原点登记与业务登记分离，以及下游多层静默降级**，使瞬时争用变成整轮功能失效。

扩大核查后的结论：

- 旧版本窗口有 2,309 个已登记 W3 Case、4,617 个分支阶段；4,499 条分支保留了 Job 和对应原生 Turn，**其中 1,693 条没有 Elapsed，比例 37.63%，涉及 854 个 Case、全部 10 个 ticker**。其余 118 条没有对应 Job 证据，列为未知，不算成功或漏注入。
- 这 1,693 条中，1,598 条当前没有原点；95 条当前有原点却没有实际注入，其中 18 条原点晚于 SDK 启动，77 条早于 SDK 启动。后者说明仅检查原点表、甚至检查“原点早于启动”，都不足以证明传递成功。
- **当前生产已经有部分修复**：11 月 19 日 07:37:28 启动的新 Scheduler 使用 v6 原子入口登记，把原点与 main/A/B 阶段、私有线程身份一同持久化。本次窗口的 53 个 Case、106 条分支，原生 Turn 全部有 Elapsed；尚不能外推到开盘争用、故障恢复或旧入口。
- 现存有值片段未发现分钟级算错或倒退。主要问题是可用性和覆盖，不是秒数计算公式。

高优需求按以下优先级落实：**不延误 W3 启动和采样；优先复用权威冻结原点，缺失时以共享内存原点尽可能继续注入；控制通道或注入异常只记录降级，不增加等待、重试或技术恢复。**

“任何情况下绝不失效”无法覆盖进程崩溃、磁盘不可写、模型服务不响应，也不能保证模型服从提醒。但这些故障不能被记作提醒正常。必须区分“成功注入”“继续运行但时间能力降级”“证据未知”。本方案不通过制造 NO_TRADE 或默认方向掩盖故障。

## 3. 写门锁为什么会导致整轮失效

### 3.1 两层锁，不是同一种竞争

`RuntimeJournal.transaction()` 先取得 `control_io.write_lock(db_path)`，再执行 SQLite `BEGIN IMMEDIATE`：

1. **进程内门锁**：按数据库路径共享的可重入互斥锁，协调 Scheduler 内各线程的写事务。普通 writer、短写结果提交、阶段登记等都经过它；`timeout=0` 连等待队列都不进入。新实现有短写优先队列；即使当前 owner 刚释放，已有排队者也可能使零等待竞争者失败。
2. **SQLite writer 锁**：门锁只保护本进程；其他进程或绕过门锁的连接仍可能持有数据库写事务。取得门锁不等于取得 SQLite writer。WAL 允许读写并行，仍然只允许一个 writer。[SQLite WAL 说明](https://www.sqlite.org/wal.html)

计时登记显式传入 `timeout=0`，因此同时覆盖掉 Journal 默认等待预算，并设置 SQLite `busy_timeout=0`。简化后的路径为：

```text
time_context(start=True)：捕获真实 UTC，先读原点，缺失才尝试写
  transaction(operation="w3.time_origin", timeout=0)
    gate.acquire(timeout=0)
      ├─ False → deadline 已到 → 手工抛 OperationalError("database is locked")
      └─ True  → BEGIN IMMEDIATE
                   └─ SQLITE_BUSY → 释放 gate，deadline 已到 → 抛异常
  except sqlite3.Error → 返回 None
业务继续：准备 / A、B 请求构造
  time_context(start=False) 只读，不补登记 → None
  WorkerRunRequest.w3_time_awareness = None
  W3TimeControl.write() 写入 enabled=false
  Harness 初始化空快照 → 每次采样不追加时间片段
```

**原两案失败在第一层，甚至没有执行计时事务的 `BEGIN IMMEDIATE` 和 INSERT。**证据中计时操作只有 `journal.gate`，随后在 Journal 自己的超时抛错行结束。两次日志时间分别为 UTC 11 月 18 日 16:41:04.690、17:00:53.949。不能把这两次写成 SQLite 已经锁表，或据错误文本判断锁持有者。

现有回归审计另外记录过 75 次此类登记异常：68 次在 gate、7 次在 SQLite BEGIN。它们是日志事件次数，不是 75 个独立失败 Case；也不能据此认定某个维护事务就是原两案的持锁者。当前证据没有记录那一瞬间的实际 owner。

本次用临时本地库分别让另一个线程持门锁、让独立连接持 `BEGIN IMMEDIATE`，均复现“登记返回 None，释放锁后只读仍为 None”。前者轨迹没有 `journal.sqlite_begin`，后者有且报错，进一步验证两层机制。

### 3.2 为什么锁很快释放，提醒却不会自行恢复

原点不是每轮重新登记：业务允许登记失败后继续，派发只读。原生 Turn 又只在开始时读取并消费控制文件，之后使用固定的 UTC 初始偏移加单调 `Instant`，不会轮询数据库。

此外，`ReceiptWorker.run()` 优先复用已冻结的 `worker_requests`。如果请求物化时原点缺失，即使排队过程中或恢复时补上数据库原点，旧请求仍可能携带 None。**SDK 启动晚于原点，不代表请求物化也晚于原点。**这能解释一种可达机制，但缺少原始请求的历史分支不能逐条宣称已证实该机制。

如果恢复重新以 `now()` 建原点，又会把之前已经花掉的准备、生成和等待时间切掉。于是还存在“后来恢复提醒，但计时重新开始”的风险；它与彻底无提醒是两种问题。

### 3.3 现存其他静默缺口

| 位置 | 当前行为 | 影响 |
|---|---|---|
| 原点 helper | SQLite 错误返回 None；仍称 optional | 旧入口及启用提醒的回测仍可丢原点 |
| 请求构造 | Trade 缺上下文仍可提交 | 上游遗漏合法穿透到 Worker |
| `W3TimeControl` | 缺补丁路径只 warning；控制文件 OSError 只 warning | 配置或文件错误可变成无提醒研判 |
| 原生 `W3TimeSnapshot::read` | 缺文件、解析/删除失败、身份不匹配等返回空快照 | 整个 Turn 不再注入，也没有后续修复 |
| 原生请求循环 | 缺快照时 `record_w3_time_awareness()` 返回 false，照常采样 | 没有“必须注入”的最后一道约束 |
| 现有测试 | 明确断言锁住时返回 None，释放后只读仍 None | 测试通过也可能是在保护错误的业务定位 |

当前 helper 还试图把 BUSY/LOCKED 降为 debug，但 gate 超时是手工创建的 `OperationalError`，没有原生 `sqlite_errorcode`，不会稳定进入该分支。调整日志等级既不能修复可靠性，也不能完整识别这类门锁事件。

业务后果：失去促进收敛的提示，双分支慢支继续占据决策关键路径，恢复后的计时也可能失真。现有证据不足以量化它造成了多少额外秒数、多少错误交易；原两案零成交有独立执行原因，不归因于 Elapsed。

## 4. 已经上线的缓解与仍需修改的部分

本地提交 `49184c517` 已将 v6 正常入口改为 `_register_entry()` → `register_trade_bundle()`，原点与必要冻结值、main/A/B 身份在同一业务事务中 INSERT IF ABSENT；冷 Template 也保留首次 main/frozen 锚点。生产源码核查确认此路径存在，原点 helper hash 为 `d56a1ca6…`，与本地一致；Worker 控制文件处理仍为原有逻辑。完整 hash 见本次证据。

因此，**不再提出第二套原子登记或单独给正常 v6 增加补登记事务**。修订方案在现有修复上提高上下文复用和异常兜底覆盖，不增加强制前置条件。新窗口 106/106 有值支持该缓解有效；原点 helper、兼容入口、错误降级、原生应用回执仍未解决，不能把这 106 个成功样本写成永久保证。

## 5. 修订后的最小实施方案

### A. 正常 v6：复用登记返回值，时间链路零新增 SQL

保留 `register_trade_bundle()`，不增加事务、writer 优先级或 busy timeout。将它已经返回的 `w3_time_awareness` 放进当前 Case 冻结上下文，A/B 请求构造直接使用。移除每分支再次通过 `read_io` 查询原点的调用，减少数据库连接和线程池切换。

历史入口若业务登记、线程及必要业务快照已经完整，**仅缺计时原点不能重新开启登记写事务**。正常业务本来需要的原子登记仍按既有机制执行；不改变业务登记、租约和 paid receipt 的要求。

### B. 原点缺失：有界共享内存兜底，不单独持久化或重试

原点选择顺序：合法且 Case 匹配的冻结上下文 → 当前 Journal 实例内缓存 → 一次 `timeout=0` 的只读查询 → 首次实际执行 UTC 的内存兜底。正常 v6 在第一步结束，完全不访问数据库。

取消 `w3.time_origin` 的独立 INSERT。兼容入口缺原点时，在研究准备前捕获 UTC；同一 Case 的两支和进程内恢复复用一个原点，并放入已有 Case 冻结上下文，供后续请求/已有保存路径复用。缓存限制 2,048 个 Case，不在锁内做 I/O；缓存不是新的持久化责任方。

数据库只读失败、坏值或 Case 不匹配均不抛业务错误。有限内存兜底不能恢复未知的历史耗时，异步诊断明确记录“prior elapsed may be unavailable”。进程重启时优先使用现有持久原点、Case/Worker 冻结值；若这些证据均不存在，允许重新取得耗时下界并继续研判，不等待补登记或恢复完整历史。

### C. 控制文件与 Harness：维持非阻塞降级，避免扩展协议

保留现有一次小控制文件原子写入、原生读取一次、UTC 偏移加 `Instant`、每次研判请求前追加档位提示。不新增协议、二进制构建、每轮文件/数据库读取或轮询。缺补丁、缺上下文、文件异常或原生空快照都不能阻止 `thread.turn` 或后续采样。

Python 控制目录创建失败时继续运行；文件写入失败只尝试一次，异步记录简短异常，并尽力删除旧控制记录，避免同线程下一阶段误用。没有退避、重试、等待队列或恢复 Effect；下一次正常 Turn 自然重写控制文件。原生损坏/缺失/身份不符的记录继续按既有方式降级，不更改交易结果。

诊断复用已有有界 `control_io` 异步队列及现有原生日志/轨迹，不新增同步诊断写入。数据库原点不是注入成功证明，控制文件成功也不是供应商收讫证明；以原生实际时间片段验收，异常/缺证据单列。

### D. 保持冻结请求与付费回执不变

不为修补旧请求修改已冻结的 request/hash，不重发已受理或受理未知的模型任务，不清除 paid receipt。旧 frozen request 已经缺元数据的情况，不能通过重新构造请求强行修复；如无可用原点，记录降级并继续既有任务。后续自然新请求使用新的上下文传递路径。

这次只改变时间元数据的复用及轻量兜底，不改变模型、effort、Prompt、交易标准或阈值文本。Elapsed 故障不得制造 NO_TRADE、默认方向或 Case 技术失败。

## 6. 验收要求与能力边界

硬约束：时间链路本身不引入秒级延时。正常 v6 原点传递零数据库读取/写入；兼容兜底零写入、至多一次零等待读取；后续分支及重入命中内存。测试在门锁和独立 SQLite writer 被持续占用时验证调用仍立即返回，并记录本地性能分布。

覆盖测试：真实 UTC 与业务时钟分离，权威值重开可恢复；A/B 同原点；缺原点不触发额外登记 writer；损坏/跨 Case 原点继续运行；数据库异常继续运行；控制目录及文件失败仍启动模型且不重试；旧幂等哈希不变；Template/Operations 不注入；真实 patched Harness 的 120/180/240 档位、工具续轮、传输重试、Fork/Resume、压缩和控制文件错误后的下一 Turn 恢复。

用现有 patched binary 和本地 mock 模型服务做原生请求验收，不调用真实模型制造故障，也不重放生产交易。以相同输入、相同 I/O fixture 做新旧路径对照，分别记录原点传递和 SDK 启动边界；不把整套业务环境波动归因于 Elapsed。

现有注入点在模型请求构造前，不能向正在生成的一次响应中途塞入新提示。跨过多个阈值后，下一请求直接使用最高适用档位；模型直接完成则不为了补提示再开一轮。**不增加定时中断、取消/续跑或新时间状态机。**

生产只读窗口用于确认既有原子路径和自然原生片段，不把历史成功当作本次变更的生产验收。发布状态、样本数量及延时结论必须在实施记录中分别列明；完成重要代码修改后追加 changelog。
