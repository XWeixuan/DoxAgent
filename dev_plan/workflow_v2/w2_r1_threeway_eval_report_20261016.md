# W2 R1 全量与三路并行召回：真实调用测试报告

日期：2026-10-16。范围：只评估 W2 R1，不修改生产编排，不执行 R2/R3、W3 或交易。

## 1. 结论

本次测试中，**按 Policy 数量均分三片、保持现有 prompt 和 medium 推理档位、并行调用后直接取并集，没有同时实现“提速、接近原 token 消耗、保持召回结果”**。

- 全部 30 条 Case 的中位耗时由 **74.4 秒增加至 94.7 秒，增加 27.3%**；超过 120 秒的 Case 从 **6 条增加至 11 条**。
- 同一批 29 条有完整双方 usage 的 Case，总 token 从 **1,011,667 增至 1,294,347，增加 27.9%**。输入增加 12.0%，输出增加 131.0%，主要增量来自推理 token。
- 29 对有效结果的 Policy 集合完全一致 **15/29，51.7%**；“是否召回任何 Policy”一致 **26/29，89.7%**。
- 存在尾部改善：全部样本 P95 从 **214.4 秒降至 170.0 秒**；全量组一条请求在约 302 秒超时，该 Case 的三路组在 110.4 秒完成。但多数有效配对并未提速：**10 条更快、19 条更慢**。

因此，目前证据不支持直接把这一分片方式上线作为 W2 R1 的默认加速方案。它能改善部分长尾 Case，但通常耗时、推理消耗和候选集合变化都需要继续处理。

## 2. 数据集如何构造

从远端生产 SQLite 只读抽取，按 Case 创建时间限定本周：**北京时间 2026-10-12 00:00 至 2026-10-16 19:38:16**。

分组依据为实际成功的 **W2 R1 输出是否包含 `candidate_policy_ids`**，不是 W2 R2 的 HIT/RELATED，也不要求整个 Case 最终成功。若同一 Case 有多份成功 R1，取最新成功回执。

| 历史 R1 分组 | 候选池 | 入选 | BE | INTC | MU | RKLB |
|---|---:|---:|---:|---:|---:|---:|
| 召回非空 | 347 | 15 | 4 | 4 | 4 | 3 |
| 召回为空 | 1,205 | 15 | 4 | 4 | 4 | 3 |
| 合计 | 1,552 | 30 | 8 | 8 | 8 | 6 |

固定 seed `20261016`，先在 ticker 内打乱，再轮询 ticker 抽样；按 title/body 内容哈希去重，30 条输入均不同。该抽样用于覆盖四个 ticker，**不是按生产流量占比加权的随机总体估计**。每个 Case 原始 Policy 数量为 **45–264**。

每条 Case 保存原冻结的消息、Policy 投影、round instructions、模型配置、版本信息和历史回执。Policy 投影沿用 `policy_id/title/match_scope`，没有加入当前数据库中的更新内容。30 条输出 Schema 哈希均与本次执行版本一致；冻结 instructions 有两个历史版本，分别覆盖 26/4 条，两种实验方案对同一个 Case 使用完全相同的版本。

历史召回结果仅用于选样和参考，**不是人工 Gold**。本次衡量方案间的一致性，不能把新增候选视为误召回，或把历史候选直接视为应当召回的正确答案。

## 3. 调用与合并协议

| 项目 | 全量 FULL | 三路 SHARDED |
|---|---|---|
| 每 Case 请求数 | 1 | 3，同时提交 |
| Policy 输入 | 原完整投影 | 按原顺序 `policies[i::3]` 分片，数量差不超过 1 |
| 消息与 prompt | 原冻结输入 | 每片保留相同完整消息和 instructions |
| 单次候选上限 | 3 | 每片 3 |
| 最终输出 | 单次候选集合 | 三片成功结果的去重并集，无模型合并、不截断 |
| Case 耗时 | 一次调用及接收处理 | 三片全部返回并合并后的墙钟耗时 |

使用远端与生产同版本的 `BailianRuntimeResponsesClient`，镜像 `doxagent-v2:main-e929134d`，对应 Git `e929134d70995933d16e23df6e66c6195d7ac3b8`；模型 **`qwen3.8-flash`、`reasoning.effort=medium`**，同生产非流式 transport 和严格 JSON 契约。仅替换分片投影及评测元数据，使用 `store=false`。

三片必须全部成功才形成可用结果；未知 Policy ID、非法输出或缺片均不能当作空召回。已核验分片输入的 Policy 无遗漏、无重复，输出身份属于对应分片。

按用户要求，**每批 15 个 Case 并发**，共两批。第一批 FULL→SHARDED，第二批 SHARDED→FULL，避免所有三路请求都固定在后面运行；观测 HTTP 峰值为 **45**。这是两种方案真实并发压力的比较，全量与三路分别最多 15/45 个请求在途，不是相同 HTTP 并发限制下的比较。

SDK 和编排重试均关闭，每个请求只调用一次。为尽量收集完整结果与 token，**仅评测将 read timeout 设置为 300 秒**，connect=10、write=30、pool=30；生产 120 秒设置未修改。超过 120 秒只表示本实验单次 Case 耗时越过该阈值，不能当作实际生产最终失败率，也不能代表包含多次 attempt 的端到端时长。

真实运行于北京时间 **19:45:18–19:59:27**，约 **14 分 9 秒**。共 **120 次请求**（30 全量＋90 分片），119 次成功、1 次全量 `provider_timeout`。启动阶段两次环境/文件校验失败发生在模型调用前，未计入 120 次请求。

## 4. 耗时结果

以下按全部 30 条 Case 统计，包含全量组超时的约 302 秒等待。分位数采用线性插值。

| 指标 | 全量 | 三路并行 |
|---|---:|---:|
| 可用 Case 结果 | 29/30 | 30/30 |
| 平均耗时 | 87.4 秒 | 99.8 秒 |
| P50 | 74.4 秒 | 94.7 秒 |
| P90 | 169.0 秒 | 164.6 秒 |
| P95 | 214.4 秒 | 170.0 秒 |
| 最大耗时 | 301.9 秒，超时 | 194.5 秒 |
| 超过 120 秒 | 6/30 | 11/30 |

排除全量超时、只比较**相同的 29 对有效 Case**后，结论仍然成立：平均 **80.0→99.4 秒**，P50 **73.7→93.7 秒**；三路更快 10 条、更慢 19 条。全量/三路耗时比的中位数为 0.769。

按历史分组观察，非空召回组 P50 为 **85.3→128.1 秒**，空召回组为 **52.0→53.6 秒**；空召回组平均耗时仍从 **51.2→70.9 秒**，且出现 2 条超过 120 秒。

| 15 Case 批次 | 执行顺序 | 全量批次完成时间 | 三路批次完成时间 |
|---|---|---:|---:|
| 批次 1 | 全量后再三路 | 301.9 秒，含超时 | 173.2 秒 |
| 批次 2 | 三路后再全量 | 179.5 秒 | 194.6 秒 |

第一批的吞吐尾部明显改善，第二批则变慢。样本每种方案只运行一次，以上保留实际观测，不推断长期稳定失败率。

## 5. Token 消耗

主比较使用**同一批 29 条双方都有完整 usage 的 Case**。全量超时 Case 的 usage 未取得，因此从双方主比较中同时排除；未知 token 没有按零计算。三路 token 为该 Case 三次请求之和。

| Provider 返回的 token | 全量 | 三路并行 | 变化 |
|---|---:|---:|---:|
| 输入 | 876,335 | 981,683 | +12.0% |
| 输出，包含推理 | 135,332 | 312,664 | +131.0% |
| 其中推理 | 131,082 | 302,396 | +130.7% |
| **输入＋输出** | **1,011,667** | **1,294,347** | **+27.9%** |
| 其中缓存输入 | 599,296 | 695,296 | +16.0% |
| 未缓存输入 | 277,039 | 286,387 | +3.4% |

推理 token 已包含在输出内，不再次累加。缓存输入是输入的子集，也不再次累加。这里只报告实际 token，不把 token 增幅等同于货币费用增幅；两个方案的 provider 缓存命中不同。

历史非空组的 14 个完整配对总 token 为 **586,069→751,373（+28.2%）**；历史空组 15 对为 **425,598→542,974（+27.6%）**，不是只由少数非空 Case 拉高。

全部 90 次分片请求实际已知 usage 合计输入 **1,017,647**、输出 **329,890**；全量只有 29 次有已知 usage。由于分母不同，不能拿这些未配对总量直接计算方案增幅。

## 6. 结果一致性

主比较为**本轮真实全量结果 vs 本轮真实三路并集**，限 29 对有效结果，Policy ID 顺序不影响集合判断。

| 指标 | 结果 | 含义 |
|---|---:|---|
| 集合完全一致 | 15/29，51.7% | 每个 Policy ID 都相同 |
| 是否召回非空一致 | 26/29，89.7% | 只比较空/非空 |
| 全量集合完整保留 | 22/29，75.9% | 三路可多召回，但不能少全量候选；含全量为空 |
| 全量非空时完整保留 | 8/15，53.3% | 排除空集天然被保留的影响 |
| 全量 Policy 覆盖率 | 19/27，70.4% | 按 Case-Policy 对统计双方交集/全量候选 |
| 三路候选中与全量重合 | 19/42，45.2% | 不是准确率；额外候选没有 Gold 判定 |

差异分布：**15 对完全一致、7 对仅增加候选、3 对仅减少候选、4 对同时增减**。因此变化不仅是“各片最多 3 个导致并集更大”，确实存在全量候选未被三路保留的情况。

历史非空组完全一致 **4/14（28.6%）**；历史空组完全一致 **11/15（73.3%）**。非空召回行为更容易受输入候选范围变化影响。

另作历史重复性参考：历史 vs 本轮全量的集合完全一致为 **15/29（51.7%）**，历史 vs 本轮三路为 **15/30（50.0%）**。现有全量方案自身重跑也存在变化，不能把本轮所有差异都归因于分片，也不能据此宣称某方案更准确。本实验没有增加重复调用来拆分随机性与分片影响。

## 7. 对后续方案的直接含义

1. **减少单次 Policy 数量，不等于减少总推理或 Case 耗时。** 本次输入只增加 12.0%，推理却增加 130.7%；三路 Case 必须等待最慢一片。现有 medium 档位下，每片并没有稳定只承担原推理量的三分之一。
2. **本次按 Policy 数量分片，没有按 match_scope 文本长度均衡。** 这准确测试了“各看三分之一 Policy”，尚不能排除按输入长度均衡后可能改善；但仅凭当前结果不能认为长度均衡就能解决推理总量翻倍的问题。
3. **15 个 Case 三路并行会形成 45 个 HTTP 请求。** 真实观测包含这种并发压力；没有首 token/服务端排队分解，不能把变慢精确归因于 provider 队列、网络或模型计算中的某一项。
4. **直接并集改变候选预算。** 3/30 条三路并集超过 3 个，最多 7 个。现有 R1 输出及 R2 相关 Policy 字段仍有最多 3 个的约束；本次并集是评测内部结果，没有强行塞进现有生产 Schema。若后续实施，必须明确扩大候选预算或选择规则；直接按 ID 截前三个会丢候选，新增模型排序则增加时间和 token，均不是本轮已经验证的方案。
5. 本次仅覆盖 R1。额外候选是否有业务价值、会给 R2/R3 增加多少耗时和 token，需要后续单独验证，不能把本报告的 R1 指标当成整个 W2 的收益。

建议保留本次数据集，后续若继续优化，优先用同一批冻结输入对照推理预算与 scope 表达长度；不要同时改变模型、prompt、分片与候选上限后再把收益全部归因于并行。
