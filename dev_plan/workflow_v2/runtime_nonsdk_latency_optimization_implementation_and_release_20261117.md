# Runtime 非模型延时优化：实施与发布记录

日期：2026-11-17。依据 `runtime_nonsdk_latency_regression_diagnosis_and_repair_plan_20261117.md` 实施；本轮用户将目标调整为 **整体非模型延时 10 秒以内**，验收延续原方案的 P95 口径，另外列出最大值，不承诺每个异常 Case 都没有长尾。

## 1. 交付状态与验收边界

已实现并发布 Worker/Scheduler 修复，双任务模式保持开启。模型、参数、Fast、Prompt/Skill、输出 Schema、W1/W2 路由、交易资格及冻结上下文业务规则没有调整。

**发布完成不等于 10 秒验收通过。** 初始发布后仍实际观察到超标，因而继续修复了输入读取放大、实时准入等待和 v6 终态快路径遗漏。过渡版本已有明确失败记录；最终版本必须独立验收，不能拿单个步骤的 A/B 或进程重启后的空闲内存冒充端到端达标。

## 2. 已修复的问题

| 原问题 | 本轮实现 | 保留的正确性保障 |
|---|---|---|
| 正式 `storage_release` 使用 `Dockerfile.source-release`，没有执行先前只在其他构建路径加入的编译 | 将既有 checked-hash 编译脚本纳入正式归档及最终应用镜像，覆盖 Worker、Runtime Schema、SDK、calendar 导入图 | 源码哈希核验；不在首个 Case 或运行中的容器补写缓存 |
| template_key 查询未带 partial index 的 kind 条件，导致历史 CASE 行扫描 | 两处查询增加 `kind='TEMPLATE'`，使用既有 `w3_template_key` 索引 | 原兼容键、唯一性、CAS、模板恢复规则 |
| 双任务 Future 带着旧 Effect owner 执行分支 stage 保存；换代后写入失败，结果虽已成功却继续等恢复 | Future 只返回每分支的结果/Job；初始返回和 continuation 都由当前 owner 保存，成功分支先保留，再处理另一分支失败 | 原 Job、Thread、worker receipt、fencing、分支幂等和一次业务提交 |
| 错误收尾自身再次 LeaseLost，可能从异常处理器逃逸 | 将这类失去所有权统一收尾；续租复用现有优先短写通道 | 不继承旧租约、不延长 lease/SQLite timeout、不擅自修改新 owner |
| ticker tick 在实时任务前同步扫补充维护，候选 LIMIT 没有限制前置历史查找 | CASE 派发后，复用现有后台 executor 按 ticker 处理一页；dirty-first 查询每页 32 条，使用轻量 seek cursor | dirty 通知仍是唯一持久来源；parent、冻结 frame、版本和比较删除规则不变 |
| 每 300 秒自动 GC 的删除数有界，但跨 run 保护证明仍遍历广域历史 | 实时循环移除该自动全历史证明；保留显式静默维护入口及原有 ACK、Capsule、生命周期退出 | 没有为了缩短查询而冒险删除引用中的数据 |
| 双任务非选中分支和完成 Operations 的物理进程没有及时退出 | 复用终态 ACK，增加可恢复的 resident release 意图；非选中分支在 Trade 提交后释放，选中分支在 Operations 提交后释放 | 不删除逻辑 Thread、原 Job 或两份结果；活跃 Capsule 拒绝释放；失败进入原收尾重试 |
| 已提交 Trade 后，还同步等待 market stop HTTP 资源通知 | 复用既有异步收尾 executor 发通知，原准备期限继续兜底 | 只移出非业务清理；决策解析、校验、提交、必要状态写入仍计入内部耗时 |

`market stop` 的同步网络依赖是明确代码事实，但不能把过渡样本中约 6 秒的未闭合尾部全部认定为该 RPC；隔离重发一个已完成 Case 的 stop 仅约 47ms。另补 route projection、ACK intent 计时，以继续区分剩余尾部。

### 发布后发现并继续修复的输入放大

**A. Library fact bridge 全历史展开。** 分段记录显示 IONQ、NBIS、INTC 单次 bridge 分别约 7.5、11.9、13.3 秒。原实现先求整库所有 Fact 的首次入库历史，再过滤已在冻结 Library / provisional 中出现的内容；immutable 分支链越长，重复工作越多。

现改为：先按现有归一化内容排除已知事实，只对剩余 Fact ID 沿原分支谱系读取历史。仍查询首次出现时间，不能把“当前版本出现”当成“首次入库”，也不能把旧内容恢复误认为新事实。没有新增缓存、线程或表。

真实 INTC 固定版本、只读文件挂载、禁网、单 CPU 隔离对照：

| 指标 | 原路径 | 新路径 |
|---|---:|---:|
| wall | 5,358.76ms | 705.63ms |
| CPU | 2,130.65ms | 694.86ms |
| 事实结果 | 与新路径逐项相同 | 与原路径逐项相同 |

该样本冻结版本 85、当前版本 86，已有 3,059 个归一化事实内容，新待桥接事实为 0；最大 RSS 约 59MiB。它证明无新增事实时消除了历史展开，不代表所有新增事实场景都固定耗时 0.7 秒。

**B. 三列 Known Event Index 加载全部 Fact 明细。** `ActivatedRuntimeInputs` 的 `case.input_snapshot` 实测约 0.8–3.3 秒；其中普通 Known Index 编译会逐 Event 加载所有 Fact 成员及修订，再只输出三列。

现为普通全量索引增加只读事件标量查询，仅取得 Event ID、发生时间/精度、known_event_summary，复用原排序与 wire 格式。每日 14/7 天保护集合的筛选规则、固定版本、ACTIVE 边界及 W1R2 详情来源不变；没有新增整份索引缓存。

同一真实 INTC 版本的 893 行、154,633 字符索引：原路径 **692.95ms**，新路径 **25.85ms**，结果逐字节相同；CPU 从 656.93ms 降至 22.83ms。没有 SDK/模型调用。

### C. 已准入的新 Case 仍要等下一轮 ticker 恢复

索引优化后再次观察到：六条 IONQ 消息在 UTC 10:36:23–33 入组，却集中在 10:36:57 领取；INTC 在 10:37:00 入组、10:37:39 才领取。新加的 `case_task` 将领取前等待和领取后准备分开，证实这些 24–39 秒没有花在模型或输入冻结上。

原正式 V2 消费者只调用 `accept_stream` 持久化任务；`background_runtime_dispatch=True` 时不执行即时派发，而是等串行 ticker 恢复轮次再次调用 `coordinator.tick`。该轮次同时承担历史恢复、日历及维护检查，因而新到消息会等在无关工作之后，并在轮次访问时集中成批启动。

修复为正式消费者在持久准入后调用轻量 `dispatch_realtime`：仅挑选本 ticker 的到期 REALTIME CASE，复用同一个 Journal claim、原 Case executor、Future/lease 注册表。恢复派发也走同一提交 helper。以一个短任务注册锁保护双入口，不再使用覆盖整个恢复轮次的锁来接纳新 Case。

保留原 Control dispatch 权限检查、六 Case 上限、120 秒原任务租约及幂等身份。CLOSED/SWEEP 不进入此即时路径；历史恢复继续作为补偿，不是新消息的唯一启动器。回归实际持有原恢复锁，验证新 Case 仍可启动，重复派发不重复领取，原六 Case 上限未增加。这也有望减少人为集中启动造成的瞬时 CPU/Fork 峰值；资源收益需由自然样本验证，不能从代码直接量化。

### D. v6 遗漏继承旧版终态快路径

`057a67e45`（11 月 11 日）已将终态标量状态更新合入 Effect 原事务，并使用无 Native 展开的终态投影。`dcded5e6f`（11 月 15 日）引入 v6 后，这两条 SQL 的版本集合仍只有 v4/v5。当前 v6 结果会回退到 `_refresh_case_completion`，重复完整 Case 读取、保存及回读，既增加 CPU/文件开销，也重新暴露旧快路径本来要避免的陈旧快照回写风险。

现在由 `TWO_PHASE_CONTRACTS` 同时供业务版本判断、终态更新 SQL、轻量投影 SQL 使用，覆盖原有 v4/v5/v6；没有新增契约或修改模型 Schema。v6 的终态完成规则和原 Service 一致。三版本事务回滚、v6 禁止完整 refresh、并发结果保留等 76 项回归通过。

### E. 当前 owner 保存也必须只把 SQL 放进短写通道

实施复审发现，本轮最初将双任务 `save()` 整个回调交给了短写执行器；回调还要读取原请求、计算哈希并编码 telemetry，这会让准备工作占据本应只执行短 SQL 的单写线程。最后一次修正将这些准备留在当前 owner 的普通执行线程，完成编码后才提交短 SQL，并将分支结果、审计 refs、ACK 意图合并为一个有 fencing 的原子事务。失败整笔回滚，已保存的结果仍不可改写。

这是修复实现本身需要收紧的地方，不能归咎于外部负载。另一方面，过渡慢 Case 的 refs 仅约 1.3KiB，**没有证据证明大对象编码是该 Case 约 40 秒延时的唯一或主要原因**。

### F. 终态清理意图合并，合成 NO_TRADE 也正确退出非选中分支

最后复审发现，`_queue_ack` 在主提交后又读 Stage、另起两次事务写释放和 ACK 意图；先前实测这段会受到写锁等待影响。现在复用 `commit_stage` 的已有事务，同时发布 ACK 和 resident 释放意图，提交后只在原 executor 发通知，owner 不再为清理重复读写。故障或进程重启后仍可从原意图恢复。

双任务分歧产生合成 NO_TRADE 时，代表结果没有 `worker_job_id`；原收尾会因此跳过非选中 resident 的及时释放。现在按代表 **Thread ID** 识别应保留给 Operations 的分支，并释放另一分支。没有改变共识方向、代表结果、Operations 线程或 SDK 调用。新增真实事务回滚及无代表 Job ID 的两类回归，最终 101 项聚焦回归通过。

### G. 消除当前事实装配的逐对象 SQL 往返

原子清理版本的固定 11 例中，W3 已全部在 8 秒内，但整 Runtime 仍有三例超过 10 秒。三个 Case 的入组→领取分别约 64–91ms；输入中的 frozen_fact_contents/bridge 耗时分别为约 2.63s＋2.23s、2.40s＋1.90s，以及一次 bridge 5.42s。由此继续修复的不是领取门槛，而是每次获取当前事实时逐 Event、逐 Fact 执行数千次 SQL 的工作量放大。

`published_events` 现在一次取得固定版本的 ACTIVE Event 最新修订，再每 400 个 Event 批量取得有效 Fact 成员及各 Fact 的最新修订，最后构造原有 CanonicalEvent。没有新表、索引、缓存或 DTO；保留成员有效区间的双端包含、数值 ID 顺序、Fact 迁移、历史 entities 字段兼容和缺修订硬错误。首次入库溯源及每日 14/7 天选择不改。

真实 INTC 两个已冻结 Case，均为 893 Event 的版本 86，禁网/单 CPU/768MiB、只读挂载的对照：

| 操作 | 原逐对象读取 | 新批量读取 |
|---|---:|---:|
| 全部 Event＋Fact，样本一 | 683.92ms | 165.37ms |
| 同一桥接调用，样本一 | 707.30ms | 164.95ms |
| 全部 Event＋Fact，样本二 | 658.86ms | 101.55ms |
| 同一桥接调用，样本二 | 784.93ms | 161.02ms |

全部对象和桥接结果逐项相同；CPU 同向下降。本次两个固定样本均没有新增合格 Fact，不能据此断言包含旧 Fact 内容修订的深层溯源也固定耗时 0.16 秒。405 个 Event 跨两个批次、三个版本的原单对象读取对照、Fact 迁移、事件屏蔽/恢复、历史字段及缺失修订回归均通过。

## 3. 修复后的执行链路

1. 新消息持久准入后直接尝试原任务领取；既有恢复轮次补偿失败/重启，不再成为新消息的必要等待。随后执行原输入冻结；日索引继续只冻结一次，provisional/bridge 保留原事实可见性。
2. W1/W2 按原模型、并发和路由运行。维护通知不再同步挡在 CASE 派发前。
3. W3 准备读取索引模板，使用正式镜像中的编译缓存；私有 Thread 和双任务身份保持原规则。
4. 原 Worker Job / SSE / receipt 返回结果。Future 不承担旧 owner 的业务 stage 写入；当前 owner 保存 A/B 并执行原共识选择。
5. Trade 原子提交并唤醒 Operations；非选中物理进程和 market stop 走既有异步清理链。
6. Operations 继续使用同一 Case 的选中 Thread，按原职责提交。选中 resident 在终态后释放，逻辑历史继续可查。

没有降低实时 W3 并发，没有新增业务队列、Provider admission 层、Redis、常驻监控服务或新的租约状态机。

### 工程预算不能由当前慢值倒推

以下是正常工作量的初始目标，单位秒；不是将每段 P95 相加后的验收阈值，也不是实测已经达到。

| 必要内部工作 | 合理 P50 目标 | 合理 P95 目标 | 当前判断 |
|---|---:|---:|---|
| 内存判定、派发、Future/SSE 通知 | 0.01 | 0.10 | 毫秒级才合理；等待恢复轮次已移除 |
| 单次索引读/短 SQL 事务 | 0.01 | 0.10 | 多秒 mutex 等待仍不合理，计入内部 |
| 一个 Case 的输入读取/编译 | 0.20 | 0.50 | 当前部分版本冷读取明显超预算 |
| Ready 已就绪后的领取/物化 | 0.05 | 0.30 | 冷 Fork 不能混入“已就绪”类别 |
| 新物理进程、SDK 初始化及私有 Fork | 尽量亚秒 | 尽量 1.0 | 当前 1.4s 导入探针及生产数秒启动仍是优化对象，不能据此放宽总目标 |
| 单阶段结果接收、校验和业务短提交 | 0.10 | 0.50 | 取消重复事务；保留业务原子性和恢复回执 |

最终仍按单 Case 的真实累计关键链验收 10 秒，而不是要求每条 SQL 单独达标就宣布完成。

## 5. 计时与实测口径

- 自然验收集合为 REALTIME 且进入 W3 的 Case；“完整 Runtime”指同一批 Case 从持久入组到 Operations 收尾，不把未进入 W3 的快速归档 Case 混入分母压低 P95。
- 分别统计 Trade、Operations、完整 W3，以及页面起点的完整 Runtime；起点不能互换。
- A/B、重试按实际 Job 取 SDK 区间并集，不把两分支时长相加。主 Trade stage 不重复计时。
- 使用实际最终 owner 的返回时刻，不能只取 `decision_effective_at` 账本下界；已观察到两者相差超过 1 秒。
- 本地 research 工具耗时先从各分支 SDK 区间移除，再求并集；另一个分支同期仍在推理的部分不会重复算内部时间。
- 内部调度、排队、SQL、锁、重试、退避、解析和提交均计入；只有有证据的外部等待才能扣除。
- **并行 W1R3 不得掩盖 W3 等待。** 现有页面将非 Operations 的所有模型区间求并集，包含 W1R3；W1R3 事实抽取与 W3 并行，可能覆盖真实 Ready/SQL 等待。因此保留该并集值用于复现页面，但严格整 Case 验收按单 Case 的“入组→W3 入口关键链内部时间＋完整 W3 内部时间”计算，再对 Case 求 P95；不是相加分段 P95。W1R3 不从 W3 关键链扣除。本轮没有静默改变生产页面口径。
- 未完成、失败、缺 Job 时钟/最终 trace 的 Case 留在入组名单，不按零耗时或成功处理；验收工具至少要求 100 例且无缺失。截止时间必须显式带时区。

### 过渡版本的失败验收记录

首批 5 个完整样本：Trade 内部最高 28.08 秒，Operations 最高 10.45 秒，完整 W3 最高 29.94 秒；首次 INTC 的原并集 Runtime 口径约 76.88 秒。因此没有在第一次发布后宣布达标。

bridge 优化后、索引标量优化前，首批 3 个完整样本：

| 口径 | P50 | 该小样本最大值 |
|---|---:|---:|
| Trade 内部 | 6.54s | 8.88s |
| Operations 内部 | 2.50s | 2.83s |
| 完整 W3 内部 | 8.25s | 10.04s |
| 原并集 Runtime 口径（含并行 R3，仅作历史复现） | 11.14s | 15.65s |

这组样本包含重启后首次输入准备，仍未达到整体 10 秒要求，且不能用 3 例的分位数代表生产 P95。

v6 终态快路径版本（`455a18176`）在 UTC 11:33:06 的窗口：22 例入组，19 例完整收尾，Trade 时钟完整 20 例。Trade P95 **38.59s**，Operations **10.04s**，完整 W3 **42.06s**，严格整 Runtime **52.45s**。这是真实不达标，不能只写成“样本不足”。

代表 INTC `case_830ef87bea7447208665129fab244736`：Trade 内部 40.64s、完整 W3 42.06s、整 Runtime 52.45s；Trade 首次 owner 本地执行 5.64s，两分支 Ready claim HTTP 分别约 19.26/20.16s，整体 ready_claim 包络约 25.64/23.62s；最后消费成功结果的 owner 仅约 0.66s。修复结果消费有价值，但该 Case 的主要残差在启动之前。

### 已闭合与尚未闭合的启动残差

原 Slot / operation 主键记录显示，两份 Capsule 的 SDK_READY 墙钟分别 **6.57s / 8.02s**，进程 CPU 均约 **1.87s**；进程导入墙钟约 5.74s / 7.19s，SDK 初始化约 0.84s。Slot 绑定到 READY 约 18.8s / 22.9s，故还存在 Fork 派发、回执和登记等启动间隔，不能全部记成 Python 导入。
