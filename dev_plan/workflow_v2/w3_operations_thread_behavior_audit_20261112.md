# W3后置运营长耗时：30个原线程的行为审查

2026-11-12。只读调查，未修改Prompt、模型、Schema、编排或生产数据。

## 核心判断

这批慢运营更像是在做“穷尽式事实归档审校”，而不是执行慢的数据库运营动作。其主要任务是逐项证明哪些事实已有Event覆盖、哪些应补录，再处理少量PIN；即使Trade已经NO_TRADE、最终运营也没有任何动作，模型仍可能花几分钟反复辨析和生成。

有三个可以直接行动的发现：**检索输出的分页契约增加了本来不必要的解析和翻页工作；“市场已知”与“冻结Event有覆盖”的两套口径使模型长时间寻找缺失证据；即使没有实际检索，当前模型配置也可能在简单运营上产生两万级reasoning token。** 因此只优化调度、工具服务器或数据库，无法消除这类长尾；反过来，直接限制工具次数也会漏掉没有工具调用却同样慢的案例。

## 样本怎么选，结论能推广多远

最初沿上一轮的11/4–6正常窗口及11/11修复后窗口筛选，208例符合SDK>300秒、区间外时间≤max(10秒,SDK的10%)。但原定30例中29例原线程索引已不在，仅1例可读；检查首例Worker registry为DELETED，不能把其最终输出假装成原始过程。

按用户“不可查就重新抽样”要求，改查当前可保留的完整原线程：扫描13,248条完成运营阶段记录，11,005条对应线程已不在当前索引；其余再要求文件存在、Job有SDK起止、Trade/Ops均已提交、SDK>300秒并通过上述区间外耗时过滤，恰有30例。取其中SDK最长10例，再以seed=20261112打乱其余20例作为随机组。**由于候选刚好30例，随机组实际覆盖全部剩余候选，并非从更大总体抽出的代表性样本。** 日期为UTC11/10的23例、11/11的7例；不能冒称仍是上周的代表性样本，也不能把两组差异当显著统计结论。

30例均查到原thread文件，并以对应Operations Job起止时间截取该回合，避免把同thread的Trade研究混进来。逐项检查输入、工具脚本/回执、原生token用量、最终JSON和时间戳。原生reasoning记录的summary多为空，无法据此恢复模型每一秒内部思考；以下认知负担判断来自可见行为和token证据，不编造隐藏思维摘要。

## 洞见一：运营最难的不是判断是否交易，而是证明“没有收录过”

最慢的RKLB `case_b4968fd10b6b4fee9e4c7fdae5870711` 用515.46秒，最终只补2条Q3收入/积压订单事实，无PIN/WATCH。它先后用公司名、收入金额、backlog、季度、精确数字等变体检索，随后连续翻页。脚本为取后面一页，多次从第一页重新取cursor并重走前面的页；16个脚本内部实际会产生更多研究RPC。

另一RKLB `case_444b3d6c1dfd4ffbafd949b97a65c8fa` 同样耗481.93秒，只补2条事实。最终理由清楚区分：财报已公开、PIN含内容，但允许Event只覆盖日程，因此事实账本仍NEW。模型并非没有看到旧消息，而是在解决“市场不新，但本轮Event未覆盖”的归档问题。

这不是建议把PIN等同Event或把已公开一概判OLD；那会改变业务语义。真正的优化方向是让模型明确知道哪个查询空间能证明Event覆盖、哪些材料只能证明曾经报道，以及查无可用Event后何时已足够停止。现在这种负证明任务缺乏清晰的完成条件，容易从定向核对变成反复搜索整个冻结研究空间。

同一主题还会在不同ticker重新做完整核对：NERC/PJM报道在BE和CEG分别抽取事实；SoftBank/OpenAI消息在COHR多个Case重新核对。这不证明跨ticker去重可以直接共用，因为各自冻结Event不同，但说明成本来自“每个ticker自己的归档覆盖核验”，不只是消息正文复杂。

## 洞见二：分页契约让模型承担了文本协议修复

15/30例脚本显式使用cursor。至少5例实际发生`Unterminated string in JSON`，另有undefined解析和脚本语法错误。典型为NBIS `case_b7b3a19983b643ec93f7bd91ba1e9e91`、CEG `case_9c8548e470a14daead77c52980c8afea`、CEG `case_e5010779f5ca4967b47910eeed01c59e`、NBIS `case_c1edb95847094ad69484295df1e76e1c`、INTC `case_33e6472e72414e8f8db7521305287f6d`。

当前源码`w3_research_store.page()`明确用`text[start:end]`构造body；外层envelope是完整JSON，但body可能是被截断的JSON文本。模型有时再对单页body执行JSON.parse，于是报错；之后自行写try/catch、拼接、调整max_bytes、继续翻页。不能将这些原线程中的解析错误归因于本次导出截断，它们已经是原始工具回执。

这是一种接口契约与自然使用方式的摩擦，不是模型业务判断太难。推荐优先做一个轻量、离线可验的接口对齐：保持现有冻结/水位/cursor保护；让“结构化对象页”和“原始文本片段”明确区分，或让结构化查询每页返回完整对象。无需新服务或协调状态。若暂不改接口，则至少明确只有完整body才能解析，文本页按文本消费；不要要求Agent每个Case重新实现分页协议。

不能为了快取消分页或直接塞入整个Library，否则会把交互成本转为上下文成本。

## 洞见三：工具调用少，也能慢到六七分钟

NBIS `case_0b3c57bf788447bd9da1f2af4a200967` 耗448.23秒，只有两次工具目录发现，没有实际资料检索；最终补录一条缺日期、身份、规模的董事售股披露。INTC `case_b43211a516e94d6baef2203f018caf0d` 379.63秒，同样只有目录发现。INTC `case_153d2c6ada1647ac8a49567ff24827b9` 374.31秒，完全无工具调用，仍产生约19.9k reasoning token。

所以不能把所有长尾解释成“研究工具用太多”。当前模型可以对现成上下文的归档边界、表达身份、既有PIN及是否应补Delta进行很长的内部处理；也可能存在未观测的模型服务等待。可见证据支持“高reasoning生成量是重要组成”，不支持精确断言这些分钟全部是有效业务思考。

如果后续优化，只减工具不会解决这组；应另外评估运营专用的更低推理档位/更直接任务表述，并以事实完整性、OLD引用正确性、PIN/WATCH结果做冻结回归，而不是直接上线降档。Trade研究模型及判断过程无需连带改变。

## 洞见四：模型在为低产出、低可验证性的条目付出很大成本

4例最终OLD、零Delta、零PIN/WATCH，仍耗约5–6分钟。COHR `case_e75558e97c5d4d9a9c665c24c7329170` 的标题含混且缺具体事实，最终OLD；NBIS `case_c1edb95847094ad69484295df1e76e1c` 正文只是免责声明，仍进行了12个工具脚本。

另一些NEW也只补录观点或模糊陈述：INTC `case_8f4d8d9c80cf41e9ac9c76b0731531db` 将Jamestown对RISC-V的评价作为信息表述；NBIS `case_bffcf2d7fd9e49178040cf97059fb9bf` 补“投资者担忧”，标UNKNOWN。不能未经业务确认说这些输出错误或应直接删除，但它们显示运营的收录边界足够宽，让评论、转载差异和低细节陈述触发长时间审校。

高价值问题不是“把超时从600改短一点”，而是明确这类材料在运营账本究竟承担什么用途、哪些事实差异值得补录、什么证据已经足够得出不补录。这里需要业务原则和提示词对齐，不应在编排层新增拍脑袋的关键词拒绝规则。

## 下一步应优先做什么

1. 先对齐分页契约，消除已证实的解析/重翻页工作；保留冻结版本、查询覆盖与完整性边界。
2. 把Event覆盖核验的成功与结束条件写清：有ID则定向读；查询未命中不无限扩散到全D1/D2；不要混淆市场新颖性和Event账本新颖性。具体停止条件须经业务确认，不能本轮擅改。
3. 独立评估运营reasoning强度，重点复测“无工具也慢”和“OLD零动作”样本。看最终业务质量，不以token少代替正确。
4. 用现有Job/回合记录验收：SDK、工具区间、工具间空档、最后工具至结果、分页解析失败数、重复查询数；必要时补单请求TTFT才能区分服务端等待。无需新增常驻采集或全量保存隐藏推理。

本轮不建议改数据库timeout、增加Worker并发或加新队列；这些无法解释此样本中工具仅1%的耗时分布。也不承诺运营必须5秒完成：之前5秒约束的是非SDK内部工作，不能混同模型回合预算。
