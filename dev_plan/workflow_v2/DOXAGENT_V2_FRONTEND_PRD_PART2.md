## 1. 文档说明

### 1.1 文档目的

本文档记录 DoxAgent V2 前端的产品需求、页面模块、数据语义、状态、交互结果及全局非功能约束。阅读者不需要预先了解 V1 页面结构或外观，也应能够根据本文档识别本期需要开发的页面、模块和数据类型。

本文档不规定具体视觉设计方案，不设计 API 路径、后端服务拆分、数据库表或具体查询语句。涉及 workflow、缓存、加载和数据读取的内容只用于明确前端产品行为、真实数据边界及必须满足的工程约束。

### 1.2 分卷范围

完整 PRD 分为两份结构一致、可独立阅读的文档：

- Part 1：全局规范、Overview、基础投研、预期研究、交易策略、事件库；
- Part 2：同一套全局规范、消息总线、运行状态、收益 / 成本审计。

两份文档中的全局规范具有相同含义。某个页面的细化要求以该页面所在分卷为准；页面细化不得放宽 V1/V2 隔离、缓存、SSE、懒加载或数据读取约束。

## 2. V2 前端边界

### 2.1 V1 与 V2 隔离

- V1 与 V2 的 workflow、数据库、后端和前端运行数据必须完全隔离。
- V2 前端不得读取 V1 的运行状态、缓存、请求结果或业务数据。
- V2 可以沿用并调整 V1 的视觉语言、组件样式和页面布局，但不能以复用界面为理由复用 V1 的业务状态语义。
- V1 后续弃用，不保留 V1 页面入口，也不提供 V1/V2 切换控件。
- 现有前端路由直接切换为 V2 页面；`/overview` 表示 V2 Overview。

### 2.2 前端职责

前端负责：

- 展示 V2 workflow 已形成的业务状态；
- 将底层状态转换成本文档定义的用户可读视图；
- 提供启动、暂停、重启、删除和失败节点重试等交互入口；
- 在单个浏览器标签页内缓存已经打开过的页面数据。

前端不负责：

- 推断或伪造 workflow 未提供的成功状态；
- 将 `PARTIAL`、`DEGRADED` 等质量诊断直接当作初始化父流程失败；
- 自行计算或决定交易日、冬夏令时、订单是否成功等服务端业务事实；
- 直接读取 V1 数据作为 V2 缺失字段的回退；
- 在本需求文档中规定 API、后端或数据库的具体实现方式。

## 3. 全局导航栏

### 3.1 Logo 与 Overview

- 全局顶栏显示 DoxAgent Logo。
- 点击 Logo 始终进入 V2 `/overview`。
- Overview 不显示 ticker 下拉选择器。
- V1 已弃用，导航栏不提供 V1 入口或 V1/V2 切换。

### 3.2 Ticker 级页面导航

除 Overview 外，ticker 级导航应提供以下页面入口：

1. 基础投研：`/ticker/:ticker/research`；
2. 事件库：`/ticker/:ticker/events`；
3. 预期研究：`/ticker/:ticker/expectations`；
4. 交易策略：`/ticker/:ticker/strategy`；
5. 消息总线：`/ticker/:ticker/message-bus`；
6. 运行状态：`/ticker/:ticker/runtime`；
7. 收益 / 成本审计：`/ticker/:ticker/audit`。

导航名称使用本文档定义的 V2 页面名称，不继续显示 V1 的“投研资料”或“执行策略”等旧名称。

### 3.3 Ticker 下拉切换

- 除 Overview 外，顶栏显示当前 ticker，并提供已有 ticker 下拉选择器。
- 下拉列表只包含尚未被前端移除、且不处于“初始化中”的 ticker。
- 正常、阻塞、已暂停和已停止的已有 ticker 均可以显示并切换。
- 已被前端移除的 ticker 不显示；不通过此处提供恢复入口。
- 切换 ticker 时保持当前业务页面不变。例如从 `/ticker/MU/runtime` 选择 `INTC` 后进入 `/ticker/INTC/runtime`。
- 切换后使用目标 ticker 与当前页面组合的缓存；若没有缓存，则按“新打开页面”规则加载该页首屏必要数据。
- 不得在 ticker 切换期间短暂展示上一 ticker 的数据，页面缓存必须按 ticker 严格隔离。

### 3.4 Ticker 列表缓存

- ticker 下拉所需列表在当前标签页第一次进入 ticker 级页面时读取，并在当前标签页共享缓存。
- 页面之间切换不重复读取 ticker 列表。
- Overview 新建、删除或改变 ticker 状态成功后，应同步更新当前标签页的 ticker 列表缓存。
- 用户人工刷新 ticker 级页面时可以同步更新 ticker 列表；失败时保留旧列表。
- 浏览器硬刷新、新开标签页、关闭后重开或重新登录后，重新建立该标签页的 ticker 列表缓存。

## 4. 全局刷新、缓存、加载与数据调用规范

### 4.1 新打开页面与人工刷新

页面只在以下情况主动读取其常规页面数据：

1. 当前浏览器标签页第一次打开某个页面与 ticker 组合；
2. 用户点击当前页面的人工刷新；
3. 用户第一次选择尚无缓存的周期、模式、Shell、Unit、Policy、日期、筛选或其他数据范围；
4. 用户主动打开需要按需加载的详情、大正文、历史内容或后续分页。

“新打开页面”不是“新登录”。登录成功时不得预加载所有页面；每个页面在用户实际进入时只读取首屏必要数据。

页面内部仅改变本地展示状态且所需数据已经缓存时，不发起读取。人工刷新只更新当前页面、当前 ticker、当前模式及已经打开的必要模块，不预取其他 ticker、其他页面、其他周期或尚未打开的详情。

### 4.2 缓存范围与生命周期

- 页面缓存范围为当前浏览器标签页。
- 缓存至少按 ticker、页面、模式、周期、筛选、版本或其他实际数据范围隔离。
- 从一个页面切换到其他页面再返回时，先显示已有缓存，不因返回或窗口重新聚焦立即刷新。
- 已加载过的数据范围再次被选择时使用缓存；只有人工刷新才重新读取该范围。
- 不为普通页面缓存设置自动失效时间。
- 浏览器硬刷新、新开标签页或关闭后重新打开，均视为新的页面打开，允许重新读取当前页首屏必要数据。
- 登出时清除当前登录会话的页面缓存，避免下一用户读取前一用户数据。
- 写操作成功后优先以操作结果更新相关缓存，不额外触发无关模块或整页读取。
- 刷新或按需加载期间保留已有内容；失败时保留旧缓存并显示对应范围的错误。
- 页面不显示“当前数据截至时间”或“最近刷新时间”。

### 4.3 页面更新频率分类

低频缓存页面包括：

- Overview；
- 基础投研；
- 预期研究；
- 交易策略；
- 事件库；
- 收益 / 成本审计；
- 消息总线中的消息渠道配置。

低频缓存页面不进行定时轮询，不因 SSE、窗口聚焦或页面往返自动刷新，只按第 4.1 节读取。

每分钟更新的组件仅包括：

- 消息总线 KPI；
- 消息源状态；
- 运行状态 KPI；
- 运行状态的最近处理记录；
- 运行状态中当前已经打开的节点详情。

分钟刷新规则：

- 以真实时钟分钟边界触发，例如 12:02、12:03、12:04；不从进入页面时重新累计 60 秒；
- 只有对应页面当前可见时才运行；
- 页面不可见时暂停；
- 返回页面时先显示缓存，不立即补一次普通刷新，在下一个真实分钟边界恢复；
- 每次只更新该组件当前可见或已打开的数据范围，不预取隐藏详情或其他筛选范围。

### 4.4 SSE 实时更新

全站只有以下两个组件使用 SSE：

1. 消息总线的消息流；
2. 运行状态的 V2 运行链路图。

SSE 规则如下：

- 页面可见时建立连接；离开对应页面时关闭连接；
- 返回页面时携带上次事件游标恢复，补收离开期间遗漏的增量事件，不重新读取完整列表或完整链路图；
- 消息流只插入符合当前消息源类型、具体消息源、路由状态和关键词条件的新消息；不符合当前范围的消息不插入，也不重置已有分页；
- 运行链路图只更新受新建或更新 Case 影响的节点、连线和计数；用户当前选择的局部路径保持不变；
- SSE 事件必须携带更新组件所需的最小增量，或携带稳定对象身份以支持一次局部读取；
- 单条 SSE 事件不得触发 KPI、消息源状态、节点详情、处理记录、整页、整表、完整消息列表或完整链路图重读；
- SSE 不替代一分钟刷新；除消息流和链路图外，其他组件不因 SSE 更新；
- 页面不常驻展示 SSE 连接状态；只有连接异常并影响实时更新时才提示；
- 断线可以自动重连，但不得通过反复全量读取实现补偿。

### 4.5 按需懒加载

页面打开时只读取形成首屏所必需的数据。以下类型默认按需加载：

- 完整文档正文和大型 JSON 产物；
- 历史版本列表之外的历史版本正文；
- Policy、Event、Fact、Expectation Unit 或 Runtime Case 的完整详情；
- reasoning、消息正文全文和其他大文本 payload；
- 节点详情和最近节点记录；
- 侧边时间线、隐藏式索引对应的非当前内容；
- 列表后续分页；
- 尚未打开的页面模式、周期、筛选或 ticker 数据。

按需加载只更新目标内容，不清空或重新加载已经成功展示的页面其他模块。折叠并再次展开已加载内容时优先使用缓存。

### 4.6 数据调用与 Supabase Egress 约束

前端与支撑本页面的读取能力必须遵守最小必要原则：

- 一次读取只取得当前 ticker、页面、周期、筛选、分页或对象所需的数据；
- 为显示一个计数、状态或摘要，不得读取完整正文、完整 JSON、完整历史集合或整张表后在前端聚合；
- 为显示一个对象详情，应按稳定对象身份读取该对象所需字段，不得读取整表或无关对象；
- 不得为了取得一个计数、状态或少量展示字段而执行跨多个表或多个完整数据集合的宽范围读取；确有跨对象语义时，只返回该页面已经需要的有界结果；
- 列表必须使用有界分页或等价的有界结果，不得一次返回全部历史记录；
- 周期 KPI、趋势和占比应直接取得满足展示所需的聚合结果，不向前端传输用于重新聚合的大量原始记录；
- 跨多个业务对象的数据必须以当前页面真实需要为边界，不得为了取得少量字段无条件读取多个完整数据集合；
- 相同数据不得因多个组件分别挂载而重复读取，应复用同一页面范围缓存；
- SSE 恢复和分钟刷新只能取得增量或当前组件的最小必要结果，不得把高频刷新实现成 Supabase 全表扫描；
- 大 payload 必须与列表摘要、KPI 和状态读取解耦，只在用户实际打开时读取；
- Supabase 数据读取必须把请求次数、扫描范围、返回字段和返回行数控制在当前展示所需范围，避免不必要 egress；
- 本地 SQLite 不受 Supabase egress 限制，但仍必须遵守 V1/V2 隔离、数据真实性和页面范围边界。

本文档只规定上述数据消费和资源约束，不规定 API 数量、接口路径、数据库表、索引或查询实现。

### 4.7 全局验收标准

1. 两份 PRD 均完整声明相同的全局导航、刷新、缓存、SSE、懒加载和数据读取规则。
2. Logo 始终返回 V2 Overview；除 Overview 外的页面均可通过下拉列表切换已有非初始化 ticker。
3. ticker 切换保持当前业务页，且不会展示上一 ticker 的缓存数据。
4. 普通页面在首次打开、首次访问未缓存范围、人工刷新或主动打开懒加载内容时读取数据。
5. 页面往返和窗口聚焦不触发额外刷新；硬刷新视为新打开页面。
6. 只有规定组件按真实分钟边界更新，只有消息流和运行链路图使用 SSE。
7. SSE 只更新最小增量，不触发整页或全量数据重读，页面隐藏期间关闭并可按游标恢复。
8. 大正文、大 JSON、详情、历史正文、reasoning 和后续分页均按需加载。
9. Supabase 读取不存在为了少量展示而进行的整表读取、无界历史读取、多集合全量读取或高频大 payload 读取。
10. 本地 SQLite 与 Supabase 均不得跨越 V1/V2 数据隔离边界。

## 5. 消息总线页面

### 5.1 页面目标与范围

消息总线是 ticker 级页面，用于查看当前 ticker 的 V2 标准消息流、消息处理路由、各消息源的实际运行状态，以及当前 ticker 的消息源 binding 配置。

- 页面名称和 ticker 级导航名称继续使用“消息总线”。
- 页面路由保持 `/ticker/:ticker/message-bus` 不变。
- 页面继续分为“消息流”和“配置”两部分，默认显示“消息流”。
- “消息流”用于查看已经进入 V2 Message Bus 的 Standard Message、Runtime 路由和消息源状态。
- “配置”用于查看和修改当前 ticker 的 source binding，不用于创建全局 Source、修改爬虫代码或管理 Crawler Plane release。
- 页面只读取 V2 Message Bus 和 Persistent Runtime V2 数据，不读取 V1 monitoring 数据、V1 DTO 或缓存作为回退。
- 除本文明确记录的结构、信息和交互要求外，不在本需求中规定具体视觉设计方式或视觉效果。

本页包含六个功能模块：

1. 页面标题与全局操作；
2. 顶层 KPI；
3. 消息流筛选与搜索；
4. Standard Message 卡片；
5. 消息源状态；
6. 消息渠道配置。

### 5.2 页面标题与全局操作

- 页面标题显示“{ticker} 消息总线”。
- 页面保留“消息流”和“配置”切换入口。
- 页面保留手动刷新入口。
- 页面不显示最近刷新时间。
- 页面不显示 SSE 连接状态。
- 页面继承第 4 节全局规范：消息流使用 SSE 增量更新；KPI 和消息源状态在页面可见时按真实分钟边界更新；配置按低频缓存和按需加载处理。
- 首次打开“消息流”时只读取首屏消息、当前周期 KPI 和消息源状态；不读取完整消息历史、消息正文全文或配置详情。
- 第一次切换到“配置”时再读取当前 ticker 的消息渠道配置；已经读取过则使用本标签页缓存。
- 切换到其他页面时关闭消息流 SSE；返回时先显示缓存，并从上次事件游标恢复增量，不进行整页刷新。
- 用户手动刷新时只更新当前模式所需的数据；消息流模式不因此预取配置，配置模式不因此读取完整消息历史。
- 手动刷新失败时保留刷新前缓存并提示失败。

### 5.3 顶层 KPI

顶层 KPI 保留五项：

1. 连续运行时长；
2. 周期新增；
3. 正文补全成功率；
4. 数据源状态；
5. 平均轮询延迟。

KPI 在业务逻辑上分为实时状态和周期数值两类，但不要求前端刻意将两类 KPI 设计成两个视觉模块。

实时状态 KPI：

- 连续运行时长；
- 数据源状态；
- 平均轮询延迟。

周期数值 KPI：

- 周期新增；
- 正文补全成功率。

实时状态 KPI 不受周期、消息源类型、具体消息源、路由状态或关键词搜索影响。周期数值 KPI 受第 5.4 节周期以及第 5.5 节业务筛选影响。

全部 KPI 在消息总线页面可见时按真实时钟分钟边界更新。该分钟读取只取得当前周期和当前筛选交集所需的 KPI 聚合结果，不读取消息正文、消息历史或消息源配置；消息流 SSE 不触发 KPI 重读。

#### 5.3.1 连续运行时长

- 原“启动时长”改名为“连续运行时长”。
- 从当前 ticker 最近一次成功进入运行状态的时间开始计算。
- ticker 暂停、停止或阻塞时，本次连续运行结束，卡片显示“未运行”。
- ticker 后续再次进入运行状态时，从零开始计算新的连续运行时长，不累计此前运行区间。
- ticker 正常运行或非阻塞降级运行时，连续运行时长继续累计。
- 页面取得本次运行开始时间后，可以在浏览器本地继续计时；本地计时不属于页面数据刷新，不触发网络请求。

#### 5.3.2 周期新增

- 原“今日原始消息”和“事件流数量”合并为“周期新增”。
- 统计口径与 Overview 的“当日消息”完全一致：统计所选周期内成功发布到标准消息流的唯一 Standard Message 数。
- 不统计 Raw Message 数量。
- 不按 Stream Item 数量计数；一个分批 Stream Item 包含多条 Standard Message 时，按其中唯一 Standard Message 分别计数。
- 同一消息被多个 Runtime 节点处理时不重复计数。
- 同一 source item 的内容没有变化、因精确去重而没有形成新 Standard Message 时不计入。
- 同一 source item 内容发生实质变化并形成新的 Standard Message revision 时，该 revision 计为一条周期新增。
- 消息归属统计周期以成功发布到标准消息流的时间及 DoxAgent 语义交易日为准，不以原始信源的 `published_at` 代替。
- 显示相邻上一等长窗口的环比变化百分比。

#### 5.3.3 正文补全成功率

- 保留“正文补全成功率”KPI。
- 统计所选周期和当前消息筛选交集内，需要进行正文补全尝试的 Standard Message。
- 成功获得有效完整正文的消息进入成功数；只能使用源摘要或短正文作为 fallback 的消息不进入成功数。
- 没有进行正文补全尝试的消息不进入分母。
- 所选范围没有可统计的正文补全记录时显示“暂无数据”，不显示为 `0%`。
- 该 KPI 随周期、API/爬虫类型、具体消息源和路由状态筛选变化。
- 显示相邻上一等长窗口的环比变化百分比。

#### 5.3.4 数据源状态

- 原“健康 channel”改名为“数据源状态”。
- 展示格式和口径与 Overview ticker 列表中的 Message Bus 状态完全一致：

```text
正常启用源数量 / 异常源数量
```

- 左侧统计当前 ticker 已启用且 Poll 状态正常的 source binding。
- 右侧统计当前 ticker 已启用但处于 `partial`、失败或其他阻止正常采集状态的 source binding。
- `never_polled` 不进入左右任一数量。
- 用户主动禁用、已经移除或尚未建立 binding 的 Source 不进入左右任一数量。
- 本 KPI 为实时状态，不受页面筛选和周期影响。

#### 5.3.5 平均轮询延迟

- 保留“平均轮询延迟”KPI。
- 统计当前 ticker 已启用消息源最近一次有有效延迟记录的 Poll 结果平均值。
- 没有有效延迟记录的消息源不进入平均值计算。
- 所有已启用消息源均没有有效延迟记录时显示“暂无数据”。
- 本 KPI 为实时状态，不受页面筛选和周期影响。

### 5.4 周期切换

“周期新增”和“正文补全成功率”共用一个周期切换，包含：

- `前一交易日`，默认选择；
- `本交易日`；
- `7天`；
- `30天`；
- `全部`。

周期完整复用 Part 1 Overview 第 5.3.2 节口径：

- 使用 DoxAgent 美东 02:00 语义交易日和真实美股交易日历；
- 前一交易日是当前语义日之前最近一个有效美股交易日；
- 本交易日只在当前语义日为有效交易日时可选，休市日禁用；
- 7天和30天分别使用最近 7 个和30个有效美股交易日；非交易日截至此前最近一个有效交易日；
- “全部”覆盖当前 ticker 可用的全部保留历史；
- 页面不得按用户设备自然日、简单工作日或固定 UTC 偏移计算周期；
- 周期切换只改变两个周期数值 KPI 和消息列表的时间范围，不改变实时状态 KPI。

环比窗口与交易策略、事件库页面保持一致：

- 前一交易日与再前一个有效交易日比较；
- 本交易日与前一个有效交易日比较；
- 7天与此前紧邻的 7 个有效交易日比较；
- 30天与此前紧邻的 30 个有效交易日比较；
- “全部”不显示环比。

环比规则如下：

- 周期新增使用 `(当前窗口值 - 上一窗口值) / 上一窗口值 × 100%`；
- 正文补全成功率同样使用当前窗口成功率与上一等长窗口成功率计算相对变化百分比，不使用百分点差替代；
- 当前窗口或上一窗口数据不完整时显示“不适用”；
- ticker 运行历史不足完整当前窗口和完整上一窗口时显示“不适用”；
- 上一窗口值为 0、上一窗口没有可统计正文补全记录或任一窗口成功率不可用时显示“不适用”；
- 不得用缺失数据补零后计算环比。

周期切换不进行整页刷新。第一次选择尚无缓存的周期时读取该周期的消息首屏与 KPI；再次选择使用缓存。页面可见时，当前周期 KPI 仍按真实分钟边界更新。

### 5.5 消息流筛选与搜索

消息流提供以下三个业务筛选：

1. 消息源类型；
2. 具体消息源；
3. 路由状态。

同时保留一个独立的标题或正文关键词搜索。

#### 5.5.1 消息源类型

类型筛选改为：

- `全部类型`；
- `API`；
- `爬虫`。

类型以 V2 Source Definition 的 `kind = api | crawler` 为准。页面不再使用或显示 V1 的“机构媒体/社媒”“media/social”分类。

#### 5.5.2 具体消息源

- 具体消息源筛选包含“全部来源”。
- 其他选项使用消息源的用户可读名称，并以稳定 `source_id` 作为筛选身份。
- 同名但 `source_id` 不同的 Source 不得错误合并。
- 具体消息源选项与当前 ticker 实际消息范围保持一致。

#### 5.5.3 路由状态

- 路由状态筛选包含“全部路由”。
- 正式路由选项使用 Persistent Runtime V2 当前主路由枚举：
  - `ARCHIVE`；
  - `TRADE`；
  - `ADD_TO_DELTA`；
  - `W3`。
- Runtime 尚未形成主路由的消息只在“全部路由”下显示，不伪造为任一正式路由。
- `BADCASE`、`EMIT_DELTA`、`CREATE_TRADE_RECORD` 等 Runtime side effect 不作为主路由筛选项。

#### 5.5.4 筛选与 KPI 联动

- 消息源类型、具体消息源和路由状态三个筛选共同生效，结果取交集。
- 三个筛选均改变当前消息列表、“周期新增”和“正文补全成功率”。
- 实时状态 KPI 不随筛选变化。
- 标题或正文关键词属于搜索，不属于 KPI 筛选；关键词只改变消息列表，不改变任何 KPI。
- 周期和三个业务筛选共同决定周期 KPI 的统计范围。
- 筛选和搜索不触发 workflow，不进行整页刷新。

### 5.6 消息卡片

- 原“Live Message Stream”改名为“消息流”。
- 消息列表以 Standard Message 为基本展示单位。
- 消息卡片继续保留折叠和展开能力。
- 折叠状态显示消息标题、消息源、API/爬虫类型、当前处理或路由状态、信源发布时间和抓取时间。
- 消息卡片完全移除 summary；前端不再生成、展示或使用 body 截断内容作为 summary。
- 展开后显示正文和原始信源入口。
- 正文字体需要适合连续阅读，并与标题形成明确区分。
- 如果返回或抓取的正文结构支持，正文至少保留段落等最小限度排版，不把全部内容压成单段文本。
- 页面不自行生成消息摘要，也不改写消息正文的业务含义。
- 消息默认继续按抓取时间由近到远排列并支持分页或继续加载。

#### 5.6.1 当前处理与路由状态

- Runtime Case 尚未形成路由时，卡片显示当前真实处理状态，例如待处理、处理中或失败。
- Runtime 首次路由为 `W3` 且 W3 尚未完成时，显示 `W3`。
- W3 完成后，显示 `resolved_route` 中最终的 `ARCHIVE`、`TRADE` 或 `ADD_TO_DELTA`。
- 非 W3 路径显示 Runtime Case 的正式 `primary_route`。
- 卡片只显示当前有效处理或路由结果，不额外展示完整路由历史链。
- 页面不得继续把全部 V2 Standard Message 固定显示为 `completed`，也不得使用 V1 processing status 冒充 V2 Runtime 路由。

### 5.7 消息源状态

原“Channel Health”改名为“消息源状态”，基本功能继续参照当前页面：逐项展示当前 ticker 已有 source binding 的轮询状态和最近运行事实。

每个消息源至少需要以下业务信息：

- 消息源名称；
- API 或爬虫类型；
- 单条或分批发布模式；
- 最近一次轮询延迟；
- 最近成功时间；
- 当前 Poll 状态；
- 最近一轮新增消息数量；
- 当前错误信息。

名称下方的小字内容调整为：

```text
API/爬虫 | 单条/分批 | 延迟时间
```

具体语义如下：

- `API/爬虫` 来自 Source Definition 的 `kind`；
- `单条` 对应 `publication_mode = immediate`；
- `分批` 对应 `publication_mode = buffered`；
- 延迟时间使用该 binding 最近一次有效 `last_latency_ms`；没有数据时显示“暂无数据”；
- 不再显示 ticker 名称；
- 不再显示 `按 ticker/按参数` 等 V1 消息源配置方式。

最近成功时间规则：

- 最近成功发生在当前 DoxAgent 语义交易日时显示时间；
- 最近成功不在当前 DoxAgent 语义交易日时显示日期；
- 没有成功记录时显示“暂无数据”。

倒计时环规则：

- 保留当前动态加载环，用于表达距离该 binding 下一次目标轮询的剩余进度；
- 加载环根据当前 Poll 调度事实和浏览器本地时间动态推进，不因动画持续请求数据；
- 暂停、禁用、不在 active window 或没有可用调度时间时，不伪造正在倒计时；
- 手动刷新后以新取得的 Poll 状态重新校准。

列表继续显示当前 ticker 已有 binding，包括 `never_polled` 和用户主动禁用的 binding。它们不进入顶层“数据源状态”左右计数，但需要在本列表中显示各自真实状态。

消息源状态在页面可见时按真实时钟分钟边界读取当前列表所需的最小状态数据。倒计时环在两次读取之间仅根据最近调度事实和浏览器本地时间推进，不产生额外请求。消息流 SSE 不触发消息源状态列表重读；离开页面后停止分钟读取，返回时等待下一个分钟边界。

### 5.8 消息渠道配置

消息渠道配置继续按消息源逐项展示当前 ticker binding，并保留当前页面已有的启用状态、配置内容、最近成功、轮询间隔、最近延迟和错误信息。

配置属于低频数据：首次进入“配置”模式时加载，之后使用当前标签页缓存；不随消息流 SSE 或页面分钟刷新自动重读。单个消息源的大型 JSON 参数只在用户打开该消息源 JSON 视图时按需加载。

配置卡片名称下方不再显示 V1 的媒体/社媒或按 ticker/按参数分类。需要显示的来源身份为：

```text
source_id | API/爬虫 | 单条/分批
```

#### 5.8.1 API 配置

- 已有 API 消息源同时支持表单和 JSON 两种参数配置方式。
- 表单只适配产品已经明确支持的现有 API 参数，不要求根据任意 JSON Schema 自动生成通用表单。
- JSON 与表单编辑的是同一份当前 ticker binding `source_parameters`，切换方式不能形成两套相互冲突的配置。
- API 没有可配置 `source_parameters` 时，页面明确显示无需额外参数，不伪造空表单字段。

#### 5.8.2 爬虫配置

- O4 自建爬虫消息源只提供 JSON 参数配置，不要求适配专用表单。
- JSON 只编辑当前 ticker binding 的 `source_parameters`。
- 页面不得通过该 JSON 修改 Source Definition、`adapter_ref`、爬虫代码、Crawler Plane package、ACTIVE release 或 Certification。
- 页面不得把修改爬虫参数描述为重新认证或重新发布爬虫。

#### 5.8.3 通用配置项

- 所有 API 和爬虫 binding 均提供启用/禁用操作。
- 所有 API 和爬虫 binding 均提供表单形式的轮询间隔调整项，不要求用户通过 JSON 修改轮询间隔。
- 轮询间隔编辑的是当前 ticker/source binding 的 `polling.target_interval_seconds`，不修改全局 Source 默认值或其他 ticker 的配置。
- 保存时必须使用 V2 Source 的参数约束和 PollingConfig 约束校验输入；失败时保留用户当前编辑内容并显示错误，不显示保存成功。
- 成功保存后更新本标签页中的当前 binding 配置和相关状态缓存，不触发 ticker 初始化或 O4 workflow。
- 页面不提供创建、删除或上传全局消息源的能力。

#### 5.8.4 尚未绑定的可用 API

- 已经存在 binding 的消息源显示在正常配置列表中，包括当前被用户禁用的 binding，以便重新启用。
- 配置列表最下方可以显示已经注册、全局启用、适用于当前 ticker 但尚未建立 binding 的 API 消息源。
- 该区域不显示尚未绑定的爬虫消息源。
- 该区域不显示全局已经禁用的 Source。
- 用户对其中 API 进行启用和配置时，形成的是当前 ticker 的 source binding，不是创建新的全局 Source。
- 页面仍不提供全局 Source 注册、Crawler 上传或 Source Definition 删除能力。

### 5.9 页面数据需求

#### 5.9.1 KPI 与周期统计

- ticker 当前真实运行状态；
- 最近一次进入运行状态的时间；
- 当前 DoxAgent 语义交易日和五个可用统计窗口；
- 所选窗口内已经成功发布到标准消息流的唯一 Standard Message；
- Standard Message revision 与精确重复关系；
- 消息的 Source Kind、source_id 和当前有效 Runtime 路由；
- 正文补全是否尝试、是否成功及可统计性；
- 当前 ticker 各 binding 的启用状态、Poll 状态和最近轮询延迟；
- 两个周期 KPI 在当前周期和业务筛选交集下的值；
- 相邻上一等长窗口、窗口完整性、上一窗口值、环比百分比或不适用原因。

#### 5.9.2 消息流

- Standard Message ID 和 revision；
- title、body、source、URL 和信源发布时间；
- source_id、Source Kind 和 binding 身份；
- 抓取时间和成功发布到标准消息流的时间；
- Runtime Case 当前状态；
- 初始主路由、W3 是否待处理、最终 resolved route；
- 分页或继续加载所需的稳定顺序事实。
- SSE 增量的稳定事件游标；
- 判断新增消息是否符合当前类型、具体消息源、路由状态和关键词范围所需的最小字段；
- 必要时按单个 Standard Message 身份补读当前卡片所需信息的稳定身份。

#### 5.9.3 消息源状态和配置

- Source ID、用户可读名称和 `api/crawler` 类型；
- 当前 ticker binding 是否存在、是否启用及其版本；
- `source_parameters` 及其参数约束；
- `publication_mode = immediate | buffered`；
- `polling.target_interval_seconds`、active window 和下一次目标调度时间；
- Poll status、最近成功、最近延迟、最近一轮新增数和当前错误；
- 已注册、全局启用、适用于当前 ticker 且尚未绑定的 API Source；
- Source 是否全局禁用，以及是否为尚未绑定的爬虫，以便从底部候选区排除。

前端只消费上述业务数据，不在本文档中规定 API 路径、后端服务拆分、数据库表或数据查询实现。

### 5.10 页面状态

- 当前 ticker 没有 Standard Message 时，消息流显示暂无消息，不用 Raw Message 或 V1 Event 替代。
- 当前周期或筛选没有消息时，消息列表显示无匹配结果，周期新增显示 `0`；没有可统计正文补全记录时，正文补全成功率显示“暂无数据”。
- 单条消息正文读取失败时，不清空其他消息和 KPI。
- Runtime 路由暂不可用时显示真实处理状态，不把缺失路由当作 `ARCHIVE` 或 `completed`。
- 单个消息源状态不可用时，只影响该消息源及相关实时统计，不清空消息流。
- 配置保存失败时保留编辑内容和保存前的生效配置。
- 手动刷新失败时保留刷新前缓存并提示失败。
- SSE 断线时保留现有消息列表并提示实时更新异常；重连后从上次游标补收增量，不清空列表或全量重读。
- 分钟刷新失败时保留上一分钟的 KPI 和消息源状态缓存，下一真实分钟边界可以再次刷新。

### 5.11 Workflow 对齐与支持边界

| 前端需求 | 当前 V2 workflow 事实 | 产品约束 |
|---|---|---|
| API/爬虫分类 | Message Bus V2 `SourceKind` 只有 `api` 和 `crawler`；V2 已删除 `media/social` 与 `by_ticker/by_parameter` 业务分类 | 页面统一使用 API/爬虫，不从 Source 名称猜测类型 |
| 单条/分批 | ticker/source binding 的 `StreamingConfig.publication_mode` 为 `immediate` 或 `buffered`；分批 Stream Item 可包含多条 Standard Message | 状态与配置页分别显示为单条/分批；周期新增按 Standard Message 而不是 Stream Item 计数 |
| Standard Message | V2 Standard Message 的 title 可选，body、source、URL 和 published_at 必须存在；正文补全发生在不可变 Standard Message 建立前 | 页面移除 summary，展开后读取正式 body，不从 Raw payload 拼接正文 |
| Revision 与去重 | 相同 source item 内容不变时不产生新 Standard Message；内容实质变化时产生新 revision 和新 Stream publication | 周期新增计 revision，不计精确重复 |
| Runtime 路由 | Message Bus Stream 由 Persistent Runtime V2 消费；主路由为 `ARCHIVE/TRADE/ADD_TO_DELTA/W3`，W3 可形成 resolved route | 当前 Dashboard 对 V2 消息固定返回 `completed` 且未关联 Runtime Case，尚不能满足页面路由展示和筛选要求 |
| 连续运行时长 | Message Bus 和 Runtime 当前都保存 started_at/status，但现有恢复路径不会完整维护“最近一次连续运行起点” | 页面要求最近运行区间事实；不能直接沿用最初启动时间冒充连续运行时长 |
| 数据源状态 | V2 Poll status 包含 `never_polled/succeeded/partial/failed/disabled`，每个 binding 独立持久化状态 | 顶层计数复用 Overview 口径；never_polled 和禁用项仅在消息源状态列表保留 |
| 动态倒计时 | PollState 提供 target due、next dispatch 和最近 Poll 事实，PollingConfig 提供 interval 与 active windows | 动态环只做本地时间推进，暂停、禁用或窗口关闭时不得伪造倒计时 |
| 配置 | V2 Source Definition 提供通用 parameter schema；binding 独立保存 source parameters、polling 和 streaming 配置 | API 可做已适配表单，爬虫仅做 JSON；两者均可通过表单改当前 binding 的轮询间隔 |
| O4 自建爬虫 | Crawler Plane 只有 ACTIVE release 才能注册为 Message Bus crawler Source，并由 binding 提供 ticker 参数 | 前端只改 binding 参数，不修改或绕过 crawler release、Certification 和 adapter 边界 |
| 周期、筛选与环比聚合 | 当前 Dashboard overview 仍使用旧的当日 Raw/Stream 聚合，消息列表对 V2 也未提供 Source Kind、真实路由或相邻等长窗口聚合 | 需要向前端提供本文定义的当前窗口、上一窗口、筛选交集、完整性和环比事实，但本文档不规定实现方式 |
| 前端刷新 | 当前页面同时存在 SSE、8/15/60 秒查询；SSE 事件会触发消息列表和 Overview 重读 | V2 仅保留消息流 SSE 增量，KPI 与消息源状态按真实分钟边界读取，配置按需缓存；SSE 不得触发整列表、整页或 KPI 重读 |

本文档只记录上述 workflow 支持事实和前端约束，不规定 API、后端或数据库实现。

### 5.12 验收标准

1. 页面继续使用 `/ticker/:ticker/message-bus`，保留消息流和配置两部分并默认显示消息流。
2. 页面不显示 SSE 状态或最近刷新时间；消息流使用可恢复游标的 SSE 增量，KPI 与消息源状态按真实分钟边界更新，配置按需加载并缓存。
3. 顶层保留连续运行时长、周期新增、正文补全成功率、数据源状态和平均轮询延迟五项 KPI。
4. 实时和周期 KPI 保持逻辑区分，但不强制拆成不同视觉模块。
5. 连续运行时长从最近一次进入运行状态开始，暂停、停止或阻塞后显示未运行，再次运行重新计时。
6. 周期新增按成功发布的唯一 Standard Message 统计；分批发布按成员消息数统计，revision 计新增，精确重复不计。
7. 周期新增和正文补全成功率共用前一交易日、本交易日、7天、30天和全部周期，默认前一交易日，并复用既定语义交易日规则。
8. 两个周期 KPI 均显示相邻上一等长窗口的环比变化；全部不显示环比，窗口不完整、历史不足、上一值为0或成功率不可用时显示“不适用”。
9. 类型、具体消息源和路由筛选共同影响消息列表与两个周期 KPI；关键词搜索只影响消息列表。
10. 类型筛选只有全部、API和爬虫，不显示机构媒体、社媒或 V1 source/interface 分类。
11. 具体消息源和路由状态均提供“全部”选项。
12. 路由使用 `ARCHIVE/TRADE/ADD_TO_DELTA/W3`；W3 完成后显示最终 resolved route，side effect 不作为路由。
13. 消息卡片完全移除 summary，折叠时不显示正文摘要，展开后显示具有基本可读排版的正式 body。
14. 消息源状态名称下方显示 API/爬虫、单条/分批和最近轮询延迟，不显示 ticker 或按 ticker/按参数。
15. 最近成功属于当前语义交易日时显示时间，否则显示日期。
16. 倒计时环根据调度事实动态推进但不请求新数据；暂停、禁用和窗口关闭时不显示虚假倒计时。
17. 顶层数据源状态与 Overview Message Bus 状态口径一致；never_polled 和禁用 binding 不计数，但仍可在消息源状态列表查看。
18. API 同时支持已适配表单和可编辑 JSON；爬虫只支持可编辑 JSON；JSON 只编辑当前 binding 的 source parameters。
19. 所有 API 和爬虫均提供表单形式的轮询间隔调整和启用/禁用能力。
20. 配置页不允许修改 Source Definition、adapter、Crawler package、ACTIVE release 或 Certification，也不提供全局 Source 创建、删除或上传。
21. 配置列表底部只显示已注册、全局启用、适用于当前 ticker 且尚未绑定的 API；不显示尚未绑定的爬虫或全局禁用 Source。
22. 页面只展示和消费 V2 Message Bus 与 Persistent Runtime V2 数据，不读取 V1 monitoring 数据作为回退。
23. 消息流 SSE 只插入符合当前筛选和搜索范围的新消息，不重置现有列表或分页。
24. 单条 SSE 不触发消息列表、KPI、消息源状态、配置或整页全量重读；页面隐藏时关闭连接，返回时按游标恢复。
25. 消息渠道配置首次进入时加载，之后使用缓存，不参加一分钟自动刷新；大型 JSON 参数按单个消息源按需加载。
26. 页面首次只读取首屏消息、当前 KPI 和消息源状态，消息正文全文、配置、JSON 和后续分页均按需加载。

## 6. 运行状态页面

### 6.1 页面定位与范围

“运行状态”页面用于查看当前 ticker 在 Persistent Runtime V2 中的处理规模、判定效率、业务结果、完整 Case 流向和单条 Case 的研判明细。

本页面是独立于“消息总线”的第七部分需求。消息总线负责消息流与消息源配置；运行状态负责 Standard Message 进入 Persistent Runtime V2 后的 W1、W2、可选 W3、结果生成和交易执行情况。

本页面沿用现有 ticker 级运行状态页面入口，但全部业务数据和状态语义切换为 V2。不得使用 V1 Runtime、A2、旧 O3 Duty Expert、Objection、Known Event Patch 或 Ingest Queue 数据作为缺失数据的回退。

### 6.2 页面模块

页面包含以下四个模块：

1. 页面标题与全局操作区；
2. 顶部 KPI 栏；
3. 运行链路图及节点详情；
4. 最近处理记录。

页面不展示 SSE 连接状态或最近刷新时间。

### 6.3 全局统计周期

页面标题区提供以下全局统计周期：

- 前一天，默认选中；
- 当天；
- 7天；
- 30天；
- 全部。

周期语义、有效美股交易日、`America/New_York` 时区、02:00 语义日边界、冬夏令时和非交易日处理复用交易策略与事件库页面已经确定的统一规则。

周期切换对本页面全部周期数据生效，包括：

- 顶部全部 KPI；
- 运行链路图的节点、连线和结果数量；
- 当前选中节点的节点详情和最近节点记录；
- 最近处理记录及其筛选结果。

“前一天”“当天”“7天”和“30天”均使用相邻上一等长有效交易日窗口计算环比；“全部”不显示环比。窗口不完整、运行历史不足、上一窗口值为 0 或数据不可比较时，环比显示“不适用”，不得虚构为 0%。比例类 KPI 的环比使用相对变化百分比，不使用百分点差。

### 6.4 顶部 KPI

顶部 KPI 栏包含以下八项。它们均为周期数据，受全局周期切换影响。

#### 6.4.1 周期处理

- 统计所选周期内进入 Persistent Runtime V2 的唯一 Runtime Case 数。
- Case 无论最终完成、仍在处理、等待重试、不可用或失败，均计入周期处理。
- 同一 Case 的多次模型尝试、多个 side effect 或多个最终结果不得重复增加本 KPI。

#### 6.4.2 一轮判定平均延时（W1+W2）

- 统计完成一轮判定的 Case 平均墙钟耗时。
- 实时模式下 W1 与 W2 并行运行，单个 Case 的耗时从 W1/W2 开始处理起，计算到 W1 与 W2 均形成最终判定为止。
- 不将并行执行的 W1 与 W2 耗时简单相加。
- 该耗时包含一轮判定内实际发生的模型重试和重试等待。
- 尚未完成 W1/W2 一轮判定的 Case 不进入平均值分母。

#### 6.4.3 二轮研判平均延时（W3）

- 只统计实际进入并完成 W3 的 Case。
- 单个 Case 使用 W3 Worker 从开始处理到返回最终有效结果的完整墙钟耗时。
- W3 未完成或没有有效结束时间时不进入平均值分母。

#### 6.4.4 新旧判定

展示格式：

```text
NEW 数量 / OLD 数量
```

统计规则：

- 每个 Case 只形成一个用于本 KPI 的有效新旧判定；
- 未经过 W3 的 Case 使用 W1 最终 NEW/OLD 判定；
- 经过并完成 W3 的 Case 使用 W3 最终 NEW/OLD 判定覆盖 W1 判定；
- 不区分 `normal` 与 `low` confidence；
- 尚未形成有效新旧判定的 Case 不计入 NEW 或 OLD。

#### 6.4.5 Policy 命中

展示内容：

- 命中数量；
- 命中比例。

统计规则：

- 命中数量为所选周期内命中过至少一个 Policy 的唯一 Case 数；
- 同一 Case 命中多个 Policy 仍只计 1；
- 命中比例为命中 Case 数除以周期处理 Case 数；
- 未经过 W3 的 Case 使用 W2 最终判定；
- 经过并完成 W3 的 Case 使用 W3 最终 Policy 判定，W3 已否决的 W2 初步命中不再计入；
- 尚未形成最终有效 Policy 判定的 Case 不计为命中。

#### 6.4.6 二轮研判

- 统计所选周期内实际流转到 W3 的唯一 Case 数。
- 每个 Case 只计一次，不因 W3 重试次数增加。
- 已流转但尚未完成、最终失败或等待重试的 W3 Case 仍计入流转数量。

#### 6.4.7 事件发现

- 统计 W1-R3 和 W3 在所选周期内成功形成的唯一新 atomic fact candidate 数量。
- W1-R3 与 W3 结果使用同一统计口径。
- 模型重试重复输出、重复落盘或相同候选的重复处理不得重复计数。
- 未通过正式结构校验、没有形成可用候选的原始模型文本不计入。

#### 6.4.8 交易执行

- 只统计已经产生实际成交的 Runtime 交易执行，不统计主路由为 `TRADE`、创建 Trade Record、生成交易意图、进入执行队列或仅被执行系统接收的情况。
- 一个 Runtime Case 只要产生至少一笔真实成交即计 1；部分成交也计入。
- 同一执行拆分成多个 broker fill 时仍按一个 Runtime Case 计 1。
- 不区分模拟盘与实盘，二者使用相同统计口径并合并展示。
- 没有成交的拒绝、过期、失败或未提交执行不计入交易执行。

#### 6.4.9 KPI 环比

- 八项 KPI 均提供当前窗口与上一可比窗口的环比事实。
- NEW/OLD 分别比较各自数量。
- Policy 命中分别比较命中数量和命中比例。
- 延时 KPI 比较平均延时。
- 其他 KPI 比较对应计数。
- 页面只展示后端已经形成的当前值、上一窗口值、环比和可比性事实，不在前端自行重建交易日窗口或补算业务口径。

### 6.5 V2 运行链路图

运行链路图是本页唯一使用 SSE 的组件。首次打开时读取当前周期的完整基础图，此后只通过 SSE 应用新增或更新 Case 对相关节点、连线和计数造成的最小增量。SSE 不触发 KPI、节点详情或最近处理记录重读。

离开运行状态页面时关闭 SSE；返回时先显示缓存并从上次事件游标补收增量，不重新读取完整链路图。用户已经选择某一结果节点或中间节点查看局部路径时，增量更新不得自动取消当前路径聚焦。

#### 6.5.1 业务链路

运行链路图必须依据 Persistent Runtime V2 的真实 Case 流转重做，不能沿用现有 V1 图的节点和人工推导连线。

主处理链路需要覆盖：

1. Runtime 接收消息；
2. W1 与 W2 一轮并行判定；
3. 确定性主路由判定；
4. 部分 Case 进入 W3 二轮研判；
5. Case 形成一个或多个最终结果。

V2 的主路由与最终结果必须在概念上区分：

- 主路由为单值，首次判定使用 `ARCHIVE`、`TRADE`、`ADD_TO_DELTA` 或中间路由 `W3`；
- W3 完成后形成 `ARCHIVE`、`TRADE` 或 `ADD_TO_DELTA` resolved route；
- 一个 Case 可以因多个 side effect 同时进入多个最终结果节点，因此下游结果数量允许重复计算同一个 Case。

#### 6.5.2 最终结果节点

链路图只保留以下最终结果节点：

- 归档；
- 事件发现；
- Badcase；
- 交易执行；
- 失败。

具体规则：

- 不单独设置“交易记录”节点；
- `CREATE_TRADE_RECORD`、交易意图生成或执行接收不能代替“交易执行”；只有实际成交才能流入交易执行节点；
- W1-R3 或 W3 成功形成唯一 atomic fact candidate 时流入事件发现节点；
- Case 同时形成 Delta 与实际成交时，可以同时计入事件发现和交易执行；
- OLD Case 同时归档并形成 Badcase 时，可以同时计入归档和 Badcase；
- Case、W1/W2、W3、side effect 或交易执行阶段出现的各种失败形式统一归入“失败”结果节点，不为不同技术失败类型增加多个结果节点；
- 仍在处理、等待重试或尚未形成结果的 Case 停留在其当前处理节点，不伪造为任一最终结果。

#### 6.5.3 数量口径

- 节点和连线数量均以唯一 Runtime Case 为基本计数单位。
- 同一 Case 在同一个节点或同一条连线上只计一次。
- 同一 Case 可以进入多个不同结果节点，因此所有结果节点数量之和可以大于入口 Case 数。
- 图表不得为了让上下游总数相等而丢弃 side effect、合并真实结果或制造虚假互斥关系。
- 所有数量均受当前全局周期影响。

#### 6.5.4 路径查看

- 默认状态显示所选周期内完整 Case 分流。
- 点击任意最终结果节点时，只保留所有通向该结果的上游路径，隐去与该结果无关的流向。
- 点击 W1、W2、路由判定或 W3 等中间节点时，只保留经过该节点的上游和下游路径。
- 点击图表空白区域时恢复完整分流。
- 路径聚焦只改变图表当前查看范围，不改变全局周期、最近处理记录筛选或 KPI。

### 6.6 节点详情

节点详情随当前选中节点和全局周期变化。

节点详情首次点击时按当前节点和周期按需加载。当前节点详情保持打开且页面可见时，在真实时钟分钟边界更新该节点的统计和最近记录；未打开的节点不预取、不参加分钟刷新。切换回已经加载过的节点时优先使用缓存。

#### 6.6.1 节点统计

节点详情保留该节点的处理数量、失败数量、最近处理时间和平均处理延时等有效运行信息，并增加以下 V2 专属统计：

- W1 节点显示 W1 最终判定中 `confidence = low` 的唯一 Case 数；
- W2 节点显示 W2 最终判定中 `confidence = low` 的唯一 Case 数；
- W3 节点分别显示流向归档、事件发现、Badcase、交易执行和失败结果的唯一 Case 数；
- 同一 W3 Case 可以计入多个不同最终结果，但同一结果内只计一次。

没有可统计记录时显示 `0` 或“暂无数据”，不得读取 V1 节点数据填充。

#### 6.6.2 最近节点记录

最近节点记录不显示 Runtime Case ID、Execution ID、Turn ID、原始 input/output 或无业务意义的内部详情。

每条记录至少显示：

- 消息标题；
- 接收时间；
- 完成时间；
- 当前状态；
- 一个或多个最终结果；
- 消息源。

尚未完成的记录不伪造完成时间。记录支持点击打开侧边详情层；该详情层使用与“最近处理记录”展开状态相同的字段集合和字段语义，不另造一套节点专用详情。

### 6.7 最近处理记录

最近处理记录首屏在新打开页面时加载；页面可见时按真实时钟分钟边界更新当前周期和当前筛选下的首屏折叠记录。已展开详情、reasoning 和消息正文不随分钟刷新重复读取，除非用户人工刷新对应已打开内容。

#### 6.7.1 列表与筛选

最近处理记录以唯一 Runtime Case 为基本列表单位，并受全局周期影响。

提供以下筛选：

- 最终结果筛选：全部、归档、事件发现、Badcase、交易执行、失败；
- 消息源筛选：全部消息源及当前结果中存在的具体消息源。

筛选规则：

- 两个筛选共同生效，结果取交集；
- 最终结果为单选并包含“全部”；
- 一个 Case 具有多个最终结果时，可以分别出现在多个单项最终结果筛选中；
- 同一个 Case 在一次筛选结果中只能出现一次；
- 尚未形成最终结果的 Case 只在“全部”下显示；
- 筛选不触发 workflow，也不改变 KPI 或链路图。

#### 6.7.2 折叠状态

折叠状态继续显示单条 Case 的核心摘要信息，不显示内部 ID。至少包括：

- 消息标题；
- 一个或多个最终结果；
- 当前处理状态；
- 接收时间；
- 完成时间；
- 总处理耗时；
- 消息源。

时间语义如下：

- 接收时间：该消息进入 Persistent Runtime V2 并形成 Runtime Case 的时间；
- 完成时间：该 Case 完成当前最终处理的时间；
- 未完成、等待重试或仍在处理的 Case 不显示虚假完成时间。

#### 6.7.3 展开状态

展开状态必须以业务语义组织信息，不直接把 Runtime JSON 字段逐项铺成松散卡片。需要在有限页面空间内保持较高信息密度，并通过已有的折叠与按需展开能力控制详细信息量。本文档不规定具体视觉实现方式。

展开内容包括：

1. 节点耗时；
2. W1 判定；
3. W2 判定；
4. W3 判定，仅适用于经过 W3 的 Case；
5. 交易执行情况，仅在存在实际交易执行事实时显示；
6. 消息源；
7. 消息正文。

节点耗时规则：

- 单位统一为秒；
- 只显示 LLM 或 Agent 节点，不显示确定性 Router、普通持久化、side effect 分发等程序节点；
- W1 按 R1、R2、R3 展示实际发生的尝试；没有执行 R3 时不显示；
- W2 按 R1、R2 展示实际发生的尝试；没有执行 R2 时不显示；
- W3 展示每一次实际 Worker 尝试；
- 发生重试时，每一次尝试分别显示，不合并、不只保留最终成功尝试；
- 每次尝试显示节点/轮次、尝试序号、状态和耗时；
- 不存在可靠耗时事实时显示“暂无数据”，不得由前端使用页面时间推算。

W1 判定显示：

- 最终 NEW/OLD；
- W1 confidence；
- 关联的已知 Event/Fact，若有；
- reasoning，默认折叠，用户点击后查看完整内容。

W2 判定显示：

- 是否命中 Policy；
- W2 confidence；
- 命中的 Policy，若有；
- reasoning，默认折叠，用户点击后查看完整内容。

W3 判定显示：

- W3 最终 NEW/OLD；
- 命中的 Policy，若有；
- 关联的已知 Event/Fact，若有；
- W3 形成的事件发现结果，若有；
- W3 交易判定，若有；
- reasoning，默认折叠，用户点击后查看完整内容。

交易执行情况：

- 只有产生交易执行事实时才显示本部分；
- 明确显示是否实际成交、成交方向和执行结果；
- 部分成交与全部成交使用真实执行状态，不统一伪装为全部成功；
- 不因模拟盘或实盘使用不同的页面信息结构。

消息正文默认显示部分内容并可继续展开；前端不得生成替代原文的 summary。消息源显示用户可识别的来源名称及来源类型，不以内部 binding ID 作为主要内容。

### 6.8 页面数据需求

#### 6.8.1 周期与 Case

- 当前 ticker 和统一语义交易日；
- 当前窗口及相邻上一等长窗口的起止边界和可比性；
- Runtime Case 的唯一身份、交易日、状态、技术状态、接收时间和完成时间；
- Case 初始主路由、W3 resolved route 和全部实际最终结果；
- Case 是否进入 W3 及 W3 当前状态；
- 当前窗口值、上一窗口值、环比或不适用原因。

#### 6.8.2 W1、W2 与 W3

- W1 最终 NEW/OLD、confidence、关联 Event/Fact 和 reasoning；
- W2 最终 Policy 命中、confidence、命中 Policy 和 reasoning；
- W3 最终 NEW/OLD、关联 Event/Fact、Policy 命中、事件候选、交易判定和各部分 reasoning；
- W1/W2 每个真实模型轮次和尝试的状态、序号及耗时；
- W1/W2 并行一轮判定的开始、完成及墙钟耗时事实；
- W3 每次 Worker 尝试的状态和墙钟耗时；
- W3 流向各最终结果的 Case 归属。

#### 6.8.3 结果与交易执行

- W1-R3 和 W3 成功形成的 atomic fact candidate 及稳定去重身份；
- Archive、Badcase、事件发现和失败结果与 Runtime Case 的对应关系；
- 交易意图、执行接收与实际成交之间可区分的状态；
- 实际成交、部分成交、全部成交、拒绝、过期和失败事实；
- 同一执行的多个 fill 与其 Runtime Case 归属，以便按 Case 去重统计；
- 所有不同阶段的失败与其 Runtime Case 归属，以便统一进入失败结果节点。

#### 6.8.4 消息内容

- 消息标题和正文；
- 用户可读的消息源名称及来源类型；
- 消息进入 Runtime 的时间；
- 分页和继续加载所需的稳定排序事实。

前端只消费上述业务事实。本文档不规定 API 路径、聚合服务、数据库表、查询方式或缓存后端。

### 6.9 刷新、缓存与加载

运行状态页面同时使用 SSE、分钟更新和按需加载，但三者作用范围必须分离：

- 运行链路图使用 SSE 最小增量，不进行秒级或 8/15 秒轮询；
- KPI、当前筛选下的最近处理记录，以及当前已经打开的节点详情，在页面可见时按真实时钟分钟边界更新；
- 单条 Case 完整详情、reasoning、消息正文、未打开的节点详情和后续分页按需加载；
- 人工刷新更新当前周期内的 KPI、基础链路图、当前最近处理记录，以及已经打开的节点详情；不预取未打开详情；
- 周期或筛选第一次选择且尚无缓存时，读取该范围首屏必要数据；再次切回使用缓存；
- 分钟刷新以真实时钟分钟边界为准，不从页面进入时另行累计 60 秒；
- 页面不可见时关闭 SSE 并停止分钟读取；
- 从其他页面返回时先展示缓存，不立即进行普通刷新；链路图仅按游标恢复 SSE 增量，其他组件在下一个真实分钟边界更新；
- 刷新期间保留当前内容；刷新失败时保留原缓存并提示失败。

首次打开仅加载：

- 当前周期 KPI；
- 当前周期完整链路图所需数据；
- 最近处理记录首屏折叠数据。

以下内容按需加载：

- 用户点击节点后的节点详情和最近节点记录；
- 用户展开单条 Case 后的完整研判详情；
- reasoning 全文；
- 消息正文完整内容；
- 最近处理记录后续分页。

按需加载不得导致整页已有 KPI、链路图和记录列表被清空或整体重新加载。

单条 SSE 事件只能更新受影响的链路节点、连线和计数，或按稳定 Case 身份读取该 Case 对链路所需的最小增量；不得借此重新读取完整 Case 历史、完整链路图、全部记录或全部节点详情。

### 6.10 页面状态与异常

- 当前周期没有 Runtime Case 时，全部计数显示 `0`，延时和比例显示“暂无数据”，链路图保留业务节点但不伪造流量。
- Case 尚未完成时显示当前真实状态和已经走过的路径，不生成最终结果或完成时间。
- W1/W2 某一并行分支尚未完成时，不生成一轮判定平均延时。
- W3 尚未完成时保留在 W3 节点，不使用 W1 结果冒充 W3 最终判定。
- 单条 Case 详情读取失败只影响该详情层，不清空其他记录、链路图或 KPI。
- 某一节点详情读取失败只影响该节点详情，不清空完整链路图。
- 分钟刷新失败时保留上一分钟缓存，下一真实分钟边界可以再次刷新。
- 交易仅生成记录或意图但没有实际成交时，不进入交易执行节点或交易执行 KPI。
- 所有失败归入统一失败结果，但单条详情仍保留其真实失败阶段和状态，不能抹去排查所需事实。

### 6.11 Workflow 对齐与支持边界

| 前端需求 | 当前 V2 workflow 事实 | 产品约束 |
|---|---|---|
| 一轮判定 | 实时 Runtime 使用线程池并行执行 W1 与 W2；Case 保存 `hot_path_latency_ms`，每个 W1/W2 模型 turn 另有 `latency_ms` | KPI 使用并行阶段墙钟耗时，详情按真实 turn/attempt 分项展示，不能把 W1/W2 并行耗时相加冒充墙钟耗时 |
| W1 新旧判定 | W1 输出 NEW/OLD、normal/low confidence、Reference Event IDs 和 reason | 未经 W3 的 Case 使用 W1；经过 W3 的 Case 在聚合 KPI 中使用 W3 最终判定覆盖 W1 |
| W2 Policy 判定 | W2 输出最多三个 Policy、matched conditions、normal/low confidence 和 reason | Policy 命中按最终有效判定的唯一 Case 计数，不按 Policy ID 数量或模型尝试数计数 |
| W3 二轮研判 | W3 是 exception plane，输出最终 novelty、Policy、expert trade、Delta candidates 和各自 reason；Worker receipt 提供墙钟遥测 | W3 作为中间节点；其最终结果覆盖 W1/W2 的聚合口径，但详情同时保留原始 W1/W2 判定 |
| 单 Case 多结果 | `primary_route` 为单值；side effects 可同时产生 Archive、Delta、Badcase 或 Trade，W3 TRADE 也可同时产生 Delta | 图和筛选使用“最终结果”表达多结果；结果节点总数允许大于入口 Case 数 |
| 事件发现 | W1-R3 输出 `RuntimeFactCandidate[]`，W3 NEW 也输出 `delta_candidates[]`，候选具有稳定 signature 并持久化 | 只统计成功形成的唯一候选，不统计无效原始输出或重试重复 |
| 交易执行 | Runtime 的 Trade Record 和 trade intent 只表示决策输出；Execution Intake、broker order 与 fill 属于后续独立执行阶段 | 交易执行 KPI 和节点只认实际 fill；部分成交计入，一个 Case 多 fill 只计一次，Paper/Live 合并 |
| 失败结果 | Case、model turn、effect、W3 和交易执行均存在各自失败或不可用状态 | 图上统一进入一个失败结果节点；详情仍显示真实失败阶段和状态 |
| 当前 Dashboard | 当前运行状态聚合与链路仍基于 V1 `RuntimeExecutionRecord`，包含 A2、O3、Objection、Known Event Patch、Ingest Queue，并人工推导旧连线 | V2 页面必须从 V2 Case、turn、W3、effect、candidate 和成交事实重建，不得继续复用旧节点或旧结果枚举 |
| 刷新 | 当前页面同时使用 SSE 和约 8 秒查询，SSE 事件会重读 Overview、完整图、记录和当前节点 | V2 只让链路图使用 SSE 最小增量；KPI、当前记录和已打开节点按真实分钟边界更新；大详情按需加载，禁止 SSE 触发整页或完整集合重读 |

本文档只记录 workflow 已有事实、前端所需数据和产品约束，不规定 API、后端或数据库实现。

### 6.12 验收标准

1. 页面名称为“运行状态”，是本分卷第 6 节，与第 5 节消息总线相互独立。
2. 页面只消费 Persistent Runtime V2、Message Bus V2 消息身份和 V2 Trade Execution 事实，不以 V1 Runtime 数据回退。
3. 页面包含全局周期、八项 KPI、运行链路图、节点详情和最近处理记录四类业务模块。
4. 周期支持前一天、当天、7天、30天和全部，默认前一天，并对本页面所有周期数据同时生效。
5. 除全部外，全部 KPI 显示相邻上一等长窗口环比；不可比较时显示“不适用”。
6. 周期处理按进入 Runtime 的唯一 Case 统计，不因失败、重试或多结果重复。
7. 一轮判定平均延时使用 W1/W2 并行阶段的完整墙钟耗时，不相加并行节点耗时。
8. 二轮研判平均延时使用 W3 Worker 完整墙钟耗时，只统计已完成 W3。
9. NEW/OLD 使用最终有效判定；W3 完成后覆盖 W1 聚合结果，但详情保留两次判定。
10. Policy 命中按命中至少一个最终有效 Policy 的唯一 Case 数及其占周期处理数量的比例显示。
11. 二轮研判统计实际流转 W3 的唯一 Case；事件发现统计 W1-R3 与 W3 的唯一有效 atomic fact candidate。
12. 交易执行只统计产生实际 fill 的 Case，部分成交计入，单 Case 多 fill 不重复，模拟盘与实盘不分开展示。
13. 链路图正确区分单一主路由和多最终结果，结果节点只有归档、事件发现、Badcase、交易执行和失败。
14. 链路图不显示交易记录节点；Trade Record、intent 或 execution accepted 均不能冒充交易执行。
15. 各种失败统一流入失败结果节点；未完成和等待重试的 Case 保留在当前节点。
16. 点击结果节点只显示通向该结果的路径，点击中间节点显示相关上下游路径，点击空白恢复完整分流。
17. W1/W2 节点详情分别显示 confidence low 数量；W3 节点详情显示流向各最终结果的数量。
18. 最近节点记录不显示内部 ID，点击后打开与最近处理记录展开状态相同字段集合的侧边详情。
19. 最近处理记录支持最终结果和消息源筛选；多结果 Case 可命中多个单项筛选，但单次结果中不重复。
20. 折叠记录明确显示接收时间和完成时间；未完成 Case 不显示虚假完成时间。
21. 展开记录按实际尝试分别显示 W1-R1/R2/R3、W2-R1/R2 和 W3 耗时，单位为秒，只包含 LLM/Agent 节点。
22. 展开记录完整覆盖 W1、W2、可选 W3、可选交易执行、消息源和消息正文；reasoning 与正文支持按需展开。
23. 页面首次只加载 KPI、链路图和首屏折叠记录；节点详情、完整 Case、reasoning、正文和后续分页按需加载。
24. 运行链路图使用可恢复游标的 SSE 最小增量，不使用秒级轮询，也不因单条事件重读完整链路图或其他页面组件。
25. KPI、当前筛选的最近处理记录和当前已打开节点详情只在页面可见时按真实分钟边界更新。
26. 页面往返时先使用当前标签页缓存；链路图按游标恢复增量，其他组件不立即刷新并在下一个真实分钟边界恢复更新。
27. 未打开节点、单 Case 详情、reasoning、消息正文和后续分页按需加载，分钟刷新和 SSE 均不得预取。

## 7. 收益 / 成本审计页面

### 7.1 页面定位与本期范围

页面沿用 ticker 级路由 `/ticker/:ticker/audit`，页面标题为“{Ticker} 收益 / 成本审计”。本页面用于查看当前 ticker 在 V2 workflow 中产生的模型 Token 用量和可计价成本，不读取或回退到 V1 workflow、V1 数据库或 V1 审计记录。

页面保留“收益审计”和“成本审计”两个入口，但本期只开发成本审计：

- 默认进入“成本审计”；
- “收益审计”入口可以点击；
- 点击“收益审计”后只显示“暂未开放”，不加载收益数据，不提供收益指标、图表或明细；
- 本期不复用 V1 收益审计功能，也不将尚未开发的收益数据展示为 `0`。

成本审计覆盖当前 ticker 的全部 V2 模型调用，包括：

- 直接通过模型 API / provider 发起的调用；
- 通过 Codex SDK Worker 发起的调用；
- 初始化 workflow 与 Persistent Runtime 中各节点实际发生的模型调用；
- 重试或续作中真实发生且能够取得用量数据的模型调用。

页面不展示调用级时间、ticker、重试次数或执行状态，也不恢复 V1 的逐调用成本流水表。

### 7.2 页面模块

成本审计由以下模块构成：

1. 审计类型切换：收益审计 / 成本审计；
2. 调用类型切换：API / Codex；
3. 全局统计周期切换；
4. 顶部 KPI；
5. 用量与成本趋势；
6. 用量或成本占比；
7. 节点明细；
8. 人工刷新。

不得新增 Audit status、最高成本节点、重试成本或其他未在本节定义的 KPI、卡片和操作。

### 7.3 API / Codex 调用类型切换

成本审计提供“API”和“Codex”两个互斥选项，默认选择“API”。该选项是全页面数据范围，不只是节点明细筛选。

#### 7.3.1 API

“API”统计当前 ticker 的全部 V2 直接 provider / API 模型调用。当前可计价模型为：

- `qwen3.8-flash`；
- `deepseek-v4-flash-0731`。

API 模式下，KPI、趋势、占比、节点明细和节点 / 模型筛选项均只使用 API 调用数据。

#### 7.3.2 Codex

“Codex”统计当前 ticker 的全部 V2 Codex SDK Worker 调用。Codex SDK 已能提供 input tokens、cached input tokens、output tokens、reasoning output tokens 和 total tokens 等 turn 级遥测，因此本期支持 Codex Token 用量审计。

Codex 个人或订阅计划的周额度不是公开的固定 Token 数，且不同任务、模型和运行方式不能通过一个稳定比例换算为周额度消耗。因此：

- 本期不提供“成本 / 周额度”切换；
- 不估算或映射 Codex 周额度；
- Codex 模式的 Token KPI、趋势和节点明细正常显示；
- Codex 模式的总成本、Input Token 成本、Output Token 成本显示“不适用”，不得显示为 `$0`；
- Codex 模式不与 API 模式合并计数或合并成本。

切换 API / Codex 时，页面所有模块必须同步切换数据范围，不能保留另一类型的 KPI、趋势、占比、节点明细或筛选结果。

### 7.4 全局统计周期

周期选项为：

- 前一天：默认；
- 当天；
- 7 天；
- 30 天；
- 全部。

周期沿用本 PRD 已定义的 DoxAgent 语义交易日规则：

- 日界线为美东时间 02:00；
- “前一天”表示当前语义交易日前一个有效交易日；
- “当天”表示当前语义交易日；
- “7 天”和“30 天”分别表示截至当前所选交易日的最近 7 个、30 个有效交易日；
- “全部”表示当前 ticker 的全部 V2 可用历史；
- 周末、休市日和冬夏令时处理复用全局语义交易日规则，不在前端写死 UTC 偏移或固定季节时间。

周期切换对 KPI、趋势、占比和节点明细同时生效。API / Codex 与周期是两个相交的数据范围；任一切换都不得混入范围外数据。

### 7.5 顶部 KPI

顶部仅保留以下六项 KPI，顺序如下：

| KPI | 显示内容 | 统计口径 |
|---|---|---|
| Token 总量 | Token 数量 | `Input Token + Output Token` |
| 可计价总成本 | 美元成本 | 只汇总当前选择范围内能够按已知价格计价的 API 调用 |
| Input Token | Token 数量 / 美元成本 | Input 数量包含缓存命中的 Input；成本由非缓存 Input 成本与缓存命中 Input 成本相加 |
| Output Token | Token 数量 / 美元成本 | 实际 Output Token 数量及其可计价成本 |
| 缓存命中 Token | Token 数量 | 只显示数量，不显示单独成本 |
| 缓存命中比例 | 百分比 | `缓存命中 Input Token / Input Token` |

统一 Token 关系为：

- `缓存命中 Input Token` 是 `Input Token` 的子集；
- `非缓存 Input Token = Input Token - 缓存命中 Input Token`；
- `Token 总量 = Input Token + Output Token`；
- 不将缓存命中 Token 在 Token 总量中重复相加；
- `Input Token = 0` 时，缓存命中比例显示“暂无数据”，不得显示无意义的 `0%`。

所有 Token 数值均以 M 为基本显示单位，即原始 Token 数除以 `1,000,000`，保留小数点后三位并带 `M`。该规则同时适用于 KPI、趋势、占比提示信息、节点明细和平均每请求 Token。例如 `184,200` Token 显示为 `0.184M`。

“可计价总成本”只表示已知价格覆盖的 API 成本：

- API 模式汇总已识别模型的 Input 与 Output 成本；
- 未识别模型仍计入 Token 数量，但其成本显示“不适用”且不进入可计价总成本；
- Codex 模式显示“不适用”；
- 不得把无法计价的数据按零成本计入；
- 不展示独立 Audit status 或计价覆盖率卡片。

### 7.6 API 固定计价规则

本期成本统一显示为美元。百炼原始价格先按人民币计算，再使用固定汇率 `1 USD = 6.8 CNY` 换算为美元。本期不跟随实时汇率变化。

当前华北 2（北京）调用使用以下固定价格快照，单位均为人民币元 / 1M Token：

| Provider | Model | 非缓存 Input | 缓存命中 Input | Output | 时段 |
|---|---|---:|---:|---:|---|
| 百炼 | `qwen3.8-flash` | 0.8 | 0.1 | 2.7 | 全时段 |
| 百炼 | `deepseek-v4-flash-0731` | 3.0 | 0.3 | 9.0 | 忙时，北京时间 08:00–22:00 |
| 百炼 | `deepseek-v4-flash-0731` | 1.5 | 0.15 | 4.5 | 闲时，北京时间 22:00–次日 08:00 |

计价公式为：

`Input 成本（CNY） = 非缓存 Input Token × 非缓存 Input 单价 / 1,000,000 + 缓存命中 Input Token × 缓存命中 Input 单价 / 1,000,000`

`Output 成本（CNY） = Output Token × Output 单价 / 1,000,000`

`总成本（USD） = (Input 成本（CNY） + Output 成本（CNY）) / 6.8`

计价约束：

- `deepseek-v4-flash-0731` 按每次调用真实发生时间选择忙时或闲时固定价；
- 本期不套用免费额度、临时促销、订阅 Credits 抵扣或其他账户级优惠；
- 当前 workflow 不使用 Batch 模型调用，因此本表不增加 Batch 折扣口径；
- 价格按完整 model ID 精确匹配，不根据名称相似度匹配；
- 后续出现新的 model ID 时，Token 仍可统计，但在该 model ID 的价格被明确补充前成本为“不适用”；
- 绝对禁止让新模型沿用 `qwen3.8-flash` 或 `deepseek-v4-flash-0731` 的旧价格。

上述价格是本期产品固定计价口径，不要求前端实时访问 provider 价格页面。本 PRD不规定计价发生于前端、服务端或数据层的哪一层。

### 7.7 用量与成本趋势

保留 V1 的趋势模块，但数据范围和指标改为 V2 口径：

- API 模式展示所选周期内的 Token 用量趋势和可计价成本趋势；
- Input Token、Output Token、缓存命中 Input Token 不得发生重复累计；
- Codex 模式展示所选周期内的 Token 用量趋势，成本数据为不适用；
- 趋势只使用当前 API / Codex 选项的数据；
- 时间粒度应当能够覆盖所选周期并保持时间顺序，本 PRD不规定具体图表类型或视觉样式；
- 没有数据时显示明确的空状态，不绘制虚假零成本或零 Token 曲线。

### 7.8 用量或成本占比

保留占比模块和“按节点 / 按模型”切换：

- API 模式按可计价总成本计算占比；
- Codex 模式没有可计价成本，改按 Token 总量计算占比；
- “按节点”以 V2 workflow 节点为统计单位；
- “按模型”以实际 model ID 为统计单位；
- 未知价格的 API 模型不进入成本占比，但其 Token 仍在节点明细中显示；
- 当前范围没有可用于计算占比的数据时显示空状态，不伪造占比。

### 7.9 节点明细

原“成本明细”改名为“节点明细”。每行代表一个 V2 workflow 节点在当前 API / Codex、周期和筛选范围内的汇总，不再逐次展示模型调用。

每行只包含以下字段：

| 字段 | 内容 |
|---|---|
| 节点 | V2 workflow 中可识别的业务节点名称 |
| 模型 | 该节点实际使用的 model ID |
| 请求数量 | 该节点取得有效用量记录的实际模型请求 / Codex turn 数量 |
| Input Token | Input Token 数量及成本；Codex 或未知价格时成本为“不适用” |
| Output Token | Output Token 数量及成本；Codex 或未知价格时成本为“不适用” |
| 缓存命中 Token | 缓存命中的 Input Token 数量 |
| 缓存命中比例 | 缓存命中 Input Token / Input Token |
| 平均每请求 Token | Token 总量 / 请求数量 |
| 总成本 | 该节点可计价的 Input + Output 美元成本；Codex 或完全无法计价时为“不适用” |

节点明细约束：

- 删除时间、ticker、重试、状态字段；
- 保留“全部节点”和“全部模型”两个筛选；
- 删除状态筛选；
- 节点和模型筛选只作用于当前 API / Codex 和周期范围；
- 一般一个节点只使用一个模型；如果同一节点在所选周期内实际使用多个模型，仍合并为一个节点行，模型字段列出真实 model ID，不得拆成模型级多行或隐瞒模型变化；
- 重试不作为字段展示，但每次真实发生并返回用量的请求均进入请求数量和 Token 聚合；
- 没有返回用量的失败请求不得虚构 Token 或成本；
- 平均每请求 Token 的分母是取得有效用量记录的请求数量；分母为零时显示“暂无数据”；
- Token 和平均每请求 Token 均使用 M 单位并保留三位小数。

### 7.10 页面数据需求

前端需要以下产品数据。字段名称仅描述页面消费语义，不规定 API、后端或数据库结构。

#### 7.10.1 页面范围

- 当前 ticker；
- 当前审计类型：收益 / 成本；
- 当前调用类型：API / Codex；
- 当前统计周期及其语义交易日起止范围；
- 当前节点筛选；
- 当前模型筛选。

#### 7.10.2 用量事实

每条可聚合用量事实至少应能表达：

- 所属 V2 ticker；
- 调用类型：API 或 Codex；
- provider；
- 精确 model ID；
- V2 workflow 业务节点；
- 调用或 turn 的真实发生时间；
- Input Token；
- Cached Input Token；
- Output Token；
- Total Token；
- 是否具有有效用量记录；
- 该调用是否具有已知计价结果，以及 Input、Output、总成本；
- 用于去重的稳定调用身份，避免同一调用因重读、重放或多个工件重复计数。

#### 7.10.3 聚合结果

- 六项 KPI；
- 趋势时间点及各时间点 Token / 可计价成本；
- 按节点和按模型的占比结果；
- 节点明细行；
- 当前范围可用的节点和模型筛选项；
- 各模块是否无数据、成本不适用或读取失败。

### 7.11 刷新、缓存与加载

本页面遵循普通审计页刷新规则，不使用 SSE，不自动轮询：

- 新打开页面时加载默认的成本审计、API、前一天数据；
- 人工刷新时刷新当前 API / Codex、周期和筛选范围；
- 某个 API / Codex、周期或筛选组合第一次被选择时加载一次；
- 已加载组合写入当前浏览器标签页缓存；
- 再次切回已加载组合时直接显示缓存，不自动刷新；
- 切换到其他页面再返回时不自动刷新；
- 刷新期间保留已有内容；失败时保留旧缓存并提示刷新失败；
- 收益审计“暂未开放”页不触发收益数据加载。

### 7.12 页面状态与异常

- 当前范围没有用量时，Token 计数显示 `0.000M`，比例显示“暂无数据”，趋势、占比和节点明细显示空状态。
- Codex 成本统一显示“不适用”，不得显示 `$0`。
- API 调用具有 Token 但 model ID 未配置价格时，Token 正常显示，成本显示“不适用”。
- 节点中同时存在可计价和不可计价 API 调用时，节点 Token 正常汇总；总成本只汇总可计价部分，且不得将不可计价部分理解为零成本。
- Cached Input Token 缺失时不得凭 Input Token 推测缓存命中量；按实际可用数据展示。
- 单个节点数据读取失败只影响对应节点明细或占比项，不应清空已经成功加载的其他页面数据。
- 页面不得从 V1 审计表或 V1 Runtime 记录补齐 V2 缺失数据。

### 7.13 Workflow 对齐与支持边界

| 前端需求 | 当前 V2 workflow 事实 | 产品约束 |
|---|---|---|
| Codex Token | Codex Worker 的 turn telemetry 已提供 input、cached input、output、reasoning output 和 total tokens，并随 Worker job / attempt 工件持久化 | 可以统计真实 Codex Token；不得换算为周额度或虚构成本 |
| API Token | 当前 model usage 事件已记录 provider、model、input、output 和 total；部分 Runtime model turn 另有 cached input | V2 页面必须覆盖全部 V2 API 调用，并以真实 cached input 计算缓存指标，不以缺失值推测 |
| 全 workflow 覆盖 | D1、D2 已有部分集中 model usage 写入；D3、O2/O4、W1/W2/W3 等节点的用量目前分布在各自 turn、receipt 或工件中 | 当前集中聚合并不完整；实现时需要形成完整可读的 V2 用量集合，但本 PRD不规定其 API、后端或数据库实现 |
| 缓存成本 | 现有通用价格表只区分 input / output，尚未完整区分 cached input；百炼 provider 已返回或支持缓存命中用量 | 页面口径必须按非缓存 Input 与缓存 Input 分开计价，不得按普通 Input 价格重复计费 |
| Codex 周额度 | SDK 遥测能反映 Token，但 Codex 订阅周额度不是固定 Token 价格表，也没有可靠公开换算关系 | 不做周额度映射，不提供额度切换 |
| API 价格 | 当前实际模型为 `qwen3.8-flash` 与 `deepseek-v4-flash-0731`；后者存在忙闲时价格 | 只按本节固定价格和精确 model ID 计价；新模型未知价格时显示“不适用” |
| 当前 Dashboard | V1 成本页以逐调用记录展示时间、ticker、节点、模型、Token、重试和状态，并包含旧 KPI | V2 改为节点汇总，删除 V1 专属字段和 KPI，不读取 V1 数据 |
| 刷新 | V1 收益审计存在 SSE，成本查询可随交互重复触发 | V2 成本审计无 SSE、无自动刷新，按首次加载、首次组合切换和人工刷新使用缓存 |

本文档只记录 workflow 已有事实、前端所需数据、固定产品计价口径和产品约束，不规定 API、后端或数据库实现。

### 7.14 验收标准

1. 页面标题为“{Ticker} 收益 / 成本审计”，默认打开成本审计。
2. 收益审计入口可点击且只显示“暂未开放”，本期不加载或展示收益数据。
3. 成本审计提供 API / Codex 全局切换，默认 API，所有 KPI、趋势、占比、明细和筛选数据随之切换且绝不合并计数。
4. 周期支持前一天、当天、7 天、30 天和全部，默认前一天，并遵循统一语义交易日、有效交易日和冬夏令时规则。
5. 顶部只有 Token 总量、可计价总成本、Input Token、Output Token、缓存命中 Token、缓存命中比例六项 KPI。
6. Audit status、最高成本节点和重试成本均已移除。
7. Input Token 和 Output Token 同时显示数量与成本；缓存命中 Token 只显示数量。
8. Input Token 数量包含缓存命中 Input，Input 成本按非缓存与缓存命中两部分分别计价后相加。
9. Token 总量等于 Input + Output，不重复累加缓存命中 Token；缓存命中比例等于 Cached Input / Input。
10. 所有 Token 数量以 M 为单位并保留三位小数，包括节点明细的平均每请求 Token。
11. API 成本使用本节固定百炼价格与 `1 USD = 6.8 CNY` 固定汇率；`deepseek-v4-flash-0731` 按真实调用时间应用忙闲时价格。
12. 未知 model ID 的 Token 可统计、成本为“不适用”且不进入可计价总成本，不会错误继承旧模型价格。
13. Codex Token 用量可统计，但成本为“不适用”，不提供周额度映射或成本 / 额度切换。
14. 趋势模块在 API 模式展示 Token 与可计价成本，在 Codex 模式展示 Token 且不虚构成本。
15. 占比模块保留按节点 / 按模型切换；API 按成本占比，Codex 按 Token 占比。
16. “成本明细”已改为“节点明细”，每行按 workflow 节点汇总，不是逐调用记录。
17. 节点明细包含节点、模型、请求数量、Input 数量 / 成本、Output 数量 / 成本、缓存命中、缓存命中比例、平均每请求 Token 和总成本。
18. 节点明细不包含时间、ticker、重试和状态字段；只保留节点和模型筛选，删除状态筛选。
19. 页面覆盖当前 ticker 初始化与 Persistent Runtime 的全部 V2 模型调用，不从 V1 数据回退。
20. 页面只在新打开、某范围组合首次选择或人工刷新时加载；已加载组合和页面往返使用标签页缓存，不使用 SSE 或自动刷新。
