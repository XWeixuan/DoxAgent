# Runtime 连续两轮批量失败：修复、发布与后续精益方案

日期：2026-11-10。本文业务时刻默认北京时间；数据库原始时间为 UTC，需加 8 小时。以留存证据区分已证实原因、代码风险和待验证项。

## 1. 结论与硬边界

两轮事故属于同一压力链路中的不同缺陷：突发准入及后台维护重叠，使 SQLite 等待和重复大对象读取增多；第一次把暂时写锁转化为不可恢复的上下文 409，第二次又使每个在途 W3 长期占用执行线程和心跳线程，最终触及 Scheduler 的进程/线程配额。上一轮的上下文与字典修复仍然有效，本轮不是同一修复被重新部署覆盖。

**任何修复不得牺牲 W3 时效性。** 因此最终方案不增加 W3 模型在途限额、不降低既有 Worker 模型准入、不推迟实时消息、不延长模型超时、不通过轮询消费已完成结果。资源优化针对无效等待、重复读取和事务工作量。模型、推理档位、提示词、Schema、交易规则及过期信号保护均保持现有业务语义。

本轮早期临时部署过 16 个 Effect 在途限制；该限制可能排队，已撤销。不能将临时版本作为最终发布基线。

## 3. 为什么潜伏一周后集中暴露

11/02–11/06 已构造的 4,656 个首阶段上下文本地绑定回执全部存在；11/08 则有 42 个缺失并保留上下文错误。正常首次绑定路径不重建目录，所以顺序缺陷可长期不暴露。写锁打断回执保存后，才进入有缺陷的恢复分支。

11/08 的 280 个 CLOSED Case 集中在 42 分钟内，212 个进入 W3，峰值 103 Case/分钟；11/09 也有 305 个 CLOSED Case 集中到达并与实时消息重叠。11/08 有 211 条 SUPPLEMENTAL 维护任务，而 11/03–11/05 只有 2、2、0 条。维护是并发压力参与者，不能只凭数量认定它独自造成事故。

前轮采样约六成 GIL 样本位于 Case 重建及 JSON 编解码；平均冻结输入约 1.5–1.7MB，并无当日新膨胀。为了一个 Sweep ID 或一条事实来源反复打开整个冻结研究包，增加了无业务价值的 CPU/IO。等待变长后，旧调度器的线程和心跳继续累积。因此前轮上线后十几分钟无新失败，并不足以证明运行数小时后的资源稳定。

## 4. 本轮已实现的修复

### 4.1 W3 等模型时不占执行线程，结果完成立即续接

文件：`persistent_runtime_v2/w3.py`、`service.py`、`w3_execution.py`。

1. 复用现有按 phase key 保存的异步 Future，不新增模型队列或模型服务。生产 Effect 遇到未完成 Future 时保留原所有权，退出当前物理执行步骤。
2. Future 完成触发回调，直接续接原 phase 已准备的结果保存、ACK 和业务 commit；不重新构造历史、上下文、线程或模型请求，也不等下一次 5 秒轮询。
3. 已完成决策的短续接立即启动，绕过准备任务积压；普通短步骤复用 32 个线程的执行池。32 是准备/提交步骤的物理线程复用容量，**不是 W3 模型在途数上限**。
4. 对齐 synchronous/offline replay 行为：只有生产 Effect 使用释放等待的方式，既有同步调用继续返回最终结果。
5. 写锁导致 commit 前重试时保留原成功结果；commit 后同步失败则识别 COMMITTED，仅恢复同步，避免重新提交、重复业务动作或改写提交时刻。失败/取消的模型 Future 不走成功续接。

### 4.2 一个共享心跳替代每 Effect 一个心跳线程

文件：`service.py`、`repository.py`。

每 20 秒批量续租活动 Effect，单线程、单短事务。更新严格要求 RUNNING、相同 lease token 且旧租约尚未过期，不复活失效 owner。claim 排除本进程仍活动的 Effect ID；进程重启后既有租约恢复机制照常工作。直接同步执行入口保留原兼容心跳。

本地线程分配压力属于基础设施延迟，不再当模型/业务失败消耗三次尝试。保留取消、停机、租约 fencing 与业务错误边界，不增加一套无限业务重试机制。

### 4.3 删除两个已定位的读取放大

文件：`repository.py`、`service.py`、`daily.py`。

- Sweep 门槛通过标量 `get_case_sweep_id` 读取，不反序列化全 Case。
- O2 `_atomic` 通过 `get_case_source` 只读 SourceMessageEnvelope，保留原来源时间和原子事实格式，不打开 frozen_inputs。
- 原生内容引用读取继续使用 `payload_json` 别名，让 source 自身被外置时也能正确解码；不能直接返回外置引用或忽略正文。

不新增表、不迁移历史 Case、不建立全库大缓存、不提高 PID 配额。不是通过扩大资源上限掩盖积累。

## 5. 进一步修复：按证据推进，保持 W3 时效性

### P1-A：缩短仍存在的 SQLite 等待

本轮上线后仍观察到 `w3.history.freeze`、`value.w3_global_input`、`value.w3_citation_scope`、`task.inputs_ready` 等短写重试及等待。不能把“线程数降低”表述为存储问题已解决。

执行方式：

1. 利用现有 transaction 日志，按 operation 汇总 begin 等待、hold、commit 和重试数；只截取有限时间窗，不扫描全部历史 payload。
2. 每次只处理最高成本且可确定缩减的一条路径。检查 `w3_execution.trade/operations` 及上下文冻结调用：不可变序列化、内容寻址、文件写入均在写事务外准备；事务内只做 fencing、必要当前状态校验、短 SQL 落盘。
3. 对只需要状态/归属/时间的调用增加窄读，禁止为了状态重新 model_validate 整个冻结包；真正构造 Agent 输入和进行业务校验时仍读完整冻结版本，不裁剪事实。
4. 针对同一 Case 不变的派生材料复用现有 frozen 记录，不能在每次 SQL 重试时重做研究上下文；不缓存可变交易资格或跨 Case 复用可变结果。
5. 每项用真实负载同口径统计等待和 SDK→commit 延迟。若降低 CPU 却增加 W3 排队，拒绝该实现。不得给实时 W3 增加维护优先级等待，也不得降低模型并发。

本轮仅实现已有直接采样支持的两个窄读；其余路径先定位具体持锁工作再改，不提前扩展成异步数据库平台或新任务系统。

### P1-B：发布与业务完成分开验收

现有 phase/Worker receipt 已能关联 `sdk_completed_at`、阶段 `committed_at` 与 Effect trace。用现有状态/health 的有界采样形成：

- 线程当前值及 `pids.events max` 增量，是否随在途等待数持续增长。
- W3 模型开始、模型完成、业务提交分别计数；不能用“模型成功”代替“交易决策可消费”。
- 同 case/phase 的 SDK→commit 延迟及准备耗时，区分重启恢复旧任务和本次发布后新准入。
- 失败按错误族及首次发生时间统计；同一个 Case 的历史 error 残留不计作新终态失败。

优先复用现有日志/索引与 15 秒级健康观察，不为每个轮询追加大 JSON、全库快照或高频持久化指标。此轮保留只读诊断脚本，不新增常驻监控服务。

最终稳定性需要覆盖数小时及一次真实突发/结算重叠，看到资源平台期和真实 W3 提交；短时间 smoke 只能证明启动和当前样本，不能承诺后续绝不失败。

### P1-C：独立问题保持边界

- 初始化库写锁导致 CDECR executor 重启是独立故障。后续仅把明确的可重试 SQLite contention 留在现有 owner/fencing 下恢复，真实 schema/程序错误仍报告；不设置盲目全服务重启，不阻塞实时 W3。
- Sail R3 持续报错后 fallback 到 Haiku 会增加正常链路耗时；是否换模型应单独决定，本轮不偷偷修改模型策略。
- 生产组件仍含其他会话的专项 overlay。后续全量 build 前核对源码与已登记组件 manifest，先合并差异；禁止用“main 新”推断已含所有生产修复。本轮只覆盖已校验的目标文件并保存基镜像与回滚记录。
- 前次 root Git 同步造成 `.git` 个别文件所有权错误，已限定在 `.git` 修复；后续远端 Git 写入以 ubuntu 用户执行。此问题影响同步操作，不是 Runtime Case 失败根因。

## 6. 回归与不变量

- 首轮相关回归 128 项通过；最终补上 commit 后同步失败重试，两阶段专项共 23 项通过。
- 40 个模拟 W3 phase 同时在途，全部实际发起一次；等待不占模型执行线程；任意结果返回后立即消费，不等轮询；两阶段都验证 prepare/run_phase 各一次。
- 批量续租保留 token，不更新过期或错误 token；本地活跃 owner 不被重领；进程丢失后的正常恢复仍保留。
- 大 Source 自身外置时读取正确，冻结研究 blob 不打开；O2 原子事实输出逐字段相等。
- commit 后投影同步失败，恢复不重复 commit/模型请求，trade 和 operations 均覆盖。
- 不为通过测试放宽过期交易保护：`test_w3_v4.py` 四个旧 fixture 在未修改基线上也因 `RUNTIME_DELAY_EXCEEDED` 失败，单列为既有时钟 fixture 问题；不冒充本轮全量测试均通过。

历史 69 个 FAILED 维持审计状态，不静默重放旧信号、不复活过期意图。自然恢复原在途 Case 与人工重新交易必须区分。
