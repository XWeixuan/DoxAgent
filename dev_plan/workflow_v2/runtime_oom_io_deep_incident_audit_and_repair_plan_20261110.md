# Runtime / W3 内存、物理 I/O 假死事故：深入排查与可执行修复方案

日期：2026-11-10。所有正文时刻均为北京时间，原始数据库及部分日志使用 UTC。

**本轮边界：紧急停服、只读取证、代码审查、方案设计；没有实施业务代码修复，没有重新构建、发布、启动研判服务或调用真实模型。** 本文取代此前方案中“32 个步骤线程不会引入 W3 排队”“线程数量下降即可代表主要资源问题已解决”的判断。

## 1. 结论

事故不是单纯的“服务器负载高”，也不能归因于一个线程池或一项 O2 任务。

已经找到一个贯穿首次批量失败及本次发布后假死的具体资源生命周期缺陷：**W3 在模型发起前已准备好的私有 Capsule，在 Case 前置失败后没有释放物理进程；`ready_slot=True` 又使它避开普通空闲回收。** 逻辑 Thread、Ready Slot 数据库状态、物理 Capsule 的存活并未同步结束。部分 Case 早已 FAILED、从未提交过模型 Job，仍保留 Python + Codex 进程数小时。

11/08 已出现这一问题：17:30 可还原出约 67 个物理 Capsule，其中 48 个关联 CLOSED Case，而有记录的运行中 W3 Job 约 1 个。至少 22 个关联 Case 在此前就因上下文 409 终态失败、未发起过模型 Job，其物理 Capsule 却继续存活。22:12 内核在旧 Worker cgroup 内记录了 65 个 Codex、71 个 Python 进程并发生容器 OOM；这为 Worker 资源归因提供了直接证据。

本轮发布没有修复这个根本缺陷，还改变了准备工作推进方式：移除临时 16 在途限制后，32 个共用步骤线程不断从持久队列领取准备任务，Future 让模型等待不再占线程，但**物理 Fork / Capsule 并未因此消失**。实时、CLOSED 与恢复工作没有在准备路径上有效区分，准备成功但未提交模型的私有 Capsule 再次增长。

资源问题随后被两类读放大进一步放大：生产资源回收在一个长只读事务内枚举历史引用；上一轮诊断统计也存在无时间索引的全历史扫描。匿名内存挤出文件缓存后，磁盘持续约 196MiB/s 读取，队列约 254、平均等待接近 200ms，SQLite、SDK、本机进程启动与 SSH 一起变慢。Swap 占满是真实状态，但严重时 Swap 换页吞吐很低，**不能把这场物理读饱和全部叫作 Swap 抖动**。

最早的上下文 409 与严重物理 I/O 饱和的先后顺序也需纠正：首次 Case 约在 11/08 15:29 已失败，持续 I/O 饱和从约 17:30 才开始。因此“先严重 I/O 紧张，才有最初错误”不成立。可证实的是：初期写入争用打断绑定回执保存，顺序缺陷把重试变成 409；失败后的物理资源遗留又成为随后内存与 I/O 恶化的重要来源，形成反馈循环。

### 4.2 一个首批失败 Case 的完整局部链路

Case：`case_a776d7a7ce884ffd99ebe1006e51e2da`，SNOW，CLOSED。

1. 15:07:45 创建 Case。
2. 15:26:44 开始该次 W3 Effect；一次执行内累计 49 次 journal begin，累计等待约 23.6 秒、13 次 begin 异常。相应 commit 累计只有约 65.7ms。
3. 15:27:13 左右启动物理 Capsule；15:27:16 Ready。
4. 15:27:30 左右，Worker 上下文绑定成功，`case.context_bind` 仅约 39ms。
5. 紧接绑定回执落盘路径，整轮约在 15:28:04 以 `OperationalError` 结束。代码中 HTTP bind 后的下一步正是通过现有 write owner 保存 `w3_context_v2`；此后重试遇到上下文 409。
6. 15:29:30 Case 终态 FAILED。所选历史中该 workspace 没有模型 Job。
7. 物理 Capsule 却直到 22:12:54 左右才被关闭记录清理，持续约 6 小时 45 分钟。它没有在为该 Case 运行模型。

这证明最早阶段存在 **SQLite / 调度争用 → 本地回执保存失败 → 409**，也证明错误后物理资源未随业务终态退出。它不能证明当时某条具体 SQL 独占了 writer；原 trace 没有完整记录所有进程的持锁归属，旧 Scheduler 日志也已随容器替换丢失。不能用 17:30 后的磁盘饱和倒推 15:27 的唯一持锁原因。

这些 Slot 后来显示 `USED` 并不推翻“未提交模型”：当前 `/market/stop` 会把有 thread_id 的 BOUND Slot 标记为 USED，但不会同步清除物理 Capsule 的 `ready_slot` 或关闭进程。因此 USED 既不是模型执行凭证，也不是物理回收回执；模型调用要核对持久 Job，物理释放要核对 owner / 进程。

原先按时间快照统计到的约 81 个失败，与 11/08 留存的 81 个 CLOSED 终态失败对应；11/09 首次报告中的 82 个失败是另一时间与语义日快照，本文不混用分母。

### 5.2 上轮改动的责任与影响

- “等待模型不占线程”只节约 Scheduler 的等待线程，不节约 Worker 中已创建的 Python / Codex 进程。上轮把前者当作主要资源问题已解决的依据，是不充分的。
- 32 个步骤线程仍是 FIFO 容量门槛。离线机制复现中，32 个准备/其他步骤阻塞后，还有 9 个排队项，新增 W3 未开始。上轮把“无模型在途限制”等同于“无实时排队”，结论不正确。
- Effect pump 每批 claim 后持续提交，`limit=20` 只是批次尺寸，不是全局容量控制；executor 的等待队列没有相应限制。被提前 claim 的 Effect 在队列里也续租。
- Future 完成旁路另起线程，能够绕过准备队列，但又引入另一组可同时竞争 SQLite 的同步续接；`_ack()` 在业务 commit 前执行，网络/Worker 写入清理仍可拖住结果消费。
- `_effect_continuations` 捕获完整 Case / reader / 执行对象，并在部分控制错误路径中缺少统一清理。它是实际代码问题和内存风险，但没有事故前堆快照，**不能声称它单独造成了十几 GB 内存占用**。
- 上轮针对两个热路径的窄读和共享心跳有价值，应保留；不能因为这次事故反向认定所有改动都有害。

### 5.3 诊断与发布操作也属于事故审查范围

上轮 `observe.py` 初版按 `runtime_v2_turns.created_at` 过滤，而生产没有该时间索引。实际计划是扫描全部 94,217 条历史 Turn 并分组；不是只读“最近几分钟”。已修改后的 rowid 有界版本才会先限制扫描范围。

03:32 左右的这个查询、自然业务推进及 Docker 构建重叠。Docker 的本地 FROM 准备一步耗时约 510 秒。两者都可能参与或放大物理 I/O，不能从耗时本身反推它们各自产生多少流量。OOM 表里 Docker 主进程约百 MB，也不能据此把 20GB Worker 占用归给 Docker build。

这两种操作不能单独解释全部事故：11/08 已出现同型物理驻留与 I/O 饱和；11/10 构建结束后压力持续至重启。上轮在显著压力下继续重建与统计，缺乏足够的资源风险判断；后续发布必须把诊断和构建的成本也纳入预算。

## 6. SQLite 争用为何加剧

最终版 Scheduler 记录了一次 `resource_gc.referenced:82` **只读事务 3,511,723ms，约 58.5 分钟**，从约 03:42:35 持续到 04:41:07。期间该函数遍历历史 Case、维护 Frame、引用和部分 Native 快照。`limit=4` 只限制后面处理的目录数，并不限制前面全量引用扫描。

生产库约 14.67GB；当前记录有 24,488 个 Case、94,217 个 Turn、29,097 个 Runtime Task、1,575 个 reference_deliveries。实际 SQL 计划证实 GC 的全局 Case 引用枚举是 `SCAN runtime_v2_cases`。

需要区分三件事：

1. **WAL 只读事务不等于直接持有 SQLite writer。** 不能把“58.5 分钟读事务”表述为“它独占写锁 58.5 分钟”。
2. 这样的长读会保留读取快照，并大量竞争文件缓存、CPU 和磁盘；可能限制 checkpoint 推进。事故前 WAL 连续大小未留存，本轮重启后的 8KB WAL 不能证明事故时大小，也不将 WAL 膨胀写成已证实根因。
3. 在磁盘队列约 254、文件缓存不足 1GB、进程频繁阻塞的情况下，短事务本身也会被拖慢；并发准备、重试和心跳继续争用 writer。日志中的 begin 等待还包含进程内 gate 等待，不能全部当作某个外部进程的 SQL 写锁。

最终版慢事务样本中：`begin_stage` 665 次累计 elapsed 约 10,077 秒，其中 begin 等待约 10,046 秒；hold 约 25.4 秒，commit 约 5.4 秒。这是并行调用累计时间，不是墙钟时间。它说明大量时间发生在进入事务之前，而非每个阶段必然持有长写事务。

初始 SNOW Case 在物理磁盘持续饱和之前，commit 累计仅约 65.7ms，但 begin 等待已约 23.6 秒。这说明初期本机并发写入、短写 owner/gate 争用和编码调度开销必须一起审查，不能只等磁盘爆掉后归因。现有旧 trace 不足以指认首个超时的唯一持锁 SQL，这一点保留为证据缺口。

## 8. 不可改变的业务与时效边界

以下属于实现验收条件，而不是建议：

- REALTIME Case 不新增全局 W3 在途上限、每 ticker W3 容量门槛、固定 W3 线程池等待或等待后台任务完成的准入条件。
- 结果完成立即消费；不能通过放慢轮询来降低成本。改进采用事件通知，并保留原持久 Job 身份。
- Prompt、AGENTS.md、唯一 Skill、模型、推理档位、Token 上限、Fallback、LLM 输入/输出 Schema 不改。
- W1/W2 路由、NEW/OLD、LOW、WATCH、HIT/RELATED、LONG/SHORT/NO_TRADE、二轮动作、72 小时历史及过期信号保护不改。
- 逻辑 Thread / Fork 关系、Case 隔离、冻结版本、manifest 字节、token、引用范围、研究时点与行情采样语义不改。
- 不为降低内存删除业务历史、裁剪研判事实、复活过期交易或改写旧 Case。

有限主机无法保证无限个同时到达的 Case 都在物理上零等待；SQLite 的必要串行提交、同一 Thread 的互斥、实际网络传输也不可能消失。方案承诺的是 **不为 REALTIME 增设人为容量排队，移除已经存在的无价值竞争，并在真实峰值场景证明时效不回退**。不能用“无限制”描述掩盖资源有限，也不能把重试、落盘和网络等待都伪装成“Agent 正在正常研判”。

## 9. 推荐实施方案：先修资源生命周期，再精简调度

### P0-1：让准备资源随所有权结束，补上终态失败的物理释放

涉及：`w3_execution.py:record_failure`、`w3.py` / Worker client、Worker `app.py`、`w3_ready.py`、`capsules.py`。

1. 增加一个窄的、幂等的内部操作：`release_unused_case(case_id, record_id)`，由已持久化的终态前置失败触发。只负责释放该 Case 的未使用物理准备资源，不删除逻辑 Thread、工作区、冻结上下文或业务历史。
2. Worker 按 Case / record / thread / Capsule 身份核实归属；复用现有活动 Job、已接受请求、执行归属和清理状态。确认没有活动或未知派发的模型调用后，使用现有 `CapsuleRuntime.release_thread()` 关闭物理进程；重复请求可直接返回已释放。
3. 只传小型身份与原因，不传完整 Case。调用不成功交给现有 W3 housekeeping 重试，不能创建新服务或另一套业务重试队列。
4. 公共、未绑定的 READY 库存与已绑定的私有准备必须区别：绑定后不应再无限享有公共 ready 标记的普通回收豁免。消费转交时清除其公共 ready 标记；未开始 Job 的私有资源仍受其真实所有者与既有准备期限保护，不能凭新短 TTL 杀活跃研判。
5. **不能把 `/market/stop` 一律改成杀 Capsule。** 正常 trade commit 后也调用这个接口，随后还有 operations；这时必须保留原 90 秒交接和 Thread 连续性。终态前置失败的释放是独立动作。
6. 保留现有正常私有空闲回收、公共预热目标和有效阶段交接；先修失效资源，不靠降低正常预热或中断活跃模型来减内存。

物理资源生命周期释放不能与大规模存储 GC 共用“等空闲再做”的语义：前者及时释放已经失效的占用，后者可以让路。也不能把两者合并成一个新的通用回收框架。

既存遗留资源修复由 Worker 在现有 housekeeping 中按确定终态与归属检查收敛，每次只处理小批；本轮停止后旧 OS 进程已不存在，不能在数据库里伪造它们“已正常执行完成”。

### P0-2：先把确定性输入准备好，再领取物理 Fork / Capsule

涉及：`w3_execution.py:trade`、`w3_context.py:history_payload`、`w3.py:_run_phase_materialized`。

1. `history_payload`、case labels、事件列表及可确定的 user payload 在 `_thread()/claim_ready()` 之前完成。它们不依赖物理 Thread，应避免准备好昂贵私有进程后再等待这些工作。
2. 不把所有输入都提前冻结：实时行情采样、模型时点语义仍在原来对应阶段取值。仅提前静态与已冻结的派生计算，保持 accepted_at、72 小时历史成员、版本、manifest/token 完全一致。
3. 若某个派生数据确实依赖 workspace / Thread，保留其位置，仅缩短必须后置部分；不为实现“先准备”改变业务读取截止时间。
4. Ready 成功后的路径只做必要身份落盘、小型材料发布和原模型派发，不再反复打开完整冻结研究包。

### P0-3：实时 W3 从共享 FIFO 中移出，CLOSED 不冒充实时准备

涉及：`service.py:dispatch_pending_effects/_run_w3_effect_thread`、`repository.py:claim_effects`、`coordinator.py`、Worker request / prepare 适配。

1. 移除 REALTIME W3 对 32 线程共用 FIFO 的依赖。沿用既有短执行线程入口直接开始准备，模型等待仍交给现有 async Future，物理线程随等待释放；不恢复“整个模型周期占线程”的旧模式。
2. 普通归档/Delta 等 Effect 继续复用既有普通工作池。CLOSED 的批量准备复用已有后台步骤容量，未有执行所有者时留在持久队列，不提前 claim 全量再放入内存队列并续租。
3. claim 的 REALTIME 过滤发生在 LIMIT 之前；按 pending 索引与 Case 主键读取 `runtime_mode` 标量，不先展开全部冻结 Case 再分类。不用改消息 NEW/OLD 或业务路由实现优先级。
4. batch limit 只限制一次 SQL 事务工作量，REALTIME pump 可继续领取下一批，不成为模型准入门槛。
5. 将已有 `WorkerRunRequest.execution_lane` 正确用于 CLOSED trade；当前 trade 一律 realtime，准备路径又将任何已绑定 Case 提升为 priority 0，这会使批量 CLOSED 也绕过后台压力判断。
6. 准备 transport 若缺少 lane，只在内部 Ready claim / prepare 请求上增加同名调度元数据；不注入 Prompt、不改 LLM Schema、不改变 Template 兼容身份。公共预热是 background，REALTIME Case 的必需准备是 realtime。
7. 审查 Worker 的 cold gate、3 路 handshake、launch ramp：REALTIME 必需的私有准备不得等待后台容量配额。保留同一 SDK 连接、同一 Thread 的正确性互斥；后台推测与 CLOSED 可沿用现有有限启动通道。不能宣称“Scheduler 没有限流”却把等待移到 Worker。

现有 cold gate 还受全局 `quarantined` 集合影响。隔离必须落在确有未知物理 owner 的 Capsule / transport；不能因一个独立后台 Capsule 清理失败而一律停止其他独立 REALTIME Capsule 的启动，也不能绕过同一个未知 SDK 连接的正确性隔离。

不新建调度框架、独立 broker 或一套多级 actor；通过既有 realtime/background 语义、短线程和现有 Future 完成这次减法。

### P0-4：立即提交已完成结果，ACK 与清理不挡决策

涉及：`w3_execution.py`、`service.py`、`w3.py`、现有 `control_io.py`。

1. 保留按原 phase key 复用 Future，禁止重复模型调用。
2. 成功结果通过原 token fencing 保存为 RESULT_SAVED，随后完成原 trade / operations commit；Worker ACK 放到业务 commit 之后，复用现有 ACK housekeeping 恢复。不能因网络清理延迟阻挡已经完成的交易决策。
3. 不用捕获完整 Case、context、research 的长期续接闭包保存成功结果。持久结果存在后，续接只保留小型身份；按已保存 result 执行业务 commit，不重建研究上下文或重新询问模型。
4. 终态成功、终态失败、取消、LeaseLost、停机退出均清理所属本地引用；旧 owner 不能继续排除新 owner 的合法接管，也不能吞掉控制错误后无限续租。
5. 保留 COMMITTED 短路、原提交时间、原 trade intent 幂等与 unknown-dispatch 处理。丢失本地 Future 不等于可以新发模型。
6. 不新建多套 pending/continuation registry。能从现有 active 映射导出的集合不重复维护；保留防止回调与原步骤并发的最小协调，不为了“全异步”重写整个业务执行器。

### P0-5：复用事件流，替换 100ms 全 Job 轮询

涉及：`codex_runtime/client.py`、Worker `app.py/jobs.py/job_store.py`。

现有 W3 客户端每 100ms GET 完整 WorkerJob；03:30—03:35 有约 17,512 次 GET，03:40—03:45 约 13,704 次。每次服务端都读取/验证、深复制完整 Job。

1. 复用已存在的 `/v1/jobs/{job_id}/events` SSE 与 Worker `_condition`，等待终态通知后只获取一次完整终态 Job。不是把轮询调慢。
2. 修正订阅时读状态与进入 wait 之间的通知竞态：在 condition 的版本/事件序号下再次核对，不能错过完成事件后等待 15 秒 heartbeat。
3. 事件等待里的存在/终态检查采用 `SELECT status` 等小投影，不每次唤醒都完整解码 Job；全局 condition 的其他 Job 通知也不能诱发无界大对象读取。
4. 连接断开后使用原 job_id / cursor 续订，先查一次当前持久状态；ACK 清理了 events 的已完成 Job 也能直接读终态。保持取消与未知派发边界。
5. 不引入 Redis、WebSocket 服务或新全局缓存；非 W3 工作流默认调用行为不在这次范围内改变。

### P0-6：停止启动时全历史 GC，改为候选先行、根范围校验

涉及：`resource_gc.py:collect/referenced/frame_owner/snapshot_version`、`maintenance.py:collect_resources`、`coordinator.py:_storage_next`。

1. `_storage_next=0`、`resource_gc_due=True` 不能导致每次 Scheduler 重启立即全历史扫描。复用已有资源退出报告/时间记录判断真正到期，下一次时间从上次结束算起；不在每个维护任务的 finally 无条件强制全局 GC。
2. 先用维护任务状态/时间索引选一个已到保留期的候选 root，再调用已有 `referenced(..., only_root=root)` 思路定点检查。不要先全局读完全部 Case / Frame，才应用 `limit=4`。
3. 任务 Frame 只读判断所需的 run_id、artifact root/version 等标量。终态 Frame 不先完整 Native decode 再取几个字段；大快照不能为了一个 version 解码全部 Fact。
4. 缺少足够元数据证据的候选本轮跳过，保留历史，不为完成回收指标扫描或删除业务资料。后续随原所有者正常写入补足小型元数据，不另建复杂全库引用体系。
5. 每批引用读取事务结束后再做文件读取、解码和校验；禁止一个读事务跨越整轮全库引用与目录扫描。最终发布继续保留原 WriterLock、版本/指纹复核及短写事务。
6. 已有 realtime W3 工作或真实 I/O 压力期间让可延后的资源退出让路；这是限制后台垃圾回收，不是限制 W3。中途暂停只保存轻量游标，不保留长 SQLite 快照。
7. 不将 GC 搬到新 daemon 掩盖成本，也不通过增加内存大缓存解决全量扫描。

### P1：减少必要事务的竞争，不盲目重建数据库架构

涉及：`w3_threads.py:begin_stage/link`、`journal.py`、`repository.py`、`w3_context.py`、现有 write owner。

- 对已存在且无变化的 stage、association、线程归属先窄读，避免每次重试都 `BEGIN IMMEDIATE + INSERT OR IGNORE`。真正创建/变更仍由原 fencing 与条件 SQL 仲裁。
- 绑定回执、结果保存和决策提交复用现有高优先级短写入口；不在队列中做 Native 文件 I/O、大 JSON 编码、网络 ACK 或研究构造。
- 已确认的 Sweep 标量读、O2 source 窄读保留。审查其他相同模式，先给出具体读取对象与成本再改，不能全量替换业务读取。
- 大型、不可变派生材料需要外置时复用现有 NativeContent；保留标量索引字段，保证解码结果、冻结摘要、原 token 字节身份一致。没有尺寸与写入量证据的字段不批量改存储格式。
- 保留单个共享心跳，不恢复每 Effect 一个线程。批量续租只覆盖实际拥有的活动步骤/Future，不包含尚未执行的共用 FIFO 项。返回失去 lease 的身份，走原控制恢复；不能仅记 warning 后把失效本地 owner 永久留在排除集合。
- 不先引入新的数据库服务、全局 Writer 队列框架、巨大 TTL 缓存或全库迁移。WAL reader 不直接阻塞 writer 这一事实必须保留在诊断口径中。

## 10. 实施顺序与变更边界

1. **保持停服**，冻结本轮源代码、镜像、选定元数据和证据摘要。先整合生产 `journal.py` overlay，明确构建基线；不直接用旧原 checkout 的脏内容覆盖生产。
2. 首先实施 P0-1 终态准备资源释放与 P0-2 晚领取物理资源，验证失效驻留能归零；这两项直接修复贯穿两次事故的主因。
3. 实施 P0-3 去除实时 FIFO 与 CLOSED 优先级误分类；不能回退到 16 限制或把 32 提高成更大的共享池。
4. 实施 P0-4 / P0-5 结果提交与事件等待，减少网络和反序列化放大，保持同一持久请求。
5. 同批修好 P0-6，避免修复后重启立即再次触发长扫描；根据专项证据补 P1 小写入改动。
6. 在本地和隔离的无外部交易环境完成确定性并发验收，再准备一次有明确源文件清单的目标组件构建。不能在再次过载时叠加数次 overlay build 和全历史验收查询。
7. 本轮不执行以上代码修改与恢复上线。下一轮授权实施时，先验收再发布，随后分清正常启动观察与恢复积压观察，不把刚重启时的低 PID 数当作通过。

禁止做法：扩大 PID 上限、扩大 Swap 代替修根因；压低实时 W3 并发；延长 Case/模型超时；删失败记录；关闭真实研判工具以减少资源；回放旧失败交易；新增重型常驻监控服务；整体全栈盲目重启。

## 11. 必须通过的回归与验收

### 业务不变

- 同一冻结 Case 的 Prompt、Schema、模型参数及被注入的事实/历史在改造前后逐字段一致；真实行情按原时点语义验证，不能拿时间提前的输入作“相同”。
- 既有 NEW/OLD、HIT/RELATED、WATCH、LOW、三方向决策、二阶段动作与过期保护回归通过。
- COMMITTED 后同步/ACK 失败不重复模型、不重复交易、不改提交时刻；保存结果后失去 lease 不允许旧 owner 写入。

### 生命周期

- 模拟 Ready 成功后上下文 409 / 本地落盘失败并最终终态、从未创建模型 Job：公共库存保持目标不变，失效私有 Capsule 在确认安全后退出，无 Python / Codex 残留；重复释放幂等。
- 模型已派发、结果尚未知时，终态清理不得误杀或重复派发。
- 正常 trade commit 的 market stop 不关闭即将运行 operations 的物理 Capsule；原 90 秒交接保留。
- 逻辑 Thread 与上下文仍可从持久资料恢复，失败资源释放不能把 Event/Policy 关联历史删除。
- 22 个历史失效驻留的身份在离线 fixture 中纳入回归，不重新运行其真实交易。

### 实时优先与资源

- 填满普通 Effect / CLOSED 准备工作池后到达 REALTIME Case，断言其开始准备不依赖释放这些池的闸门；Worker 必需启动也不依赖后台配额。
- 多个模型在途时物理执行线程不随模型等待时长累积；完成结果即通知，不等 100ms/15s/5s 人工轮询周期。
- CLOSED 突发、维护任务和实时 Case 同时存在时，记录 physical Capsule、已绑定未派发 Capsule、运行中 Job 分别计数；不能再以模型在途数代替物理占用。
- 复现约 200 个 CLOSED 历史任务与一组实时新消息交错的离线负载；不同运行持续时长后，终态无 Job 的私有驻留应归零，内存应随活跃工作回落，不能留下固定失败台阶。
- GC 选候选之前不扫描全部 Case；读取事务不跨批。查询计划与实际读取字节/耗时同时验证，不能只因为代码有 LIMIT 就算有界。
- 以已知稳定基线和同负载对照评估准入→准备、模型完成→commit 的 p50/p95/最大值，并单列恢复旧任务。任何通过人为容量等待换来的“资源改善”不接受。

发布后观察必须覆盖原先出现问题的持续时间和一次真实业务波峰；当前机型下验证内存/物理 Capsule 达到平台后回落、磁盘不持续饱和、实时准备无隐藏队列。不把“启动成功”“线程 87”“测试 23 项通过”替代这项验收。

## 12. 尚需保留的证据缺口

目前已足以确定终态物理资源遗留、实时 FIFO、准备顺序、全历史读及轮询放大的具体修复点。仍不能诚实地声称已精确得到：

- 11/08 第一次绑定回执超时当时，所有 writer / gate 的完整持有者序列；
- GC、业务读取、诊断扫描和 Docker 构建各自贡献了多少物理读字节；
- 11/10 每个历史 PID 的精确 PSS 和连续容器峰值；
- 事故前 Safety Controller 的全部状态转移及错过资源回收的独立原因。

若后续验证仍出现异常，只对选定窗口做低成本的 transaction owner / cgroup IO 差分及少量分配样本，不扫描全部业务正文，也不常驻逐 Case 大日志。先修已有直接证据的问题，不通过添加一套监控或调度平台来掩盖它们。
