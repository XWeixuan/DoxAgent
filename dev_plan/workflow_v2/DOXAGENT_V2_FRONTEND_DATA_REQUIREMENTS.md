# DoxAgent V2 前端数据需求方案

- 文档状态：第一版
- 更新日期：2026-09-07
- 来源文档：`DOXAGENT_V2_FRONTEND_PRD_PART1.md`、`DOXAGENT_V2_FRONTEND_PRD_PART2.md`
- 面向对象：前端、API Contract、后端开发与联调人员

## 1. 文档目的

本文档将两份前端 PRD 中分散的数据需求提炼为统一的产品要求，作为后续 API Contract 设计和后端开发的业务输入。

本文档只回答以下问题：

- 前端需要哪些业务数据；
- 数据必须表达什么业务语义；
- 哪些数据属于摘要、列表、详情、历史、实时增量或操作反馈；
- 各类数据何时加载、何时更新、如何区分缺失与真实零值；
- 当前 V2 Workflow 已有事实与尚需补足的前端可消费能力。

本文档不规定：

- API 路径、协议方法、请求或响应 Schema；
- 接口数量及接口拆分方式；
- 后端服务、缓存层或聚合层设计；
- 数据库表、索引、SQL、RPC 或跨表查询方式。

文中按业务用途组织的数据组不代表必须设计为一个接口或一份响应。

## 2. 全局数据边界

### 2.1 V1 / V2 绝对隔离

- 本文档全部数据只允许来自 DoxAgent V2 Workflow、V2 Runtime、V2 Message Bus、V2 交易执行与 V2 审计事实。
- V2 数据缺失时必须明确显示缺失、不可用或尚未产生，不得读取 V1 数据补齐。
- 不得将 V1 与 V2 的状态、消息、Policy、事件、交易或成本汇总后展示。
- V2 页面可以沿用 V1 的页面路由和模块概念，但不得沿用与 V2 语义不一致的旧 DTO 或枚举。

### 2.2 前端消费原则

前端应消费已经确定业务语义的数据，不承担以下计算或推断：

- 美东 02:00 语义交易日、有效交易日及冬夏令时换算；
- 当前时段判定；
- 当前窗口和上一等长窗口边界；
- 版本、运行、Activation Revision 之间的固定引用关系；
- Policy、Event、Fact、消息、Case 或交易的业务去重；
- Workflow 父状态、质量注解和页面状态之间的业务归并；
- Trade intent、执行接收、成交和收益之间的判定；
- 缺失值补零、成本估算或不可比窗口的环比计算。

### 2.3 公共身份与版本上下文

需要在相关数据中保留足以稳定关联和去重的业务身份：

| 对象 | 前端所需身份或版本上下文 |
|---|---|
| Ticker | Ticker 标识及其当前可见、运行和初始化状态 |
| 初始化 | 初始化运行身份、父状态、节点或步骤身份 |
| D1 / D2 / D3 | 运行身份、产物身份、版本、发布时间及当前/历史标识 |
| 激活版本 | Activation Revision 及其固定引用的 D1、D2、Event Library、PolicySet |
| Shell / Unit | `shell_id`、`expectation_id` 及文档内原始顺序 |
| Policy | `policy_id`、Policy Revision、Activation Revision |
| Event / Fact | 稳定 Event / Fact 身份、Library Version、版本成员关系 |
| Standard Message | Message 身份、Revision、来源身份及精确重复关系 |
| Runtime Case | 稳定 Case 身份及与消息、判定、结果、交易的关联 |
| 模型调用 | 稳定调用或 Turn 身份，避免重读、重放或多份工件重复计数 |

前端不应使用名称、标题、数组位置或显示时间代替稳定身份。

## 3. 统一时间周期与比较口径

### 3.1 语义交易日上下文

所有涉及“当天”“前一天”“7 天”“30 天”的页面均需要获得：

- 当前 DoxAgent 语义交易日；
- 当前语义日是否为有效交易日；
- 前一有效交易日；
- 当前可选周期集合及默认周期；
- 所选周期的起止边界和有效交易日集合；
- 相邻上一等长窗口的起止边界和有效交易日集合；
- 当前窗口和上一窗口的数据完整性、可比性；
- 不可选择或不可比较时的明确原因。

统一规则：

- 交易日以美东时间 02:00 为语义边界，并支持冬夏令时；前端不得写死 UTC 偏移或盘前、盘中、盘后时间。
- 7 天和 30 天均指有效交易日窗口，不是自然日窗口。
- “全部”没有上一等长窗口，不显示环比。
- 当前运行历史不足、任一窗口不完整或上一窗口基数无法形成有效比例时，返回“不适用”及原因，不以零补齐。
- 休市日禁用“本交易日”。

### 3.2 周期值与环比

每个要求环比的指标均需要：

- 当前窗口值；
- 上一等长窗口值；
- 环比百分比；
- 是否适用；
- 不适用原因。

比率类指标的环比仍为相对变化百分比，不使用百分点差替代。

### 3.3 时间展示所需事实

需要区分而不能混用的时间包括：

- 信源发布时间、采集时间、进入标准消息流时间；
- Runtime 接收时间、完成时间；
- Event `occurred_at`、版本发布时间；
- Workflow 首次开始、最终结算及持续时间；
- 模型调用或 Worker Attempt 的开始、完成及耗时；
- 最近成功轮询、下一目标调度时间；
- 交易委托、成交和退出时间。

## 4. 状态、缺失值与列表通用要求

### 4.1 状态与质量注解

- Workflow 父状态与 `PARTIAL`、`DEGRADED` 等质量注解必须分开表达。
- 初始化父状态只有 `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED` 具有流程语义；质量注解不得直接映射为初始化失败。
- 尚未完成的 Case、W3 或交易不得提前生成最终结果或完成时间。
- 失败聚合可以统一计数，但详情仍需保留真实失败阶段和状态。

### 4.2 零值、不可用与失败

- `0` 只表示已经确认业务数量为零。
- 未产生、未记录、不可计价、不可比较、权限不足和读取失败必须分别表达，不得统一补零。
- 单个模块或单条详情失败不得清空其他已成功加载的数据。
- 刷新失败时保留旧缓存，并能表达缓存数据仍在展示和本次刷新失败。

### 4.3 列表、分页与详情

所有可能持续增长的消息、Case、Event、Policy 历史和审计明细需要支持：

- 稳定排序；
- 有界首屏和继续加载；
- 在筛选和周期范围内保持顺序一致；
- 通过稳定身份按需读取单条详情；
- 新增实时数据插入后不造成既有项重复或错位。

## 5. 全局导航数据

Ticker 下拉需要一份可切换 Ticker 清单，至少表达：

- Ticker 标识；
- 当前运行状态；
- 是否仍在初始化；
- 是否已从 Overview 移除。

进入下拉的 Ticker 包括正常、阻塞、已暂停和已停止；初始化中和已移除的 Ticker 不显示。切换 Ticker 后，当前页面只读取目标 Ticker 对应的 V2 数据。

## 6. Overview 页面数据需求

### 6.1 实时状态摘要

| 数据 | 业务口径 |
|---|---|
| 当前时段 | 盘前运行、盘中运行、盘后运行、夜盘运行、周末休眠或周末维护 |
| 正常 Ticker 数 | 仅统计当前应纳入正常/阻塞判断且状态正常的 Ticker |
| 阻塞 Ticker 数 | 仅统计当前应纳入正常/阻塞判断且状态阻塞的 Ticker |

初始化中、已暂停和已停止不计入正常或阻塞，也不另行汇总展示。

### 6.2 周期 KPI

支持前一交易日（默认）、本交易日、7 天、30 天：

| KPI | 当前窗口口径 | 比较要求 |
|---|---|---|
| Policy 命中 | 被命中的唯一 Policy 数 | 需要环比 |
| 交易 | 实际成功执行数 / 实际触发数；部分成交计成功 | 两项均需要可比值 |
| 消息 | 唯一 Standard Message 数 | 需要环比 |
| Token 成本 | V2 实际可计价成本 | 需要环比或不可用原因 |
| 非例行维护触发 | 当前只统计 O4 消息源 Repair，当前实现显示 0 | 不要求环比 |
| 收益变化 | 按 Exit 成交统计已实现净收益，Paper / Live 分开，并标识是否暂估 | 两项均需要环比 |

### 6.3 Ticker 监控列表

每个可见 Ticker 需要：

- 当前实际生效的监测模式：消息监测、模拟交易或实盘交易；
- 当前运行状态和健康状态；
- 最近 Standard Message 时间；
- 正常启用消息源数量、异常消息源数量；`never_polled` 和禁用源不计入两者；
- 所选周期内交易成功数 / 触发数、消息数、Token 成本及可用性；
- 是否存在未完成初始化；
- 是否已从 Overview 持久移除。

### 6.4 初始化进度

初始化未完整成功时需要：

- 初始化父状态和是否允许人工恢复；
- 当前失败节点集合；
- 以下六个前端归并步骤的状态与持续时间：基础投研、事件库初始化、预期研究、Policy 初始化、消息源准备与激活、启动运行；
- 重试操作是否提交中，以及操作成功或失败结果。

每步状态仅为待开始、进行中、已完成或失败。完整成功后不再需要返回进度卡片数据。重试语义为从当前失败节点集合断点恢复，不是全局重跑。

### 6.5 新建与管理操作所需反馈

前端提交 Ticker、运行模式和复用当前文档/强制初始化选择后，需要获得：

- 操作是否被接受；
- 是否直接进入运行或进入初始化；
- 当前 Ticker 真实状态；
- 不可执行或失败时的用户可读原因。

暂停、重启、断点重试和移除同样需要确定的处理中、成功或失败反馈。移除成功后，该 Ticker 必须立即且持久地退出 Overview 和全局 Ticker 下拉，但既有业务历史仍保留。

## 7. 基础投研页面数据需求

### 7.1 当前 Document 1

首屏需要：

- Ticker、Document 1 运行身份、文档身份；
- 当前/历史标识；
- Document Run 状态和 Global Research 状态；
- 生成时间及真实更新时间；
- 四项内容的存在性和内容类型；
- 默认“基本面研究”正文。

四项内容为：

- 基本面研究（C1）；
- 行业研究（C3）；
- 市场隐含预期研究（C5）；
- 未来节点（Future Nodes）。

C3、C5 和 Future Nodes 正文第一次选择时按需加载。文档下载在用户点击时读取。页面不需要 D2、Entity Map、C4 中间产物或汇总文档数据。

### 7.2 历史 Document 1

打开历史功能时需要历史运行清单，包括运行身份、状态和时间。选择某次历史运行后，需要该次运行对应的 C1、C3、C5、Future Nodes 和下载内容。

四项内容必须属于同一次运行，不允许跨运行拼接；历史仅供查看，不需要激活或切换为现行版本的操作数据。

### 7.3 数据完整性要求

- 当前没有 D1 时不得用 D2 或其他研究产物替代。
- 单项缺失不影响其他项目。
- 如果 Workflow 没有独立更新时间，必须明确为不可用，不得使用发布时间或读取时间冒充。
- `PARTIAL` 或单个研究产物失败时，应保留已正式发布的其他内容和真实状态。

## 8. 预期研究页面数据需求

### 8.1 当前 D2 摘要与 Shell 清单

首屏需要：

- Ticker、当前 Activation Revision 及其固定引用的 D2；
- D2 运行状态、发布状态（`COMPLETE` / `PARTIAL`）和发布时间；
- 按 D2 产物原始顺序排列的 Shell 清单；
- 每个 Shell 的稳定身份、核心问题、边界规则和成功/失败结果；
- 默认第一个 Shell 的全部 Unit。

当前版本必须取 Activation Revision 固定引用的 D2，不得用时间更新的其他 D2 替代。

### 8.2 Shell 与 Unit 详情

成功 Shell 需要：

- 有序 Unit 清单及稳定身份；
- Unit 命题和时间范围；
- State；
- Realization Factors；
- Potential Gaps。

前端需能按同一 Shell 获得以下范围：全部 Unit、单个 Unit、全部 State、全部 Factors、全部 Gaps。点击已加载 Unit 只改变本地显示状态，不应要求重新读取整份 D2。

失败 Shell 需要失败阶段、失败状态、失败信息及已有正式内容。`PARTIAL` 不得导致成功 Shell 被隐藏。

### 8.3 历史 D2

打开历史功能时需要历史 D2 清单、发布时间和发布状态；选择后按需获得该版本完整 Shell、Unit 和结构化内容。历史版本仅供查看。

## 9. 交易策略页面数据需求

### 9.1 当前 PolicySet 与 Shell 关联

首屏需要：

- Ticker、当前 Activation Revision；
- 该 Revision 固定引用的 D2 和 D3；
- D2 Shell 的稳定身份、核心问题和原始顺序；
- 当前 PolicySet 版本、发布时间；
- 当前筛选下的 Policy 摘要首屏及路由清单；
- 默认第一个具体 Shell 对应的 Policy；
- 已消费的 `policy_id + activation_revision` 事实，用于判断当前生效。

一个 Policy 可关联多个 Shell；在各相关 Shell 下均可出现，在“全部 Shell”中只显示一次。全部 Shell 位于 Shell 路由最右侧。

### 9.2 Policy 结构化详情

选择 Policy 后按需获得完整 D3 结构化业务内容，包括其稳定身份、名称、生效方向、生命周期状态、Activation Conditions、来源引用及页面需要展示的业务字段。

多个 Activation Conditions 使用固定 OR 语义。前端不得按字段存在性自行推断 Policy 是否生效、命中或已消费。

### 9.3 KPI、周期和筛选事实

支持前一交易日（默认）、本交易日、7 天、30 天、全部：

| KPI | 口径 | 环比 |
|---|---|---|
| 生效数量 | 当前未被消费的有效 Policy 数 | 无 |
| 多空方向比例 | 当前生效 Policy 的多空方向组成 | 无 |
| 周期新增 | 周期内首次出现的唯一 Policy | 有 |
| 周期命中 | 周期内实际命中的唯一 `policy_id + activation_revision` | 有 |
| 周期修改 | 周期内发生实质修改的唯一 Policy | 有 |
| 周期失效 | 周期内 Retire 的唯一 Policy | 有 |
| 周期交易执行 | 周期内关联 Policy 且实际成交的唯一执行 | 有 |

筛选项为当前生效（默认）、周期新增、周期命中、周期修改、周期失效和周期交易执行。需要提供能直接支持筛选归属的生命周期、命中和实际成交事实，不能用当前完整 PolicySet 的简单差集代替。

### 9.4 Policy 变更时间线

用户打开时间线时，按需获得：

- 变更时间和事件类型；
- Policy 身份和名称；
- 变更前后 PolicySet 版本；
- 简略变更内容；
- 修改后的 Policy Revision，或失效前最后一个 Revision。

版本号列表不能替代逐 Policy 的变更事件。

## 10. 事件库页面数据需求

### 10.1 两套独立数据范围

页面包含两套不同业务数据：

- 完整事件：当前 Canonical Event Library；
- 新增事件：O2 按语义交易日形成、供 O3 使用的 Reference View Delta。

二者不是同一数据源的两种筛选方式，必须分别表达版本、时间范围和内容身份。

### 10.2 完整事件

首屏需要当前 Library Version、发布时间、当前筛选结果首屏和事件索引摘要。每个 Event 及其 Facts 至少需要：

- 稳定身份、状态和版本成员关系；
- Event `occurred_at` 及时间精度；
- Event 与 Fact 的层级归属；
- 支持新增、实质修改、失效筛选所需的版本事实；
- 页面选定展示的结构化业务内容。

筛选项为当前生效（默认）、周期新增、周期修改和周期失效。

Event 按 `occurred_at` 由近到远；时间缺失或精度为 `UNKNOWN` 的 Event 放在所属结果末尾。Fact 保持正式产物中的原始顺序。

### 10.3 新增事件

需要：

- 可选语义交易日清单，默认前一有效交易日；
- 选定日期的基础 Library Version 和目标 Library Version；
- Reference View Delta 中新增、修改、移除的 Event；
- 新增或修改 Event 的结构化 Event / Fact 内容；
- 移除 Event 的身份及展示所需的移除前事实；
- 每项变化的 `add`、`modify` 或 `remove` 类型。

该模式无状态筛选；切换日期时读取对应日的独立增量结果。

### 10.4 KPI 与周期

支持前一交易日（默认）、本交易日、7 天、30 天、全部：

- 生效数量：当前唯一 Event 数 / Fact 数，无环比；
- 周期新增：周期内新增的唯一 Event 数 / Fact 数，有环比；
- 周期修改：周期内实质修改的唯一 Event 数 / Fact 数，有环比；
- 周期失效：周期内失效的唯一 Event 数 / Fact 数，有环比。

## 11. 消息总线页面数据需求

### 11.1 页面 KPI

支持前一交易日（默认）、本交易日、7 天、30 天、全部：

| KPI | 口径 | 更新方式 |
|---|---|---|
| 连续运行时长 | 从最近一次进入当前连续运行区间起算 | 每分钟更新展示事实 |
| 周期新增 | 成功发布到标准消息流的唯一 Standard Message Revision；精确重复不计 | 周期值及环比 |
| 正文补全成功率 | 可统计的正文补全尝试中成功占比 | 周期值及环比 |
| 数据源状态 | 正常启用源数 / 异常源数；排除 `never_polled` 和禁用源 | 每分钟更新 |
| 平均轮询延迟 | 当前纳入统计消息源的真实轮询延迟 | 每分钟更新 |

消息源类型、具体消息源和路由状态筛选会同时改变周期新增及正文补全成功率；关键词搜索只改变消息列表，不改变 KPI。

### 11.2 消息列表与实时增量

消息摘要需要：

- Standard Message 稳定身份和 Revision；
- 标题、消息源名称、信源 URL 和信源发布时间；
- Source ID、API / 爬虫类型、Binding 身份；
- 采集时间和进入标准消息流时间；
- Runtime Case 当前状态；
- 初始主路由、W3 是否待处理、最终 resolved route；
- 稳定排序和继续加载信息。

正文不包含 Summary。正文全文在卡片展开时按需读取，并保留源内容可支持的最小段落结构。

消息流实时增量需要：

- 可恢复的稳定游标；
- 新消息或 Revision 的稳定身份；
- 判断其是否符合当前类型、具体消息源、路由筛选和关键词搜索所需的最小字段；
- 必要时按单条身份补读卡片数据的能力。

当前 V2 路由为 `ARCHIVE`、`TRADE`、`ADD_TO_DELTA`、`W3`；进入 W3 后需要区分待处理与最终 resolved route。

### 11.3 消息源状态

每个当前 Ticker Binding 需要：

- Source ID、用户可读名称、API / 爬虫类型；
- 单条 / 分批发布模式；
- 是否启用及 Binding Version；
- Poll Status；
- 最近成功、最近一轮新增数、最近延迟和当前错误；
- 轮询间隔、Active Window、下一目标调度时间。

最近成功发生在当前语义交易日时可显示时间，否则需要完整日期。动态倒计时由下一目标调度时间驱动；暂停、禁用或窗口关闭时不得表现为仍在倒计时。

### 11.4 消息源配置

打开配置时按需获得：

- 当前 Binding 生效配置和版本；
- 参数值及其约束；
- `immediate` / `buffered` 发布模式；
- 轮询间隔和 Active Window；
- 是否可通过已适配表单编辑；
- 保存中的状态和保存结果。

API Source 支持已适配表单和 JSON；爬虫只要求 JSON。所有 Binding 的轮询间隔均需要可通过表单调整。

配置页底部还需要已注册、全局启用、适用于当前 Ticker 且尚未绑定的 API Source 清单；不包括爬虫和全局禁用 Source。

## 12. 运行状态页面数据需求

### 12.1 周期 KPI

支持前一交易日（默认）、本交易日、7 天、30 天、全部，全部 KPI 均需要当前值；可比较周期需要上一窗口值、环比或不适用原因。

| KPI | 口径 |
|---|---|
| 周期处理 | 周期内唯一 Runtime Case 数 |
| 一轮判定平均延时 | W1 与 W2 并行阶段的墙钟平均耗时，不是二者相加 |
| 二轮研判平均延时 | 进入 W3 的 Case 对应 W3 Worker 墙钟平均耗时 |
| 新旧判定 | 最终 NEW / OLD Case 数，不受 Confidence 高低影响；经过 W3 时由 W3 覆盖 W1 |
| Policy 命中 | 最终有效判定命中的 Case 数 / 比例，不按命中 Policy 个数计 |
| 二轮研判 | 流转至 W3 的唯一 Case 数 |
| 事件发现 | W1-R3 与 W3 成功输出且稳定去重后的新 Atomic Fact Candidate 数 |
| 交易执行 | 存在实际 Fill 的唯一 Case 数；部分成交计入，多 Fill 按 Case 去重，Paper / Live 合并 |

### 12.2 Case 链路事实

每个 Runtime Case 需要能够表达：

- 稳定 Case 身份、所属语义交易日、业务状态和技术状态；
- 接收时间、完成时间；
- 关联 Standard Message；
- W1、W2 并行阶段及其结果；
- 初始主路由；
- 是否进入 W3、W3 当前状态和最终结果；
- Archive、事件发现、Badcase、交易执行、失败中的零个或多个实际结果；
- Case 与每个结果节点的关联。

一个 Case 可以对应多个最终结果，下游节点允许重复计数；失败统一进入失败结果节点，但保留真实失败阶段。

链路图 SSE 增量需要稳定游标，以及只更新受影响 Case、节点、连线和计数所需的最小事实。不得依赖每次增量重新读取完整图或完整 Case 历史。

### 12.3 W1、W2、W3 详情

- W1：最终 NEW / OLD、Confidence、关联 Event / Fact、Reasoning；
- W2：Policy 命中判定、Confidence、命中 Policy、Reasoning；
- W3：最终 NEW / OLD、关联 Event / Fact、Policy 命中、事件候选、交易判定及各部分 Reasoning；
- W1 / W2 每个真实模型轮次和 Attempt 的状态、顺序、耗时；
- W1 / W2 并行阶段的开始、完成和墙钟耗时；
- W3 每次 Worker Attempt 的状态和墙钟耗时；
- W3 到各最终结果节点的 Case 数量。

W1 / W2 节点摘要额外需要 Confidence Low 数量；W3 节点摘要额外需要流向各最终结果的数量。

### 12.4 节点详情与最近记录

节点详情需要处理数、失败数、最近处理时间和平均延时。最近节点记录摘要显示消息标题、接收时间、完成时间、状态、最终结果和消息源，不显示内部 ID。

选择记录后按需读取与“最近处理记录”展开态同粒度的 Case 详情。

### 12.5 最近处理记录

列表支持按最终结果和消息源筛选。折叠态需要：

- 消息标题；
- Case 状态；
- 接收时间和完成时间；
- 总耗时；
- 全部最终结果；
- 消息源。

展开态按需需要：

- 仅 LLM / Agent 节点的逐节点耗时，单位秒；
- W1 判定、Confidence、关联已知 Event / Fact 和 Reasoning；
- W2 判定、Confidence、命中 Policy 和 Reasoning；
- 实际经过 W3 时的 W3 判定、Policy 或 Event / Fact 关联及 Reasoning；
- 实际交易执行情况；
- 消息源和消息正文。

Reasoning 和完整正文默认不进入列表首屏，可分别按需读取。

### 12.6 结果与交易事实

需要明确区分：

- Trade intent；
- 执行接收；
- 委托及其状态；
- Fill、部分成交和全部成交；
- 拒绝、过期和失败。

只有实际 Fill 进入交易执行节点和 KPI。W1-R3 与 W3 Candidate 需要稳定去重身份。所有阶段失败均需能关联回原 Runtime Case。

## 13. 收益 / 成本审计页面数据需求

### 13.1 页面范围

- 本期只提供成本审计数据；收益审计入口只需表达“暂未开放”，不读取收益数据。
- API 与 Codex 是两个互斥的全页数据范围，不允许合并计数，默认 API。
- 支持前一交易日（默认）、本交易日、7 天、30 天、全部。
- 支持按节点和模型筛选，并提供当前范围内真实可用的筛选选项。

### 13.2 用量事实

每条可聚合用量事实需要：

- 所属 V2 Ticker；
- API / Codex 调用类型；
- Provider 和精确 Model ID；
- V2 Workflow 业务节点；
- 调用或 Turn 真实发生时间；
- Input Token、Cached Input Token、Output Token、Total Token；
- 用量是否有效；
- API 调用的非缓存 Input、缓存 Input、Output 和总成本及是否可计价；
- 稳定调用身份。

统一关系：Cached Input 是 Input 的子集；Total Token = Input Token + Output Token。缓存命中比例 = Cached Input Token / Input Token。Cached Input 缺失时不得推测。

### 13.3 KPI 与聚合数据

顶部需要六项 KPI：

- Token 总量；
- 总成本；
- Input Token 数量 / 成本；
- Output Token 数量 / 成本；
- Cached Input Token 数量；
- 缓存命中比例。

所有 Token 以 M 为显示单位并保留三位小数。Codex 只显示真实 Token，用量成本和周额度映射均为不适用。

还需要：

- 按时间的 Token / 可计价成本趋势；
- API 按节点、按模型的成本占比，或 Codex 按节点、按模型的 Token 占比；
- 节点明细；
- 各模块无数据、部分不可计价或读取失败状态。

### 13.4 节点明细

每行按业务节点聚合：

- 节点名称；
- 该节点通常使用的模型；
- 请求数；
- Input Token 数量 / 成本；
- Output Token 数量 / 成本；
- Cached Input Token 数量；
- 缓存命中比例；
- 平均每请求 Total Token；
- 总成本。

不需要逐调用时间、Ticker、重试或状态字段。

### 13.5 API 固定计价口径

当前产品固定使用以下精确 Model ID 计价：

| Model ID | 时段 | Input（元 / 1M） | Cached Input（元 / 1M） | Output（元 / 1M） |
|---|---:|---:|---:|---:|
| `qwen3.8-flash` | 全时段 | 0.8 | 0.1 | 2.7 |
| `deepseek-v4-flash-0731` | 中国时间 08:00–22:00 | 3.0 | 0.3 | 9.0 |
| `deepseek-v4-flash-0731` | 中国时间 22:00–次日 08:00 | 1.5 | 0.15 | 4.5 |

按固定汇率 `1 USD = 6.8 CNY` 显示美元成本。Input 成本必须由非缓存命中 Input 与 Cached Input 分别计价后相加。

未配置价格的新 Model ID 仍统计 Token，但成本为“不适用”，并从可计价总成本中排除；不得继承相似名称模型的价格。

## 14. 更新、缓存与按需加载矩阵

| 数据范围 | 新打开页面 | 页面可见时 | 切出再切回 | 人工刷新 | 按需加载 |
|---|---|---|---|---|---|
| Overview、D1、D2、策略、事件库、成本审计 | 加载默认首屏 | 不自动刷新 | 使用本标签页缓存 | 刷新当前已打开范围 | 非默认周期、正文、历史、时间线、后续页 |
| 消息总线 KPI、消息源状态 | 加载当前范围 | 真实时钟每分钟边界更新 | 先用缓存，下个分钟边界更新 | 刷新当前范围 | 配置、正文、后续页 |
| 消息流 | 加载首屏并接入 SSE | SSE 最小增量 | 按游标恢复，不全量刷新 | 刷新当前首屏并重建游标基线 | 正文、后续页 |
| 运行状态 KPI、最近记录、已打开节点 | 加载当前范围 | 真实时钟每分钟边界更新 | 先用缓存，下个分钟边界更新 | 刷新当前已打开范围 | Case、Reasoning、正文、节点详情、后续页 |
| 运行链路图 | 加载基础图并接入 SSE | SSE 最小增量 | 按游标恢复，不全量刷新 | 刷新基础图并重建游标基线 | 节点与 Case 详情 |

共同要求：

- “新打开页面”指当前标签页本次会话中第一次打开该页面；不是每次路由返回。
- 分钟更新按真实时钟整点分钟边界，例如 12:02、12:03，不从进入页面时另算 60 秒。
- 页面不可见时停止分钟读取并断开 SSE；返回后 SSE 按游标恢复，普通模块不立即刷新。
- 人工刷新只更新当前页面、Ticker、周期、筛选和已打开模块，不预取未打开的大数据。
- 周期、筛选或历史版本第一次选择时读取一次；再次切回使用本标签页缓存。
- SSE 只传送判断和应用增量所需的最小事实，不触发 KPI、完整列表、完整图或详情全集重读。

## 15. 数据量与读取约束

以下为前端产品对数据交付的硬性非功能需求，不代表后端实现方案：

- 首屏只交付当前页面立即可见且必要的数据。
- 报告正文、结构化文档、完整消息正文、Reasoning、历史版本、配置 JSON、时间线和 Case 详情必须与摘要解耦并按需读取。
- 长列表必须有界分页或继续加载；不得为了首屏读取完整历史。
- KPI 应获得适合展示的聚合结果；前端不得为了计算一个 KPI 拉取完整明细全集。
- 同一页面读取一个局部值时，不应要求同时交付无关大对象或多个完整业务集合。
- Supabase 来源尤其需要避免高频读取和大 Payload 导致 Egress 放大；不得以全表、无界时间范围或完整跨集合读取满足局部展示。
- 本地 SQLite 没有相同的 Egress 约束，但仍需遵守最小必要、分页、懒加载和 V2 隔离原则。

## 16. 当前需补足的前端可消费能力

以下为现有 V2 Workflow 事实与前端需求之间的主要缺口；这里只定义结果能力，不指定实现方式：

| 页面 | 需补足能力 |
|---|---|
| Overview | Ticker 级 Paper / Live 运行事实；完整周期与上一窗口摘要；六步初始化聚合状态和耗时；持久移除事实 |
| 基础投研 | Global Research Bundle 的真实独立更新时间；不得用其他时间冒充 |
| 预期研究 | `PARTIAL` D2 失败 Shell 若需展示阶段性 Unit，需形成可正式消费的已有内容 |
| 交易策略 | 当前生效所需的 Policy + Activation Revision 消费事实；逐 Policy 生命周期周期摘要及变更时间线 |
| 事件库 | Reference View Delta 的完整结构化新增、修改、移除摘要及移除前展示事实；周期聚合 |
| 消息总线 | Standard Message 与 Runtime V2 Case 的真实路由关联；连续运行起点；筛选交集、比较窗口与环比聚合 |
| 运行状态 | 从 V2 Case、Turn、W3、Effect、Candidate 和 Fill 事实形成全新链路、节点摘要、Case 详情和增量；不得复用 V1 Runtime 图 |
| 成本审计 | 覆盖全部 V2 节点的统一用量事实；完整 Cached Input；精确 Model ID 计价；API / Codex 分离聚合 |

- O4 非例行 Repair 当前固定为 0；
- 收益审计正文；
- Codex Token 到订阅周额度的换算；
- V1 数据回退；
- 已移除 Ticker 的前端恢复入口。

## 17. 数据联调验收标准

1. 任一 V2 页面在数据缺失时均不会读取或展示 V1 数据。
2. 当前文档、策略和运行数据均能证明其属于当前 Ticker 的同一 Activation Revision 或指定历史运行，不发生跨版本拼接。
3. 所有周期页面使用同一语义交易日、有效交易日窗口和上一等长窗口事实。
4. 零值、无数据、不可用、不可计价、不可比较和读取失败可被前端明确区分。
5. Policy、Event、Fact、Message Revision、Runtime Case、Candidate、Fill 和模型调用均可稳定去重。
6. Trade intent 或委托存在但没有 Fill 时，不进入交易执行 KPI；收益只来自 Exit Fill。
7. `PARTIAL`、`DEGRADED` 和单项失败不会错误清空其他已成功产物。
8. 首屏不依赖完整报告、完整历史、完整 Reasoning 或完整消息正文才能展示。
9. 所有增长型列表支持稳定排序、有界首屏和继续加载。
10. SSE 断线重连可以按游标补收增量，不重复、不漏收，也不触发全页重读。
11. 分钟更新只影响规定组件；页面返回不会额外触发普通刷新。
12. 人工刷新失败时，前端可继续展示刷新前缓存并明确本次失败。
13. API / Codex 审计切换后 KPI、趋势、占比和节点明细全部使用各自独立数据。
14. 未知模型仍可展示真实 Token，但不会产生虚构成本。
15. 后续 API Contract 可以从本文档逐项追溯到明确的页面用途、业务口径和更新方式，而无需重新从视觉 PRD 推断。
