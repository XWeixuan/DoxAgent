文档状态：需求对齐稿，持续补充

## 1. 文档说明

### 1.1 文档目的

本文档记录 DoxAgent V2 前端的产品需求、页面模块、数据语义、状态、交互结果及全局非功能约束。阅读者不需要预先了解 V1 页面结构或外观，也应能够根据本文档识别本期需要开发的页面、模块和数据类型。

本文档不规定具体视觉设计方案，不设计 API 路径、后端服务拆分、数据库表或具体查询语句。涉及 workflow、缓存、加载和数据读取的内容只用于明确前端产品行为、真实数据边界及必须满足的工程约束。

### 1.2 分卷范围

完整 PRD 分为两份结构一致、可独立阅读的文档：

- Part 1：全局规范、Overview、基础投研、预期研究、交易策略、事件库；
- Part 2：同一套全局规范、消息总线、运行状态、收益 / 成本审计。

两份文档中的全局规范具有相同含义。某个页面的细化要求以该页面所在分卷为准；页面细化不得放宽 V1/V2 隔离、缓存、SSE、懒加载或数据读取约束。

## 2. V2 前端边界

### 2.1 V1 与 V2 隔离

- V1 与 V2 的 workflow、数据库、后端和前端运行数据必须完全隔离。
- V2 前端不得读取 V1 的运行状态、缓存、请求结果或业务数据。
- V2 可以沿用并调整 V1 的视觉语言、组件样式和页面布局，但不能以复用界面为理由复用 V1 的业务状态语义。
- V1 后续弃用，不保留 V1 页面入口，也不提供 V1/V2 切换控件。
- 现有前端路由直接切换为 V2 页面；`/overview` 表示 V2 Overview。

### 2.2 前端职责

前端负责：

- 展示 V2 workflow 已形成的业务状态；
- 将底层状态转换成本文档定义的用户可读视图；
- 提供启动、暂停、重启、删除和失败节点重试等交互入口；
- 在单个浏览器标签页内缓存已经打开过的页面数据。

前端不负责：

- 推断或伪造 workflow 未提供的成功状态；
- 将 `PARTIAL`、`DEGRADED` 等质量诊断直接当作初始化父流程失败；
- 自行计算或决定交易日、冬夏令时、订单是否成功等服务端业务事实；
- 直接读取 V1 数据作为 V2 缺失字段的回退；
- 在本需求文档中规定 API、后端或数据库的具体实现方式。

## 3. 全局导航栏

### 3.1 Logo 与 Overview

- 全局顶栏显示 DoxAgent Logo。
- 点击 Logo 始终进入 V2 `/overview`。
- Overview 不显示 ticker 下拉选择器。
- V1 已弃用，导航栏不提供 V1 入口或 V1/V2 切换。

### 3.2 Ticker 级页面导航

除 Overview 外，ticker 级导航应提供以下页面入口：

1. 基础投研：`/ticker/:ticker/research`；
2. 事件库：`/ticker/:ticker/events`；
3. 预期研究：`/ticker/:ticker/expectations`；
4. 交易策略：`/ticker/:ticker/strategy`；
5. 消息总线：`/ticker/:ticker/message-bus`；
6. 运行状态：`/ticker/:ticker/runtime`；
7. 收益 / 成本审计：`/ticker/:ticker/audit`。

导航名称使用本文档定义的 V2 页面名称，不继续显示 V1 的“投研资料”或“执行策略”等旧名称。

### 3.3 Ticker 下拉切换

- 除 Overview 外，顶栏显示当前 ticker，并提供已有 ticker 下拉选择器。
- 下拉列表只包含尚未被前端移除、且不处于“初始化中”的 ticker。
- 正常、阻塞、已暂停和已停止的已有 ticker 均可以显示并切换。
- 已被前端移除的 ticker 不显示；不通过此处提供恢复入口。
- 切换 ticker 时保持当前业务页面不变。例如从 `/ticker/MU/runtime` 选择 `INTC` 后进入 `/ticker/INTC/runtime`。
- 切换后使用目标 ticker 与当前页面组合的缓存；若没有缓存，则按“新打开页面”规则加载该页首屏必要数据。
- 不得在 ticker 切换期间短暂展示上一 ticker 的数据，页面缓存必须按 ticker 严格隔离。

### 3.4 Ticker 列表缓存

- ticker 下拉所需列表在当前标签页第一次进入 ticker 级页面时读取，并在当前标签页共享缓存。
- 页面之间切换不重复读取 ticker 列表。
- Overview 新建、删除或改变 ticker 状态成功后，应同步更新当前标签页的 ticker 列表缓存。
- 用户人工刷新 ticker 级页面时可以同步更新 ticker 列表；失败时保留旧列表。
- 浏览器硬刷新、新开标签页、关闭后重开或重新登录后，重新建立该标签页的 ticker 列表缓存。

## 4. 全局刷新、缓存、加载与数据调用规范

### 4.1 新打开页面与人工刷新

页面只在以下情况主动读取其常规页面数据：

1. 当前浏览器标签页第一次打开某个页面与 ticker 组合；
2. 用户点击当前页面的人工刷新；
3. 用户第一次选择尚无缓存的周期、模式、Shell、Unit、Policy、日期、筛选或其他数据范围；
4. 用户主动打开需要按需加载的详情、大正文、历史内容或后续分页。

“新打开页面”不是“新登录”。登录成功时不得预加载所有页面；每个页面在用户实际进入时只读取首屏必要数据。

页面内部仅改变本地展示状态且所需数据已经缓存时，不发起读取。人工刷新只更新当前页面、当前 ticker、当前模式及已经打开的必要模块，不预取其他 ticker、其他页面、其他周期或尚未打开的详情。

### 4.2 缓存范围与生命周期

- 页面缓存范围为当前浏览器标签页。
- 缓存至少按 ticker、页面、模式、周期、筛选、版本或其他实际数据范围隔离。
- 从一个页面切换到其他页面再返回时，先显示已有缓存，不因返回或窗口重新聚焦立即刷新。
- 已加载过的数据范围再次被选择时使用缓存；只有人工刷新才重新读取该范围。
- 不为普通页面缓存设置自动失效时间。
- 浏览器硬刷新、新开标签页或关闭后重新打开，均视为新的页面打开，允许重新读取当前页首屏必要数据。
- 登出时清除当前登录会话的页面缓存，避免下一用户读取前一用户数据。
- 写操作成功后优先以操作结果更新相关缓存，不额外触发无关模块或整页读取。
- 刷新或按需加载期间保留已有内容；失败时保留旧缓存并显示对应范围的错误。
- 页面不显示“当前数据截至时间”或“最近刷新时间”。

### 4.3 页面更新频率分类

低频缓存页面包括：

- Overview；
- 基础投研；
- 预期研究；
- 交易策略；
- 事件库；
- 收益 / 成本审计；
- 消息总线中的消息渠道配置。

低频缓存页面不进行定时轮询，不因 SSE、窗口聚焦或页面往返自动刷新，只按第 4.1 节读取。

每分钟更新的组件仅包括：

- 消息总线 KPI；
- 消息源状态；
- 运行状态 KPI；
- 运行状态的最近处理记录；
- 运行状态中当前已经打开的节点详情。

分钟刷新规则：

- 以真实时钟分钟边界触发，例如 12:02、12:03、12:04；不从进入页面时重新累计 60 秒；
- 只有对应页面当前可见时才运行；
- 页面不可见时暂停；
- 返回页面时先显示缓存，不立即补一次普通刷新，在下一个真实分钟边界恢复；
- 每次只更新该组件当前可见或已打开的数据范围，不预取隐藏详情或其他筛选范围。

### 4.4 SSE 实时更新

全站只有以下两个组件使用 SSE：

1. 消息总线的消息流；
2. 运行状态的 V2 运行链路图。

SSE 规则如下：

- 页面可见时建立连接；离开对应页面时关闭连接；
- 返回页面时携带上次事件游标恢复，补收离开期间遗漏的增量事件，不重新读取完整列表或完整链路图；
- 消息流只插入符合当前消息源类型、具体消息源、路由状态和关键词条件的新消息；不符合当前范围的消息不插入，也不重置已有分页；
- 运行链路图只更新受新建或更新 Case 影响的节点、连线和计数；用户当前选择的局部路径保持不变；
- SSE 事件必须携带更新组件所需的最小增量，或携带稳定对象身份以支持一次局部读取；
- 单条 SSE 事件不得触发 KPI、消息源状态、节点详情、处理记录、整页、整表、完整消息列表或完整链路图重读；
- SSE 不替代一分钟刷新；除消息流和链路图外，其他组件不因 SSE 更新；
- 页面不常驻展示 SSE 连接状态；只有连接异常并影响实时更新时才提示；
- 断线可以自动重连，但不得通过反复全量读取实现补偿。

### 4.5 按需懒加载

页面打开时只读取形成首屏所必需的数据。以下类型默认按需加载：

- 完整文档正文和大型 JSON 产物；
- 历史版本列表之外的历史版本正文；
- Policy、Event、Fact、Expectation Unit 或 Runtime Case 的完整详情；
- reasoning、消息正文全文和其他大文本 payload；
- 节点详情和最近节点记录；
- 侧边时间线、隐藏式索引对应的非当前内容；
- 列表后续分页；
- 尚未打开的页面模式、周期、筛选或 ticker 数据。

按需加载只更新目标内容，不清空或重新加载已经成功展示的页面其他模块。折叠并再次展开已加载内容时优先使用缓存。

### 4.6 数据调用与 Supabase Egress 约束

前端与支撑本页面的读取能力必须遵守最小必要原则：

- 一次读取只取得当前 ticker、页面、周期、筛选、分页或对象所需的数据；
- 为显示一个计数、状态或摘要，不得读取完整正文、完整 JSON、完整历史集合或整张表后在前端聚合；
- 为显示一个对象详情，应按稳定对象身份读取该对象所需字段，不得读取整表或无关对象；
- 不得为了取得一个计数、状态或少量展示字段而执行跨多个表或多个完整数据集合的宽范围读取；确有跨对象语义时，只返回该页面已经需要的有界结果；
- 列表必须使用有界分页或等价的有界结果，不得一次返回全部历史记录；
- 周期 KPI、趋势和占比应直接取得满足展示所需的聚合结果，不向前端传输用于重新聚合的大量原始记录；
- 跨多个业务对象的数据必须以当前页面真实需要为边界，不得为了取得少量字段无条件读取多个完整数据集合；
- 相同数据不得因多个组件分别挂载而重复读取，应复用同一页面范围缓存；
- SSE 恢复和分钟刷新只能取得增量或当前组件的最小必要结果，不得把高频刷新实现成 Supabase 全表扫描；
- 大 payload 必须与列表摘要、KPI 和状态读取解耦，只在用户实际打开时读取；
- Supabase 数据读取必须把请求次数、扫描范围、返回字段和返回行数控制在当前展示所需范围，避免不必要 egress；
- 本地 SQLite 不受 Supabase egress 限制，但仍必须遵守 V1/V2 隔离、数据真实性和页面范围边界。

本文档只规定上述数据消费和资源约束，不规定 API 数量、接口路径、数据库表、索引或查询实现。

### 4.7 全局验收标准

1. 两份 PRD 均完整声明相同的全局导航、刷新、缓存、SSE、懒加载和数据读取规则。
2. Logo 始终返回 V2 Overview；除 Overview 外的页面均可通过下拉列表切换已有非初始化 ticker。
3. ticker 切换保持当前业务页，且不会展示上一 ticker 的缓存数据。
4. 普通页面在首次打开、首次访问未缓存范围、人工刷新或主动打开懒加载内容时读取数据。
5. 页面往返和窗口聚焦不触发额外刷新；硬刷新视为新打开页面。
6. 只有规定组件按真实分钟边界更新，只有消息流和运行链路图使用 SSE。
7. SSE 只更新最小增量，不触发整页或全量数据重读，页面隐藏期间关闭并可按游标恢复。
8. 大正文、大 JSON、详情、历史正文、reasoning 和后续分页均按需加载。
9. Supabase 读取不存在为了少量展示而进行的整表读取、无界历史读取、多集合全量读取或高频大 payload 读取。
10. 本地 SQLite 与 Supabase 均不得跨越 V1/V2 数据隔离边界。

## 5. Overview 页面

### 5.1 页面目标

Overview 是 DoxAgent V2 的全局入口，帮助用户完成三件事：

1. 查看当前运行时段和 ticker 总体状态；
2. 查看选定统计窗口内的 Policy、交易、消息、成本、维护和收益数据；
3. 启动新 ticker，并管理已经存在的 ticker。

### 5.2 页面总体布局

页面从上至下分为四个区域：

1. 页面标题与全局操作区；
2. 实时状态模块；
3. 区间统计模块；
4. 启动新标的监控与标的监控列表组成的主工作区。

桌面端主工作区采用左右布局：

- 左侧为“启动新标的监控”；
- 右侧为“标的监控列表”；
- 右侧列表占据主要宽度；
- 窄屏下两个区域改为上下排列，启动区在前，列表在后。

Overview 不再提供回测入口、回测模式、回测周期、回测任务切换或回测任务列表。

### 5.3 页面标题与全局操作区

#### 5.3.1 页面标题

- 左侧显示 `Overview`。
- 不显示当前数据截至时间。
- 不显示最近刷新时间。

#### 5.3.2 全局统计周期切换

标题区提供以下统计周期切换项：

- `前一交易日`
- `本交易日`
- `7天`
- `30天`

规则如下：

- 页面首次打开时默认选择“前一交易日”。
- “前一交易日”指当前语义日之前最近一个有效的美股交易日，不按自然日或简单工作日计算。
- “本交易日”指当前美东 02:00 语义日对应的有效美股交易日。
- 当前语义日为周末、法定休市日或其他非交易日时，“本交易日”按钮禁用，不能选择。
- “7天”指截至当前语义日最近 7 个有效美股交易日；当前语义日不是交易日时，截至此前最近一个有效交易日。
- “30天”指截至当前语义日最近 30 个有效美股交易日；当前语义日不是交易日时，截至此前最近一个有效交易日。
- 统计周期选择对 Overview 内全部区间统计卡片，以及标的监控列表中的区间统计列全局生效。
- 选择前一交易日或本交易日时沿用“当日”名称；选择 7 天或 30 天时，对应卡片和列表字段名称分别使用“7日”或“30日”，不得继续用“当日”指代多日窗口。
- 统计周期切换不改变实时状态卡片、ticker 当前运行状态、最近消息时间或 Message Bus 当前状态。

#### 5.3.3 手动刷新

- 标题区保留一个手动刷新按钮。
- 点击后只刷新当前 Overview 中可见的实时状态、当前选中统计周期和标的监控列表，不预取其他统计周期。
- 刷新期间按钮显示进行中状态并暂时禁止重复点击。
- 刷新成功后更新页面缓存。
- 刷新失败时保留刷新前的内容，并提示刷新失败。

### 5.4 实时状态模块

实时状态模块只展示当前时刻的状态，不受统计周期切换影响。本模块只包含两张卡片。

#### 5.4.1 当前时段

卡片名称：`当前时段`

允许显示的状态：

- 盘前运行
- 盘中运行
- 盘后运行
- 夜盘运行
- 休市维护
- 休市休眠

状态语义：

- 盘前、盘中、盘后和夜盘必须以 `America/New_York` 市场时间、有效交易日和市场时段事实为准。
- 不得在前端写死北京时间或以固定 UTC 偏移换算。
- 必须正确支持美国冬令时和夏令时切换。
- `休市维护` 表示休市周期内仍存在应执行、正在执行或等待结算的计划维护。
- `休市休眠` 表示休市周期内没有正在进行或应执行的计划维护。

#### 5.4.2 Ticker 状态

卡片名称：`Ticker 状态`

展示格式：

```text
正常数量 / 阻塞数量
```

示例：

```text
3 / 1
```

计数规则：

- 正常：ticker 已就绪，必要运行能力可用，当前没有阻止其继续运行的故障。
- 阻塞：ticker 的必要能力不可用，无法继续当前运行，或初始化失败并等待人工恢复。
- 初始化中、已暂停和已停止的 ticker 不计入正常数量。
- 初始化中、已暂停和已停止的 ticker 不计入阻塞数量。
- 卡片不额外展示初始化中、已暂停或已停止的数量。

### 5.5 区间统计模块

区间统计模块展示全局统计周期切换当前所选窗口的数据。卡片按以下顺序排列：

1. 当日 Policy 命中
2. 当日交易
3. 当日消息
4. 当日 token 成本
5. 非例行维护触发数
6. 当日收益变化

选择前一交易日或本交易日时，本文档中的“当日”指当前选中的交易日，而不是用户设备所在时区的自然日。选择 7 天或 30 天时，各卡片按整个窗口聚合统计。

#### 5.5.1 当日 Policy 命中

卡片名称：`当日 Policy 命中`

展示内容：选中统计窗口内，被至少一次有效命中的唯一 Policy 数量。

计数规则：

- 同一个 Policy 在同一统计窗口内被多条消息或多个 Case 命中，只计为一个唯一 Policy。
- 不同 ticker 下的 Policy 分别计数。
- 只出现候选匹配但未形成有效 Policy 命中的记录不计入。
- 该卡片必须位于“当日交易”左侧。

#### 5.5.2 当日交易

卡片名称：`当日交易`

展示格式：

```text
实际成功执行数 / 实际触发数
```

示例：

```text
1 / 2
```

计数规则：

- 实际触发数：选中统计窗口内已经形成可执行 Trade intent 的次数。
- 仅命中 Policy、但最终没有形成可执行 Trade intent 的事件不计入触发数。
- 实际成功执行数：对应 Entry 至少产生一笔实际 fill 的交易次数。
- 部分成交只要已经产生实际 fill，也计为成功执行一次。
- 风控拒绝、行情不可用、broker 拒单、过期和未成交进入触发数，但不进入成功执行数。

#### 5.5.3 当日消息

卡片名称：`当日消息`

展示内容：选中统计窗口内，全部 ticker 成功发布到标准消息流的唯一标准消息总数。

计数规则：

- 不按 raw message 数量计数。
- 不因同一标准消息被多个 Runtime 节点处理而重复计数。
- 顶层数量必须等于列表中所有未移除 ticker 的“消息数量”之和。

#### 5.5.4 当日 token 成本

卡片名称：`当日 token 成本`

展示内容：选中统计窗口内全部 ticker 的模型 token 实际成本合计，使用美元展示。

展示示例：

```text
$42.36
```

没有可用成本记录时显示 `暂无数据`，不将未知成本显示为 `$0`。

#### 5.5.5 非例行维护触发数

卡片名称：`非例行维护触发数`

展示内容：选中统计窗口内，排除 O2、O3 等日常计划内维护后的其他 agent 维护触发次数。

当前版本规则：

- 统计范围预留给 O4 消息源 REPAIR。
- 当前 V2 持久化运行没有启用运行期 O4 REPAIR，因此本卡片当前固定显示 `0`。
- ticker 初始化中的 O4 CONFIGURE、DELIVER、注册或失败恢复不计入本卡片。
- 后续加入其他非例行 agent 维护类型时，再在本文档中补充其计数口径。

#### 5.5.6 当日收益变化

卡片名称：`当日收益变化`

展示格式：

```text
模拟盘收益 / 实盘收益
```

示例：

```text
$232 / $324
```

计数规则：

- 只统计选中统计窗口内发生实际 Exit fill 的 DoxAgent 归属份额。
- 未退出的持仓和未成交的 Exit 不计入已实现收益。
- 部分退出只计算已经退出部分的已实现收益。
- 交易归属日以 Exit 的实际 broker execution time 和美东 02:00 语义日确定。
- 展示扣除已经取得佣金后的净收益。
- 佣金尚未返回时，相关环境的金额显示为暂估状态。
- 正收益使用 `$232`，负收益使用 `-$232`。
- 所选统计窗口没有退出成交时显示 `$0 / $0`。

#### 5.5.7 环比变化

除“非例行维护触发数”外，区间统计模块中的可比数据均需同时显示环比变化百分比。

对比窗口：

- 前一交易日：与再前一个有效交易日比较；
- 本交易日：与前一个有效交易日比较；
- 7 天：与当前 7 个交易日窗口之前紧邻的 7 个有效交易日比较；
- 30 天：与当前 30 个交易日窗口之前紧邻的 30 个有效交易日比较。

计算与显示规则：

- 环比变化使用 `(当前窗口值 - 上一窗口值) / 上一窗口值 × 100%`。
- 当前窗口或上一窗口缺少完整数据时，环比显示 `不适用`。
- ticker 实际运行历史不足以覆盖完整当前窗口和完整上一窗口时，环比显示 `不适用`。
- 上一窗口值为 0 时不计算百分比，显示 `不适用`。
- “当日交易”的实际成功执行数和实际触发数分别计算环比。
- “当日收益变化”的模拟盘收益和实盘收益分别计算环比。
- 不用缺失数据补零后计算环比。
- “非例行维护触发数”当前为固定前瞻数据 `0`，不显示无意义的环比。

### 5.6 启动新标的监控

#### 5.6.1 模块结构

模块名称：`启动新标的监控`

仅包含以下配置：

1. Ticker 输入框；
2. 运行模式；
3. 文档初始化方式；
4. 启动按钮。

不增加 Live 风险提示、二次确认、当前 execution profile、账户信息、模型配置、prompt 配置、research cutoff、单独消息源选择或轮询频率配置。

#### 5.6.2 Ticker 输入

- 输入框标签为 `Ticker`。
- 输入示例为 `例如 MU`。
- 用户点击启动按钮后提交当前输入。
- 启动处理中禁用启动按钮，避免同一次操作重复提交。

#### 5.6.3 运行模式

运行模式为三选一：

- 消息监测
- 模拟交易
- 实盘交易

业务含义：

- 消息监测：启动该 ticker 的消息监测和 Runtime 分析，但不向交易执行器释放订单。
- 模拟交易：该 ticker 形成的可执行 Trade intent 进入 Paper 交易环境。
- 实盘交易：该 ticker 形成的可执行 Trade intent 进入 Live 交易环境。

当前 workflow 的 execution profile 为全局 active profile，尚不支持不同 ticker 同时固定到不同 Paper/Live 环境。V2 前端仍按上述三种 ticker 模式设计；正式开发前，workflow 和后端必须补足 ticker 级交易环境能力。前端不得通过切换全局 profile 冒充 ticker 级模式已经生效。

#### 5.6.4 文档初始化方式

文档初始化方式为二选一：

- 复用当前文档
- 强制初始化

`复用当前文档` 的定义：

- 仅适用于已经存在有效 active revision 的 ticker。
- 保留现有 D1、Event Library、D2、D3 和监测配置成果。
- 不重新执行完整初始化研究链。
- 使用现有 active revision 重新接纳并恢复 Message Bus 和 Runtime。
- ticker 没有有效 active revision 时，不能以“复用当前文档”启动。

`强制初始化` 的定义：

- 创建一次新的完整 ticker 初始化。
- 执行 V2 初始化主链并形成新的候选成果。
- ticker 已有 active revision 时，在新初始化成功激活前继续保留原 active revision，不因新初始化开始而提前替换。

#### 5.6.5 启动结果

- 操作被接受后，将 ticker 加入当前页面缓存中的标的监控列表。
- 需要执行初始化时，立即展示初始化进度卡片。
- 操作失败时保留表单内容并展示失败提示。
- 操作结果不触发 Overview 全页刷新。

### 5.7 标的监控列表

#### 5.7.1 列表工具区

保留两个筛选控件：

- 运行状态筛选；
- 健康状态筛选。

完全移除“标的/回测”切换控件。

#### 5.7.2 桌面端表头顺序

列表从左至右显示以下列：

1. Ticker
2. 监测模式
3. 状态
4. 最近消息
5. Message Bus 状态
6. 当日交易
7. 消息数量
8. 当日成本
9. 操作

“当日交易”“消息数量”和“当日成本”使用页面全局选中的统计窗口，并按第 5.3.2 节规则随多日窗口调整名称。“最近消息”和“Message Bus 状态”始终使用实时状态。

#### 5.7.3 Ticker

- 显示 ticker 符号。
- 点击行进入该 ticker 的默认详情页。
- 行内操作控件不触发行跳转。

#### 5.7.4 监测模式

显示以下三种模式之一：

- 消息监测
- 模拟交易
- 实盘交易

列表中的模式必须表示该 ticker 当前实际生效的模式，不能只显示用户最近一次选择但尚未生效的值。

#### 5.7.5 状态

状态列显示该 ticker 当前运行状态，包括正常运行、初始化中、已暂停、已停止或阻塞等用户可读状态。

`PARTIAL`、`DEGRADED` 等初始化成果质量注解不能直接覆盖 ticker 主状态。只有必要能力不可用并实际阻止 ticker 继续运行时，才显示阻塞。

#### 5.7.6 最近消息

显示该 ticker 最近一条标准消息进入标准消息流的时间。没有标准消息时显示 `暂无数据`。

#### 5.7.7 Message Bus 状态

展示格式：

```text
正常启用源数量 / 异常源数量
```

示例：

```text
4 / 1
```

计数规则：

- 左侧计入已启用且当前正常的 ticker source binding。
- 右侧计入已启用但处于降级、失败、阻塞或终止状态的 ticker source binding。
- `never_polled` 不展示，也不进入左右任一数量。
- 用户主动禁用或已经移除的 source binding 不进入左右任一数量。

#### 5.7.8 当日交易

展示格式和口径与顶层“当日交易”卡片一致，但只统计当前 ticker：

```text
实际成功执行数 / 实际触发数
```

#### 5.7.9 消息数量

显示当前 ticker 在选中统计窗口内成功发布到标准消息流的唯一标准消息数。

该列替代 V1 的 `Worker 处理`，并放置在“当日成本”左侧。

#### 5.7.10 当日成本

显示当前 ticker 在选中统计窗口内的模型 token 实际成本。没有可用成本记录时显示 `暂无数据`。

#### 5.7.11 操作

每个 ticker 保留以下操作：

- 暂停；
- 重启；
- 删除。

暂停和重启用于 ticker 运行状态管理，不等同于初始化失败节点重试。

### 5.8 初始化进度卡片

#### 5.8.1 展示条件

- ticker 初始化尚未完整成功时显示初始化进度卡片。
- 初始化完整成功后立即隐藏整张进度卡片。
- 不保留“已完成”的初始化进度卡片。
- 初始化失败时继续显示进度卡片和重试按钮。

#### 5.8.2 简化步骤

进度卡片将 V2 初始化主链简化为六个前端步骤：

| 顺序 | 前端步骤名称 | 对应 workflow 范围 |
|---|---|---|
| 1 | 基础投研 | D1 与 CDECR 并行执行 |
| 2 | 事件库初始化 | O2 |
| 3 | 预期研究 | D2 |
| 4 | Policy 初始化 | D3 |
| 5 | 消息源准备与激活 | O4 CONFIGURE、O4 DELIVER、REGISTER、Activation Prepare、Activation Commit |
| 6 | 启动运行 | Message Bus Ready、Runtime Ready、Verify Ready |

前端不展示固定总百分比。动态展开的内部 agent 节点不会改变上述六个步骤的数量。

#### 5.8.3 步骤状态

每个步骤只显示以下状态：

- 待开始；
- 进行中；
- 已完成；
- 失败。

归并规则：

- 归并范围内存在失败节点时，该步骤显示失败。
- 没有失败节点但存在运行节点时，该步骤显示进行中。
- 归并范围内所有必需节点均成功时，该步骤显示已完成。
- 其余情况显示待开始。
- `PARTIAL`、`DEGRADED`、NOOP 或其他质量注解不单独增加步骤状态；只要 workflow 将交接物认定为可用并继续执行，该节点按成功处理。

#### 5.8.4 已进行时间

- 每个已经开始的步骤旁显示该步骤已经进行的时间。
- 进行中的步骤显示从该步骤首次开始到当前的持续时间。
- 已完成或失败的步骤显示从首次开始到最终结算的持续时间。
- 并行或归并步骤从其中最早节点开始计时，到该步骤最终结算为止。
- 时间使用简洁格式，例如 `36秒`、`8分钟`、`1小时12分钟`。
- 不增加 attempt 次数、详细时间轴或展开式耗时分析。

#### 5.8.5 失败重试

- 只有初始化失败且允许人工恢复时显示重试按钮。
- 点击重试后，从当前失败节点断点恢复。
- 已成功节点不重新执行。
- 同时存在多个失败节点时，只恢复当前失败节点集合，不重跑整个初始化 workflow。
- 重试为直接操作，不增加节点选择、原因填写或高级重跑选项。
- 重试提交期间禁用按钮，避免重复提交。

### 5.9 删除行为

#### 5.9.1 用户可见结果

删除 ticker 后：

- 停止该 ticker 的运行和监测；
- 从 Overview 默认列表中立即移除；
- 刷新页面、关闭后重新打开或从其他页面返回时，该 ticker 仍不再显示；
- 不删除既有研究产物、初始化历史、交易账本或审计记录。

#### 5.9.2 不提供的能力

- Overview 不提供“已移除标的”筛选。
- Overview 不提供恢复已移除 ticker 的入口。
- 前端不继续显示已移除 ticker 的停止记录。

### 5.10 前端所需数据类型

本节只定义产品展示需要的数据，不规定接口字段名、接口数量、存储位置或查询方式。

#### 5.10.1 页面级实时状态

需要的数据：

- 当前时段枚举；
- 正常 ticker 数量；
- 阻塞 ticker 数量。

#### 5.10.2 页面级统计周期上下文

需要的数据：

- 前一有效交易日；
- 当前语义日是否为有效交易日；
- 本交易日是否允许选择；
- 当前选中的统计周期；
- 当前窗口包含的有效交易日范围；
- 紧邻上一等长窗口包含的有效交易日范围；
- 当前窗口和上一窗口是否具备完整可比数据。

#### 5.10.3 页面级区间统计

需要的数据：

- 被命中的唯一 Policy 数；
- 实际成功执行交易数；
- 实际触发交易数；

- Paper 已实现净收益及是否暂估；
- Live 已实现净收益及是否暂估。
- 除非例行维护触发数外，各可比数值对应的上一等长窗口值；
- 各可比数值的环比百分比或不适用原因。

#### 5.10.4 Ticker 列表项

每个 ticker 需要的数据：

- ticker；
- 当前实际生效的监测模式；
- 当前运行状态；
- 当前健康状态；
- 最近标准消息时间；
- 正常启用 source binding 数；
- 异常 source binding 数；
- 当前选中统计窗口的成功执行数；
- 当前选中统计窗口的实际触发数；
- 当前选中统计窗口的标准消息数；
- 当前选中统计窗口的 token 成本及是否可用；
- 是否存在未完成初始化；
- 是否已从 Overview 移除。

#### 5.10.5 初始化进度

初始化未完整成功时需要的数据：

- 初始化总体是否正在执行、失败或等待恢复；
- 是否允许人工重试；
- 六个简化步骤各自的状态；
- 六个简化步骤各自的已进行时间；
- 当前失败节点集合；
- 重试操作是否正在提交。

### 5.11 页面状态

#### 5.11.1 首次加载

- 首次打开 Overview 且没有缓存时，按模块显示加载占位。
- 不用一个整页加载层遮挡全部页面。
- 首次只加载实时状态、默认前一交易日统计、启动表单所需选项和当前标的列表；本交易日、7 天和 30 天数据在第一次选择时加载。

#### 5.11.2 空列表

没有可显示 ticker 时，在标的监控列表区域显示：

```text
暂无 ticker
```

启动新标的监控模块保持可用。

#### 5.11.3 数据不可用

- 单个统计值不可用时，该值显示 `暂无数据`。
- 单个模块失败不清空其他已经成功加载的模块。
- 不用 `$0`、`0 / 0` 或“正常”伪装未知数据；只有业务事实明确为零时才显示零。

#### 5.11.4 手动刷新失败

- 保留刷新前缓存。
- 显示刷新失败提示。
- 刷新按钮恢复可点击状态。

### 5.12 Workflow 对齐与开发依赖

| 前端需求 | 当前 V2 workflow 事实 | 产品约束 |
|---|---|---|
| 美东 02:00 交易日口径 | 已有共享语义时钟和真实交易日历 | 前端不得用本地自然日替代 |
| 初始化状态 | 父状态为 QUEUED、RUNNING、SUCCEEDED、FAILED | 前端映射为六步简化视图 |
| PARTIAL/DEGRADED | 属于质量诊断，不是父流程 gate | 不得直接显示为初始化失败 |
| 初始化重试 | 已支持失败节点精确 resume | 重试不得变成全局重跑 |
| Policy 命中 | 已有 Policy activation 记录 | 按唯一 Policy 计数 |
| 交易触发 | Runtime Trade intent 与执行账本可区分 | 分子分母必须使用本文档口径 |
| Paper/Live 收益 | 已有环境、订单、fill 和佣金事实 | 前端只展示实际 Exit 已实现收益 |
| ticker 级 Paper/Live | 当前为全局 active execution profile | 正式开发前必须补足 ticker 级能力，前端不得伪装支持 |
| O4 REPAIR | 当前生产运行不触发 O4 REPAIR | 卡片当前固定显示 0 |
| 7天/30天统计 | 已有共享语义时钟和有效交易日历，可确定交易日窗口 | 所有区间值必须按完整有效交易日窗口聚合 |
| 环比 | 当前账本保留时间事实，但 Overview 尚无完整窗口及对比摘要 | 需要提供当前窗口、上一等长窗口及数据完整性事实；前端不得用缺失数据补零 |
| 初始化步骤耗时 | 本地初始化事件有时间事实，公开摘要尚不完整 | 需要向前端提供六步聚合后的状态和耗时 |
| 删除后持久隐藏 | 当前停止记录仍可能出现在列表 | 需要提供可持久识别的“已从 Overview 移除”事实 |
| 页面缓存 | V1 当前使用轮询且返回路由会重新请求 | V2 使用本标签页缓存，只在新打开、人工刷新或首次选择未缓存周期时读取 |

本文档只记录上述能力缺口，不规定其 API、服务或数据库实现方案。

### 5.13 Overview 验收标准

1. `/overview` 只展示 V2 数据，不存在 V1 页面或版本切换入口。
2. 页面标题区不显示数据截至时间或最近刷新时间。

6. 区间统计卡片与实时状态卡片视觉上分成两个独立模块。
7. 页面默认展示前一有效交易日数据。
8. 周期切换包含前一交易日、本交易日、7天和30天，不包含“全部”。
9. 休市日“本交易日”不可选择，7天和30天截至此前最近一个有效交易日。

15. 可比的区间统计值显示相邻上一等长窗口的环比百分比。

18. 启动表单只有 Ticker、三种运行模式、两种文档初始化方式和启动按钮。
19. 页面中不存在任何回测入口或回测任务列表。
20. 标的列表包含规定的九列，消息数量位于成本左侧。
21. Message Bus 的 `never_polled` 不进入正常数或异常数。
22. 初始化进度只显示六个简化步骤，不显示固定总百分比。

25. 页面打开后无轮询、无 SSE 自动更新，页面往返不会重新获取数据。
26. 手动刷新和首次选择尚未缓存的统计窗口是页面打开后仅有的数据刷新入口。

### 7.2 页面标题与缓存规则

### 7.3 Expectation Shell 切换

页面标题下方设置居中的 Shell 切换导航。

### 7.4 当前 Shell 默认显示模式

- 页面默认显示模式以当前选中的一个 Shell 为范围。
- 默认选择该 Shell 中顺序第一的 Expectation Unit；主阅读区显示当前选中 Unit 的全部内容（2026-09-08 浏览器批注修订）。
- 每个 Unit 必须属于当前 Shell，不能混入其他 Shell、其他 D2 运行或其他 ticker 的 Unit。
- 页面需将 D2 JSON 转换成结构化、适合人类阅读的内容，不以原始 JSON 文本作为主要阅读形式。
- 内容表达应根据 D2 业务语义选择实际需要展示的字段，不完整照搬所有底层 JSON 字段。
- State 等指标数据应根据值类型和业务含义选择适合的表达方式。
- 页面需要具备精细、简洁的成品 UI 质量，不增加与 D2 阅读无关的多余设计。
- 本文档不规定上述结构化正文、指标表达或 UI 质量要求的具体设计方案，由执行开发的 Codex 会话在满足业务结构和验收要求的前提下处理。

### 7.5 Shell 内部内容路由

当前 Shell 正文右侧设置独立的内容路由。该路由支持以下查看范围：

1. 上层选择当前 Shell 中的某一个 Expectation Unit；
2. 下层按 State、Realization Factors 和 Potential Gaps 分组，不设置“全部内容”或“全部某类型”入口；
3. 每类内容提供二级条目，可定位具体 State value、Factor 或 Gap。

交互规则：

- Unit 路由项对应一个 `expectation_id`。
- 选择某个 Unit 后，显示该 Unit 的命题、时间范围、State、Realization Factors 和 Potential Gaps。
- 选择 State、Realization Factors 或 Potential Gaps 时，只显示当前选中 Unit 中对应类型的内容；具体条目按稳定业务 ID 定位。
- 点击 Unit 或其他内部路由项不刷新页面，不重新获取 D2，也不改变当前 Shell 或文档版本。
- 内部路由只作用于当前 Shell，不提供跨 Shell 混合聚合。

### 7.6 简化文档状态

右侧保留简化后的文档状态，只显示：

- 当前文档或历史文档标识；
- D2 运行状态；
- 发布状态 `COMPLETE` 或 `PARTIAL`；
- 发布时间。

以下信息不在该简化状态模块中展示：

- citation 状态；
- source D1 运行信息；
- 独立的运行 ID、artifact ID 或其他技术标识；
- 基础投研页面中的其他文档统计字段。

页面默认展示当前 ticker 的 activation revision 实际固定引用的 D2。若该 activation revision 正式接受的是 `PARTIAL` D2，页面必须展示该版本，不得自行替换成仓库中更新或更完整的其他 D2。

### 7.7 简化历史文档

- 保留 D2 历史文档功能。
- 历史列表在用户点击历史文档按钮后以左侧边栏卡片展示运行概况；选择卡片时在主阅读区按需加载该历史 D2 的 Shell 和 Unit 内容。
- 历史列表只显示每次历史 D2 的发布时间及 `COMPLETE` 或 `PARTIAL` 状态。
- 用户可以打开并只读查看某一次历史 D2 的完整 Shell 和 Unit 内容。
- 历史 D2 不提供激活为当前版本、切换现行版本或其他改变 activation revision 的能力。
- 查看历史 D2 不改变当前 ticker activation revision 固定引用的 D2。
- 历史页面中的 Shell、Unit、State、Realization Factors 和 Potential Gaps 必须全部来自同一次 D2 运行。
- 历史文档沿用本页相同的 Shell 切换、默认完整内容和 Shell 内部内容路由能力。

### 7.8 结构化内容范围

D2 正文以 Expectation Shell 和 Expectation Unit 为核心。前端需要理解以下业务数据类型，但不代表必须原样展示每个底层字段：

#### 7.8.1 Shell 数据

- Shell ID；
- 核心问题；
- 边界规则；
- Shell 执行结果；
- 失败阶段及失败信息；
- Shell 所包含的 Unit 及其原始顺序。

#### 7.8.2 Unit 基础数据

- Expectation ID；
- 预期命题；
- 时间范围；
- 所属 Shell。

#### 7.8.3 State 数据

- State 参数及参数定义；
- 参数值类型；
- 当前值及存在时的前值；
- 数值、区间、时间、阶段、方向或证据等不同值类型；
- 数据来源角色；
- 时间范围与数据时间；
- 有效性状态；
- 引用信息。

#### 7.8.4 Realization Factor 数据

- Factor ID；
- 条件；
- 结构角色；
- 当前状态；
- 影响；
- 可观测匹配条件；
- 引用信息。

#### 7.8.5 Potential Gap 数据

- Gap ID；
- 可能发生的变化；
- 推导关系；
- 预期修正；
- 识别条件；
- 引用信息。

前端应基于业务含义选择和组织上述数据，不得把完整对象逐字段平铺，也不得以通用 JSON 查看器代替正式页面。

### 7.9 页面数据需求

预期研究页面需要以下类型的数据：

#### 7.9.1 当前 D2

- ticker；
- ticker 当前 activation revision 固定引用的 D2 标识；
- 当前或历史标识；
- D2 运行状态；
- D2 发布状态；
- 发布时间；
- Shell 有序列表；
- 每个 Shell 的核心问题、边界规则和执行结果；
- 每个成功 Shell 的完整 Unit 列表；
- 每个 Unit 的 State、Realization Factors 和 Potential Gaps；
- 每个失败 Shell 的失败阶段、失败状态、失败信息及已有内容。

#### 7.9.2 历史 D2

- 属于当前 ticker 的历史 D2 列表；
- 每次历史 D2 的发布时间和发布状态；
- 被用户打开的历史 D2 的完整 Shell、Unit 及其结构化内容。

前端只消费上述业务数据，不在本文档中规定数据由哪个 API、服务或数据库查询提供。

### 7.10 页面状态

- 当前 ticker 没有 activation revision 固定引用的 D2 时，页面明确显示没有可查看的预期研究文档，不以其他 D2 或 D1 内容替代。
- D2 不包含 Shell 时，页面不生成虚构 Shell。
- `PARTIAL` D2 中单个 Shell 失败不清空已成功 Shell 的内容。
- 单个 Shell 或 Unit 内容读取失败时，不清空其他已经成功读取的内容。
- 历史 D2 读取失败时，不影响当前 D2 的展示。
- 手动刷新失败时保留刷新前缓存，并提示刷新失败。

### 7.11 Workflow 对齐与支持边界

| 前端需求 | 当前 V2 workflow 事实 | 产品约束 |
|---|---|---|
| 多 Shell | D2 O0 形成有序 Shell Seed，O1 按 Shell 独立并行运行 | 顶层导航以一个 Shell 为切换单位，默认选择产物中的第一个 Shell |
| Shell 名称 | 每个 Shell 提供 `shell_id`、`core_question` 和 `boundary_rule` | 前端使用 `core_question` 作为名称，使用 `shell_id` 保持数据身份 |
| 多 Unit | 每个 Shell 包含有序的 Expectation Unit 列表 | 默认选择当前 Shell 的首个 Unit，按 Unit 切换并提供类型和具体条目的二级菜单 |
| Unit 内容 | 每个 Unit 包含命题、时间范围、State、Realization Factors 和 Potential Gaps | 右侧路由支持单 Unit 和三类跨 Unit 聚合查看 |
| 结构化 JSON | D2 正式文档为 `document2.v2` JSON | 前端按业务含义转换，不使用报告排版或通用 JSON 查看器直接替代 |
| 部分发布 | D2 可发布为 `COMPLETE` 或 `PARTIAL`，每个 Shell 有独立 outcome | `PARTIAL` 中成功与失败 Shell 都保留在导航中，失败状态不得被隐藏或伪装 |
| 失败 Shell 内容 | Shell outcome 已提供 Shell Seed、失败阶段、错误类型和错误信息；最终 Shell artifact 只为成功 Shell 发布 | 失败 Shell 可展示现有正式事实；若需读取其阶段性 Unit 内容，当前发布结果尚未形成可直接供前端读取的完整产物，开发时必须补足前端可消费的数据但不得伪造内容 |
| 当前版本 | D2 bundle 有 `current` 状态，但 ticker 运行实际使用 activation revision 固定引用的版本 | 页面以 activation revision 引用为准，不自行按最新时间或 `current` 选择其他版本 |
| 历史运行 | V2 可列出并读取指定 D2 运行；当前研究接口没有历史版本激活操作 | 历史 D2 只读，不提供激活能力 |
| 前端现状 | 当前前端研究 bundle 类型和页面尚未承载 Document 2 正式结构 | 开发需新增 D2 页面数据类型和结构化内容呈现能力 |
| 页面刷新 | Shell、Unit 和聚合视图均属于同一份 D2 文档的本地查看状态 | 页面内切换不刷新、不触发 workflow，页面往返使用缓存 |

本文档只记录上述 workflow 支持事实和前端约束，不规定 API、后端或数据库实现。

### 7.12 预期研究页面验收标准

1. ticker 级导航新增“预期研究”，页面路由为 `/ticker/:ticker/expectations`。
2. 基础投研页面不再显示任何 D2 内容。
3. 页面默认展示 ticker 当前 activation revision 固定引用的 D2，包括正式接受的 `PARTIAL`。
4. 标题下方按 D2 原始顺序显示 Shell，并使用核心问题作为切换名称。
5. 首次进入页面时默认选择第一个 Shell。
6. `PARTIAL` D2 的成功和失败 Shell 均显示，失败 Shell 保留真实状态及已有内容。
7. 默认选中当前 Shell 的首个 Unit，主阅读区显示该 Unit 的全部内容。
8. 右侧内容路由切换 Unit，并按类型定位该 Unit 的具体 State、Factor、Gap；索引随页面滚动保持可用，超长索引内部滚动。
9. Unit 和聚合内容切换不刷新页面、不重新读取 D2、不触发 workflow。
10. 页面不跨 Shell、跨 D2 运行或跨 ticker 混合 Unit 和结构化内容。
11. D2 JSON 被转换为结构化的人类可读内容，不以原始 JSON 或通用 JSON 查看器作为正式页面。
12. 页面根据业务逻辑选择需要展示的 State 等字段，不完整平铺全部底层字段。
13. 文档状态只显示当前/历史标识、运行状态、`COMPLETE/PARTIAL` 和发布时间。
14. 历史列表只显示发布时间及 `COMPLETE/PARTIAL`，历史 D2 可只读打开但不能激活。
15. 页面不存在轮询、SSE、窗口聚焦或定时自动刷新，页面往返使用本标签页缓存。
16. 页面只展示和消费 V2 数据，不读取 V1 D2 或缓存作为回退。
17. 首次只加载 Shell 目录和默认第一个 Shell；其他 Shell、历史列表及历史正文按首次访问加载并缓存。

## 8. 交易策略页面

### 8.1 页面目标与范围

原“执行策略”页面改名为“交易策略”，从 Known Events 与 Policy 混合页面调整为仅展示 Policy 的页面。

- ticker 级导航名称和页面标题均改为“交易策略”。
- 路由保持 `/ticker/:ticker/strategy` 不变。
- 页面只展示当前 ticker 对应的 V2 Document 3 Policy 数据。
- 页面完全移除 Known Events 列表、Known Events 数量、Expectation 筛选和相关说明。
- 页面不提供独立的文档状态板块。
- 除本文明确记录的结构和功能要求外，不在本需求中规定具体视觉设计方式或视觉效果。

本页包含七个功能模块：

1. 页面标题与全局操作；
2. Shell 切换；
3. KPI 统计；
4. 周期与 Policy 状态筛选；
5. Policy 结构化正文；
6. 侧边 Policy 路由；
7. Policy 变更时间线。

### 8.2 页面标题与全局操作

- 页面标题显示“交易策略”。
- ticker 标识继续作为当前查看对象显示。
- 页面标题区域保留手动刷新入口。
- 原“下载 Markdown”改为页面全局小按钮。
- 全局下载始终导出当前 activation revision 固定引用的完整 PolicySet。
- 下载内容不受当前 Shell、周期、状态筛选或当前 Policy 选择影响。
- 页面不保留原文档状态板块。

### 8.3 缓存与刷新

- 页面继承第 4 节的缓存与刷新原则。
- 页面首次打开时只读取当前 activation revision、Shell 目录、默认第一个 Shell 的当前生效 Policy 首屏、默认周期 KPI 和 Policy 路由摘要；切换到其他页面再返回时使用本标签页缓存。
- 页面不进行轮询，不因推送事件、窗口聚焦或固定时间间隔自动刷新。
- Shell、周期、状态筛选、Policy 路由和变更时间线操作不触发 D3 workflow或整页刷新；第一次选择尚无缓存的数据范围时只读取该范围。
- Policy 完整正文只在选中对应 Policy 时加载；变更时间线只在用户打开时加载；完整 PolicySet 只在用户点击下载时取得。
- 用户手动刷新时更新当前 activation revision、当前 Shell、周期、筛选、Policy 和已经打开的时间线，不预取其他范围。
- 手动刷新失败时保留刷新前缓存并提示失败。

### 8.4 Shell 切换

页面标题下方设置居中的 Shell 切换导航。

- 具体 Shell 按当前 activation revision 固定引用的 D2 原始顺序排列。
- 每个具体 Shell 使用 D2 中对应的 `core_question` 作为前端名称，并使用 `shell_id` 保持数据身份。
- “全部 Shell”固定排列在所有具体 Shell 的最右侧。
- 页面首次进入时默认选择第一个具体 Shell，不默认选择“全部 Shell”。
- 选择具体 Shell 时，显示 `source_refs` 中至少包含该 `shell_id` 的 Policy。
- 一个 Policy 可以引用多个 Shell；该 Policy 在任一相关 Shell 下都可以被筛选到，不强制指定唯一主 Shell。
- 同一个 Policy 在“全部 Shell”中只显示一次。
- Shell 切换与 Policy 状态筛选共同生效，最终结果取两者交集。

### 8.5 KPI 统计

顶部 KPI 按以下顺序展示：

1. 生效数量；
2. 多空方向比例；
3. 周期新增；
4. 周期命中；
5. 周期修改；
6. 周期失效；
7. 周期交易执行。

#### 8.5.1 生效数量

- 统计当前 activation revision 中仍可被 Runtime 命中的唯一 Policy 数。
- 已经命中过并被消费的一次性 `policy_id + activation_revision` 不再计入生效数量。
- 已被 D3 retire 的 Policy 不计入。
- 本 KPI 为当前状态，不受周期切换影响，不显示环比。

#### 8.5.2 多空方向比例

- 统计当前生效 Policy 中 LONG 与 SHORT 的数量占比。
- LONG 和 SHORT 分别以百分比展示。
- 已消费或已 retire 的 Policy 不进入比例计算。
- 本 KPI 为当前状态，不受周期切换影响，不显示环比。

#### 8.5.3 周期新增

- 统计所选周期内首次进入正式 PolicySet 的唯一 Policy 数。
- 同一 Policy 在窗口内被后续版本再次发布时不重复计为新增。
- 显示相邻上一等长窗口的环比变化百分比。

#### 8.5.4 周期命中

- 统计所选周期内被有效命中的唯一 `policy_id + activation_revision` 数。
- 同一 Policy revision 被多条消息或多个 Case 命中时只计一次。
- 只出现候选匹配但未形成正式 Policy activation 的记录不计入。
- 显示相邻上一等长窗口的环比变化百分比。

#### 8.5.5 周期修改

- 统计所选周期内发生实质内容修改的唯一 Policy 数。
- 同一 Policy 在窗口内被修改多次时只计一个唯一 Policy。
- 没有改变 Policy 正式内容的重复发布或幂等写入不计入。
- 显示相邻上一等长窗口的环比变化百分比。

#### 8.5.6 周期失效

- 只统计所选周期内被 D3 明确 retire 的唯一 Policy 数。
- Policy 一次性命中并被 Runtime 消费不属于本 KPI 的“失效”。
- 同一 Policy 在窗口内只有一个唯一计数。
- 显示相邻上一等长窗口的环比变化百分比。

#### 8.5.7 周期交易执行

- 统计所选周期内与 Policy 关联且由 Broker 实际成功执行的交易数量。
- 只形成 Runtime Trade intent、但未产生实际成交的记录不计入成功执行。
- 部分成交只要已经产生实际 fill，计为成功执行一次。
- 同一次交易的多笔 fill 不重复计为多次策略执行。
- 显示相邻上一等长窗口的环比变化百分比。

### 8.6 周期切换与环比

周期切换包含：

- `前一天`
- `当天`
- `7天`
- `30天`
- `全部`

规则如下：

- 页面首次进入时默认选择“前一天”。
- “前一天”和“当天”使用 DoxAgent 美东 02:00 语义交易日及真实美股交易日历。
- “7天”指截至当前语义日最近 7 个有效美股交易日；当前语义日不是交易日时，截至此前最近一个有效交易日。
- “30天”指截至当前语义日最近 30 个有效美股交易日；当前语义日不是交易日时，截至此前最近一个有效交易日。
- “全部”覆盖当前 ticker 可用的全部保留历史。
- 周期只影响周期新增、周期命中、周期修改、周期失效、周期交易执行及对应筛选，不影响生效数量和多空方向比例。

环比窗口：

- 前一天与再前一个有效交易日比较；
- 当天与前一个有效交易日比较；
- 7 天与此前紧邻的 7 个有效交易日比较；
- 30 天与此前紧邻的 30 个有效交易日比较；
- 全部不显示环比。

环比规则：

- 使用 `(当前窗口值 - 上一窗口值) / 上一窗口值 × 100%`。
- 当前或上一窗口没有完整数据时显示 `不适用`。
- ticker 运行历史不足完整当前窗口和完整上一窗口时显示 `不适用`。
- 上一窗口值为 0 时显示 `不适用`，不计算百分比。
- 不用缺失数据补零后计算环比。

### 8.7 Policy 状态筛选

筛选为单选，包含：

- `当前生效`，默认选择；
- `周期新增`；
- `周期命中`；
- `周期修改`；
- `周期失效`；
- `周期交易执行`。

筛选规则：

- “当前生效”显示当前 activation revision 中仍可被 Runtime 命中、未消费且未被 retire 的 Policy，不受周期切换影响。
- 其他五个筛选项只显示当前所选周期内符合对应事实的 Policy。
- 周期新增显示首次进入正式 PolicySet 时对应的 Policy revision。
- 周期命中显示命中事件对应的 Policy revision。
- 周期交易执行显示实际成功交易对应的 Policy revision。
- 周期修改显示修改后的 Policy revision。
- 周期失效显示失效前最后一个 Policy revision。
- Shell 与状态筛选取交集。
- 一个 Policy 在同一筛选结果中只形成一个 Policy 路由项，不因关联多个事件或多个 Shell 重复显示。

### 8.8 侧边 Policy 路由

- Policy 正文侧边设置 Policy 路由。
- 路由以 Policy 为粒度排列，前端名称使用 Policy 的 `title`，数据身份使用 `policy_id`。
- 路由只显示当前 Shell 与当前状态筛选交集中的全部 Policy。
- 页面默认显示第一个 Shell 下符合状态筛选的全部 Policy，正文按列表连续排列；分页通过居中的加载更多组件追加。
- 切换 Shell 或状态筛选后，正文与侧边索引同步切换到该范围的 Policy 列表。
- 点击侧边 Policy 索引只滚动定位到对应正文，不替换为单篇 Policy，不进行整页刷新或触发 workflow；已读取正文使用缓存。
- 同名但 `policy_id` 不同的 Policy 保持为不同记录，不按名称错误合并。

### 8.9 Policy 结构化正文

- 页面以一个 Policy 为基本单位展示 D3 内容。
- D3 JSON 需转换为结构化、适合人类阅读的正式页面内容，不以原始 JSON 文本作为主要阅读形式。
- 页面需根据 Policy 业务含义选择需要展示的字段，不完整照搬所有底层 JSON 字段。
- 多个激活条件必须按当前 `document3.v2.2` 固定 OR 语义正确表达，不得误示为需要同时满足。
- 页面需要具备精细、简洁的成品 UI 质量，不增加与 Policy 阅读和判断无关的多余设计。
- 本文档不规定 Policy 正文结构、字段取舍或 UI 质量要求的具体设计方案，由执行开发的 Codex 会话在满足业务语义和验收要求的前提下处理。

前端需要理解的 D3 数据类型包括但不限于：

- Policy ID；
- Policy 名称；
- LONG 或 SHORT 决策方向；
- Policy 引用的 Shell、Expectation Unit 和 Potential Gap；
- 匹配范围；
- 一个或多个独立充分的激活条件；
- 每个激活条件的 criterion；
- 每个激活条件的 reference state；
- 每个激活条件的 trigger boundary；
- PolicySet 版本和 activation revision；
- 当前是否已被 Runtime 消费；
- 与该 Policy 相关的命中、修改、失效和实际交易事实。

上述数据范围用于说明前端所需业务事实，不要求页面逐字段平铺。

### 8.10 Policy 变更时间线

- 原历史版本入口改为“变更时间线”。
- 入口位于页面全局操作区，点击后从页面左侧展开边栏，不从属于某个 Policy。
- 左侧边栏可用面积应大于原历史版本边栏。
- 时间线为只读，不提供历史 PolicySet 激活、切换现行版本或修改 Policy 的能力。
- 时间线只记录 Policy 定义生命周期事件，不记录 Policy 命中或交易执行事件。
- 事件类型只包含新增、实质修改和失效/retire。
- 每次事件显示变更发生时间、事件类型、相关 Policy 及变更简略内容。
- 变更发生时间以对应正式 PolicySet 版本的发布时间为准。
- 同一次 PolicySet 发布涉及多个 Policy 时，每个 Policy 的变更事实均需可识别。
- 打开或查看时间线不进行整页刷新，不改变当前 Shell、筛选、Policy 或 activation revision；第一次打开时按当前 ticker 的全部 Shell、全部保留周期加载全局时间线，之后使用缓存。
- 本文档不规定时间线和左侧边栏的具体视觉设计。

### 8.11 页面数据需求

#### 8.11.1 当前策略与 Shell

- ticker；
- 当前 activation revision；
- 当前 activation revision 固定引用的 D2 和 D3；
- D2 Shell 的 `shell_id`、`core_question` 和原始顺序；
- 当前 PolicySet 版本、发布时间和全部 Policy；
- 每个 Policy 的完整 D3 结构化数据；
- 已消费的 `policy_id + activation_revision` 集合。

#### 8.11.2 周期统计与筛选

- 当前所选周期的开始、结束和有效交易日集合；
- 相邻上一等长窗口及其完整性；
- 窗口内唯一 Policy activation 记录；
- 窗口内 Policy 新增、实质修改和 retire 记录；
- 窗口内关联 Policy 的 Broker 实际成功交易记录；
- 各 KPI 当前值、上一窗口值、环比百分比或不适用原因。

#### 8.11.3 变更时间线

- 每个 Policy 变更事件的发生时间；
- 事件类型；
- Policy ID 和 Policy 名称；
- 变更前后对应的 PolicySet 版本；
- 简略变更内容；
- 修改后的 Policy revision 或失效前最后一个 Policy revision。

前端只消费上述业务数据，不在本文档中规定数据由哪个 API、服务或数据库查询提供。

### 8.12 页面状态

- 当前 ticker 没有可用 activation revision 或没有其固定引用的 D3 时，页面明确显示没有可查看的交易策略，不读取其他版本替代。
- 当前筛选结果没有 Policy 时，Policy 路由和正文显示无匹配结果，不展示筛选范围外的 Policy 作为替代。
- 单个 Policy 内容不可用时，不清空其他已经成功读取的 Policy。
- KPI 单项不可用时只标记该项不可用，不清空 Policy 正文。
- 变更时间线不可用时不影响当前 Policy 展示。
- 手动刷新失败时保留刷新前缓存并提示失败。

### 8.13 Workflow 对齐与支持边界

| 前端需求 | 当前 V2 workflow 事实 | 产品约束 |
|---|---|---|
| PolicySet | D3 正式产物为 `document3.v2.2` JSON PolicySet | 页面只展示 V2 Policy，不复用现有 V1 Policy 字段语义 |
| Shell 归属 | Policy 的 `source_refs` 可包含多个 `shell_id + expectation_id + gap_id` | 一个 Policy 可出现在多个相关 Shell，全部 Shell 中只显示一次 |
| Shell 名称 | D3 只有 Shell ID，核心问题和 Shell 顺序来自 activation revision 固定引用的 D2 | 页面必须使用同一 activation revision 的 D2 建立名称和顺序，不得关联其他 D2 |
| 当前生效 | 当前 PolicySet 提供 Policy；Runtime activation 账本记录已消费的 `policy_id + activation_revision` | 生效数量和默认筛选需排除已消费 revision，当前前端摘要尚未直接提供这一组合事实 |
| 固定 OR | 每个 Policy 的多个 activation conditions 使用固定 OR 语义 | 页面不得表达成全部条件同时满足 |
| 命中 | Runtime 已持久记录 Policy activation、Policy revision 和命中时间 | 周期命中按唯一 `policy_id + activation_revision` 统计 |
| 新增、修改与失效 | D3 保存不可变 PolicySet 版本，并以首次出现、upsert 和 retire 表达 Policy 生命周期 | 当前没有产品级逐 Policy 变更事件摘要，需要形成可供前端读取的周期事实和时间线事实，但本文档不规定实现方式 |
| 交易执行 | Runtime Trade 记录和交易执行账本可通过 Policy ID、activation revision 和交易身份关联；Trade intent 与 Broker fill 可区分 | 周期交易执行只统计实际成功成交，不统计单纯意图或拒单 |
| KPI 周期摘要 | 底层版本、activation、交易和时间事实存在，但当前交易策略页面没有这些聚合数据 | 需要向前端提供本文定义的窗口值、对比值和完整性事实，前端不得自行拼接不完整来源 |
| Policy 下载 | D3 源产物为 JSON，现有页面提供 Markdown 下载行为 | 全局按钮下载完整当前 PolicySet，具体转换方式不在本 PRD 中设计 |
| 变更时间线 | 当前只有版本元数据和完整 PolicySet，没有现成的逐 Policy 时间线 | 前端不得用版本号列表冒充变更事件和简略内容 |
| 前端现状 | 当前页面使用 Known Events 和旧 Policy DTO，并存在 SSE、聚焦和定时刷新 | V2 页面移除 Known Events，改用 D3 正式结构并遵守低频缓存、首次未缓存范围按需加载和人工刷新规则 |

本文档只记录上述 workflow 支持事实和前端约束，不规定 API、后端或数据库实现。

### 8.14 交易策略页面验收标准

1. ticker 级导航和页面标题由“执行策略”改为“交易策略”，路由继续使用 `/ticker/:ticker/strategy`。
2. 页面不显示 Known Events、Expectation 筛选或独立文档状态板块。
3. 标题下方先按 D2 顺序排列具体 Shell，“全部 Shell”位于最右侧。
4. 页面默认选择第一个具体 Shell，不默认选择“全部 Shell”。
5. 一个 Policy 在所有相关 Shell 中均可找到，在“全部 Shell”中只显示一次。
6. 顶部依次展示生效数量、多空方向比例、周期新增、周期命中、周期修改、周期失效和周期交易执行。
7. 生效数量和多空方向比例只反映当前可执行状态，不受周期影响且不显示环比。
8. 周期切换包含前一天、当天、7天、30天和全部，默认前一天。
9. 7天和30天均按有效美股交易日计算；全部不显示环比。
10. 周期 KPI 使用紧邻上一等长窗口计算环比，历史不足或上一窗口值为0时显示“不适用”。
11. 周期交易执行只统计与 Policy 关联且实际产生 Broker fill 的成功交易。
12. 筛选为单选且默认当前生效，并包含周期新增；其他筛选项受当前周期控制。
13. Shell 与状态筛选取交集，侧边 Policy 路由只显示交集中的 Policy。
14. Policy 索引以 `title` 为名称、以 `policy_id` 为身份，定位当前 Shell 连续列表中的对应正文。
15. Policy JSON 被转换为结构化的人类可读内容，不以原始 JSON 或通用 JSON 查看器作为正式页面。
16. 多个激活条件按固定 OR 语义表达，页面不完整平铺所有底层字段。
17. 原历史版本替换为左侧变更时间线，边栏面积大于原历史版本边栏。
18. 时间线只记录新增、实质修改和 retire，显示发生时间及简略变更内容，不记录命中和交易。
19. 时间线不提供历史版本激活或现行版本切换能力。
20. 全局小按钮下载当前 activation revision 的完整 PolicySet，不受筛选和页面选择影响。
21. 页面内 Shell、周期、筛选、Policy 和时间线操作均不触发 workflow或整页刷新；未缓存范围只进行一次目标内容读取。
22. 页面不存在轮询、SSE、窗口聚焦或定时自动刷新，页面往返使用本标签页缓存。
23. 页面只展示和消费 V2 数据，不读取 V1 Policy 或缓存作为回退。
24. Policy 完整正文、变更时间线和完整下载内容均按用户实际操作加载，页面首次打开不预取。

## 9. 事件库页面

### 9.1 页面目标与范围

事件库是 ticker 级新增页面，用于查看 V2 Canonical Event Library 当前完整内容，以及 O2 每日交给 O3 的 Reference View Delta。

- ticker 级导航名称和页面标题均为“事件库”。
- 页面路由为 `/ticker/:ticker/events`。
- ticker 级导航中，本页排列在“基础投研”之后、“预期研究”之前。
- 页面只展示当前 ticker 的 V2 Event Library 数据，不读取 V1 Known Events、V1 缓存或其他 ticker 数据作为回退。
- 本页不设置文档状态板块、文档历史版本板块或常驻侧边路由。
- 除本文明确记录的结构和功能要求外，不在本需求中规定具体视觉设计方式、视觉效果或字段排版方案。

本页包含六个功能模块：

1. 页面标题与模式切换；
2. KPI 统计与周期切换；
3. 完整事件筛选；
4. 新增事件日期选择；
5. Event-Fact 结构化正文；
6. 隐藏式事件索引。

### 9.2 页面标题、模式与刷新

- 页面标题显示“事件库”，并显示当前 ticker 标识。
- 页面标题区域保留手动刷新入口。
- 页面标题下方提供“完整事件”和“新增事件”两个显示模式的切换入口。
- 页面首次进入时默认选择“完整事件”。
- 两种模式对应两个不同业务数据源，不得把“新增事件”实现成对当前完整事件列表的普通前端筛选。
- 模式切换、周期切换、筛选、日期选择和事件索引定位均不触发 workflow。
- 页面继承第 4 节的低频缓存规则：页面往返使用本标签页缓存，不轮询、不监听 SSE、不因窗口聚焦或固定时间间隔自动刷新。
- 首次打开只读取“完整事件”默认筛选的首屏 Event 摘要、默认周期 KPI 和当前索引所需摘要，不读取全部 Event/Fact 正文或历史日 Delta。
- 第一次切换模式、周期、筛选或日期时，只读取对应范围的首屏或目标数据；已读取范围再次选择时使用缓存。
- Event/Fact 完整内容在用户打开对应对象时按需加载，隐藏式索引不预取所有对象正文。
- 用户手动刷新时只更新当前模式、周期、筛选或日期及当前已经打开的 Event/Fact，不读取其他日期或其他筛选范围；失败时保留刷新前缓存并提示失败。

### 9.3 两种显示模式的数据语义

#### 9.3.1 完整事件

- “完整事件”对应当前已发布版本的完整 Canonical Event Library。
- 该模式包含当前库内的 Canonical Event 及其 Canonical Fact，不等同于仅供 D2/D3 使用的 Reference View。
- 页面依据第 9.6 节的筛选状态显示当前生效或所选周期内新增、修改、失效的 Event/Fact。
- 页面不提供历史 Library Version 的人工激活或现行版本切换能力。

#### 9.3.2 新增事件

- “新增事件”是产品显示名称，实际业务数据源固定为所选语义交易日 O2 交给 O3 的完整 Reference View Delta。
- 该数据包含三类变化：新进入 Reference View 的 Event、内容发生变化且继续进入 Reference View 的 Event，以及从 Reference View 移除的 Event ID。
- 本模式不得将该数据错误解释为“仅首次创建稳定 Event ID 的记录”。
- 本模式不得使用当前完整 Canonical Event Library 按日期筛选后冒充 Reference View Delta。
- 页面应能够区分 Delta 中的新增、修改和移除事实；用于展示的结构化 Event/Fact 内容必须与该次 Delta 的起止 Library Version 对应。
- 一个交易日没有形成 Reference View 变化时，显示该日没有新增事件数据，不以其他日期或当前完整事件替代。

### 9.4 KPI 统计

顶部 KPI 按以下顺序展示：

1. 生效数量；
2. 周期新增；
3. 周期修改；
4. 周期失效。

所有 KPI 均使用 `Event 数量 / Fact 数量` 的成对口径，例如 `13/23`。Event 和 Fact 必须分别统计，不得把 Fact 数量解释成 Event 包含的字段数量。

#### 9.4.1 生效数量

- Event 统计当前状态为 `ACTIVE` 的唯一 Canonical Event 数。
- Fact 统计当前仍属于生效 Event 的唯一 Canonical Fact 数。
- 同一 Fact 不因出现在重复读取结果中被重复计数。
- 本 KPI 表示当前状态，不受周期切换影响，不显示环比。

#### 9.4.2 周期新增

- Event 统计所选周期内首次分配稳定 E# 身份的唯一 Event 数。
- Fact 统计所选周期内首次分配稳定 F# 身份的唯一 Fact 数，包括加入新 Event 或既有 Event 的新 Fact。
- 同一 E#/F# 在窗口内只计一次。
- Event 与 Fact 分别显示相邻上一等长窗口的环比变化百分比。

#### 9.4.3 周期修改

- Event 统计所选周期内既有 E# 发生实质内容修订的唯一 Event 数。
- Fact 统计所选周期内既有 F# 发生实质内容修订的唯一 Fact 数。
- Event 的普通修订只计该 Event；其 Fact 没有发生实际变化时，不连带计入 Fact 修改。
- 同一 E#/F# 在窗口内发生多次修改时只计一次。
- Event 与 Fact 分别显示相邻上一等长窗口的环比变化百分比。

#### 9.4.4 周期失效

- Event 统计所选周期内进入 `SUPPRESSED` 或 `MERGED` 状态的唯一 Event 数。
- Fact 统计所选周期内不再属于任何生效 Event、因而被抑制的唯一 Fact 数。
- 同一 E#/F# 在窗口内只计一次。
- Event 与 Fact 分别显示相邻上一等长窗口的环比变化百分比。

### 9.5 周期切换与环比

周期切换包含：

- `前一天`
- `当天`
- `7天`
- `30天`
- `全部`

页面首次进入时默认选择“前一天”。周期与环比规则完整复用第 8.6 节交易策略页面口径：

- “前一天”和“当天”使用 DoxAgent 美东 02:00 语义交易日及真实美股交易日历；
- “7天”和“30天”分别指截至语义日最近 7 个和 30 个有效美股交易日；语义日不是交易日时，截至此前最近一个有效交易日；
- “全部”覆盖当前 ticker 可用的全部保留历史；
- 前一天与再前一个有效交易日比较，当天与前一个有效交易日比较，7天和30天与此前紧邻的等长有效交易日窗口比较；
- 使用 `(当前窗口值 - 上一窗口值) / 上一窗口值 × 100%`；
- “全部”不显示环比；
- 当前窗口或上一窗口数据不完整、ticker 运行历史不足两个完整窗口，或者上一窗口值为 0 时，显示“不适用”，不得用缺失数据补零计算。

周期切换只影响周期新增、周期修改、周期失效及“完整事件”中的对应筛选结果，不影响生效数量，也不改变“新增事件”模式当前选择的单日正文。

### 9.6 完整事件筛选

“完整事件”模式提供单选筛选，包含：

- `当前生效`，默认选择；
- `周期新增`；
- `周期修改`；
- `周期失效`。

筛选规则如下：

- “当前生效”显示当前状态为 `ACTIVE` 的 Event 及其当前 Fact，不受周期切换影响。
- “周期新增”显示所选周期内首次创建的 Event，以及包含周期内首次创建 Fact 的相关 Event。
- “周期修改”显示所选周期内发生实质修改的 Event/Fact 对应内容。
- “周期失效”显示所选周期内失效 Event 的失效前最后一个版本，以及在周期内被抑制的 Fact 所属事实。
- 同一 E#/F# 在一个筛选结果中只形成一个唯一对象，不因窗口内多次变化重复显示。
- 筛选结果变化后，Event-Fact 正文和隐藏式事件索引同步使用新的结果集合。

### 9.7 新增事件日期选择

- “新增事件”模式不提供第 9.6 节的状态筛选。
- 该模式改为按单个语义交易日选择 Reference View Delta。
- 页面首次进入“新增事件”模式时默认选择前一个有效交易日。
- 日期使用 Persistent Runtime Daily Close 的 `trading_date`，即 DoxAgent 美东 02:00 语义交易日，不使用 Event 的实际发生日或数据库写入时间代替。
- 用户可以选择过去可用的语义交易日查看对应 Delta。
- 日期选择只影响“新增事件”正文和对应事件索引，不改变顶部 KPI 的周期选择。
- 日期切换不进行整页刷新；已读取过的日期结果优先使用本标签页缓存，尚未读取的日期在用户选择时读取一次。

### 9.8 Event-Fact 结构化正文

- 页面以 Event 为上层、Fact 为下层展示 Event-Fact 层级关系。
- Canonical Event Library 和 Reference View Delta 的结构化数据需要转换为适合人类阅读的正式页面内容，不以原始 JSON、数据库字段表或通用 JSON 查看器作为正式展示。
- 页面根据 Event Library 业务含义选择需要展示的 Event 和 Fact 字段，不完整平铺全部底层字段。
- 页面应保留区分 Event 与 Fact、对象身份、发生时间、事件类型、业务状态、核心内容、Event-Fact 归属及必要关系所需的业务事实。
- “新增事件”模式需要明确区分本次 Delta 中的新增、修改和移除，不将三者混为同一变化类型。
- 页面需要具备结构化、精细、简洁的成品 UI 质量，不增加与 Event/Fact 阅读无关的内容。
- 本文档不规定正文结构、具体字段取舍或 UI 质量要求的实现方案，由执行开发的 Codex 会话在满足业务语义和验收要求的前提下处理。

前端需要理解的数据类型包括但不限于：

- Event ID、标题、事件类型和发生时间；
- Event occurrence time precision；
- Event 当前状态；
- Event canonical summary；
- Event 是否进入 Reference View；
- Event 的 related、derived-from 和 supersedes 关系；
- Fact ID、proposition、assertion state、subject time 和 fact occurrence time；
- Event 与 Fact 的当前成员关系；
- Event/Fact 首次创建版本、发生实质修改的版本及失效版本；
- Reference View Delta 的起始版本、目标版本、变化 Event 及移除 Event；
- 每项 Delta 变化属于新增、修改或移除的业务事实。

上述范围用于说明页面所需业务事实，不要求页面逐字段平铺。

### 9.9 隐藏式事件索引

- Event 数量较多，不设置常驻侧边事件路由。
- 页面提供类似 ChatGPT 网页版右侧隐藏式路由菜单行为的事件索引，并以紧凑方式排列当前结果中的 Event。
- 索引只包含当前显示模式、筛选或日期范围内实际显示的 Event，不列出当前结果之外的 Event。
- 选择索引中的 Event 后，定位到当前完整正文中的对应 Event，不把正文切换成只展示单个 Event。
- Event 索引操作不进行整页刷新，也不改变当前模式、周期、筛选或日期；目标 Event/Fact 正文尚未缓存时只读取该对象详情。
- 同名但 Event ID 不同的 Event 必须保持为不同记录，不按标题错误合并。
- 本文档不规定隐藏式菜单的具体尺寸、样式、动效或触发控件设计。

### 9.10 排序规则

- 当前结果中的 Event 按 `occurred_at` 由近到远排列。
- `occurred_at` 缺失或 `occurrence_time_precision` 为 `UNKNOWN` 的 Event 放在所属结果末尾。
- 同一个 Event 内的 Fact 保持其业务数据源顺序，前端不按 `fact_occurred_at` 重新排序。
- Event 排序不改变 Event-Fact 归属关系，也不跨 Event 合并 Fact。
- “完整事件”和“新增事件”两种模式均执行相同的 Event 排序规则。

### 9.11 页面数据需求

#### 9.11.1 完整事件

- ticker；
- 当前已发布 Library Version 及其发布时间；
- 当前版本的完整 Canonical Event 和 Canonical Fact；
- Event/Fact 的稳定身份、当前状态和成员关系；
- Event/Fact 的创建、实质修改和失效事实及对应语义交易日；
- 周期筛选所需的对象版本事实。

#### 9.11.2 新增事件

- 可选择的历史 `trading_date`；
- 每个交易日对应的起始 Library Version 和目标 Library Version；
- 该次 O2→O3 Reference View Delta 中新增或修改 Event 的结构化 Event/Fact 内容；
- 从 Reference View 移除的 Event ID，以及满足页面结构化阅读所需的移除前对象事实；
- 每项变化属于新增、修改或移除的明确分类。

#### 9.11.3 KPI 与环比

- 当前生效的唯一 Event/Fact 数；
- 当前窗口和相邻上一等长窗口的有效交易日集合及完整性；
- 两个窗口内首次创建、实质修改、失效的唯一 Event/Fact 集合；
- 各 KPI 的 Event 值、Fact 值、对应上一窗口值、环比百分比或不适用原因。

前端只消费上述业务数据，不在本文档中规定数据由哪个 API、后端服务或数据库查询提供。

### 9.12 页面状态

- 当前 ticker 没有已发布 Event Library 时，页面明确显示没有可查看的事件库，不读取 V1 Known Events 或其他 ticker 数据替代。
- “完整事件”筛选没有结果时，正文和事件索引显示无匹配结果。
- 所选日期没有 Reference View Delta 变化时，“新增事件”正文和事件索引显示该日无数据。
- 单个 Event 或 Fact 内容不可用时，不清空其他已经成功读取的内容。
- KPI 单项不可用时只标记该项不可用，不清空正文。
- 隐藏式事件索引不可用时不影响当前正文阅读。
- 手动刷新失败时保留刷新前缓存并提示失败。

### 9.13 Workflow 对齐与支持边界

| 前端需求 | 当前 V2 workflow 事实 | 产品约束 |
|---|---|---|
| 完整事件 | Event Library 按已发布版本保存完整 Canonical Event、Canonical Fact、对象状态和成员关系 | 页面读取完整当前发布版本，不以 Reference View 代替完整 Library |
| Event-Fact 层级 | Canonical Event 包含完整当前 Fact membership；Event 与 Fact 使用稳定 E#/F# 身份 | 页面保持 Event-Fact 层级和稳定身份，不按标题或正文合并对象 |
| 对象状态 | Event 状态包含 `ACTIVE`、`SUPPRESSED`、`MERGED`；失去全部生效 membership 的 Fact 会被抑制 | 生效和失效 KPI 使用正式对象状态和成员关系，不依据页面是否可见自行推断 |
| O2→O3 日度数据 | Daily Close 以 `trading_date` 运行，并向 O3 传递 `ReferenceViewDeltaSnapshot` | “新增事件”使用该独立日度数据源，不从完整 Library 做日期筛选模拟 |
| Delta 内容 | 当前 Reference View Delta 包含新增或修改后的 Reference Event 文本，以及移除 Event ID | 页面要求结构化 Event/Fact 和新增、修改、移除分类；当前还没有完全满足前端读取需要的现成结构化摘要 |
| 移除项 | 当前 Delta 对移除对象只持久化 `removed_event_ids` | 页面若要结构化显示移除对象，需要获得与起止版本一致的移除前对象事实；本文档不规定提供方式 |
| 周期统计 | Event/Fact 的创建版本、revision、状态和 membership 历史可用于识别对象变化，但当前前端没有产品级窗口聚合 | 需要向前端提供本文定义的窗口值、比较值和完整性事实，前端不得自行拼接不完整来源 |
| 排序时间 | Event 使用 `occurred_at` 和 occurrence precision；部分历史对象可能缺失精确时间或为 `UNKNOWN` | 页面按正式 Event occurrence 排序，未知时间置后，不使用发布时间冒充发生时间 |
| 前端现状 | 当前前端没有独立事件库路由，旧交易策略页曾混合展示 Known Events | V2 新增独立事件库页；交易策略页继续只展示 Policy，不复用旧 Known Events DTO |

本文档只记录上述 workflow 支持事实和前端约束，不规定 API、后端或数据库实现。

### 9.14 验收标准

1. ticker 级导航新增“事件库”，路由为 `/ticker/:ticker/events`，排列在基础投研之后、预期研究之前。
2. 页面标题下提供“完整事件”和“新增事件”两个模式，默认选择完整事件。
3. 完整事件读取当前已发布的完整 Canonical Event Library，不以 Reference View 或 V1 Known Events 代替。
4. 新增事件读取所选 `trading_date` 的完整 O2→O3 Reference View Delta，不由当前完整事件列表筛选生成。
5. 新增事件能够区分 Delta 中的新增、修改和移除，不将产品名称解释为纯新增 Event ID 集合。
6. 顶部依次展示生效数量、周期新增、周期修改和周期失效，全部采用 Event/Fact 成对数量。
7. 生效数量不受周期影响且不显示环比；其他三项分别显示 Event 和 Fact 的环比或不适用原因。
8. 周期包含前一天、当天、7天、30天和全部，默认前一天，并完整复用交易策略的有效交易日和环比规则。
9. 完整事件筛选包含当前生效、周期新增、周期修改和周期失效，单选且默认当前生效。
10. 新增事件没有状态筛选，改为单日选择，默认前一个有效交易日，并使用 Daily Close `trading_date`。
11. 顶部周期切换与新增事件的单日选择相互独立。
12. 正文以 Event-Fact 层级展示，不以原始 JSON、字段表或通用 JSON 查看器作为正式页面。
13. 页面按业务逻辑选择展示字段，不完整平铺所有底层字段。
14. 隐藏式事件索引只列出当前结果中的 Event；选择 Event 定位到完整正文中的对应位置，不切换为单 Event 页面。
15. Event 按 `occurred_at` 由近到远排列，时间缺失或精度为 `UNKNOWN` 的 Event 置于结果末尾。
16. Fact 保持业务数据源顺序，不按 `fact_occurred_at` 重新排序。
17. 页面没有文档状态、文档历史版本、历史版本激活或常驻侧边路由。
18. 模式、周期、筛选、日期和事件索引操作均不触发 workflow 或整页刷新。
19. 页面不存在轮询、SSE、窗口聚焦或定时自动刷新，页面往返使用本标签页缓存。
20. 页面只展示和消费 V2 Event Library 数据，不读取 V1 Known Events 或缓存作为回退。
21. 首次只加载完整事件默认范围首屏与 KPI；其他模式、日期、筛选、Event/Fact 正文和后续分页均按需加载并缓存。
